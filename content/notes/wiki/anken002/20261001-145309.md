## 1. 概要

製造業のA社で利用されている既存業務システムについて、Windows Serverの老朽化に伴い、Windows Server 2025への移行を検討する案件。

仮想環境上に2つのシステムが存在しており、それぞれ異なるWindows Server、アプリケーション、ミドルウェアを使用している。

本資料は、現時点で確認できている資料や打ち合わせ内容、一般的な移行観点をもとに整理したものであり、最終的な要件・構成を確定したものではない。

---

## 2. 案件の目的

主な目的は、以下の既存システムをWindows Server 2025環境へ移行すること。

### 2.1 システム①

現行環境はWindows Server 2016。

主にWeb系の業務アプリケーションが稼働していると想定される。

主な構成要素は以下。

- Windows Server 2016
    
- IIS
    
- .NET Framework 4.6.2
    
- ComponentOne
    
- Aspose
    
- SQL Server
    
- 業務Webアプリケーション
    

移行後は以下を想定。

- Windows Server 2025
    
- .NET Framework 4.8.1
    
- IIS
    
- ComponentOne / Asposeの対応バージョン
    
- SQL Server継続利用を基本線として検討
    

基本的にはOS移行と、Windows Server 2025で動作させるための互換性対応が中心になる可能性が高い。

---

### 2.2 システム②

現行環境はWindows Server 2012 R2。

業務アプリケーションに加えて、ハンディターミナルとのデータ連携を行っているシステムと考えられる。

主な構成要素は以下。

- Windows Server 2012 R2
    
- IIS 8.5
    
- VB.NET系アプリケーション
    
- データベース
    
- ハンディターミナル
    
- ハンディとのデータ送受信機能
    

システム①と比較すると、単純なOS移行だけでなく、ハンディターミナル刷新やデータ連携方式の確認が重要になる。

---

## 3. システム①の主な確認事項

### 3.1 Windows Server 2025への互換性

既存アプリケーションがWindows Server 2025上で正常に動作するか確認する。

特に以下を確認する。

- IISの互換性
    
- .NET Frameworkの互換性
    
- OS依存APIの利用有無
    
- ファイルパスや権限設定
    
- Windows認証利用有無
    
- TLSなど通信方式
    
- 32bit / 64bit依存
    

---

### 3.2 .NET Framework

現行では.NET Framework 4.6.2を使用している可能性がある。

Windows Server 2025への移行に伴い、.NET Framework 4.8.1への更新を想定する。

確認事項は以下。

- ソースコードの互換性
    
- 廃止・非推奨APIの利用
    
- 外部ライブラリとの互換性
    
- ビルド環境
    
- Web.config等の設定変更
    

---

### 3.3 ComponentOne / Aspose

Excel出力やグラフ表示などで利用されている可能性がある。

Windows Server 2025および.NET Framework 4.8.1で利用可能か確認する。

特に以下を確認する。

- 現在利用している製品名
    
- バージョン
    
- ライセンス
    
- Windows Server 2025対応状況
    
- .NET Framework 4.8.1対応状況
    
- バージョンアップ時のアプリ改修有無
    

古いバージョンを利用している場合、OS移行よりもライブラリ更新に伴うアプリ改修のほうが大きくなる可能性がある。

---

## 4. システム②の主な確認事項

## 4.1 ハンディターミナル

システム②では、ハンディターミナルとの連携が重要なポイントになる。

現時点では、以下のような運用を行っている可能性がある。

- 工場内でハンディを使用
    
- Wi-Fi接続できない場所でも利用
    
- オフライン状態で端末内にデータを保持
    
- Wi-Fi接続時にサーバへ送信
    
- クレードル接続時にサーバと同期
    

このため、単純なオンラインWebシステムとして刷新するのではなく、オフライン運用を考慮する必要がある。

---

## 4.2 ハンディ連携方式

現行のハンディとサーバ間の連携方式を確認する必要がある。

候補としては以下が考えられる。

- TCP/IP通信
    
- HTTP / HTTPS API
    
- CSVファイル連携
    
- 共有フォルダ
    
- FTP / SFTP
    
- データベース直接接続
    
- メーカー専用ミドルウェア
    
- 専用SDK
    

現行方式によって、Windows Server 2025移行時の影響範囲が大きく変わる。

---

## 4.3 ハンディ端末の刷新

現在使用しているハンディターミナル自体を継続利用するのか、新しい端末へ変更するのか確認する。

刷新する場合は、以下を確認する。

- オフライン動作
    
- Wi-Fi利用
    
- クレードル同期
    
- バーコード読取
    
- QRコード読取
    
- バッテリー性能
    
- 耐久性
    
- 防塵・防水
    
- メーカーサポート期間
    
- Windows / Android等のOS
    
- SDK提供状況
    
- サーバ側との接続方法
    

ハンディ端末の選定をこちら側である程度コントロールできる場合、既存システムへの依存が少ない端末・方式を選定することで、アプリケーション改修を抑えられる可能性がある。

---

## 5. データベース

現行ではSQL Serverを利用していると考えられる。

システム①についてはSQL Server継続利用が有力。

一方で、一部システムについては無償DBへの変更も検討対象となっている。

候補としてSQL Server Expressが考えられる。

---

## 5.1 SQL Server Express

データ量が小規模であれば、SQL Server Expressを利用できる可能性がある。

現時点では、

- DB容量は1GB未満の可能性
    
- 1日のデータ更新件数も数十件程度の可能性
    

があるため、単純な容量・処理性能だけであればExpressでも対応できる可能性がある。

ただし、可用性要件によって判断が大きく変わる。

---

## 5.2 データ損失要件

重要な確認事項として、

「1件もデータを失いたくない」

という要望の意味を確認する必要がある。

具体的には以下を確認する。

### RPO

障害発生時に、どこまでデータ損失を許容できるか。

例：

- RPO = 0
    
- 数分以内
    
- 1時間以内
    
- 前日バックアップ時点まで
    

RPO = 0が必須の場合、SQL Server Express単体での実現は難しく、冗長化や上位エディションを含めた構成を検討する必要がある。

---

### RTO

障害発生後、どの程度の時間でシステムを復旧させる必要があるか。

例：

- 即時
    
- 30分以内
    
- 1時間以内
    
- 数時間以内
    
- 翌営業日
    

RPOとRTOによって、必要なバックアップ・冗長化構成が決まる。

---

## 6. バックアップ

最低限、日次バックアップは必要と考えられる。

ただし、バックアップのみでは障害発生直前のデータを保護できない。

以下を要件として整理する必要がある。

- フルバックアップ
    
- 差分バックアップ
    
- トランザクションログバックアップ
    
- バックアップ取得頻度
    
- バックアップ保存期間
    
- 別サーバ / 別ストレージへの保存
    
- リストア試験
    
- 障害復旧手順
    

---

## 7. 仮想基盤

現在は仮想環境上でWindows Serverが稼働している。

今回も仮想マシンとしてWindows Server 2025を構築する可能性が高い。

インフラ側では以下を確認する。

- 仮想基盤の種類
    
- CPU
    
- メモリ
    
- ストレージ
    
- ネットワーク
    
- VLAN
    
- IPアドレス
    
- DNS
    
- Active Directory参加
    
- バックアップ方式
    
- ウイルス対策
    
- 監視
    
- Windows Update
    
- サーバ証明書
    

---

## 8. ネットワーク

特にシステム②では、ハンディとの通信があるためネットワーク確認が重要。

以下を確認する。

- 工場内Wi-Fi構成
    
- Wi-Fiが届かないエリア
    
- ハンディ利用場所
    
- サーバ接続経路
    
- 使用ポート
    
- Firewall設定
    
- 拠点間通信
    
- VPN
    
- お客様先でハンディを利用するか
    
- インターネット経由通信の有無
    

特に、

「ハンディを自社工場内だけで使うのか」

「お客様先でも利用するのか」

はシステム構成に大きく影響する。

---

## 9. 業務内容

対象システムは物流・製造系の業務管理に関連していると考えられる。

現時点で想定されている業務イメージは以下。

- コンテナ箱の貸出
    
- コンテナ箱の回収
    
- 洗浄
    
- 製品等の詰め込み
    
- ハンディによるバーコード等の読み取り
    
- サーバへの実績登録
    

具体的な業務フローについては、追加確認が必要。

---

## 10. アプリケーション側の主な懸念事項

今回の案件では、インフラ移行だけでなくアプリケーション側の影響が比較的大きい可能性がある。

特に以下が重要。

- .NET Framework互換性
    
- VB.NET互換性
    
- IIS互換性
    
- ComponentOne / Aspose
    
- DB接続方式
    
- SQL Serverバージョン
    
- OS依存処理
    
- ファイル共有
    
- ハンディSDK
    
- ハンディ連携ミドルウェア
    
- 通信プロトコル
    
- オフライン同期処理
    

現時点の感覚では、案件全体としてはアプリ側の割合が比較的大きく、

アプリ：インフラ = 7：3程度

場合によっては、

アプリ：インフラ = 8：2程度

になる可能性がある。

ただし、これはソースコードや現行設定を詳細確認する前の暫定的な見立て。

---

## 11. 特にリスクが高いポイント

### 11.1 ハンディ依存

業務アプリケーションやDB設計が現行ハンディの仕様に強く依存している場合、端末変更に伴うアプリ改修が大きくなる可能性がある。

---

### 11.2 古いライブラリ

ComponentOne、Aspose等のバージョンが古い場合、Windows Server 2025への移行に伴いライブラリ更新が必要になる可能性がある。

その場合、単純なOS移行ではなく、アプリケーション改修案件となる。

---

### 11.3 現行仕様が不明

古いシステムでは、仕様書と実装が一致していない可能性がある。

そのため、

- 設計書
    
- ソースコード
    
- IIS設定
    
- DB
    
- サーバ設定
    
- ハンディ設定
    

を実環境と照らし合わせる必要がある。

---

### 11.4 データ損失要件

「1件も失いたくない」がRPO=0を意味する場合、DB構成・バックアップ構成の検討範囲が大きくなる。

最初に確認すべき重要項目。

## 13. 今後の進め方

まず現行環境の棚卸しを行い、Windows Server 2025でそのまま動作するものと、改修が必要なものを切り分ける。

そのうえで、

1. OS移行影響調査
    
2. アプリケーション互換性調査
    
3. ミドルウェア互換性調査
    
4. DB移行方式検討
    
5. ハンディ連携方式確認
    
6. ハンディ刷新方針決定
    
7. バックアップ・可用性要件整理
    
8. 新環境設計
    
9. 移行方式設計
    
10. 移行・切替・試験計画作成
    

の順で整理していくのがよいと考える。
