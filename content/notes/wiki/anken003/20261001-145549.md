## 1. 概要

大量の端末キッティング作業を管理するための業務システムを、AWS上で構築することを検討している。

現時点では、数十人の作業者が利用し、繁忙期には1日最大17,000台程度の端末を処理する可能性がある。

業務画面は5〜6画面程度を想定しており、端末の受付、作業状況更新、進捗確認、完了処理などをWeb画面から操作するイメージ。

本資料は現時点の要件・調査内容をもとにした構成案であり、正式な要件やAWS構成を確定したものではない。

---

## 2. 想定するシステム利用規模

現時点では以下のような利用を想定している。

- 作業者：数十人
    
- 対象端末：最大約17,000台/日
    
- 業務画面：5〜6画面程度
    
- 利用形態：社内向けWebシステム
    
- 利用端末：PCを中心に想定
    
- データ更新：端末ごとの作業ステータス更新が中心
    

1台につき複数回の操作が行われる場合、1日あたりのAPIリクエスト数は数万〜数十万件になる可能性がある。

ただし、この規模であればAWSのサーバーレス構成で十分対応できる可能性が高い。

---

## 3. 想定AWS構成

現時点では以下の構成を候補としている。

|分類|AWSサービス|
|---|---|
|Web画面|Amplify Hosting|
|認証|Amazon Cognito|
|API|Amazon API Gateway|
|業務処理|AWS Lambda|
|データベース|Amazon DynamoDB|
|バックアップ|DynamoDB PITR / AWS Backup|
|ログ・監視|Amazon CloudWatch|
|操作履歴|AWS CloudTrail|
|Web保護|AWS WAF|

基本的には、EC2等の常時稼働サーバを持たないサーバーレス構成を想定する。

---

## 4. システム構成イメージ

利用者がWebブラウザからシステムへアクセスする。

主な処理の流れは以下。

1. 利用者がWeb画面へアクセス
    
2. Cognitoでログイン
    
3. Web画面からAPI Gatewayへリクエスト
    
4. API GatewayがLambdaを呼び出す
    
5. Lambdaが業務処理を実行
    
6. DynamoDBへデータを登録・更新
    
7. 処理結果をWeb画面へ返却
    

画面そのものはAmplify Hostingで配信する。

---

## 5. Amplify Hosting

フロントエンドのWebアプリケーションをホスティングする。

ReactやNext.js等を利用する場合にも使用可能。

想定用途は以下。

- ログイン画面
    
- キッティング受付画面
    
- 作業状況更新画面
    
- 進捗一覧
    
- 端末検索
    
- 管理画面
    

Gitリポジトリと連携することで、ソースコード更新時の自動デプロイも可能。

---

## 6. Amazon Cognito

利用者認証に使用する。

想定機能は以下。

- ログイン
    
- ログアウト
    
- ユーザー管理
    
- パスワード管理
    
- JWT発行
    
- APIアクセス制御
    

利用者数が100人程度であれば、認証部分のコストは比較的小さいと考えられる。

---

## 7. API Gateway

フロントエンドから業務処理を呼び出すAPIの入口として利用する。

例として以下のAPIが考えられる。

- 端末登録
    
- 端末検索
    
- 作業開始
    
- 作業完了
    
- ステータス更新
    
- 作業履歴取得
    
- 集計結果取得
    

Cognitoと連携することで、ログイン済みユーザーのみAPIを実行可能にする構成が考えられる。

---

## 8. AWS Lambda

業務ロジックを実装する。

例として以下の処理をLambdaで実装する。

- キッティング端末登録
    
- ステータス変更
    
- 入力値チェック
    
- 作業履歴登録
    
- DynamoDB検索
    
- 集計
    
- エラー処理
    

サーバを常時起動する必要がなく、アクセスされた分だけ処理が実行される。

キッティング作業のように日中にアクセスが集中し、夜間はほぼ利用しないシステムとの相性がよい。

---

## 9. DynamoDB

キッティング対象端末や作業状況のデータ保存先として利用する。

想定データ例。

- 端末ID
    
- シリアル番号
    
- 作業ステータス
    
- 担当者
    
- 作業開始日時
    
- 作業完了日時
    
- エラー内容
    
- 更新日時
    

リレーショナルDBのような複雑な結合処理が少なく、端末IDを中心に検索・更新するシステムであればDynamoDBとの相性がよい。

---

## 10. データ設計で確認したい点

DynamoDBを採用する場合、事前に検索パターンを整理することが重要。

例えば以下。

- 端末IDから検索
    
- シリアル番号から検索
    
- ステータス別一覧
    
- 担当者別一覧
    
- 作業日別一覧
    
- 未完了端末一覧
    
- エラー端末一覧
    

検索要件によって、Partition KeyやSort Key、GSIの構成を決める。

---

## 11. バックアップ

DynamoDBについてはPoint-in-Time Recoveryを有効化することを想定する。

これにより、誤削除や誤更新が発生した場合に過去時点のテーブルへ復元できる。

検討項目は以下。

- PITR有効化
    
- AWS Backup利用
    
- バックアップ保存期間
    
- リストア手順
    
- 誤操作時の復旧方法
    

---

## 12. CloudWatch

システムのログ・監視に利用する。

主な対象は以下。

- Lambda実行ログ
    
- APIエラー
    
- Lambdaエラー
    
- Lambda実行時間
    
- APIレスポンス時間
    
- エラー件数
    

必要に応じてアラームを設定し、異常発生時に通知する。

---

## 13. CloudTrail

AWS環境に対する操作履歴を記録する。

主に以下を確認できる。

- 誰がAWS設定を変更したか
    
- いつ変更したか
    
- どのサービスに対して操作したか
    

AWS管理者側の監査ログとして利用する。

---

## 14. AWS WAF

Webアプリケーションへの不正アクセス対策として利用する。

主な用途は以下。

- 不正なリクエストの遮断
    
- SQL Injection対策
    
- XSS対策
    
- IPアドレス制限
    
- レート制限
    

社内システムであっても、インターネット経由でアクセスする場合は導入を検討する。

---

## 15. 認証と認可

Cognitoによるログインだけでなく、ユーザーごとの権限制御も必要になる可能性がある。

例として以下。

### 一般作業者

- 端末検索
    
- 作業開始
    
- ステータス更新
    
- 作業完了
    

### 管理者

- 全端末参照
    
- ユーザー管理
    
- 作業履歴確認
    
- データ修正
    
- 集計確認
    

API側でも権限を確認し、画面を非表示にするだけではなく、実際のAPI実行を制限する必要がある。

## 16. 想定コスト

現時点の概算として、以下のような月額費用を想定している。

|AWSサービス|月額イメージ|
|---|---|
|Amplify Hosting|500〜2,000円|
|Cognito|ほぼ0〜数百円|
|API Gateway|2,000〜5,000円|
|Lambda|数百〜2,000円|
|DynamoDB|1,000〜5,000円|
|PITR / Backup|数百〜数千円|
|CloudWatch|500〜3,000円|
|CloudTrail|ほぼ0〜数百円|
|WAF|1,500〜5,000円程度|

概算では月額1万円前後〜2万円台程度が一つの目安。

ただし以下によって変動する。

- APIリクエスト数
    
- DynamoDBアクセス量
    
- ログ量
    
- データ保存量
    
- WAFルール数
    
- データ転送量
    

繁忙期に17,000台/日の処理が発生しても、サーバーレス構成では極端に大きな費用になる可能性は低いと考えられる。

## 17. 固定費と従量課金

今回のAWS構成では、多くのサービスが従量課金となる。

そのため、完全な固定費ではない。

### 比較的固定費に近いもの

- WAFの基本料金
    
- 一部バックアップ保存費用
    
- ドメイン関連費用
    

### 利用量によって変動するもの

- Amplify
    
- API Gateway
    
- Lambda
    
- DynamoDB
    
- CloudWatch
    
- データ転送
    

アクセスが少ない月は費用が下がり、繁忙期は多少増える構成になる。

## 18. 性能面

最大17,000台/日という数字だけを見ると大きく感じるが、24時間で均等処理した場合は非常に小さい負荷となる。

実際には数時間に集中する可能性があるため、ピーク時間を考慮する必要がある。

確認したいのは以下。

- 最大同時利用者数
    
- 1台あたりの操作回数
    
- 1時間あたり最大処理台数
    
- 一括登録有無
    
- CSV取込有無
    
- バーコード連続読取有無
    

これらを確認した上で負荷試験条件を決める。

---

## 19. 排他制御

複数人が同じ端末データを同時に操作する可能性がある場合、排他制御が必要。

例えば、

- 作業者Aが端末を作業中
    
- 作業者Bも同じ端末を開く
    

といったケース。

対策として以下が考えられる。

- DynamoDB Conditional Write
    
- Version番号
    
- 更新日時による楽観ロック
    

同時更新によるデータ上書きを防止する。

---

## 20. 作業履歴

キッティング業務では、最終状態だけでなく作業履歴を保存したほうがよい。

例。

- 誰が
    
- いつ
    
- どの端末を
    
- どの状態から
    
- どの状態へ変更したか
    

障害調査や問い合わせ対応にも利用できる。

## 22. IaC

AWS環境については、画面から手作業で作成するよりもIaCで管理する方針が望ましい。

候補は以下。

- AWS CDK
    
- AWS SAM
    
- Terraform
    
- CloudFormation
    

今回のような構成であれば、AWS CDKまたはTerraformが候補。

IaC化することで以下のメリットがある。

- 環境構築を再現できる
    
- Gitで設定を管理できる
    
- 開発・検証・本番環境を作りやすい
    
- 設定変更履歴を追跡できる

## 27. 現時点での評価

システム規模としては、小規模〜中規模程度の業務Webシステムになる可能性が高い。

最大17,000台/日という業務量はあるものの、1件あたりの処理が軽量であれば、AWSサーバーレス構成で十分対応可能と考えられる。

特に、

- Amplify
    
- Cognito
    
- API Gateway
    
- Lambda
    
- DynamoDB
    

を中心にすることで、サーバ運用を極力減らしたシンプルな構成にできる。

一方で、技術的に重要になるのは性能そのものよりも、

- キッティング業務フロー
    
- データ設計
    
- 同時更新
    
- 作業履歴
    
- 権限制御
    
- 誤操作時の復旧
    

といった業務アプリケーション側の設計と考えられる。

そのため、AWS基盤を先に細かく設計しすぎるより、まず業務フローとデータ項目・検索パターンを整理してから、DynamoDBやAPI設計へ落とし込む進め方が適している。
