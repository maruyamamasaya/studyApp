## 1. Azure OpenAIとは

Azure OpenAIは、

**Azure上からOpenAI系の生成AIモデルやEmbeddingモデルを利用するためのサービス**

です。

RAGでは主に、

- Embedding生成
    
- LLMによる回答生成
    

の2か所で利用します。

つまり、

Azure OpenAI自体がRAG全体を担当する

わけではありません。

RAGを構成する複数の部品のうち、

**AIモデルを実行する部分**

を担当します。

---

## 2. RAG全体での位置

RAG全体を簡単にすると、

文書  
→ Chunk  
→ Embedding  
→ Search Index

質問時：

Question  
→ Embedding  
→ Search  
→ Context  
→ Prompt  
→ LLM  
→ Answer

となります。

Azure OpenAIは主に、

Chunk  
→ Embedding

Question  
→ Embedding

Prompt  
→ LLM  
→ Answer

の部分を担当します。

---

## 3. Embeddingでの利用

RAGでは、文書ChunkをVectorへ変換します。

例えば、

「バックアップは30日保存します。」

という文章を、

Azure OpenAIのEmbeddingモデル

へ送信します。

すると、

```
[0.12, -0.43, 0.88, ...]
```

のようなVectorが返ります。

Azure OpenAIのEmbeddingは、文章の意味を浮動小数点数のVectorとして表現し、意味的に近い文章をVector Searchで探すために利用できます。

---

## 4. 質問もEmbeddingする

文書だけでなく、ユーザーの質問も同じEmbeddingモデルでVector化します。

例えば、

Question:

「バックアップは何日保存されますか？」

をEmbeddingします。

そのVectorと、

文書ChunkのVector

を比較して、意味が近い文章を検索します。

---

## 5. Embeddingモデル

Azure OpenAIではEmbedding用のモデルをデプロイして利用します。

Microsoftの現行ドキュメントでは、例として、

- text-embedding-3-small
    
- text-embedding-3-large
    
- text-embedding-ada-002
    

などが案内されています。

実際にどのモデルを利用できるかは、

- Azureリージョン
    
- モデル提供状況
    
- デプロイ設定
    

などを確認します。

---

## 6. Deployment

Azure OpenAIでは、

モデルを選ぶだけではなく、

**利用するモデルをAzure上へDeploymentする**

考え方があります。

例えば、

Embedding Model  
text-embedding-3-small

を、

my-embedding

というDeployment名で登録したとします。

アプリケーションからは、そのDeploymentを指定して呼び出します。

現行のAzure OpenAI APIでは、`model`にAzure上で作成したモデルDeployment名を指定します。

---

## 7. Endpoint

Azure OpenAIを利用すると、

Azure OpenAI Resource用のEndpoint

が発行されます。

イメージとしては、

```
https://<resource-name>.openai.azure.com/
```

です。

アプリケーションは、このEndpointへHTTP Requestを送ります。

現行v1 APIでは、たとえばEmbeddingは `/openai/v1/embeddings` へ送信できます。

---

## 8. API呼び出し

Pythonなどから、

HTTP / SDK

を使ってAzure OpenAIへRequestを送ります。

Embeddingの場合は概念的に、

```
Python
→ Azure OpenAI Endpoint
→ Embedding Model
→ Vector
```

となります。

生成の場合は、

```
Python
→ Azure OpenAI Endpoint
→ LLM
→ Answer
```

となります。

---

## 9. 認証

Azure OpenAIへアクセスするには認証が必要です。

主に、

- Microsoft Entra ID
    
- API Key
    

を利用できます。

Microsoftの現行ドキュメントでは、長期間保持する認証情報を避けられるため、Entra ID認証が推奨されています。

---

## 10. API Key

Azure OpenAI Resourceに発行されたKeyを使う方法です。

例えば、

Python  
→ API KeyをHeaderへ付与  
→ Azure OpenAI

という流れです。

簡単ですが、

API Keyは秘密情報

なので、

- ソースコードへ直接書かない
    
- GitへCommitしない
    
- 環境変数やKey Vaultで管理する
    

ことが重要です。

---

## 11. Microsoft Entra ID

Microsoft Entra IDを利用すると、

Azure上のIdentityを使って認証できます。

例えば、

ユーザー  
Managed Identity  
Service Principal

などです。

Azure上で動作するアプリケーションでは、

Managed Identity

と組み合わせることができます。

現行ドキュメントでは、Azure OpenAIのEmbedding利用時に `Cognitive Services OpenAI User` ロールなどの適切なRBAC設定が必要です。

---

## 12. Managed Identity

Azure上で動作するアプリに、

Azureが管理するIdentity

を付与する仕組みです。

例えば、

App Service  
→ Managed Identity  
→ Azure OpenAI

とできます。

API Keyをアプリケーションへ保存しなくても認証できます。

---

## 13. RBAC

RBACは、

Role-Based Access Control

の略です。

Azure Resourceに対して、

誰が何を実行できるか

をRoleで制御します。

例えば、

Azure OpenAIを利用できるユーザー

Azure OpenAIを管理できる管理者

を分けられます。

---

## 14. 生成AIとしての利用

検索結果からContextを作った後、

PromptをAzure OpenAIの生成モデルへ送ります。

例えば、

```
System Instruction

Context
「バックアップは30日保存します。」

Question
「バックアップの保存期間は？」
```

をLLMへ送ります。

LLMは、

「30日間です。」

という回答を生成します。

---

## 15. Azure OpenAIは検索しない

ここは重要です。

Azure OpenAIの生成モデルが、

自動的に社内PDFを検索してくれる

わけではありません。

通常のRAGでは、

Search処理

は別の仕組みで行います。

例えば、

- Azure AI Search
    
- Elasticsearch
    
- Vector DB
    

などです。

その検索結果をAzure OpenAIへ渡します。

---

## 16. Azure AI Searchとの関係

Azure環境のRAGでは、

Azure OpenAI  
＋  
Azure AI Search

という構成があります。

役割は、

Azure OpenAI  
→ Embedding / 回答生成

Azure AI Search  
→ Keyword Search / Vector Search / Hybrid Search

です。

Azure AI Searchには、Azure OpenAIでデプロイしたEmbeddingモデルを利用してIndexing時にEmbeddingを生成する仕組みもあります。

---

## 17. 基本構成

例えば、

PDF  
→ テキスト抽出  
→ Chunk  
→ Azure OpenAI Embedding  
→ Azure AI Searchへ保存

質問時：

User  
→ Question  
→ Azure OpenAI Embedding  
→ Azure AI Search  
→ 関連Chunk  
→ Prompt作成  
→ Azure OpenAI LLM  
→ Answer

となります。

## 18. PythonからEmbeddingするイメージ

現行APIの考え方では、概念的には以下のようになります。

```
response = client.embeddings.create(
    model="my-embedding-deployment",
    input="バックアップは30日保存します。"
)

vector = response.data[0].embedding
```

重要なのは、

`model`

にAzure上のDeployment名を指定する点です。

---

## 19. 生成モデルを呼ぶイメージ

概念的には、

```
response = client.responses.create(
    model="my-generation-deployment",
    input=prompt
)
```

のように、

Deploymentされた生成モデル

を呼び出します。

SDKやAPI形式は更新されることがあるため、実装時は利用しているAPI Versionと公式ドキュメントを確認します。

## 20. Azure OpenAI Resource

Azureではまず、

Azure OpenAIを利用できるResource

を作成します。

大まかには、

Azure Subscription  
→ Resource Group  
→ Azure OpenAI Resource  
→ Model Deployment

という関係になります。

---

## 21. Resource Group

Resource Groupは、

Azure Resourceをまとめて管理する箱

のようなものです。

例えば、

rag-dev-rg

というResource Groupの中に、

- Azure OpenAI
    
- Azure AI Search
    
- Storage
    
- Key Vault
    

などをまとめられます。

---

## 22. モデルDeploymentの考え方

例えば、

Generation:

Deployment名  
rag-gpt

Embedding:

Deployment名  
rag-embedding

のように分けます。

アプリケーションは、

「GPTというモデル」

ではなく、

**自分のAzure環境に作ったDeployment**

を呼び出します。

---

## 23. Rate Limit

Azure OpenAIには、

利用量に応じた制限

があります。

大量のEmbeddingやLLM Requestを送ると、

Rate Limit

に達する可能性があります。

そのため、

- Queue
    
- 並列数制限
    
- Retry
    
- Exponential Backoff
    

などを組み合わせます。

---

## 24. Tokenとの関係

Azure OpenAIでも、

Input Token  
Output Token

などが処理量に関係します。

RAGでは、

Prompt  
＋ Context  
＋ Question

が入力になります。

Contextを大量に入れると、

Token使用量も増えます。

---

## 25. EmbeddingのToken

Embeddingの場合も、

文章をTokenとして処理します。

大量文書の場合、

PDF  
→ 多数Chunk  
→ 大量Embedding Request

になるため、

Chunk Size

や、

差分更新

が重要になります。

---

## 26. Cacheとの関係

一度作ったEmbeddingをCacheしておけば、

同じChunkを何度もAzure OpenAIへ送らずに済みます。

例えば、

Chunk Hash  
→ Cache確認

Cacheあり  
→ Vector再利用

Cacheなし  
→ Azure OpenAI Embedding

とできます。

---

## 27. Queueとの関係

大量文書をEmbeddingする場合、

Queue

を利用できます。

例えば、

PDF Upload  
→ Queue  
→ Worker  
→ Chunk  
→ Azure OpenAI Embedding  
→ Search Index

という構成です。

---

## 28. Retryとの関係

Azure OpenAI呼び出しで一時エラーが発生した場合、

Retry

を行います。

例えば、

429  
503

などの一時的エラーに対して、

Exponential Backoff

を利用します。

---

## 29. Timeoutとの関係

LLM APIが長時間応答しない場合に備えて、

Timeout

を設定します。

例えば、

Azure OpenAI  
→ 30秒応答なし  
→ Timeout  
→ Retry

のような制御です。

---

## 30. Logging

運用では、

- Request ID
    
- Model / Deployment
    
- Token数
    
- 処理時間
    
- Status
    
- Error
    
- Retry回数
    

などを記録すると調査しやすくなります。

ただし、

Prompt全文や機密情報

をログへ残す場合は注意が必要です。

---

## 31. Azure OpenAIが担当しないもの

Azure OpenAIだけで、

RAGのすべてが完成するわけではありません。

例えば、

### Azure OpenAIが担当

- Embedding
    
- LLM回答生成
    

### 別処理が担当

- PDF解析
    
- OCR
    
- Chunk
    
- 文書保存
    
- Keyword Search
    
- Vector Search
    
- Metadata Filter
    
- 権限制御
    
- Queue
    

という役割分担になります。

---

## 32. RAG構成での代表的な役割分担

Azureで構成する場合のイメージは、

### Azure Blob Storage

元PDFなどを保存

### Document解析

PDF / OCR / Layout解析

### Azure OpenAI

Embeddingと回答生成

### Azure AI Search

Keyword / Vector / Hybrid Search

### Key Vault

API Keyなどの秘密情報管理

### Entra ID

ユーザーやアプリケーションの認証

という構成があります。

必ずこの構成にする必要があるわけではありません。

## 37. 一言で理解する

Azure OpenAIとは、

**「Azure上からLLMとEmbeddingモデルを利用するためのAI実行基盤」**

です。

RAGでは主に、

**Embedding = 検索用Vectorを作る**

**LLM = Contextを使って回答を生成する**

という2つを担当します。

そして、

**Azure OpenAI = 検索エンジンそのものではない**

という点が重要です。

覚え方としては、

**Azure OpenAI = RAGの『意味をVector化するAI』と『回答を書くAI』**

と考えると分かりやすいです。
