## 1. APIとは

APIは、

Application Programming Interface

の略です。

簡単にいうと、

**アプリケーション同士が決められた方法でデータや処理をやり取りする仕組み**

です。

例えば、

Web画面  
→ API  
→ サーバー  
→ データベース

という形で使われます。

RAGでも、

画面  
→ 質問API  
→ RAG処理  
→ LLM  
→ 回答API

という構成になります。

---

## 2. APIを使う理由

画面から直接データベースやLLMへ接続するのではなく、

APIを間に置くことで、

- 処理を共通化できる
    
- 認証を入れられる
    
- 権限制御できる
    
- ログを残せる
    
- エラー処理できる
    
- 外部システムと連携できる
    

ようになります。

---

## 3. APIの基本イメージ

例えばユーザーが、

「バックアップの保存期間は？」

と質問するとします。

流れは、

画面  
→ APIへ質問送信  
→ RAG検索  
→ LLM回答  
→ APIレスポンス  
→ 画面表示

です。

APIは、

**画面とバックエンド処理の窓口**

と考えると分かりやすいです。

---

## 4. RequestとResponse

APIでは、

Request

と

Response

が基本です。

### Request

クライアントからサーバーへ送る情報です。

例えば、

- URL
    
- HTTP Method
    
- Header
    
- Body
    
- Query Parameter
    

などがあります。

### Response

サーバーからクライアントへ返す情報です。

例えば、

- Status Code
    
- Header
    
- JSON Body
    

などです。

---

## 5. ClientとServer

APIを呼び出す側を、

Client

と呼びます。

例えば、

- Webブラウザ
    
- スマホアプリ
    
- 別システム
    
- Pythonプログラム
    

などです。

APIを提供する側を、

Server

と呼びます。

---

## 6. HTTP

Web APIでは、

HTTP

という通信方式がよく使われます。

例えば、

GET  
POST  
PUT  
PATCH  
DELETE

などのHTTP Methodを使って、

「何をしたいか」

を伝えます。

---

## 7. GET

GETは、

**データを取得する**

ときに使います。

例えば、

GET /documents/123

なら、

document_id = 123

の文書情報を取得するイメージです。

---

## 8. POST

POSTは、

**新しいデータを送る、または処理を実行する**

ときに使います。

RAGの質問APIなら、

POST /ask

として、

質問内容をBodyに入れることがあります。

---

## 9. PUT

PUTは、

**リソース全体を更新する**

ときに使われることがあります。

例えば、

PUT /users/123

で、

ユーザー123の情報を全体更新します。

---

## 10. PATCH

PATCHは、

**データの一部分だけ更新する**

場合に使います。

例えば、

ユーザーの表示名だけ変更する

といった処理です。

---

## 11. DELETE

DELETEは、

**データを削除する**

ときに使います。

例えば、

DELETE /documents/123

で、

文書123を削除するイメージです。

---

## 12. URL

APIにはアクセス先があります。

例えば、

[https://example.com/api/documents](https://example.com/api/documents)

です。

このうち、

/api/documents

の部分を、

Endpoint

と呼ぶことがあります。

---

## 13. Endpoint

Endpointは、

**APIの処理ごとの入口**

です。

例えば、

POST /ask  
GET /documents  
GET /documents/{id}  
DELETE /documents/{id}

のように分けます。

RAGでは、

/ask  
/search  
/documents

などのEndpointを作る場合があります。

---

## 14. Path Parameter

URLの一部に値を入れる方法です。

例えば、

GET /documents/123

の、

123

がPath Parameterです。

意味としては、

「123番のDocument」

を指定しています。

---

## 15. Query Parameter

URLの後ろに条件を付ける方法です。

例えば、

GET /documents?category=manual

です。

この場合、

category = manual

という検索条件を指定しています。

---

## 16. Request Body

POSTやPUTでは、

Body

にデータを入れることがあります。

例えば、

```
{
  "question": "バックアップの保存期間は？"
}
```

です。

RAGの質問APIでは、このように質問本文を送ります。

---

## 17. JSON

APIでは、

JSON

という形式でデータをやり取りすることが多いです。

例えば、

```
{
  "name": "Taro",
  "age": 30
}
```

です。

Pythonでは、

dict

と非常に相性が良い形式です。

---

## 18. Header

HTTP Requestには、

Header

という付加情報があります。

例えば、

- Content-Type
    
- Authorization
    
- User-Agent
    

などがあります。

API認証でもHeaderをよく使います。

---

## 19. Content-Type

送信するデータ形式を指定します。

例えば、

Content-Type: application/json

なら、

「BodyはJSONです」

という意味です。

---

## 20. Authorization Header

APIへ認証情報を送るときによく使います。

例えば、

Authorization: Bearer xxxxx

のような形式です。

このBearer Tokenを使って、

「誰からのRequestか」

を確認します。

---

## 21. Authentication

Authenticationは、

**誰なのかを確認する処理**

です。

日本語では、

認証

と呼びます。

例えば、

ログイン  
→ ID Token取得  
→ APIへToken送信  
→ APIで本人確認

という流れです。

---

## 22. Authorization

Authorizationは、

**そのユーザーが何をしてよいか確認する処理**

です。

日本語では、

認可

と呼びます。

例えば、

一般ユーザー  
→ 文書閲覧のみ

管理者  
→ 文書登録・削除も可能

のように制御します。

---

## 23. AuthenticationとAuthorizationの違い

よく混同します。

Authentication  
＝ あなたは誰か

Authorization  
＝ あなたは何をしてよいか

です。

RAGでも、

認証  
→ ユーザー確認

認可  
→ 検索できる文書を制御

という流れになります。

---

## 24. API Key

API Keyは、

APIを利用するための識別情報です。

例えば外部LLM APIを呼び出すときに、

API Key

を送ることがあります。

ただし、API Keyは秘密情報なので、

コードに直接書かない

ようにします。

---

## 25. Bearer Token

Bearer Tokenは、

認証済みユーザーを表すToken

としてよく使われます。

例えば、

Authorization: Bearer eyJ...

のような形です。

API側でTokenを検証します。

---

## 26. JWT

JWTは、

JSON Web Token

の略です。

「ジョット」または「ジェイ・ダブリュー・ティー」と呼ばれます。

JWTには、

- User ID
    
- Role
    
- 有効期限
    
- Scope
    

などの情報を含めることがあります。

API側ではJWTを検証して、

ユーザー情報を取得します。

---

## 27. JWT署名

JWTは、

署名

によって改ざんされていないか確認します。

流れは、

JWT受信  
→ 署名検証  
→ 有効期限確認  
→ Claims取得

です。

署名に使う鍵は秘密情報として管理します。

---

## 28. Claims

JWTの中に入っている情報を、

Claims

と呼びます。

例えば、

- sub
    
- role
    
- scope
    
- exp
    
- group
    

などです。

API側でClaimsを使って権限制御します。

---

## 29. Role

Roleは、

ユーザーの役割

です。

例えば、

- admin
    
- user
    
- manager
    

などです。

API側で、

adminだけ削除可能

のような制御ができます。

---

## 30. Scope

Scopeは、

Tokenに許可された操作範囲

を表します。

例えば、

documents.read

documents.write

rag.ask

などです。

Roleより細かい権限制御に使うことがあります。

---

## 31. Status Code

APIは処理結果を、

HTTP Status Code

で返します。

代表的なものは、

- 200 OK
    
- 201 Created
    
- 400 Bad Request
    
- 401 Unauthorized
    
- 403 Forbidden
    
- 404 Not Found
    
- 500 Internal Server Error
    

です。

---

## 32. 200 OK

処理が正常に完了した場合です。

例えば、

RAGの質問に正常回答できた場合

200

を返します。

---

## 33. 400 Bad Request

Request内容に問題がある場合です。

例えば、

questionが空

などです。

---

## 34. 401 Unauthorized

主に、

**認証されていない**

場合です。

例えば、

Tokenがない  
Tokenが無効  
Tokenが期限切れ

などです。

---

## 35. 403 Forbidden

認証はできているが、

**その操作を行う権限がない**

場合です。

例えば、

一般ユーザーが管理者専用APIを呼ぶ

場合です。

---

## 36. 404 Not Found

指定されたデータが存在しない場合です。

例えば、

GET /documents/999

で文書999が存在しない

場合です。

---

## 37. 500 Internal Server Error

サーバー内部で予期しないエラーが発生した場合です。

例えば、

- DB障害
    
- バグ
    
- 外部API例外
    

などです。

---

## 38. Error Response

エラーの場合もJSONで返すことがあります。

例えば、

```
{
  "error": "INVALID_REQUEST",
  "message": "question is required"
}
```

です。

クライアント側でエラー処理しやすくなります。

---

## 39. Validation

APIに入ってきた値が正しいか確認します。

例えば、

- 必須項目があるか
    
- 文字数制限
    
- 型が正しいか
    
- 不正な値ではないか
    

などです。

RAGなら、

questionが空文字でないか

などを確認します。

---

## 40. APIとセキュリティ

APIでは、

画面側で制御しているから安全

とは考えません。

ユーザーはAPIを直接呼び出せる可能性があります。

そのため、

**API側でも必ず認証・認可を実施する**

ことが重要です。

---

## 41. 入力チェック

APIには外部から入力が入るため、

入力値を信用しない

ことが基本です。

例えば、

- SQL Injection
    
- 不正なURL
    
- 巨大文字列
    
- 想定外のJSON
    

などを考慮します。

---

## 42. API側でも権限確認する

例えば画面上で、

「削除ボタンを管理者だけ表示」

していても、

DELETE API自体に権限制御がなければ、

直接APIを呼ばれる可能性があります。

そのため、

画面  
＋  
API

の両方で制御します。

特に重要なのはAPI側です。

---

## 43. APIからDBへ接続する

一般的なWebシステムでは、

画面  
→ API  
→ DB

という構成になります。

画面からDBへ直接接続しません。

API側で、

- SQL実行
    
- Validation
    
- Authorization
    
- Transaction
    

などを管理します。

---

## 44. APIから外部APIを呼ぶ

RAGでは、

自分のAPI

から、

- Embedding API
    
- LLM API
    
- Search API
    

などを呼び出します。

例えば、

Client  
→ RAG API  
→ Embedding API  
→ Search  
→ LLM API

という構成です。

---

## 45. Timeout

外部APIを呼ぶ場合、

応答が返ってこない可能性があります。

そのため、

Timeout

を設定します。

例えば、

30秒以上応答がない  
→ エラー

とします。

---

## 46. Retry

外部APIが一時的に失敗した場合、

再試行

することがあります。

例えば、

LLM API失敗  
→ 1秒待つ  
→ 再試行

です。

ただし、すべてのエラーをRetryするわけではありません。

---

## 47. Exponential Backoff

Retry間隔を、

1秒  
2秒  
4秒  
8秒

のように増やす方法です。

APIのRate Limitや一時障害対策で使われます。

---

## 48. Rate Limit

APIへのアクセス回数を制限する仕組みです。

例えば、

1ユーザー  
1分100Request

などです。

大量アクセスや不正利用を防ぐために使います。

---

## 49. Logging

APIでは、

- Request
    
- User ID
    
- Endpoint
    
- Status Code
    
- Processing Time
    
- Error
    

などをログに残すことがあります。

ただし、

- Password
    
- API Key
    
- Token全文
    

などの秘密情報は残さないようにします。

---

## 50. Request ID

1回のRequestごとに、

Request ID

を発行することがあります。

例えば、

req-123456

です。

複数システムをまたいでも同じIDをログへ残すことで、

処理を追いやすくなります。

---

## 51. API Version

APIの仕様変更に備えて、

Version

をURLへ付ける場合があります。

例えば、

/api/v1/ask

/api/v2/ask

です。

旧システムを壊さずに新APIへ移行しやすくなります。

---

## 52. REST API

よく使われるAPI設計方式の1つが、

REST

です。

リソースをURLで表現し、

HTTP Methodで操作します。

例えば、

GET /documents  
POST /documents  
GET /documents/123  
DELETE /documents/123

のような形です。

---

## 53. RAG APIの例

RAGなら、例えば、

POST /api/v1/ask

を作ります。

Request:

```
{
  "question": "バックアップの保存期間は？"
}
```

Response:

```
{
  "answer": "30日間保存します。",
  "sources": [
    {
      "document": "backup-rule.pdf",
      "page": 12
    }
  ]
}
```

という形にできます。

---

## 54. PythonでAPIを作る

Pythonでは、

FastAPI

などを利用できます。

例えば、

```
from fastapi import FastAPI

app = FastAPI()


@app.get("/hello")
def hello():
    return {
        "message": "Hello"
    }
```

です。

これで、

GET /hello

というAPIを作れます。

---

## 55. POST APIの例

例えばRAG質問APIなら、

```
from fastapi import FastAPI
from pydantic import BaseModel


app = FastAPI()


class AskRequest(BaseModel):
    question: str


@app.post("/ask")
def ask(request: AskRequest):

    return {
        "answer": f"質問: {request.question}"
    }
```

のように作れます。

---

## 56. Pydantic

FastAPIでは、

Pydantic

を使ってRequestの型やValidationを定義することがあります。

例えば、

```
class AskRequest(BaseModel):
    question: str
```

とすると、

question

がRequestに必要だと定義できます。

---

## 57. async / await

APIから、

- DB
    
- LLM API
    
- Embedding API
    
- Search API
    

などを呼ぶ場合、

async / await

を使うことがあります。

例えば、

```
@app.post("/ask")
async def ask(request: AskRequest):

    answer = await rag_service.ask(
        request.question
    )

    return {
        "answer": answer
    }
```

です。

---

## 58. APIの処理を分離する

API Endpointの中にすべての処理を書くのではなく、

API  
→ Service  
→ Repository

のように役割を分けます。

RAGなら、

API  
→ RAGService  
→ Retriever / LLM

のようにできます。

例えば、

Web画面

→ POST /api/v1/ask

→ Authentication

→ Authorization

→ RAGService

→ Search

→ Reranking

→ Prompt

→ LLM

→ Response

という流れです。

## 60. 一言で理解する

APIとは、

**「システム同士が決められたルールで処理やデータをやり取りするための窓口」**

です。

基本は、

**Request → API処理 → Response**

です。

RAGでは、

**画面 → API → RAG処理 → LLM → API → 画面**

という流れになります。

特に覚えておきたいのは、

- Endpoint
    
- Request / Response
    
- GET / POST
    
- JSON
    
- Status Code
    
- Authentication
    
- Authorization
    
- Token
    
- Timeout / Retry
    

あたりです。
