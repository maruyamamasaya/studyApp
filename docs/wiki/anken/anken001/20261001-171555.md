## 1. Retryとは

Retry（リトライ）は、

**処理が一時的に失敗したとき、もう一度実行する仕組み**

です。

例えば、

LLM API呼び出し  
→ 一時的に失敗  
→ 数秒待つ  
→ 再実行

という流れです。

RAGでは外部APIや検索サービスを使うことが多いため、よく使われます。

---

## 2. Retryが必要な理由

外部サービスは、一時的に失敗することがあります。

例えば、

- ネットワークエラー
    
- 一時的なサーバー障害
    
- Timeout
    
- Rate Limit
    
- 一時的な接続失敗
    

などです。

こうしたエラーは、少し待って再実行すると成功する場合があります。

---

## 3. 基本イメージ

例えば、

1回目  
→ 失敗

2回目  
→ 失敗

3回目  
→ 成功

なら、ユーザーから見ると正常に処理できます。

ただし、無限にRetryしてはいけません。

---

## 4. Retry回数

通常は、

- 最大3回
    
- 最大5回
    

など上限を決めます。

例えば、

```
MAX_RETRIES = 3
```

です。

上限を超えたらエラーとして処理します。

---

## 5. 単純なRetry

Pythonでは概念的に、

```
for attempt in range(3):
    try:
        result = call_api()
        break

    except TemporaryError:
        continue
```

のように実装できます。

---

## 6. すべてのエラーをRetryしない

これが重要です。

例えば、

API Keyが間違っている

場合、何回Retryしても成功しません。

そのため、

Retryしてよいエラー

と、

Retryしてはいけないエラー

を分けます。

---

## 7. Retryしやすいエラー

代表例は、

- 一時的な通信エラー
    
- HTTP 429
    
- HTTP 502
    
- HTTP 503
    
- HTTP 504
    
- 一時的なTimeout
    

などです。

サービス仕様によって判断します。

---

## 8. Retryしないことが多いエラー

例えば、

- 400 Bad Request
    
- 401 Unauthorized
    
- 403 Forbidden
    
- 入力値エラー
    
- API Key不正
    

などです。

Request自体が間違っているため、再実行しても改善しない可能性が高いです。

---

## 9. Wait

失敗した直後にすぐRetryすると、同じ原因でまた失敗することがあります。

そのため、

失敗  
→ 少し待つ  
→ Retry

とします。

例えば、

1秒待つ  
→ Retry

です。

---

## 10. Exponential Backoff

Retryの待ち時間を、

1秒  
2秒  
4秒  
8秒

のように徐々に増やす方法があります。

これを、

Exponential Backoff

と呼びます。

APIのRate Limitや一時障害でよく使われます。

---

## 11. Jitter

複数の処理が同時にRetryすると、

全員が同じタイミングで再接続

してしまうことがあります。

そのため、

待ち時間に少しランダムな時間を加える

場合があります。

これをJitterと呼びます。

例えば、

2秒  
＋  
0〜1秒のランダム待機

のようにします。

---

## 12. Timeoutとの違い

Timeoutは、

**処理を何秒まで待つか**

です。

Retryは、

**失敗したあと何回やり直すか**

です。

例えば、

1回のAPI呼び出し  
Timeout = 30秒

失敗したら  
Retry = 最大3回

という組み合わせです。

---

## 13. RAGでRetryする場所

RAGでは例えば、

- OCR API
    
- Embedding API
    
- Search API
    
- Reranking API
    
- LLM API
    

などでRetryを使います。

---

## 14. Embeddingでの注意

Embedding処理では大量のChunkを処理することがあります。

途中で1件失敗した場合、

最初から全部やり直す

のではなく、

失敗したChunkだけRetry

できる設計にすると効率的です。

---

## 15. LLM APIでのRetry

LLM APIが一時的に失敗した場合、

Retryによって回復できる場合があります。

ただし、

同じRequestをRetryすると、

二重処理

が問題になる処理では注意が必要です。

単純な回答生成なら比較的Retryしやすいですが、DB更新などを伴う場合は別途考慮します。

---

## 16. Idempotency

同じ処理を何回実行しても結果がおかしくならない性質を、

Idempotency

と呼びます。

日本語では、

冪等性

と呼ばれます。

Retryでは重要な考え方です。

---

## 17. 二重登録に注意

例えば、

文書登録API  
→ Serverでは登録成功  
→ Responseだけ通信失敗  
→ ClientがRetry  
→ 同じ文書をもう一度登録

となる可能性があります。

そのため、

document_id

や、

idempotency key

などを使って二重登録を防ぐことがあります。

---

## 18. Retryのログ

Retryした場合は、

- 何回目か
    
- 何のエラーか
    
- 何秒待ったか
    
- 最終的に成功したか
    

をログへ残すと調査しやすくなります。

---

## 19. Retryで重要なポイント

覚えておきたいのは、

**失敗したら何でも再実行する仕組みではない**

という点です。

基本は、

一時的なエラー  
→ 待つ  
→ Retry

恒久的なエラー  
→ すぐ失敗として扱う

です。

---

## 20. 一言で理解する

Retryとは、

**「一時的な失敗なら、少し待ってもう一度試す仕組み」**

です。

RAGでは、

LLM API  
Embedding API  
Search API

などの外部通信でよく使います。

特に、

**Retry回数 + Timeout + Exponential Backoff**

をセットで考えると分かりやすいです。
