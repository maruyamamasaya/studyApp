## 1. 概要

RAGでは、

文書取り込み  
→ Chunk  
→ Embedding  
→ Search  
→ Reranking  
→ Context  
→ LLM  
→ Answer

と複数の処理を通ります。

そのため、回答がおかしい場合でも、

**LLMだけが原因とは限りません。**

問題がどの段階で起きているかを切り分けることが重要です。

---

# 2. 正しい文書を検索できない

よくある問題の1つです。

例えば、

質問：

「バックアップの保存期間は？」

正解文書：

「バックアップは30日保存する。」

が存在するのに、検索結果へ出てこない場合です。

原因として、

- Chunkが適切でない
    
- Embeddingが合っていない
    
- Keyword Searchで表記が一致しない
    
- Top-Kが小さい
    
- Metadata Filterが厳しすぎる
    

などがあります。

---

## 3. 関係ない文書が検索される

検索結果には出るものの、

質問とあまり関係ないChunk

が上位になることがあります。

例えば、

「バックアップの保存期間」

を聞いているのに、

「バックアップの実行時間」

ばかり取得するケースです。

対策として、

- Hybrid Search
    
- Reranking
    
- Chunk改善
    
- Query Rewrite
    

などを検討します。

---

# 4. Chunkが大きすぎる

1つのChunkに、

- 認証
    
- バックアップ
    
- ネットワーク
    
- 障害対応
    

など多くの話題が入ると、

検索時に意味がぼやけます。

その結果、

関連性の低いChunkが取得される

可能性があります。

---

## 5. Chunkが小さすぎる

逆に、

「30日間保存します。」

だけでは、

何を30日保存するのか分かりません。

Chunkが小さすぎると、

- 主語がない
    
- 条件が消える
    
- 文脈が切れる
    

といった問題が起きます。

---

# 6. OCR誤認識

スキャンPDFでは、

OCRの間違い

がそのままRAGへ入ることがあります。

例えば、

原文：

「10日以内」

OCR：

「70日以内」

となれば、検索・回答も間違います。

この場合はLLMではなく、

文書取り込み側の問題

です。

---

# 7. PDFの読み順がおかしい

2段組みや複雑なPDFでは、

文章の順番が崩れる

ことがあります。

例えば、

左列と右列が混ざる

表の列が崩れる

などです。

その結果、不自然なChunkが作られます。

---

# 8. 表が壊れる

PDFやExcelの表を単純にテキスト化すると、

行と列の関係

が失われることがあります。

例えば、

商品  
価格  
A  
1000

だけでは、

Aの価格が1000円

という関係が分かりにくくなります。

---

# 9. 古い文書が検索される

旧版と最新版の両方がIndexに存在すると、

古いChunk

が検索される可能性があります。

例えば、

旧規程  
→ 30日

新規程  
→ 10日

の場合です。

対策として、

- version
    
- updated_at
    
- valid_from
    
- 最新版Filter
    

などを利用します。

---

# 10. 削除した文書が残る

Blob StorageからPDFを削除しても、

Search Index側のChunkが残っている

ことがあります。

すると、

削除済み文書をRAGが回答に使う

可能性があります。

文書削除時は、

原本  
＋ Search Index

を同期して削除する必要があります。

---

# 11. 権限変更が反映されない

例えば、

昨日  
→ 全社員閲覧可能

今日  
→ 人事部限定

に変わったのに、

Index側のMetadataが古い

場合です。

一般社員が人事文書を検索できる可能性があります。

これはセキュリティ上重要な問題です。

---

# 12. Metadata Filterが厳しすぎる

検索精度を上げようとして、

department = IT  
category = manual  
year = 2026

など大量のFilterを付けると、

本来必要な文書まで検索対象外

になる場合があります。

---

# 13. Metadata Filterが緩すぎる

逆にFilterが不足すると、

- 古い資料
    
- 関係ない部署
    
- 権限外資料
    

が検索対象になる可能性があります。

特に権限Filterは、

検索精度とは別に確実に適用

する必要があります。

---

# 14. Top-Kが小さすぎる

Top-K = 1

などにすると、

正解Chunkが2位だった場合に取得できません。

また、複数Chunkを組み合わせないと回答できない質問にも弱くなります。

---

# 15. Top-Kが大きすぎる

Top-Kを増やしすぎると、

- 不要なContextが増える
    
- Token数が増える
    
- LLMが混乱する
    
- コストが増える
    

といった問題が起きます。

---

# 16. Vector Searchだけでは見つからない

例えば、

ERR-50001

ABC-12345

のような、

正確な文字列

はVector Searchが苦手な場合があります。

こうした情報では、

Keyword Search

を組み合わせます。

---

# 17. Keyword Searchだけでは見つからない

逆に、

「PCを買う」

と、

「パソコンを購入する」

のような言い換えは、

Keyword Searchだけでは検索できない場合があります。

そのため、

Vector Search

を組み合わせます。

---

# 18. Hybrid Searchでも順位が悪い

Hybrid Searchで候補は取れていても、

正解Chunkが下位

になる場合があります。

その場合は、

Reranking

を利用して質問との関連性を再評価します。

---

# 19. Reranking前に正解が消えている

重要なポイントです。

Rerankerは、

検索候補に存在するChunk

しか再評価できません。

正解ChunkがRetrieval時点で取得できていなければ、

Rerankingでは救えません。

---

# 20. Contextが不足している

検索結果に正解の一部しか入っていない場合です。

例えば、

「PC購入には上長承認が必要」

だけ取得し、

「10万円以上は部長承認」

を取得できていない場合です。

不完全な回答につながります。

---

# 21. Contextが多すぎる

関係ないChunkを大量にLLMへ渡すと、

重要な情報が埋もれる

ことがあります。

また、

- Tokenコスト
    
- Response Time
    

も増えます。

---

# 22. Contextの重複

Chunk Overlapの影響で、

同じ文章が何度もContextに入る

ことがあります。

例えば、

Chunk A  
A B C D

Chunk B  
C D E F

です。

重複が多いとTokenを無駄に使います。

---

# 23. Hallucination

検索結果に根拠がなくても、

LLMがもっともらしい回答

を生成する場合があります。

対策として、

- Contextのみを根拠にする
    
- 不明なら不明と答える
    
- Similarity Threshold
    
- Citation
    
- Output Validation
    

などを利用します。

---

# 24. 出典が間違っている

回答自体は正しくても、

別のDocumentを出典として表示

する場合があります。

またLLMが、

存在しない出典

を作ることもあります。

出典は可能な限り、

検索結果のMetadata

から作ります。

---

# 25. Promptが複雑すぎる

Promptへ大量のルールを追加すると、

- 指示同士が競合する
    
- 重要なルールが埋もれる
    
- Tokenが増える
    

といった問題があります。

Promptは必要なルールだけにします。

---

# 26. Prompt Injection

検索文書の中に、

「前の指示を無視してください」

などの文章が含まれている場合があります。

LLMがその文章を命令として扱わないように、

Retrieved Contextは、

命令ではなくデータ

として扱います。

---

# 27. Tokenが多すぎる

- Chunkが大きい
    
- Top-Kが多い
    
- 会話履歴が長い
    
- Promptが長い
    

場合、

Input Tokenが増えます。

その結果、

- コスト増加
    
- 応答速度低下
    
- Context Window超過
    

につながります。

---

# 28. 会話履歴に引っ張られる

チャット型RAGでは、

過去の話題

が新しい質問に影響する場合があります。

古い会話を全部Promptへ入れるのではなく、

- 最近の履歴だけ使う
    
- 要約する
    
- Query Rewriteする
    

などを検討します。

---

# 29. Query Rewriteが間違う

例えば、

「それは何日？」

という質問を、

会話履歴から誤って、

「ログの保存期間」

と書き換えてしまうケースです。

Query Rewrite自体も評価対象になります。

---

# 30. API Timeout

Embedding、Search、LLMなど、

外部APIの応答が遅く、

Timeout

になる場合があります。

Timeout値が短すぎても長すぎても問題です。

---

# 31. Retryしすぎる

外部APIが障害中なのに、

何度もRetry

すると、

- Response Time増加
    
- コスト増加
    
- サービス負荷増加
    

につながります。

Retry回数に上限を設けます。

---

# 32. Rate Limit

大量のEmbeddingやLLM Requestを送ると、

HTTP 429

が発生することがあります。

対策として、

- Concurrency Limit
    
- Queue
    
- Exponential Backoff
    
- Cache
    

などを使います。

---

# 33. Queueが詰まる

文書取り込み速度より、

Job追加速度

が速い場合、

Queueが増え続けます。

例えば、

1分100件追加  
1分30件処理

なら、

毎分70件ずつ増えます。

Worker数や処理性能を確認します。

---

# 34. Workerが二重処理する

Queueの再配信などにより、

同じDocumentを複数回処理

する可能性があります。

その結果、

同じChunkを二重登録

する場合があります。

IdempotencyやDocument IDで防止します。

---

# 35. Cacheが古い

文書が更新されたのに、

古いSearch結果やAnswer Cache

が残る場合があります。

これを、

Stale Cache

と呼びます。

Index VersionやTTLを使って無効化します。

---

# 36. Cacheによる情報漏えい

User A用の検索結果を、

User Bへ返す

といった問題です。

権限によって結果が異なる場合、

Cache Keyにも、

- User
    
- Group
    
- Permission Scope
    

などを考慮します。

---

# 37. ログが多すぎる

Prompt全文やContext全文をすべて保存すると、

- Logコスト増加
    
- 機密情報保存
    
- 調査しにくい
    

といった問題があります。

基本は、

ID・Score・Latency・Error

などの構造化ログを残します。

---

# 38. ログが少なすぎる

逆に、

「Error occurred」

だけでは原因調査できません。

最低限、

- request_id
    
- operation
    
- error_type
    
- dependency
    
- duration
    

などを記録します。

---

# 39. コストが急増する

例えば、

- Top-K増加
    
- Prompt肥大化
    
- 無限Retry
    
- Cache無効
    
- OCR全ページ実行
    
- 大量並列
    

などでコストが急増することがあります。

Token数やAPI利用量を監視します。

---

# 40. Responseが遅い

遅延原因は複数あります。

例えば、

- Search
    
- Embedding
    
- Reranking
    
- LLM
    
- Queue
    
- DB
    

です。

処理ごとのLatencyを記録し、

どこが遅いか切り分けます。

---

# 41. RAG品質問題の切り分け

回答がおかしい場合は、

以下の順番で確認すると分かりやすいです。

### 1. 原文

正しい情報が存在するか。

### 2. Parse / OCR

正しくテキスト化されているか。

### 3. Chunk

意味が壊れていないか。

### 4. Retrieval

正解Chunkを取得できたか。

### 5. Reranking

正解を上位へ持ってこれたか。

### 6. Context

必要な情報をLLMへ渡したか。

### 7. Generation

LLMがContextどおり回答したか。

---

# 42. よくある「LLMのせい」という誤解

RAGの回答が間違っていると、

LLMが悪い

と思われがちです。

しかし実際には、

- OCR
    
- Chunk
    
- Search
    
- Filter
    
- Context
    

の問題であることも多いです。

そのため、

**生成だけでなくRetrieval側を確認する**

ことが重要です。

---

# 43. よくある問題を分類すると

### 文書取り込み

- OCR誤り
    
- PDF解析崩れ
    
- 表崩れ
    
- 古い文書
    

### 検索

- 正解が出ない
    
- 関係ない結果
    
- Top-K不適切
    
- Filter不適切
    

### LLM

- Hallucination
    
- Context無視
    
- Citation誤り
    

### セキュリティ

- 権限漏れ
    
- Prompt Injection
    
- Cache漏えい
    

### 運用

- Timeout
    
- Retry
    
- Queue詰まり
    
- コスト増加
    
- 監視不足
    

です。

---

# 44. 一言で理解する

RAGでよく起きる問題は、

**「正しい文書を正しく取り込み、正しく検索し、必要な情報だけをLLMへ渡す」**

という流れのどこかが崩れることで発生します。

問題が起きたときは、

**Document → Parse → Chunk → Search → Context → LLM**

の順番で確認すると原因を切り分けやすいです。

特に重要なのは、

**RAGの問題 = LLMの問題とは限らない**

という点です。
