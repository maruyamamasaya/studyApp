## 1. OAuth 2.0とは

OAuth 2.0は、

**アプリケーションが、ユーザーや別アプリの代わりにAPIへアクセスするための権限を取得する仕組み**

です。

簡単にいうと、

「このアプリに、この範囲までAPIを使わせてよい」

という権限を、

Access Token

として渡します。

---

## 2. OAuth 2.0は認証そのものではない

ここは重要です。

OAuth 2.0は基本的に、

**認可の仕組み**

です。

つまり、

「誰なのか」

を確認する仕組みそのものではなく、

「何をしてよいか」

を決める仕組みです。

Authentication  
= 誰か

Authorization  
= 何をしてよいか

OAuth 2.0は主に後者です。

---

## 3. 基本イメージ

例えば、

ユーザー  
→ Webアプリ

Webアプリ  
→ 認可サーバー

認可サーバー  
→ Access Token発行

Webアプリ  
→ Access Tokenを付けてAPI呼び出し

という流れです。

---

## 4. Access Token

OAuth 2.0で重要なのが、

Access Token

です。

Access Tokenは、

**APIへアクセスしてよいことを示すToken**

です。

例えば、

```
Authorization: Bearer eyJ...
```

のようにHTTP Headerへ付けて送ります。

---

## 5. Bearer Token

OAuth 2.0では、

Bearer Token

形式がよく使われます。

Bearerには、

「このTokenを持っている人が使える」

という意味があります。

そのため、

Access Tokenが漏れると危険

です。

---

## 6. OAuth 2.0の登場人物

基本的には以下があります。

### Resource Owner

リソースの所有者。

多くの場合はユーザーです。

### Client

APIを利用したいアプリケーション。

### Authorization Server

Access Tokenを発行するサーバー。

### Resource Server

実際のAPIを提供するサーバー。

---

## 7. RAGで考える例

例えば、

ユーザー  
→ 社内RAG Webアプリ

Entra ID  
→ Authorization Server

RAG API  
→ Resource Server

と考えられます。

ユーザーがログイン後、

Access Tokenを取得

して、

RAG APIを呼び出します。

---

## 8. Scope

OAuth 2.0では、

どこまでAPIを使ってよいか

をScopeで表します。

例えば、

```
rag.read
documents.read
documents.write
```

などです。

Access Tokenに許可されたScopeをAPI側で確認します。

---

## 9. Scopeの例

例えば、

documents.read

だけ持っているユーザーなら、

文書閲覧は可能

ですが、

documents.write

がなければ、

文書登録は拒否できます。

---

## 10. Roleとの違い

ScopeとRoleは似ていますが少し違います。

### Scope

APIで許可された操作範囲。

### Role

ユーザーやアプリの役割。

例えば、

Role  
= admin

Scope  
= documents.write

のように使えます。

---

## 11. Authorization Code Flow

Webアプリなどでよく使われる方式です。

流れは、

ユーザー  
→ Login画面

→ 認可サーバー

→ Authorization Code取得

→ CodeをTokenと交換

→ Access Token取得

です。

---

## 12. Authorization Code

Login後にいきなりAccess TokenをURLへ返すのではなく、

一度、

Authorization Code

を返します。

アプリはそのCodeを、

認可サーバーへ送り、

Access Tokenへ交換します。

---

## 13. なぜCodeを使うのか

Access Tokenを直接ブラウザ経由で扱うより、

Codeを経由したほうが安全に管理しやすいためです。

現在のWebアプリやSPAでは、

Authorization Code Flow

が基本的な方式として使われます。

---

## 14. PKCE

PKCEは、

Proof Key for Code Exchange

の略です。

Authorization Codeを横取りされても、

Tokenへ交換しにくくするための仕組みです。

特に、

- SPA
    
- モバイルアプリ
    

で重要です。

---

## 15. Client Credentials Flow

ユーザーではなく、

**アプリケーション自身がAPIへアクセスする**

場合に使います。

例えば、

RAG Worker  
→ Azure AI Search

のような、

アプリ対アプリ

の通信です。

---

## 16. Client Credentialsの流れ

例えば、

Application  
→ Client ID / Credentialを使う

→ Entra ID

→ Access Token取得

→ API呼び出し

という流れです。

人間のユーザーは登場しません。

---

## 17. RAGでの使い分け

例えば、

ユーザー  
→ RAG Web App  
→ RAG API

なら、

Authorization Code Flow

が使われることがあります。

一方、

RAG API  
→ Azure Resource

なら、

Client CredentialsやManaged Identity

のようなアプリ認証を使います。

---

## 18. Refresh Token

Access Tokenには有効期限があります。

期限切れのたびにユーザーへLoginを求めると不便です。

そのため、

Refresh Token

を使って、

新しいAccess Tokenを取得

する場合があります。

---

## 19. Access Tokenの有効期限

Access Tokenは、

永続的には使えません。

一定時間後に期限切れになります。

これによって、

Tokenが漏れた場合の影響時間を短くできます。

---

## 20. Refresh Tokenの注意

Refresh Tokenは、

新しいAccess Tokenを発行できる

ため非常に重要な秘密情報です。

安全に保管する必要があります。

---

## 21. Consent

OAuth 2.0では、

アプリがどの権限を要求しているか

をユーザーや管理者が承認する仕組みがあります。

これを、

Consent

と呼びます。

例えば、

「このアプリにプロフィール情報の読み取りを許可しますか？」

といったものです。

---

## 22. Admin Consent

組織全体に関係する強い権限の場合、

管理者による承認

が必要になることがあります。

これを、

Admin Consent

と呼びます。

---

## 23. Redirect URI

Authorization Code Flowでは、

Login完了後、

どこへ戻るか

をRedirect URIで指定します。

例えば、

```
https://example.com/auth/callback
```

です。

登録済みのRedirect URIと一致することが重要です。

---

## 24. Client ID

OAuth 2.0では、

どのアプリがTokenを要求しているか

をClient IDで識別します。

Entra IDのApp Registrationでは、

Application（Client）ID

がこれに該当します。

---

## 25. Client Secret

Server側アプリでは、

Client Secret

を使う場合があります。

これは、

アプリ自身のPassword

のようなものです。

漏えいすると危険なので、

Key Vaultなどで管理します。

---

## 26. Managed Identityとの関係

Azure上のアプリでは、

Client Secretを使わず、

Managed Identity

を使える場合があります。

その場合も、

内部的にはTokenを取得してAPIへアクセスする

という考え方は同じです。

---

## 27. OAuth 2.0とJWT

OAuth 2.0は、

認可の仕組み

です。

JWTは、

Tokenの形式の1つ

です。

つまり、

OAuth 2.0  
→ Tokenをどう取得・使うか

JWT  
→ Tokenをどう表現するか

という違いです。

---

## 28. Access TokenがJWTとは限らない

Access Tokenは、

必ずJWT

とは限りません。

OAuth 2.0としては、

Tokenの内部形式

を限定していません。

ただし、Entra IDではJWT形式のAccess Tokenがよく使われます。

---

## 29. OAuth 2.0とOpenID Connect

OAuth 2.0だけでは、

ユーザーLoginの仕組み

としては不足します。

そこで、

OpenID Connect

を組み合わせます。

OpenID Connectは、

OAuth 2.0の上に、

ユーザー認証の仕組み

を追加したものです。

---

## 30. OpenID Connect

OpenID Connectでは、

ID Token

を使って、

「このユーザーは誰か」

をClientへ伝えます。

つまり、

OAuth 2.0  
= APIアクセスの認可

OpenID Connect  
= ユーザー認証

という関係です。

---

## 31. Entra IDとの関係

Microsoft Entra IDは、

OAuth 2.0

と、

OpenID Connect

をサポートしています。

そのため、

ユーザーLogin  
→ OpenID Connect

APIアクセス  
→ OAuth 2.0

という構成ができます。

---

## 32. RAGでのLoginフロー

例えば、

User  
→ RAG Web App

→ Entra ID Login

→ ID Token / Access Token取得

→ RAG APIへAccess Token送信

→ RAG APIがToken検証

→ Question処理

となります。

---

## 33. API側で確認するもの

Access Tokenを受け取ったAPIは、

例えば、

- 署名
    
- Issuer
    
- Audience
    
- 有効期限
    
- Scope
    
- Role
    

を確認します。

Tokenがあるだけで無条件に許可してはいけません。

---

## 34. Audience

Audienceは、

そのTokenが、

どのAPI向けに発行されたか

を表します。

RAG API向けTokenなら、

RAG API側でAudienceを確認します。

---

## 35. Issuer

Issuerは、

誰がTokenを発行したか

を表します。

信頼するEntra ID Tenantから発行されたTokenか確認します。

---

## 36. Scope確認

例えば、

POST /documents

を呼ぶ場合、

documents.write

Scopeが必要

といった制御ができます。

---

## 37. Role確認

例えば、

Admin API

なら、

Admin Role

が必要

といった制御ができます。

ScopeとRoleを組み合わせる場合もあります。

---

## 38. OAuth 2.0とMetadata Filter

RAGでは、

OAuth 2.0で取得したToken

から、

UserやGroup、Role

を特定し、

Azure AI SearchのMetadata Filter

へつなげることがあります。

例えば、

Access Token  
→ User確認  
→ HR Group所属  
→ HR文書だけ検索

という流れです。

---

## 39. 認証後もAPIで制御する

Web画面でLogin済みでも、

API側でTokenを検証します。

画面だけで、

「このボタンを隠す」

だけでは不十分です。

API側でも、

ScopeやRole

を確認します。

---

## 40. OAuth 2.0で重要なポイント

最低限、

- Access Token
    
- Scope
    
- Client
    
- Authorization Server
    
- Resource Server
    
- Authorization Code
    
- Client Credentials
    
- Redirect URI
    
- Refresh Token
    

を理解すると十分です。

---

## 41. RAG全体での位置

例えば、

User  
→ Entra ID

→ OAuth 2.0でAccess Token取得

→ RAG API

→ Token検証

→ Role / Scope確認

→ Metadata Filter

→ Azure AI Search

→ Azure OpenAI

という流れになります。

---

## 42. 一言で理解する

OAuth 2.0とは、

**「アプリがAPIを使うためのアクセス権を、Access Tokenとして取得・利用する仕組み」**

です。

覚え方としては、

**OAuth 2.0 = APIアクセスの認可**

**OpenID Connect = ユーザー認証**

**Access Token = APIを使うための通行証**

で十分です。
