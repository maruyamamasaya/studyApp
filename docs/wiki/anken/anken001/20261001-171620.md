## 1. 概要

RAG基盤では、

- LLM
    
- Embedding
    
- Search
    
- Storage
    
- OCR
    
- API基盤
    
- 監視
    
- Queue / Worker
    

など、複数のサービスでコストが発生します。

そのため、

**どの処理がどれだけ費用を使っているかを把握し、品質を落とさずに無駄を減らす**

ことが重要です。

---

## 2. 主なコスト要素

RAGでは主に以下で費用が発生します。

### LLM

回答生成に使うToken数。

### Embedding

文書や質問をVector化する処理。

### Search

検索IndexやQuery処理。

### Storage

元文書やログの保存。

### OCR

スキャンPDFや画像の文字認識。

### Compute

APIやWorkerを動かす基盤。

### Monitoring

Application InsightsやLog Analyticsなど。

---

## 3. LLMコスト

RAGでは、

Prompt  
＋ Context  
＋ Question

をLLMへ送ります。

そのため、

Contextが大きいほどInput Tokenが増え、

コストも増えやすくなります。

特に、

- Chunk Size
    
- Top-K
    
- 会話履歴
    
- Prompt長
    

が影響します。

---

## 4. Input TokenとOutput Token

LLMでは一般的に、

- Input Token
    
- Output Token
    

の両方が料金に関係します。

例えば、

Input Tokenが多すぎる

場合は、

Contextや会話履歴を見直します。

Output Tokenが多すぎる

場合は、

回答を簡潔にするPrompt

などを検討します。

---

## 5. Top-Kとコスト

例えば、

1 Chunk = 500 Token

Top-K = 5

なら、

約2500 Token分のContext

になります。

Top-K = 20

なら、

約10000 Token

になります。

そのため、

**Top-Kを増やすと検索Recallは上がる可能性があるが、LLMコストも増える**

という関係があります。

---

## 6. Rerankingで絞る

検索では多めに候補を取得し、

Reranking後に少数へ絞る

ことで、

LLMへ渡すContext量を減らせます。

例えば、

検索  
→ Top 30

Reranking  
→ Top 5

LLM  
→ Top 5のみ

という構成です。

---

## 7. Embeddingコスト

文書取り込みでは、

大量のChunkをEmbeddingします。

例えば、

1000文書  
→ 10000 Chunk

なら、

10000回分のEmbedding処理

が必要になります。

そのため、

- Chunk数
    
- Token数
    
- 再Embedding回数
    

がコストに影響します。

---

## 8. 差分更新

文書が少し変更されたたびに、

全件再Embedding

すると無駄が大きくなります。

そのため、

- File Hash
    
- Chunk Hash
    
- Version
    

などを使って、

変更された部分だけ再Embedding

します。

---

## 9. Embedding Cache

同じ文章を何度もEmbeddingしないように、

Cache

を使えます。

例えば、

text_hash  
→ Cache確認  
→ 既存Vectorあり  
→ 再利用

とします。

これによって、

API回数

と、

Embeddingコスト

を削減できます。

---

## 10. OCRコスト

スキャンPDFではOCRが必要です。

ただし、

すべてのPDFにOCR

するとコストが増えます。

そのため、

通常のテキスト抽出  
→ 文字取得できないページだけOCR

とする構成が効率的です。

---

## 11. ページ単位でOCRする

例えば、

100ページ中10ページだけ画像

なら、

10ページだけOCR

します。

PDF全体をOCRするより、

処理時間と費用を抑えられます。

---

## 12. Searchコスト

検索サービスでは、

- Index Size
    
- Vector数
    
- Query数
    
- Replica
    
- Partition
    

などがコストに関係する場合があります。

大量のChunkを細かく作りすぎると、

Vector数やIndex Sizeも増えます。

---

## 13. Chunk SizeとSearchコスト

Chunkを小さくしすぎると、

1文書から大量のChunk

が作られます。

例えば、

1000文書  
→ 50000 Chunk

となれば、

- Embedding数
    
- Vector数
    
- Index Size
    

も増えます。

そのため、

検索精度だけでなくコストとのバランスも見ます。

---

## 14. Storageコスト

保存対象として、

- PDF原本
    
- OCR結果
    
- Chunk
    
- Vector
    
- Log
    
- Backup
    

などがあります。

特に、

ログ

や、

古い文書Version

が増え続けると、Storage Costが積み上がります。

---

## 15. Blob StorageのTier

原本PDFを頻繁に読まない場合、

Storage Tier

を見直せます。

例えば、

Hot  
→ 頻繁に利用

Cool / Cold  
→ 利用頻度が低い

Archive  
→ 長期保管

などです。

ただし、取り出し頻度や復元時間も考慮します。

---

## 16. Logコスト

Application InsightsやLog Analyticsでは、

ログ量

がコストに影響します。

例えば、

Prompt全文  
Context全文  
Answer全文

を毎回保存すると、

かなり大きなログ量

になる可能性があります。

---

## 17. ログを必要最小限にする

例えば、

- request_id
    
- document_id
    
- chunk_id
    
- latency
    
- token_count
    
- error_type
    

を中心に記録し、

本文全文

は必要な場合だけ保存します。

これは、

コスト削減

と、

セキュリティ

の両方に有効です。

---

## 18. Cacheによるコスト削減

Cacheは、

同じ処理を何度も実行しない

ために有効です。

例えば、

- Embedding Cache
    
- OCR Cache
    
- Search Cache
    
- Prompt Cache
    
- Answer Cache
    

などがあります。

ただし、

権限や文書更新

に注意します。

---

## 19. Answer Cacheの注意

同じ質問でも、

- User権限
    
- 文書Version
    
- 会話履歴
    

が違えば、

同じ回答を返してはいけない

場合があります。

そのため、

単純に質問文だけでCache

するのは危険です。

---

## 20. Queueとコスト

大量の文書処理を一気に実行すると、

一時的にComputeやAPI利用量が急増

します。

Queueで処理量を平準化することで、

- Rate Limit回避
    
- Worker数制御
    
- 急激なコスト増加抑制
    

につながります。

---

## 21. 並列数の制御

並列数を増やせば処理は速くなりますが、

API呼び出しも一気に増えます。

そのため、

Concurrency Limit

を設定します。

例えば、

最大5件  
最大10件

などです。

---

## 22. Worker数の調整

Workerを増やしすぎると、

処理速度は上がっても、

Compute Cost

が増えます。

Queue Lengthと処理時間を見ながら、

必要な台数へ調整します。

---

## 23. Auto Scaling

負荷に応じて、

WorkerやAPI Instance数を自動調整

する方法があります。

例えば、

Queue Lengthが増加  
→ Worker増加

Queueが空  
→ Worker削減

とします。

常時最大台数を動かすより効率的です。

---

## 24. モデル選択

すべての処理で、

最も高性能なLLM

を使う必要はありません。

例えば、

- Query Rewrite
    
- Classification
    
- 簡単な要約
    

などは、

より小さいモデル

で十分な場合があります。

重要な回答生成だけ高性能モデルを使う

という構成もできます。

---

## 25. モデルルーティング

質問内容によって、

利用するモデルを変える

方法もあります。

例えば、

簡単な質問  
→ 小さいモデル

複雑な質問  
→ 高性能モデル

とします。

これによって、

品質とコストのバランス

を取れます。

---

## 26. 不要なLLM呼び出しを減らす

例えば、

Search結果が0件

Similarityが極端に低い

場合、

LLMを呼ばずに、

「該当情報がありません」

と返せます。

無駄なLLM呼び出しを減らせます。

---

## 27. Token Budget

RAGでは、

1RequestあたりのToken Budget

を考えると管理しやすいです。

例えば、

Prompt  
1000 Token

Context  
5000 Token

Output  
1000 Token

などです。

一定以上になったら、

Contextを削減する

設計もできます。

---

## 28. 1Requestあたりのコスト

RAGでは、

1質問あたりのコスト

を算出すると分かりやすいです。

例えば、

LLM  
＋ Embedding  
＋ Search

を合計して、

1 Request = 約○円

とします。

これを、

月間Request数

へ掛ければ、

月額の概算を出せます。

---

## 29. 月額試算

例えば、

1 Request = 0.5円

月100,000 Request

なら、

約50,000円

という考え方です。

さらに、

- Search固定費
    
- Storage
    
- Monitoring
    
- Compute
    

を加えます。

---

## 30. 固定費と従量課金を分ける

RAG基盤では、

### 固定費に近いもの

- Search Service
    
- App Service
    
- 常時Worker
    
- Private Endpointなど
    

### 従量課金に近いもの

- LLM Token
    
- Embedding
    
- OCR
    
- Log取り込み
    
- Storage容量
    

のように分けると、見積しやすくなります。

---

## 31. Cost Allocation

複数部署がRAGを使う場合、

どの部署がどれくらい使っているか

を記録すると便利です。

例えば、

- department
    
- application_id
    
- tenant
    
- user_group
    

ごとに、

Request数  
Token数

を集計します。

---

## 32. Budget

Azure側では、

月額Budget

を設定して、

一定金額を超えたら通知

する構成があります。

例えば、

50%  
80%  
100%

でAlert

とします。

---

## 33. 異常コスト監視

例えば、

通常1日100万Token

なのに、

突然1000万Token

になった場合です。

原因として、

- バグ
    
- 無限Retry
    
- 大量アクセス
    
- Prompt肥大化
    
- 攻撃
    

などが考えられます。

そのため、

コストも監視対象

にします。

---

## 34. Retryとコスト

Retryが増えると、

同じAPI処理を何度も実行

することになります。

そのため、

Retry Rate

が高い状態は、

安定性だけでなくコスト面でも問題です。

---

## 35. Hallucinationとコスト

品質を上げるために、

Contextを大量に増やす

LLMを大型化する

と、

コストは増えます。

しかし、

高コスト = 高品質

とは限りません。

まず、

検索品質

を改善したほうが効率的な場合があります。

---

## 36. 品質とコストを一緒に見る

例えば、

Top-K = 5  
→ 正答率90%  
→ 1Request 0.5円

Top-K = 20  
→ 正答率91%  
→ 1Request 1.5円

なら、

追加コストに対して品質改善が小さい

可能性があります。

このように比較します。

---

## 37. Cost KPI

RAGで見やすい指標として、

- Cost / Request
    
- Cost / User
    
- Cost / Department
    
- Token / Request
    
- Embedding Cost / Document
    
- OCR Cost / Document
    
- Cache Hit Rate
    

などがあります。

---

## 38. コスト監視Dashboard

例えば、

### LLM

Input / Output Token  
Cost / Request

### Search

Query数  
Index Size

### Ingestion

Embedding件数  
OCR件数

### Infrastructure

Compute Cost  
Storage Cost

### Total

日次 / 月次Cost

という形で確認します。

---

## 39. コスト削減の優先順位

一般的には、

1. 無駄なLLM呼び出しを減らす
    
2. Context / Tokenを減らす
    
3. Embedding再計算を減らす
    
4. Cacheを使う
    
5. OCR対象を限定する
    
6. Worker / Computeを適正化する
    
7. ログ量を調整する
    

という順で見ると分かりやすいです。

---

## 40. コストだけで最適化しない

コストを下げすぎると、

- 正解Chunkを取れない
    
- Context不足
    
- 回答品質低下
    
- 処理遅延
    

につながる場合があります。

そのため、

**品質・性能・コストの3つを一緒に見る**

ことが重要です。

---

## 41. 一言で理解する

RAG基盤のコスト管理とは、

**「LLM・Embedding・Search・OCR・Storage・Computeなどの費用を可視化し、品質を落とさず無駄な処理を減らすこと」**

です。

特に重要なのは、

**Token**

**Top-K**

**Embedding再計算**

**Cache**

**OCR対象**

**Worker / 並列数**

です。

覚え方としては、

**Cost = 使ったAI量 + 検索基盤 + 保存 + 実行基盤 + 監視**

と考えると分かりやすいです。
