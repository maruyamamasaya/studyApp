## 1. Entra IDとは

Microsoft Entra IDは、

**ユーザーやアプリケーションのIdentityを管理し、認証・アクセス制御を行うMicrosoftのクラウド型Identity基盤**

です。

以前は、

Azure Active Directory  
Azure AD

と呼ばれていました。

RAGでは主に、

- ユーザーのログイン
    
- APIの認証
    
- Role / Groupの取得
    
- Azure Resourceへのアクセス制御
    
- アプリケーション同士の認証
    

などで利用します。

Microsoftの現行ドキュメントでも、Entra IDはユーザーとアプリケーションの認証やToken発行を担うIdentity基盤として説明されています。

---

## 2. RAGでの役割

例えば社内RAGで、

「この質問をしている人は誰なのか」

を確認する必要があります。

そのため、

User  
→ Entra IDでLogin  
→ Token取得  
→ RAG APIへToken送信

という流れにします。

RAG API側では、

Tokenを検証して、

- User ID
    
- Role
    
- Group
    
- Scope
    

などを取得します。

---

## 3. Authentication

Authenticationは、

**誰なのか確認すること**

です。

日本語では、

認証

と呼びます。

例えば、

メールアドレス  
＋  
Password  
＋  
MFA

などを使って、

本人かどうか

を確認します。

---

## 4. Authorization

Authorizationは、

**そのユーザーが何をしてよいか確認すること**

です。

日本語では、

認可

と呼びます。

例えば、

一般社員  
→ 全社資料だけ閲覧可能

人事部  
→ 人事資料も閲覧可能

管理者  
→ 文書登録・削除可能

のように制御します。

---

## 5. AuthenticationとAuthorizationの違い

重要なので分けて覚えます。

Authentication  
= あなたは誰か

Authorization  
= あなたは何をしてよいか

です。

RAGでは、

認証  
→ User確認

認可  
→ 検索対象文書を制御

という流れになります。

---

## 6. Token

Entra IDで認証すると、

Token

が発行されます。

アプリケーションはこのTokenを使って、

「このユーザーは認証済みです」

ということを確認します。

Microsoft Entra IDでは、アプリケーションがTokenを取得してユーザーやアプリを識別する流れが基本です。

---

## 7. Access Token

APIへアクセスするときによく使うのが、

Access Token

です。

例えば、

```
Authorization: Bearer eyJ...
```

という形でAPIへ送ります。

API側はAccess Tokenを検証し、

Requestを許可するか判断します。

---

## 8. ID Token

ID Tokenは、

**ログインしたユーザーが誰なのか**

をClient Applicationへ伝えるために使います。

例えば、

- User ID
    
- 名前
    
- Tenant情報
    

などを含みます。

APIアクセスには通常、

Access Token

を使います。

---

## 9. JWT

Entra IDのTokenでは、

JWT

JSON Web Token

形式が利用されます。

JWTの中には、

Claims

と呼ばれる情報が含まれます。

---

## 10. Claims

Claimsは、

Tokenに含まれるユーザーやアプリの情報

です。

例えば、

- sub
    
- oid
    
- tid
    
- roles
    
- groups
    
- scopes
    
- exp
    

などです。

API側ではClaimsを使って、

誰なのか  
何をしてよいか

を判断できます。

---

## 11. Tenant

Entra IDでは、

組織単位のIdentity領域

をTenantと呼びます。

例えば、

A社のEntra ID Tenant

の中に、

- 社員
    
- Group
    
- Application
    
- Service Principal
    

などが存在します。

---

## 12. Tenant ID

Tenantには、

Tenant ID

という一意のIDがあります。

アプリケーションからEntra IDへ接続するときに利用します。

---

## 13. User

人間の利用者を表します。

例えば、

- 社員
    
- 管理者
    
- 外部ゲスト
    

などです。

ユーザーには、

- Group
    
- Role
    
- 属性
    

などを割り当てられます。

---

## 14. Group

複数のUserをまとめるために、

Group

を利用します。

例えば、

HR  
Finance  
IT

などです。

RAGでは、

Userが所属するGroup

を使って文書アクセス制御できます。

---

## 15. RAGとGroup

例えば、

Document A  
allowed_groups = ["All"]

Document B  
allowed_groups = ["HR"]

の場合、

HR所属ユーザー

だけDocument Bを検索できる

ようにします。

流れは、

Entra ID  
→ User Group取得  
→ Metadata Filter  
→ Azure AI Search

です。

---

## 16. Role

Roleは、

ユーザーやアプリの役割

を表します。

例えば、

- User
    
- Manager
    
- Admin
    

などです。

RAG APIでは、

Adminのみ文書登録可能

のような制御に利用できます。

---

## 17. Scope

Scopeは、

APIで許可する操作範囲

を表します。

例えば、

rag.read

documents.read

documents.write

などです。

Access Tokenに付与されたScopeをAPI側で確認します。

---

## 18. RBACとの関係

RBACは、

Role-Based Access Control

です。

Azure Resourceへのアクセス権をRoleで管理します。

例えば、

RAG Application  
→ Azure AI Search読み取り可能

RAG Application  
→ Blob Storage読み取り可能

などです。

Entra IDでIdentityを確認し、

Azure RBACでResourceへの権限を制御

するイメージです。

---

## 19. App Registration

人間だけでなく、

**アプリケーション自身にもIdentity**

を持たせることができます。

そのために使うのが、

App Registration

です。

Entra IDへApplicationを登録すると、そのアプリを識別するApplication Objectが作成されます。通常、ホームTenantには対応するService Principalも作成されます。

---

## 20. Client ID

App Registrationすると、

Application（Client）ID

が発行されます。

例えば、

RAG Web App

をEntra IDへ登録すると、

そのアプリを識別するClient ID

が作られます。

---

## 21. Redirect URI

Web ApplicationでLoginする場合、

認証完了後に、

どこへ戻るか

を設定します。

これを、

Redirect URI

と呼びます。

例えば、

```
https://example.com/auth/callback
```

です。

---

## 22. Service Principal

Service Principalは、

**Entra ID Tenant内で実際に権限を持つアプリケーションのIdentity**

です。

Application Objectが、

アプリそのものの定義

なら、

Service Principalは、

そのTenant内で使われるアプリの実体

と考えると分かりやすいです。

---

## 23. Application ObjectとService Principal

簡単にいうと、

Application Object  
= アプリの設計図

Service Principal  
= Tenant内で動くアプリIdentity

です。

Application ObjectはホームTenantに存在し、Service Principalはそのアプリを利用するTenantごとに作成されることがあります。

---

## 24. アプリケーション同士の認証

例えば、

RAG API  
→ Azure AI Search

のように、

UserではなくApplication自身

がAzure Resourceへアクセスする場合があります。

そのとき、

Service Principal

や、

Managed Identity

を使います。

---

## 25. Client Secret

App Registrationで、

Client Secret

を作成することがあります。

アプリは、

- Tenant ID
    
- Client ID
    
- Client Secret
    

を使ってTokenを取得します。

ただしClient Secretは秘密情報なので、

Key Vaultなどで管理します。

---

## 26. Certificate認証

Client Secretの代わりに、

Certificate

を使う方法もあります。

一般的に、

PasswordのようなSecretより強い認証方法

として使われることがあります。

---

## 27. Managed Identity

Azure Resource上で動くApplicationには、

Managed Identity

を付与できます。

例えば、

App Service  
→ Managed Identity  
→ Azure AI Search

とします。

Managed Identityでは、AzureがCredentialを管理してくれるため、アプリ側でSecretを管理する必要を減らせます。Microsoftも、対応Resource間ではManaged Identityを検討するよう案内しています。

---

## 28. System-assigned Managed Identity

Azure Resource自体にIdentityを付与します。

例えば、

RAG App Service

に、

System-assigned Managed Identity

を有効化します。

Resourceを削除すると、

Identityも一緒に削除されます。

---

## 29. User-assigned Managed Identity

Identityを独立したAzure Resourceとして作成します。

複数のApplicationから、

同じIdentity

を利用できます。

Resourceとは別に管理できます。

---

## 30. RAGでのManaged Identity

例えば、

RAG API  
→ Azure AI Search  
→ Blob Storage  
→ Key Vault

へアクセスするとき、

Managed Identity

を使える場合があります。

これによって、

API KeyやClient Secretを減らせます。

---

## 31. Key Vaultとの関係

Key Vaultは、

Secretを安全に保存する場所

です。

Entra IDは、

誰がKey Vaultへアクセスできるか

を認証します。

つまり、

Entra ID  
→ Identity確認

RBAC  
→ Key Vaultへの権限確認

Key Vault  
→ Secret取得

という流れです。

---

## 32. Azure OpenAIとの関係

Azure OpenAIも、

Entra ID認証

を利用できる構成があります。

例えば、

RAG API  
→ Managed Identity  
→ Entra ID Token  
→ Azure OpenAI

です。

API Keyを使わない構成にできます。

---

## 33. Azure AI Searchとの関係

Azure AI Searchも、

Entra ID + RBAC

でアクセス制御できます。

例えば、

RAG API  
→ Managed Identity  
→ Azure AI Search

とします。

RAG Applicationに必要なRoleだけを付与します。

---

## 34. Blob Storageとの関係

Blob Storageへのアクセスも、

Entra ID

で制御できます。

例えば、

RAG Worker  
→ Managed Identity  
→ Blob読み取り

という構成です。

---

## 35. SSO

SSOは、

Single Sign-On

の略です。

1回Loginすれば、

複数の対応Applicationへ再Loginせずアクセスできる仕組みです。

Entra IDはMicrosoft 365や企業ApplicationとのSSOにも利用されます。

---

## 36. MFA

MFAは、

Multi-Factor Authentication

の略です。

例えば、

Password  
＋  
スマホ認証

のように、

複数要素で本人確認します。

Account乗っ取り対策として重要です。

---

## 37. Conditional Access

状況に応じて、

Loginを許可・拒否したり、

MFAを要求したりする仕組みです。

例えば、

社外NetworkからLogin  
→ MFA必須

などです。

企業向け認証では重要な機能です。

---

## 38. API側でもTokenを検証する

Web画面でLogin済みだからといって、

API側で何もしなくてよい

わけではありません。

API側でも、

- 署名
    
- Issuer
    
- Audience
    
- 有効期限
    

などを検証します。

---

## 39. Audience

Tokenが、

どのAPI向けに発行されたか

を表します。

例えば、

RAG API向けのToken

を、

別のAPIで利用させない

ために確認します。

---

## 40. Issuer

Tokenを、

誰が発行したか

を示します。

API側では、

信頼しているEntra ID Tenantから発行されたTokenか

を確認します。

---

## 41. Expiration

Tokenには、

有効期限

があります。

期限切れTokenは使用できません。

これによって盗まれたTokenを永続的に使われるリスクを減らします。

---

## 42. RAGのログインフロー

例えば、

User  
→ RAG Web Application

→ Entra ID Login

→ Token取得

→ POST /api/ask

→ RAG APIがToken検証

→ User Group / Role確認

→ Metadata Filter

→ Azure AI Search

→ LLM

という流れです。

---

## 43. RAGの権限制御

特に重要なのは、

Entra IDでLoginできた

だけでは、

すべての文書を見せてよいわけではない

という点です。

Entra IDから、

User / Group / Role

を取得し、

検索側でPermission Filter

を適用します。

---

## 44. 認証と文書権限を分ける

例えば、

Entra ID  
→ 誰なのか確認

RAG Application  
→ Group / Roleを取得

Azure AI Search  
→ allowed_groupsでFilter

という役割分担です。

---

## 45. Azure RAG構成での位置

Azure環境では、

Entra ID  
→ 利用者・ApplicationのIdentity管理

Blob Storage  
→ 文書原本

Azure AI Search  
→ 検索

Azure OpenAI  
→ Embedding / LLM

Key Vault  
→ Secret

Application Insights  
→ 監視

という役割分担になります。

---

## 46. Python Applicationからの認証

Azure SDKでは、

DefaultAzureCredential

を使うことがあります。

例えば、

```
from azure.identity import DefaultAzureCredential

credential = DefaultAzureCredential()
```

です。

ローカル開発とAzure本番環境で、

利用可能な認証方式を切り替えやすくなります。

---

## 47. Secretを減らす

Azure上のApplicationであれば、

Client SecretをKey Vaultへ保存する

よりも、

Managed Identityを使ってSecret自体をなくす

ほうが適している場合があります。

つまり、

**安全にSecretを保存する**

だけでなく、

**可能ならSecretを持たない**

という考え方も重要です。

---

## 48. App Registrationが必要なケース

例えば、

Web ApplicationをEntra ID Login対応にする

外部Applicationから自社APIを利用する

独自API Scopeを定義する

といった場合に、

App Registration

を利用します。

## 49. Managed Identityが向いているケース

例えば、

Azure上の、

- Worker

Azure Resourceへアクセスする場合です。

Microsoftの現行ガイドでも、対応するAzure Resource同士ではManaged Identityを優先的に検討することが推奨されています。

## 51. 一言で理解する

Microsoft Entra IDとは、

**「人とApplicationが誰なのかを管理し、Tokenを発行してアクセス制御につなげるMicrosoftの認証基盤」**

です。

RAGでは、

**User Login**

と、

**ApplicationからAzure Resourceへの認証**

の両方で使います。

特に覚えておきたいのは、

**Authentication = 誰か**

**Authorization = 何をしてよいか**

**Entra ID = Identityを確認してTokenを発行**

**RBAC / Metadata Filter = 実際のアクセス範囲を制御**

という関係です。
