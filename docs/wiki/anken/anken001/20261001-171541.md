## 1. Vector Searchとは

Vector Search（ベクトル検索）は、

**文章をEmbeddingによってVectorへ変換し、そのVector同士の近さを使って関連情報を検索する方法**

です。

通常のKeyword Searchが、

「同じ単語が含まれているか」

を中心に探すのに対して、Vector Searchは、

「意味が近いか」

を中心に探します。

例えば、

「パソコンを購入したい」

という質問に対して、

「PCを買う場合は上長の承認が必要です」

という文章を見つけることができます。

「パソコン」と「PC」、「購入」と「買う」は文字列としては違いますが、意味が近いためです。

---

## 2. RAGでVector Searchを使う理由

RAGでは、ユーザーが必ずしも文書と同じ表現で質問するとは限りません。

例えば文書に、

「端末購入申請」

と書かれていても、ユーザーは、

「新しいパソコンを買いたい」

と質問するかもしれません。

Keyword Searchだけでは検索できない場合があります。

Vector Searchを利用すると、

**言い換えや自然な質問でも、意味が近い文書を探しやすくなります。**

---

## 3. Vector Searchの基本イメージ

文書側では、事前にChunkをEmbeddingします。

Chunk A  
「PC購入には上長承認が必要です。」

Chunk B  
「パスワードは90日ごとに変更します。」

Chunk C  
「バックアップは30日間保存します。」

それぞれ、

Chunk A  
→ Vector A

Chunk B  
→ Vector B

Chunk C  
→ Vector C

として保存しておきます。

ユーザーが、

「パソコンを買うときの承認方法は？」

と質問すると、この質問もEmbeddingします。

質問  
→ Question Vector

そして、

Question Vectorと各Chunk Vectorの近さを比較します。

最も近いChunk Aが検索結果として返される、という流れです。

---

## 4. Vector Searchの処理フロー

基本的な流れは以下です。

### 文書登録時

Document  
→ Chunk  
→ Embedding  
→ Vector作成  
→ Vector Indexへ保存

### 質問時

Question  
→ Embedding  
→ Question Vector作成  
→ Vector Index検索  
→ 類似Vector取得  
→ 関連Chunk取得

つまり、

**文書と質問を同じVector空間で比較する**

のがVector Searchです。

---

## 5. Vector空間とは

Embeddingされた文章は、多次元のVectorとして表現されます。

例えば簡単に3次元で考えると、

文章A  
[0.8, 0.2, 0.1]

文章B  
[0.75, 0.25, 0.15]

文章C  
[-0.3, 0.9, 0.6]

のようになります。

意味が近い文章Aと文章Bは、Vector空間上でも近い位置になります。

意味が違う文章Cは離れます。

実際には数百〜数千次元のVectorが使われます。

---

## 6. Similarity

Vector Searchでは、

Vector同士がどれくらい似ているか

を計算します。

これをSimilarity（類似度）と呼びます。

代表的な方法には、

- Cosine Similarity
    
- Dot Product
    
- Euclidean Distance
    

があります。

Embeddingモデルや検索サービスによって、利用する方法が異なります。

---

## 7. Cosine Similarity

Cosine Similarityは、

**Vector同士の向きがどれくらい近いか**

を見る方法です。

日本語ではコサイン類似度と呼ばれます。

文章の意味比較でよく利用されます。

イメージとしては、

同じ方向  
→ 意味が近い

違う方向  
→ 意味が遠い

と考えます。

---

## 8. Dot Product

Dot Productは内積です。

2つのVectorを計算して類似度を求めます。

Embeddingモデルによっては、

Cosine SimilarityよりDot Productを使うことを前提としている場合があります。

どの計算方法を利用するかは、

Embeddingモデルと検索サービスの仕様

を確認します。

---

## 9. Euclidean Distance

Euclidean Distanceは、

Vector同士の距離

を計算します。

日本語ではユークリッド距離と呼ばれます。

距離が小さいほど、

似ている

と判断します。

Cosine Similarityなどとは、

「値が大きいほど近い」

「値が小さいほど近い」

のようにScoreの意味が異なる場合があります。

---

## 10. Nearest Neighbor Search

Vector Searchは、

質問Vectorに最も近いVectorを探す処理

とも言えます。

この考え方を、

Nearest Neighbor Search

と呼びます。

日本語では、

最近傍探索

と呼ばれます。

例えば、

Question Vector

に最も近い5つのChunk Vectorを取得します。

---

## 11. Top K

Vector Searchでは、

「上位何件取得するか」

を指定します。

これをTop Kと呼びます。

例えば、

Top K = 5

なら、

質問Vectorに近いChunkを5件取得します。

Top KはRAGの検索品質に大きく影響します。

---

## 12. Top Kが小さすぎる場合

Top K = 1

などにすると、

最も近いChunkだけ取得します。

処理量は少なくなりますが、

正解が2位や3位だった場合に取得できません。

また、

複数のChunkを組み合わせないと回答できない質問

にも弱くなります。

---

## 13. Top Kが大きすぎる場合

Top K = 50

など大量に取得すると、

正解を含みやすくなる一方、

- 関係ない情報が増える
    
- Reranking処理が増える
    
- LLMへのToken量が増える
    
- 回答が混乱する
    

可能性があります。

そのため、Top Kは検索評価をしながら調整します。

---

## 14. Similarity Score

検索結果にはSimilarity Scoreが返されることがあります。

例えば、

Chunk A  
0.92

Chunk B  
0.84

Chunk C  
0.63

などです。

Scoreを使うことで、

どのChunkが質問に近かったか

を確認できます。

ただし、

「0.8以上なら正解」

のような絶対基準ではありません。

モデルや検索方式によってScoreの意味は変わります。

---

## 15. Similarity Threshold

一定以上のScoreを持つChunkだけを使う方法があります。

例えば、

Similarity >= 0.75

のみ採用する、といった形です。

これをSimilarity Thresholdと考えます。

関連性が低い文書をLLMへ渡さないために利用できます。

---

## 16. Thresholdの注意点

Thresholdを高くしすぎると、

本当は必要なChunkまで除外される

可能性があります。

逆に低すぎると、

関係ないChunkまで大量に取得されます。

そのため、

Thresholdも実際の質問データを使って評価します。

---

## 17. Exact Search

最も単純なVector Searchは、

質問VectorとすべてのVectorを比較する方法です。

これをExact Searchと考えます。

例えば、

1万件のVector

なら、

1万件すべてと比較します。

正確ですが、Vector数が増えると処理量が大きくなります。

---

## 18. Approximate Nearest Neighbor

大量のVectorから高速に検索するため、

Approximate Nearest Neighbor

略してANN

が利用されます。

日本語では近似最近傍探索と呼ばれます。

完全にすべてのVectorを比較するのではなく、

**近そうな候補を効率よく探す**

方式です。

大規模なVector Searchではよく使われます。

---

## 19. ANNを使う理由

例えば、

100件のVector

ならすべて比較しても問題ありません。

しかし、

100万件  
1000万件

と増えると、毎回全件比較するのは重くなります。

ANNを利用すると、

検索精度をある程度維持しながら高速化

できます。

---

## 20. HNSW

ANNの代表的なアルゴリズムとして、

HNSW

があります。

Hierarchical Navigable Small World

の略です。

Vector同士の近さをグラフ構造として管理し、

近いVectorへ移動しながら候補を探します。

Vector DBや検索サービスでよく使われる方式です。

---

## 21. IVF

IVFもVector Searchで使われる方式です。

Inverted File Index

の略です。

Vectorをあらかじめ複数のグループへ分類し、

質問Vectorに近いグループだけを検索します。

すべてのVectorを検索しなくてよいため高速化できます。

---

## 22. Vector Index

大量のVectorを効率よく検索するために、

Vector Index

を作成します。

通常のデータベースでIndexを作るのと同じように、

Vector Searchでも検索用のIndexを作ります。

例えば、

- HNSW
    
- IVF
    

などの方式があります。

---

## 23. Vector DBとは

Vectorを保存・検索できるデータベースや検索サービスを、

Vector DB

と呼ぶことがあります。

代表例として、

- Azure AI Search
    
- Elasticsearch
    
- OpenSearch
    
- Pinecone
    
- Weaviate
    
- Milvus
    
- Qdrant
    
- PostgreSQL + pgvector
    

などがあります。

必ず専用Vector DBを使う必要はありません。

既存の検索サービスやDBがVector Searchへ対応している場合もあります。

---

## 24. Vector SearchとMetadata

Vector Searchだけで検索対象を決めるのではなく、

Metadata Filter

と組み合わせることがあります。

例えば、

department = "総務部"

という条件を付けてからVector Searchします。

これによって、

「総務部の文書の中から意味が近いChunkを探す」

といった検索ができます。

---

## 25. 権限制御との組み合わせ

社内RAGでは特に重要です。

例えば、

ユーザーA  
→ 人事文書を閲覧可能

ユーザーB  
→ 人事文書を閲覧不可

の場合、

Vector Search前後でアクセス権のFilterを適用します。

つまり、

質問  
→ 権限Filter  
→ Vector Search

という流れです。

Vector的には似ている文書でも、

閲覧権限がなければ検索結果に含めない

ようにします。

---

## 26. Keyword Searchとの違い

Keyword Searchは、

文字そのもの

を検索します。

例えば、

「ERR-50001」

というエラーコードを検索する場合には強いです。

一方Vector Searchは、

意味

を検索します。

例えば、

「ログインできない」

という質問から、

「認証に失敗する場合の対応方法」

を見つけることができます。

---

## 27. Vector Searchが苦手なもの

Vector Searchは万能ではありません。

特に、

- 型番
    
- エラーコード
    
- IPアドレス
    
- 人名
    
- 製品名
    
- ID
    
- バージョン番号
    

など、

完全一致が重要な情報

ではKeyword Searchのほうが適している場合があります。

---

## 28. Hybrid Search

そのためRAGでは、

Keyword Search  
＋  
Vector Search

を組み合わせることがあります。

これをHybrid Searchと呼びます。

例えば、

質問：

「ERR-50001が出てログインできません」

の場合、

ERR-50001  
→ Keyword Search

ログインできない  
→ Vector Search

という両方の特徴を使えます。

---

## 29. Search Scoreの統合

Hybrid Searchでは、

Keyword SearchのScore

と

Vector SearchのScore

を組み合わせて順位を決めます。

検索サービスによって、

- Weighted Score
    
- Reciprocal Rank Fusion
    
- 独自ランキング
    

などの方式があります。

単純にVector Scoreだけを見るわけではありません。

---

## 30. Reciprocal Rank Fusion

複数の検索結果ランキングを統合する方式の1つです。

略してRRFと呼ばれます。

例えば、

Keyword Searchで1位

Vector Searchで3位

の文書を総合的に高く評価する

といった使い方ができます。

Hybrid Searchで利用されることがあります。

---

## 31. Vector SearchとReranking

Vector Searchは、

「候補を取得する処理」

として使うことがあります。

例えば、

Vector Search  
→ Top 30取得

Reranker  
→ Top 5へ絞る

LLM  
→ Top 5だけ利用

という流れです。

Vector Search単体ですべてを決めるのではなく、

後段でより精密に評価する

構成です。

---

## 32. Vector SearchとChunk

Vector Searchでは、

基本的にChunk単位

で検索します。

つまり、

文書  
→ Chunk  
→ Embedding  
→ Vector Search

というつながりです。

Chunk設計が悪いと、Vector Searchの精度も下がります。

---

## 33. Chunkが大きすぎる場合

例えば1Chunkに、

- 認証
    
- ネットワーク
    
- バックアップ
    
- パスワード
    

が全部入っている場合、

Embeddingされた意味が曖昧になります。

その結果、

Vector Searchで正しいChunkが上位に来にくくなる可能性があります。

---

## 34. Chunkが小さすぎる場合

例えば、

「30日間保存します。」

だけのChunkでは、

何を30日間保存するのか分かりません。

質問が、

「バックアップの保持期間は？」

でも、このChunkを正しく検索できない可能性があります。

Vector Searchの前提として、

意味が成立するChunk

を作ることが重要です。

---

## 35. 検索対象が増えるとどうなるか

文書が増えると、

Chunk数  
Vector数

も増えます。

例えば、

100文書  
→ 1万Chunk

1万文書  
→ 100万Chunk

になる場合があります。

大量のVectorを扱う場合は、

- Index方式
    
- 検索速度
    
- メモリ
    
- ストレージ
    
- ANN設定
    

なども重要になります。

---

## 36. Query Embedding

Vector Searchでは、質問をEmbeddingしてから検索します。

この処理を、

Query Embedding

と考えます。

つまり、

「パソコンを買いたい」

という文章そのものを検索するのではなく、

その意味を表したVector

を使って検索しています。

---

## 37. 文書側と質問側のモデル

文書側と質問側では、基本的に同じEmbeddingモデルを使用します。

文書  
→ Model A

質問  
→ Model A

とします。

異なるEmbeddingモデルを使うと、

同じVector空間で比較できなくなる

ためです。

---

## 38. Embeddingモデル変更時

Embeddingモデルを変更した場合、

文書側のVectorも作り直す必要があります。

つまり、

新Embedding Model  
→ 全Chunkまたは対象Chunkを再Embedding  
→ Vector Indexを再作成

します。

質問側だけ新モデルへ変更することは基本的にできません。

---

## 39. Query Rewriteとの組み合わせ

質問をそのままEmbeddingするだけでなく、

検索しやすい文章へ書き換える

場合があります。

例えば、

ユーザー：

「それって何日？」

直前の会話：

「バックアップ保存期間について」

なら、

Query Rewrite：

「バックアップの保存期間は何日ですか？」

としてからVector Searchします。

会話型RAGでは重要です。

---

## 40. 複数Queryを使う方法

1つの質問から複数の検索Queryを作る場合もあります。

例えば、

「認証エラーの原因と対処方法を教えて」

を、

Query 1  
「認証エラーの原因」

Query 2  
「認証エラーの対処方法」

に分けて検索します。

複雑な質問で検索漏れを減らす方法の1つです。

---

## 41. Vector Searchの検索漏れ

意味検索だからといって、必ず正しいChunkが取得できるわけではありません。

原因として、

- Embeddingモデル
    
- Chunk設計
    
- Queryの書き方
    
- Top K
    
- ANN設定
    
- 文書自体の不足
    

などがあります。

そのため、検索結果を実際に評価する必要があります。

---

## 42. Recall

検索品質を見るときに重要なのがRecallです。

簡単にいうと、

**本来取得すべき正解Chunkをちゃんと検索できたか**

を見る指標です。

正解Chunkが存在しているのにTop Kへ入らない場合、

Recallに問題があります。

---

## 43. Precision

Precisionは、

検索したChunkの中に、どれだけ必要な情報が含まれているか

を見る考え方です。

例えばTop 10のうち、

9件が関係ない文書

なら、Precisionが低いと考えられます。

RAGでは、

Recallだけ高ければよい

というわけではありません。

---

## 44. RecallとPrecisionのバランス

Top Kを増やすと、

正解を拾いやすくなる

ためRecallは上がりやすくなります。

一方で、

不要なChunkも増える

ためPrecisionが下がることがあります。

そのため、

Top K  
Threshold  
Reranking

などでバランスを調整します。

---

## 45. Vector Searchの評価方法

実際の質問セットを用意して評価します。

例えば、

質問：

「パスワードの変更期限は？」

正解Chunk：

「パスワードは90日ごとに変更します。」

を事前に決めます。

そして、

Top 1に出るか  
Top 3に出るか  
Top 5に出るか

を確認します。

---

## 46. 検索ログ

RAGの改善では検索ログも重要です。

例えば、

- Question
    
- Query Vector生成時間
    
- Top K
    
- 検索結果
    
- Similarity Score
    
- document_id
    
- chunk_id
    
- 検索時間
    

などを記録します。

これにより、

回答ミスが検索原因なのか

を調査できます。

---

## 47. Vector SearchとHallucination

Vector Search自体が文章を生成するわけではありません。

ただし、

間違ったChunkを検索  
→ LLMへ渡す  
→ 間違った回答

という流れがあります。

そのためRAGのHallucination対策では、

LLMだけでなく、

**Vector Searchが正しい根拠を取得できているか**

を確認することが重要です。

---

## 48. 検索結果がない場合

Similarityが低く、

十分に関連する文書がない

と判断する場合があります。

その場合、

無理にLLMへ検索結果を渡す

のではなく、

「関連する情報を確認できませんでした」

と返す設計もあります。

これはHallucination防止にもつながります。

---

## 49. Vector Searchで重要な設定

主に以下を確認します。

### Embedding

- 使用モデル
    
- Dimension
    
- 言語対応
    

### Index

- Vector数
    
- Index方式
    
- Distance Metric
    

### Search

- Top K
    
- Similarity Threshold
    
- Filter
    

### Retrieval

- Chunk Size
    
- Metadata
    
- Reranking
    

これらは独立ではなく、相互に影響します。

---

## 50. Vector Searchでよくある問題

### 関係ない文章が上位に出る

ChunkやEmbeddingを確認します。

### 正解が上位に出ない

Top K、Query、Embeddingモデルなどを確認します。

### 型番を間違える

Keyword SearchとのHybrid Searchを検討します。

### 同じ文書ばかり出る

Overlapや重複Chunkを確認します。

### 検索が遅い

Vector数やANN Index設定を確認します。

---

## 51. RAG全体での位置

RAGでは、

Document  
→ Parse  
→ Chunk  
→ Embedding  
→ Vector Index

までを事前に行います。

質問時は、

Question  
→ Embedding  
→ **Vector Search**  
→ Reranking  
→ Context  
→ Prompt  
→ LLM

となります。

Vector Searchは、

**Embeddingによって作られた意味情報から、質問に近い根拠を探す処理**

です。

---

## 52. 一言で理解する

Vector Searchとは、

**「文章をVectorに変換し、質問Vectorと意味的に近い文章Vectorを探す検索方法」**

です。

Keyword Searchが、

**同じ文字を探す**

仕組みなのに対して、

Vector Searchは、

**意味が近い文章を探す**

仕組みです。

RAGでは、

**Chunk → Embedding → Vector Search → 関連Chunk取得**

という流れで使われます。

ただしVector Searchだけですべてを解決するのではなく、

**Keyword Search・Metadata Filter・Reranking**

などと組み合わせて検索品質を高めることが重要です。
