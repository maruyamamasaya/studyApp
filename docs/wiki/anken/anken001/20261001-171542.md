## 1. Keyword Searchとは

Keyword Search（キーワード検索）は、

**ユーザーが入力した単語や文字列をもとに、文書内の一致・関連度を使って検索する方法**

です。

例えば、

「Windows Server 2025」

と検索すると、

その単語を含む文書やChunkを探します。

RAGではVector Searchだけでなく、Keyword Searchも重要な検索方法です。

特に、

- 製品名
    
- 型番
    
- エラーコード
    
- 人名
    
- 固有名詞
    
- バージョン番号
    

など、文字そのものが重要な情報を探すときに強みがあります。

---

## 2. Keyword Searchの基本イメージ

例えば文書に以下があるとします。

Chunk A  
「Windows Server 2025への移行手順を説明します。」

Chunk B  
「Linuxサーバーのバックアップ方法を説明します。」

Chunk C  
「Windows Server 2019のサポート情報です。」

ユーザーが、

「Windows Server 2025」

と検索した場合、

Chunk A

が強く一致します。

Keyword Searchでは、

**入力された単語が文書にどれだけ含まれているか**

を重要な判断材料にします。

---

## 3. RAGでKeyword Searchを使う理由

Vector Searchは意味検索に強いですが、すべての検索に適しているわけではありません。

例えば、

「ERR-50421」

というエラーコードを探したい場合、

意味の近さより、

**完全に同じ文字列があるか**

のほうが重要です。

同様に、

- KB5030211
    
- Windows Server 2025
    
- SQL Server 2022
    
- ABC-1234
    
- 192.168.1.100
    

のような情報ではKeyword Searchが有効です。

---

## 4. Keyword Searchの処理フロー

基本的な流れは以下です。

文書  
→ テキスト抽出  
→ Chunk  
→ 検索Index作成

質問時は、

ユーザーQuery  
→ Query解析  
→ Keyword Search  
→ 関連Chunk取得

となります。

Vector Searchのように、必ずしもEmbeddingする必要はありません。

---

## 5. 検索Index

大量の文書を毎回最初から全文検索すると処理が重くなります。

そのため、検索しやすいようにIndexを作ります。

例えば、

Windows  
→ Chunk 1, Chunk 5, Chunk 20

Server  
→ Chunk 1, Chunk 7, Chunk 20

のように、

「どの単語がどの文書に存在するか」

を管理します。

これにより高速に検索できます。

---

## 6. Inverted Index

Keyword Searchでよく使われる仕組みが、

Inverted Index

です。

日本語では、

転置インデックス

と呼ばれます。

通常は、

文書  
→ 含まれる単語

と考えます。

転置インデックスでは逆に、

単語  
→ その単語を含む文書

という形で管理します。

例えば、

バックアップ  
→ Document A, Document C

認証  
→ Document B, Document D

となります。

---

## 7. Tokenization

Keyword Searchでは文章を検索可能な単語単位に分割します。

この処理を、

Tokenization

と呼びます。

例えば、

「Windows Serverの設定を変更する」

という文章を、

Windows  
Server  
設定  
変更

などに分けます。

この単位をTokenと呼びます。

---

## 8. 日本語検索の難しさ

英語では空白によって単語が分かれていることが多いですが、日本語では空白がありません。

例えば、

「パスワード変更方法」

という文章があります。

これを、

パスワード  
変更  
方法

と分ける必要があります。

そのため、日本語Keyword Searchでは形態素解析などを利用する場合があります。

---

## 9. 形態素解析

形態素解析は、

文章を意味のある最小単位へ分解する処理

です。

例えば、

「パスワードを変更します」

を、

パスワード  
を  
変更  
します

のように分解します。

日本語検索では重要な処理です。

---

## 10. N-gram

日本語検索ではN-gramという方式も使われます。

例えば、

「パスワード」

を2文字単位で分けると、

パス  
スワ  
ワー  
ード

のようになります。

この方式を、

Bigram

と呼びます。

文字単位で検索できるため、辞書にない単語にも対応しやすい特徴があります。

---

## 11. 形態素解析とN-gramの違い

### 形態素解析

文章の意味を考えて単語へ分割します。

メリット：

- 自然な単語単位
    
- 検索精度を高めやすい
    

デメリット：

- 辞書依存
    
- 新しい専門用語に弱い場合がある
    

### N-gram

一定文字数で機械的に分割します。

メリット：

- 未知語にも対応しやすい
    
- 製品名や固有名詞に強い場合がある
    

デメリット：

- 不要な一致が増えることがある
    

---

## 12. Exact Match

入力文字列と完全に一致するものを探す検索です。

例えば、

「ERR-50001」

に対して、

ERR-50001

だけを一致させます。

エラーコードやIDなどでは非常に重要です。

---

## 13. Partial Match

文字列の一部が一致するものを探します。

例えば、

「Server」

で検索すると、

Windows Server  
SQL Server  
Application Server

などが一致します。

便利ですが、検索範囲が広くなりすぎる場合があります。

---

## 14. Phrase Search

複数の単語を、

「この順番で並んでいる文章」

として検索します。

例えば、

"Windows Server 2025"

をPhraseとして検索します。

単語単位ではなく、フレーズ全体を重視できます。

---

## 15. AND検索

複数キーワードをすべて含む文書を探します。

例えば、

Windows AND Backup

なら、

Windows  
かつ  
Backup

を含む文書を検索します。

条件を厳しくできる検索方法です。

---

## 16. OR検索

複数キーワードのどれかを含む文書を探します。

例えば、

Windows OR Linux

なら、

Windowsを含む文書  
または  
Linuxを含む文書

を検索します。

検索範囲を広げたい場合に利用します。

---

## 17. NOT検索

特定のキーワードを除外します。

例えば、

Server NOT Linux

とすると、

Serverを含むがLinuxを含まない文書

を探します。

---

## 18. Keyword SearchにもRankingがある

Keyword Searchは、

「一致したかどうか」

だけではありません。

複数の文書が一致した場合、

どの文書を上位にするか

を計算します。

そのために検索Scoreを利用します。

---

## 19. TF

TFは、

Term Frequency

の略です。

簡単にいうと、

**ある単語がその文書の中に何回登場するか**

を表します。

例えば、

「バックアップ」

という単語が文書Aに10回登場し、

文書Bに1回だけ登場する場合、

文書Aのほうがバックアップに関係している可能性があります。

---

## 20. IDF

IDFは、

Inverse Document Frequency

の略です。

多くの文書に出てくる単語より、

珍しい単語

を重要視します。

例えば、

「システム」

という単語は多くの文書に登場するため、重要度は低くなりやすいです。

一方、

「ERR-50217」

のような珍しい文字列は重要度が高くなります。

---

## 21. TF-IDF

TFとIDFを組み合わせたものが、

TF-IDF

です。

考え方としては、

**その文書にはよく出てくるが、他の文書にはあまり出てこない単語**

を重要と判断します。

検索エンジンで昔から使われている代表的な考え方です。

---

## 22. BM25

現在のKeyword Searchでは、

BM25

というRanking方式がよく使われます。

BM25は、

- 単語の出現頻度
    
- 文書全体での珍しさ
    
- 文書の長さ
    

などを考慮してScoreを計算します。

ElasticsearchやOpenSearchなど、多くの検索エンジンで利用されています。

---

## 23. BM25のイメージ

例えばユーザーが、

「バックアップ 保存期間」

と検索したとします。

以下の文書がある場合、

文書A  
「バックアップは30日間保存します。」

文書B  
「システムの保存について説明します。」

文書Aのほうが、

バックアップ  
保存

というキーワードに強く一致するため、上位になりやすくなります。

---

## 24. Stop Words

検索では、

「の」  
「は」  
「を」  
「です」

など、

頻繁に登場して検索価値が低い単語

を除外する場合があります。

これらをStop Wordsと呼びます。

ただし、日本語検索では削除しすぎると意味が変わる場合もあるため注意します。

---

## 25. Stemming

英語では、

run  
running  
runs

のような単語を、

run

として扱うことがあります。

この処理をStemmingと呼びます。

表記の違いを吸収し、検索しやすくします。

---

## 26. Lemmatization

Lemmatizationは、単語を辞書的な基本形へ変換する処理です。

例えば、

went  
→ go

のように変換します。

Stemmingより言語的な意味を考慮する方法です。

---

## 27. Synonym

Keyword Searchでは同義語辞書を利用する場合があります。

例えば、

PC  
＝ パソコン

購入  
＝ 買う

として登録します。

すると、

「PC購入」

で検索しても、

「パソコンを買う」

という文書を検索できる可能性があります。

---

## 28. 同義語辞書の課題

同義語を増やせばよいわけではありません。

例えば、

Server  
＝ サーバー  
＝ サーバ

程度なら使いやすいですが、

意味が曖昧な単語を大量に登録すると、

関係ない検索結果が増える

可能性があります。

---

## 29. Fuzzy Search

多少のスペルミスや文字違いを許容する検索方法です。

例えば、

Windows

を、

Windwos

と入力しても近い候補を検索します。

ユーザー入力の誤字に対応できます。

---

## 30. Fuzzy Searchの注意点

Fuzzy Searchを緩くしすぎると、

関係ない単語まで一致

する可能性があります。

特に、

- 型番
    
- ID
    
- エラーコード
    

では、1文字違うだけで別物の場合があります。

そのため、対象によって使い分けます。

---

## 31. Field Search

文書全体ではなく、

特定の項目だけ

を検索する方法があります。

例えば、

title  
heading  
body  
file_name

などです。

「タイトル一致を本文一致より強く評価する」

といった設計もできます。

---

## 32. Field Boost

特定Fieldの一致を強く評価する方法があります。

例えば、

titleに一致  
→ Score × 3

headingに一致  
→ Score × 2

bodyに一致  
→ Score × 1

とします。

重要な項目を上位に出しやすくできます。

---

## 33. Metadata Filter

Keyword SearchにもMetadata Filterを組み合わせられます。

例えば、

department = "情報システム部"

かつ、

Keyword = "バックアップ"

という検索です。

これにより、

情報システム部の資料だけを対象にバックアップを検索

できます。

---

## 34. 権限制御

社内RAGでは、Keyword Searchでも権限制御が必要です。

例えば、

ユーザー  
→ 認証  
→ 閲覧可能DocumentをFilter  
→ Keyword Search

という流れにします。

検索結果を返した後で隠すのではなく、

検索対象から除外する

ことが重要です。

---

## 35. Keyword Searchが得意な情報

Keyword Searchは特に以下に強いです。

- エラーコード
    
- 型番
    
- 製品名
    
- バージョン番号
    
- IPアドレス
    
- 人名
    
- 部署名
    
- 正式名称
    
- 固有名詞
    
- 法令番号
    

文字列そのものが重要な検索で有効です。

---

## 36. Keyword Searchが苦手な情報

例えば、

文書：

「PCを購入するときは所属長の承認が必要です。」

質問：

「新しいパソコンを買う場合は誰の許可が必要？」

の場合、

文書と質問の単語がかなり違います。

Keyword Searchだけでは検索しにくい場合があります。

こうした検索はVector Searchが得意です。

---

## 37. Keyword SearchとVector Searchの違い

|項目|Keyword Search|Vector Search|
|---|---|---|
|基準|文字・単語|意味|
|言い換え|苦手|得意|
|型番|得意|苦手な場合あり|
|エラーコード|得意|苦手|
|自然な質問|条件次第|得意|
|Embedding|不要|必要|
|Exact Match|得意|不向き|
|意味検索|限定的|得意|

どちらが優れているというより、

用途が違う

と考えることが重要です。

---

## 38. Hybrid Search

実際のRAGでは、

Keyword Search  
＋  
Vector Search

を組み合わせることがあります。

これをHybrid Searchと呼びます。

Keyword Searchで、

文字として重要な情報

を拾い、

Vector Searchで、

意味として近い情報

を拾います。

---

## 39. Hybrid Searchの例

ユーザー質問：

「ERR-50001が出てログインできません」

Keyword Searchでは、

ERR-50001

を探します。

Vector Searchでは、

ログインできない  
認証失敗  
サインインエラー

などの意味が近い文章を探します。

両方を組み合わせることで検索精度を高められます。

---

## 40. Keyword SearchとReranking

Keyword Searchで取得した検索結果を、

Reranker

へ渡して再評価することもできます。

例えば、

Keyword Search  
→ Top 30

Reranking  
→ Top 5

LLM  
→ Top 5

という流れです。

---

## 41. Queryの前処理

Keyword Searchでは、ユーザーの質問から検索用キーワードを取り出す場合があります。

例えば、

「Windows Server 2025へ移行するときの注意点を教えて」

から、

Windows Server 2025  
移行  
注意点

などを取得します。

---

## 42. Query Rewrite

検索しやすいQueryへ書き換えることもあります。

例えば、

「それっていつまで？」

という質問だけでは検索できません。

会話履歴から、

「パスワード変更期限」

などのQueryへ変換します。

これはVector SearchだけでなくKeyword Searchでも有効です。

---

## 43. Search Score

Keyword Searchでは、各検索結果にScoreが付くことがあります。

例えば、

Chunk A  
8.5

Chunk B  
5.2

Chunk C  
1.9

などです。

Scoreが高いほど、Queryとの関連性が高いと判断します。

ただし、Scoreの値は検索エンジンによって異なります。

---

## 44. Keyword SearchとChunk

RAGでは文書全体ではなく、

Chunk単位

でKeyword Searchする場合があります。

例えば、

Document  
→ 100 Chunk

に分割し、

その100 Chunkを検索対象にします。

これによって、

文書全体ではなく、必要な部分だけ

を取得できます。

---

## 45. Chunkが小さすぎる場合

Keyword SearchでもChunk設計は重要です。

例えば、

「90日」

だけのChunkでは、

何が90日なのか分かりません。

キーワード一致しても、LLMへ渡したときに文脈不足になります。

---

## 46. Chunkが大きすぎる場合

逆に巨大Chunkでは、

検索キーワードが一度だけ登場しているだけなのに、

大量の不要情報

まで取得する場合があります。

そのため、

Keyword Searchでも適切なChunk Sizeが重要です。

---

## 47. Keyword SearchとHallucination

Keyword Search自体が回答を作るわけではありません。

しかし、

関係ない文書を検索  
→ LLMへ渡す  
→ 誤った回答

ということがあります。

そのため、

検索結果が本当に質問に関係しているか

を評価する必要があります。

---

## 48. 検索結果がない場合

Keyword Searchで一致する結果がない場合、

無理にLLMへ回答させるのではなく、

Vector Searchへ切り替える

方法があります。

例えば、

Keyword Search  
→ 0件

Vector Search  
→ 意味検索

というフォールバックも可能です。

---

## 49. Keyword Searchの評価

検索品質を確認するには、実際の質問を使います。

例えば、

質問：

「ERR-50001の対処方法」

正解Chunk：

「ERR-50001が発生した場合はサービスを再起動します。」

がTop 1、Top 3、Top 5に入るか確認します。

---

## 50. PrecisionとRecall

Keyword Searchでも、

Precision  
Recall

を確認できます。

### Precision

取得した検索結果のうち、どれだけ正しい情報だったか。

### Recall

本来取得すべき正解文書を、どれだけ取りこぼさなかったか。

検索条件を厳しくするとPrecisionは高くなりやすいですが、Recallが下がる場合があります。

---

## 51. Keyword Searchでよくある問題

### 検索結果が出ない

表記ゆれ、同義語、形態素解析などを確認します。

### 関係ない結果が多い

Stop Words、検索条件、Field Boostなどを確認します。

### 日本語の複合語を検索できない

TokenizationやAnalyzerを確認します。

### 型番を完全一致できない

AnalyzerやExact Match用Fieldを確認します。

### 同義語で検索できない

Synonym設定やVector Search併用を検討します。

---

## 52. Analyzer

検索エンジンでは、

文章をどうTokenへ分割・正規化するか

を決める設定をAnalyzerと呼ぶことがあります。

Analyzerには、

- Tokenizer
    
- 小文字化
    
- Stop Word
    
- Synonym
    
- Stemming
    

などの処理を組み合わせます。

Keyword Searchの精度に大きく影響します。

---

## 53. Index作成時と検索時

Keyword Searchでは、

文書登録時の解析方法

と、

Query検索時の解析方法

を合わせることが重要です。

例えば文書側では、

「WindowsServer」

を1Tokenとして保存しているのに、

検索側では、

Windows  
Server

に分割してしまうと、意図した検索にならない場合があります。

---

## 54. RAG全体での位置

RAGでは、

Document  
→ Parse  
→ Clean  
→ Chunk  
→ Search Index

までを事前に準備します。

質問時は、

Question  
→ Query解析  
→ **Keyword Search**  
→ 関連Chunk取得  
→ Reranking  
→ Context  
→ Prompt  
→ LLM

という位置になります。

Vector Searchと並ぶ、

**RAGのRetrievalを担当する重要な検索方式**

です。

---

## 55. 一言で理解する

Keyword Searchとは、

**「入力された文字や単語を手がかりに、関連する文書を探す検索方法」**

です。

特に、

- 固有名詞
    
- 製品名
    
- 型番
    
- エラーコード
    
- ID
    

など、

**文字そのものが重要な検索に強い**

という特徴があります。

一方で、

「PCを買う」

と

「パソコン購入」

のような言い換えは苦手な場合があります。

そのためRAGでは、

**Keyword Search + Vector Search**

を組み合わせるHybrid Searchがよく使われます。
