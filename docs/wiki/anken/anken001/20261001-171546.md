## 1. Metadata Filterとは

Metadata Filterは、

**文書本文の内容ではなく、文書に付いている属性情報を使って検索対象を絞り込む仕組み**

です。

RAGでは、Chunk本文とは別にMetadataを持たせることがあります。

例えば、

- 文書名
    
- 部署
    
- カテゴリ
    
- 作成日
    
- 更新日
    
- ページ番号
    
- 権限
    
- 公開範囲
    

などです。

このMetadataを使って、検索対象を限定します。

---

## 2. 具体例

例えば、文書に以下のMetadataが付いているとします。

document_id  
DOC001

department  
人事部

category  
就業規則

updated_at  
2026-09-01

access_level  
管理職

この場合、

「人事部の文書だけ検索する」

「管理職が閲覧できる文書だけ検索する」

といった絞り込みができます。

---

## 3. なぜMetadata Filterが必要なのか

Vector SearchやKeyword Searchは、

「質問と文書がどれだけ関連しているか」

を探します。

しかし、

**その文書を検索してよいか**

までは判断しません。

例えばVector Searchでは、

質問に非常に近い機密文書

が検索上位になる可能性があります。

そのためMetadata Filterで、

検索対象そのもの

を制限します。

---

## 4. 基本的な流れ

例えば、

ユーザー  
→ 認証  
→ ユーザー情報取得  
→ Metadata Filter作成  
→ Keyword / Vector Search  
→ 検索結果取得

という流れです。

重要なのは、

**検索した後で隠すのではなく、検索時点で対象外にする**

ことです。

---

## 5. 属性による絞り込み

Metadata Filterは、権限だけではなく普通の検索条件にも使えます。

例えば、

department = "情報システム部"

category = "設計書"

year = 2026

のような条件です。

これによって、

「2026年の情報システム部の設計書だけ」

を検索対象にできます。

---

## 6. 権限による絞り込み

社内RAGでは特に重要です。

例えば、

ユーザーA  
→ 全社文書のみ閲覧可能

ユーザーB  
→ 全社文書 + 人事部文書を閲覧可能

の場合、

同じ質問をしても、

検索対象になる文書

が異なります。

---

## 7. よく使うMetadata

代表的には、

- document_id
    
- file_name
    
- department
    
- category
    
- document_type
    
- page_number
    
- created_at
    
- updated_at
    
- version
    
- access_level
    
- user_group
    
- role
    

などがあります。

---

## 8. AND条件

複数条件をすべて満たす文書だけ検索できます。

例えば、

department = "人事部"  
AND  
year = 2026

なら、

人事部かつ2026年の文書

だけを検索します。

---

## 9. OR条件

複数条件のどれかを満たす文書を検索できます。

例えば、

department = "人事部"  
OR  
department = "総務部"

なら、

人事部または総務部の文書

を検索します。

---

## 10. 日付によるFilter

更新日などでも絞り込めます。

例えば、

updated_at >= 2026-01-01

とすれば、

2026年以降に更新された文書

だけを対象にできます。

最新版の資料を優先したい場合などに使えます。

---

## 11. Metadata FilterとVector Search

Vector Searchでは、

質問との意味の近さ

を計算します。

その前後でMetadata Filterを適用し、

対象文書を限定します。

例えば、

人事部文書だけ  
→ Vector Search

とすれば、

人事部の文書の中から意味が近いChunk

を取得できます。

---

## 12. Metadata FilterとKeyword Search

Keyword Searchでも同じように使えます。

例えば、

category = "障害対応"

というFilterを設定して、

ERR-50001

を検索します。

これによって、

障害対応資料の中だけ

を検索できます。

---

## 13. Metadata FilterとHybrid Search

Hybrid SearchでもMetadata Filterを組み合わせます。

例えば、

Permission Filter  
→ Keyword Search  
＋  
Vector Search  
→ Hybrid Ranking

という流れです。

Filterされた対象の中でHybrid Searchします。

---

## 14. Permission Filter

権限制御目的で使うMetadata Filterを、

Permission Filter

や、

Security Filter

のように呼ぶことがあります。

例えば、

allowed_groups に、

- all
    
- sales
    
- manager
    

などを登録します。

ユーザーのGroupと一致する文書だけ検索します。

---

## 15. ACL

文書ごとのアクセス権情報を、

ACL

Access Control List

として持つ場合があります。

例えば、

Document A  
allowed_users = User001, User002

Document B  
allowed_groups = HR, Manager

のように管理します。

検索時にユーザー情報と比較します。

---

## 16. MetadataはEmbeddingしなくてよい場合が多い

例えば、

department = 人事部

という情報をEmbeddingして意味検索する必要はありません。

通常は、

本文  
→ Embedding

属性  
→ Metadata Filter

として分けます。

これによって検索条件を正確に制御できます。

---

## 17. Metadata設計が重要な理由

後から、

「部署で絞り込みたい」

と思っても、department情報を保存していなければFilterできません。

そのため、文書取り込み時に、

どんな検索条件や権限制御が必要か

を考えてMetadataを設計します。

---

## 18. ChunkごとにMetadataを持つ

通常、MetadataはChunkごとに保持します。

例えば、

Chunk 001

document_id = DOC001  
page = 10  
department = 人事部  
access_level = manager

のようにします。

これによって、検索結果単位で条件を判定できます。

---

## 19. Metadata Filterの注意点

Filter条件を厳しくしすぎると、

本来必要な文書まで検索対象外

になることがあります。

例えば、

category = "規程"

だけに限定したことで、

正解が書かれたFAQ

を検索できなくなる場合があります。

そのため、Filter条件も検索品質に影響します。

---

## 20. 権限Filterは緩めてはいけない

検索精度向上のためのFilterは調整できますが、

権限制御のFilter

は別です。

権限がない文書を検索対象に含めると、

情報漏えい

につながります。

そのため、

検索精度よりもセキュリティを優先

します。

---

## 21. 検索後に隠すのは危険

悪い例：

全Documentを検索  
→ 機密Chunkも取得  
→ LLMへ渡す  
→ 最後に画面だけ非表示

この方法では、

LLMがすでに機密情報を読んでいる

可能性があります。

良い考え方は、

認証  
→ Permission Filter  
→ 検索  
→ LLM

です。

---

## 22. Metadata FilterとTop-K

Filterを適用した後にTop-K検索を行います。

例えば、

全体100万Chunk

Permission Filter後  
10万Chunk

Vector Search  
→ Top 10

という流れです。

検索対象を先に絞ることで、不要な結果を減らせます。

---

## 23. Metadata FilterとReranking

基本的には、

Metadata Filter  
→ Retrieval  
→ Reranking

の順です。

Rerankerへ渡す段階でも、

ユーザーが閲覧できるChunkだけ

になっている必要があります。

---

## 24. RAG全体での位置

質問時の流れでは、

Question  
→ 認証  
→ ユーザー属性取得  
→ **Metadata Filter**  
→ Keyword / Vector / Hybrid Search  
→ Reranking  
→ Context  
→ LLM

という位置になります。

---

## 25. 一言で理解する

Metadata Filterとは、

**「検索する前に、文書の属性やユーザー権限を使って検索対象を絞り込む仕組み」**

です。

Keyword SearchやVector Searchが、

「どの文書が質問に近いか」

を判断するのに対して、

Metadata Filterは、

**「そもそも、どの文書を検索してよいか」**

を決めます。

特に社内RAGでは、

**認証 → 権限Filter → 検索**

という順番を覚えておくと分かりやすいです。
