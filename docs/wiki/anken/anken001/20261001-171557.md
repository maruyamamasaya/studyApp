## 1. Timeoutとは

Timeout（タイムアウト）は、

**処理が一定時間以内に終わらなかった場合、その処理を失敗として扱う仕組み**

です。

例えば、

LLM APIを呼び出す  
→ 30秒待つ  
→ 応答が返らない  
→ Timeout Error

という流れです。

---

## 2. なぜTimeoutが必要なのか

外部APIやDBが、

いつまでも応答を返さない

可能性があります。

Timeoutを設定していないと、

処理が長時間止まったままになる

場合があります。

そのため、

「この処理は最大何秒まで待つ」

という上限を決めます。

---

## 3. 基本イメージ

例えば、

Timeout = 30秒

とします。

API呼び出し  
→ 10秒で応答  
→ 正常終了

API呼び出し  
→ 30秒経過  
→ 応答なし  
→ Timeout

となります。

---

## 4. Pythonの簡単な例

HTTP通信では、例えば以下のように指定できます。

```
import requests

response = requests.get(
    "https://example.com/api",
    timeout=30,
)
```

30秒以内に処理できなければ、Timeoutとして扱います。

---

## 5. asyncでのTimeout

非同期処理でもTimeoutを設定できます。

例えば、

```
import asyncio


result = await asyncio.wait_for(
    call_api(),
    timeout=30,
)
```

です。

30秒を超えるとTimeoutになります。

---

## 6. RAGでTimeoutを使う場所

RAGでは例えば、

- OCR API
    
- Embedding API
    
- Search API
    
- Reranking API
    
- LLM API
    
- DBアクセス
    

などに設定します。

外部サービスを呼び出す場所では特に重要です。

---

## 7. TimeoutとRetryの違い

Timeoutは、

**1回の処理を何秒まで待つか**

です。

Retryは、

**失敗した処理を何回やり直すか**

です。

例えば、

Timeout  
= 30秒

Retry  
= 最大3回

という組み合わせです。

---

## 8. TimeoutとExponential Backoff

よくある流れは、

API呼び出し  
→ 30秒でTimeout  
→ 1秒待つ  
→ Retry  
→ また失敗  
→ 2秒待つ  
→ Retry

です。

つまり、

Timeout  
→ 1回の処理を止める基準

Exponential Backoff  
→ 次のRetryまでの待ち時間

です。

---

## 9. Timeoutが短すぎる場合

例えば、

Timeout = 1秒

にすると、

正常なら3秒で返るAPIでも、

毎回Timeout

になってしまいます。

短すぎると、

正常な処理まで失敗扱い

になります。

---

## 10. Timeoutが長すぎる場合

例えば、

Timeout = 5分

にすると、

障害中のAPIを長時間待ち続ける

可能性があります。

その結果、

- ユーザーが待たされる
    
- Serverの接続を長時間使用する
    
- 後続処理が遅れる
    

といった問題が起きます。

---

## 11. APIごとにTimeoutを変える

すべて同じTimeoutにする必要はありません。

例えば、

Search API  
→ 5秒

Embedding API  
→ 20秒

LLM API  
→ 60秒

のように、

処理の性質に合わせて設定できます。

---

## 12. Connect Timeout

HTTP通信では、

Serverへ接続するまでのTimeout

を分けて設定する場合があります。

これを、

Connect Timeout

と呼びます。

例えば、

Serverへ5秒以内に接続できない  
→ Timeout

とします。

---

## 13. Read Timeout

接続後、

Responseが返ってくるまでのTimeout

を、

Read Timeout

と呼びます。

例えば、

接続成功  
→ 30秒待ってもResponseなし  
→ Read Timeout

となります。

---

## 14. Total Timeout

処理全体の時間に上限を設定する場合もあります。

例えば、

RAG全体  
→ 最大60秒

とします。

内部で複数APIを呼んでいても、全体で60秒を超えたら終了します。

---

## 15. RAG全体のTimeout

例えば、

質問受付  
→ Embedding  
→ Search  
→ Reranking  
→ LLM

という処理があります。

各処理にTimeoutがあっても、

合計すると非常に長くなる

可能性があります。

そのため、

各APIのTimeout

と、

RAG全体のTimeout

の両方を考えることがあります。

---

## 16. Timeout後の処理

Timeoutが発生したら、

- Retryする
    
- エラーを返す
    
- 別サービスへ切り替える
    
- 一部処理をスキップする
    

などの対応をします。

何をするかは処理の重要度によって変わります。

---

## 17. Fallback

主処理がTimeoutした場合に、

別の方法へ切り替える

ことがあります。

これをFallbackと呼びます。

例えば、

Reranking API Timeout  
→ Rerankingを諦める  
→ Search結果の上位をそのまま使う

といった設計です。

---

## 18. LLM Timeoutの例

例えば、

LLM API Timeout  
→ Retry 1回  
→ それでもTimeout  
→ ユーザーへエラー返却

という流れにできます。

無限に待ち続けないことが重要です。

---

## 19. Timeoutのログ

Timeoutが発生した場合は、

- どのAPIか
    
- 何秒待ったか
    
- Retry回数
    
- Request ID
    

などをログへ残します。

障害調査に役立ちます。

---

## 20. Timeoutで重要なポイント

Timeoutは、

短ければ良い

わけでも、

長ければ安全

というわけでもありません。

**通常時の応答時間を確認して、少し余裕を持たせた値**

を設定します。

---

## 21. 一言で理解する

Timeoutとは、

**「処理をいつまで待つか決める制限時間」**

です。

RAGでは、

外部APIをいつまでも待ち続けない

ために使います。

覚え方としては、

**Timeout = 1回の処理の待ち時間**

**Retry = 失敗後にやり直す回数**

**Exponential Backoff = Retryまでの待ち時間**

とセットで理解すると分かりやすいです。
