## 1. Key Vaultとは

Azure Key Vaultは、

**API Key・パスワード・証明書・暗号鍵などの秘密情報を安全に保存・管理するAzureサービス**

です。

アプリケーションのソースコードへ秘密情報を直接書かず、

必要なときにKey Vaultから取得する

ために使います。

---

## 2. RAGで使う理由

RAGでは複数の外部サービスへ接続します。

例えば、

- Azure OpenAI
    
- Azure AI Search
    
- Blob Storage
    
- Database
    
- 外部API
    

などです。

これらで、

- API Key
    
- Connection String
    
- Password
    
- Certificate
    

が必要になる場合があります。

こうした情報をKey Vaultで一元管理します。

---

## 3. 悪い例

例えばPythonコードに、

```
AZURE_OPENAI_KEY = "abcd1234..."
```

と直接書くのは避けます。

このコードをGitへCommitすると、

秘密情報がリポジトリへ残る

可能性があります。

---

## 4. Key Vaultを使う場合

イメージとしては、

```
Python App
→ Key Vault
→ Secret取得
→ Azure OpenAIへ接続
```

となります。

秘密情報をコードと分離できます。

---

## 5. Key Vaultで管理できるもの

主に、

- Secrets
    
- Keys
    
- Certificates
    

を管理できます。

それぞれ役割が違います。

---

## 6. Secret

Secretは、

**文字列として扱う秘密情報**

です。

例えば、

- API Key
    
- Password
    
- Connection String
    
- Client Secret
    

などです。

RAGでは最も使う機会が多いものです。

---

## 7. Key

Keyは、

**暗号化や署名などに使う暗号鍵**

です。

例えば、

- RSA Key
    
- EC Key
    

などがあります。

Key Vault内部で暗号処理を行い、

秘密鍵そのものをアプリへ渡さない

構成もできます。

---

## 8. Certificate

Certificateは、

証明書

を管理する機能です。

例えば、

- TLS証明書
    
- Client Certificate
    

などです。

証明書の更新やライフサイクル管理にも利用できます。

---

## 9. SecretとKeyの違い

混同しやすいです。

### Secret

文字列を保存します。

例：

```
API_KEY=xxxx
```

### Key

暗号化や署名処理に利用する暗号鍵です。

つまり、

**Secret = 秘密の値**

**Key = 暗号処理に使う鍵**

と理解すると分かりやすいです。

---

## 10. Key Vaultの基本構成

例えば、

Azure Subscription  
→ Resource Group  
→ Key Vault

という形で作成します。

そのKey Vaultの中に、

```
azure-openai-api-key
search-api-key
database-password
```

などのSecretを保存します。

---

## 11. Secret Name

Secretには名前を付けます。

例えば、

```
azure-openai-api-key
```

です。

アプリは、

「azure-openai-api-keyを取得する」

という形で利用します。

---

## 12. Secret Version

SecretにはVersionを持たせることができます。

例えば、

v1  
→ 古いAPI Key

v2  
→ 新しいAPI Key

のように管理できます。

Key Rotationに便利です。

---

## 13. Key Rotation

API Keyや暗号鍵を定期的に変更することを、

Key Rotation

と呼びます。

例えば、

古いKey  
→ 新しいKey発行  
→ Key Vault更新  
→ アプリ側で新Key使用

という流れです。

---

## 14. なぜRotationするのか

同じ秘密鍵を長期間使い続けると、

漏えいした場合のリスク

が大きくなります。

定期的に変更することで、リスクを減らします。

---

## 15. 認証

アプリケーションがKey Vaultへアクセスする場合、

「誰がSecretを取得しようとしているか」

を確認します。

この認証には、

Microsoft Entra ID

を利用します。

---

## 16. Managed Identity

Azure上のアプリケーションからKey Vaultへアクセスする場合、

Managed Identity

を使うと便利です。

例えば、

App Service  
→ Managed Identity  
→ Key Vault

という構成です。

この場合、

アプリ自身のPasswordやClient Secretを持たずにKey Vaultへアクセスできます。

---

## 17. Managed Identityのメリット

例えばKey Vaultへ接続するために、

Client ID  
Client Secret

を保存すると、

そのClient Secret自体をどこに保存するか

という問題が発生します。

Managed Identityなら、

AzureがIdentityを管理

してくれるため、Secretを減らせます。

---

## 18. RBAC

Key Vaultへのアクセス権は、

RBAC

Role-Based Access Control

で制御できます。

例えば、

アプリA  
→ Secret読み取り可能

ユーザーB  
→ Secret管理可能

ユーザーC  
→ アクセス不可

といった設定ができます。

---

## 19. 最小権限

アプリに必要以上の権限を与えないことが重要です。

例えば、

Secretを読むだけのアプリ

に、

Secret削除権限

まで与える必要はありません。

これを、

Principle of Least Privilege

最小権限の原則

と呼びます。

---

## 20. Access Policy

Key Vaultには、

Access Policy

というアクセス制御方式もあります。

環境や設計によって、

- Azure RBAC
    
- Access Policy
    

を利用します。

新しい設計ではAzure RBACを使う構成がよくあります。

---

## 21. PythonからSecretを取得するイメージ

概念的には、

```
from azure.identity import DefaultAzureCredential
from azure.keyvault.secrets import SecretClient

credential = DefaultAzureCredential()

client = SecretClient(
    vault_url="https://example.vault.azure.net/",
    credential=credential,
)

secret = client.get_secret(
    "azure-openai-api-key"
)

api_key = secret.value
```

のような流れです。

---

## 22. DefaultAzureCredential

DefaultAzureCredentialは、

利用可能なAzure認証方法を順番に試してくれる仕組みです。

例えば、

ローカル開発  
→ Developer Login

Azure本番  
→ Managed Identity

のように環境によって認証方法を切り替えやすくなります。

---

## 23. RAGでの利用例

例えばAzure OpenAIへ接続する場合、

```
RAG API
→ Managed Identity
→ Key Vault
→ Azure OpenAI API Key取得
→ Azure OpenAI呼び出し
```

という構成にできます。

ただし、Azure OpenAI自体へEntra IDで直接認証できる構成なら、

API Keyそのものを使わない

設計も可能です。

---

## 24. Key Vaultを使えば何でも保存してよいわけではない

例えば、

大量の文書本文

をKey Vaultへ保存するものではありません。

Key Vaultは、

**秘密情報や鍵を管理するためのサービス**

です。

文書原本なら、

Blob Storage

などを使います。

---

## 25. Key Vaultに入れるもの

例えば、

- API Key
    
- Database Password
    
- Client Secret
    
- Connection String
    
- Certificate
    
- Encryption Key
    

などです。

---

## 26. Key Vaultに入れないもの

例えば、

- PDF原本
    
- Chunk本文
    
- Embedding Vector
    
- Search Index
    
- 普通の設定値
    

などです。

通常の設定値は、

Configuration

や環境変数で十分な場合があります。

---

## 27. 環境変数との違い

環境変数にもSecretを入れることがあります。

例えば、

```
AZURE_OPENAI_KEY=xxxx
```

です。

ただし、

どこからその環境変数へ値を設定するか

という問題があります。

Key Vaultから起動時に取得する構成もあります。

---

## 28. .envとの違い

ローカル開発では、

.env

を使うことがあります。

例えば、

```
AZURE_OPENAI_KEY=xxxx
```

です。

ただし、

.envはGitへCommitしない

ようにします。

本番ではKey VaultなどのSecret管理サービスを使うほうが安全です。

---

## 29. Loggingの注意

Key Vaultから取得したSecretを、

ログへ出力してはいけません。

悪い例：

```
logger.info(api_key)
```

です。

秘密情報は、

取得しても表示しない

ことが基本です。

---

## 30. Error Messageの注意

例外発生時にも、

Connection String

API Key

Password

などがError Messageへ含まれないよう注意します。

---

## 31. Network制御

Key Vaultへのアクセス経路も制限できます。

例えば、

- Firewall
    
- Private Endpoint
    
- VNet
    

などを利用できます。

重要な企業システムでは、

Public Internetから直接アクセスさせない

構成を検討します。

---

## 32. Private Endpoint

Private Endpointを使うと、

Key VaultをAzureのPrivate Network経由で利用できます。

例えば、

VNet  
→ Private Endpoint  
→ Key Vault

という構成です。

---

## 33. Soft Delete

Key Vaultでは、

誤ってSecretやKeyを削除した場合に備えて、

Soft Delete

を利用できます。

一定期間は復旧可能な状態になります。

---

## 34. Purge Protection

Soft DeleteされたKey VaultやSecretを、

すぐ完全削除できないようにする

機能があります。

これを、

Purge Protection

と呼びます。

重要な鍵を誤って完全削除する事故を防ぎます。

---

## 35. Audit Log

誰が、

- Secretを取得した
    
- Secretを変更した
    
- Keyを利用した
    

などを監査できるようにログを残します。

企業システムでは重要です。

---

## 36. Secret更新時の注意

Secretを更新した場合、

アプリケーションが、

古い値をCacheしている

可能性があります。

そのため、

- 再取得
    
- 再起動
    
- TTL
    

などを考慮します。

---

## 37. Cacheとの関係

毎回Key Vaultへアクセスすると、

通信回数が増えます。

そのためアプリ起動時に取得して、

短時間Cache

する場合があります。

ただし、

Secret Rotation

したときに新しい値へ切り替わるようにします。

---

## 38. Azure OpenAIとの役割分担

例えば、

Azure OpenAI  
→ LLM / Embedding

Azure AI Search  
→ Search

Blob Storage  
→ 文書原本

Key Vault  
→ API KeyやSecret

という役割分担です。

---

## 39. Azure RAG構成での位置

例えば、

User  
→ RAG API

RAG API  
→ Key VaultからSecret取得

→ Blob Storage  
→ Azure AI Search  
→ Azure OpenAI

という構成になります。

Key Vaultは、

RAG処理そのもの

ではなく、

**RAGを安全に動かすための秘密情報管理基盤**

です。

---

## 40. できればSecretを持たない

さらに安全な設計では、

API KeyをKey Vaultへ保存する

よりも、

Managed Identity + Entra ID

によって、

Secret自体を使わない

構成にできる場合があります。

つまり、

Secretを安全に管理する

より、

**そもそもSecretを減らす**

ほうが良い場合があります。

---

## 41. Key Vaultで重要な考え方

特に覚えておきたいのは、

1. Secretをコードへ直書きしない
    
2. Gitへ保存しない
    
3. Managed Identityを使えるなら検討する
    
4. 最小権限にする
    
5. Rotationできる設計にする
    
6. ログへSecretを出さない
    

です。

---

## 42. 一言で理解する

Azure Key Vaultとは、

**「API Key・パスワード・証明書・暗号鍵などの秘密情報を、安全に集中管理するAzureサービス」**

です。

RAGでは、

Azure OpenAI  
Azure AI Search  
Database

などへ接続するためのSecret管理に利用できます。

覚え方としては、

**Blob Storage = 文書を保存**

**Azure AI Search = 文書を検索**

**Azure OpenAI = AIを実行**

**Key Vault = 秘密情報を守る**

とすると分かりやすいです。
