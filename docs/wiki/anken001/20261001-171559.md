# 1. 概要

Queue（キュー）は、処理すべき仕事を一時的にため、Workerが順に取り出す仕組みです。仕事を登録する側と実行する側を時間的に分離できます。[負荷平準化パターン](https://learn.microsoft.com/en-us/azure/architecture/patterns/queue-based-load-leveling)

# 2. 何のために使うか

PDF解析や大量Embeddingなど、長い取り込み処理を質問APIから切り離し、突発的なアップロード量を平準化するために使います。

# 3. 仕組み

Producer（仕事を登録する側）が文書IDなどを送信し、Consumer（処理する側）が取得して実行します。成功時に完了を確定します。可視性タイムアウトやロック期限は、処理中の仕事が再取得されるのを制御します。方式はStorage QueueとService Busなどで異なります。

# 4. 具体例

Te社の想定例で100件のPDFが追加されても、受付APIは処理IDを返し、Workerが許可された並列数で処理します。メッセージ本文には原本のIDと版を入れ、必要以上の文書本文や秘密情報を入れません。

# 5. 実装・設定時のポイント

- 少なくとも一度届く前提で、重複処理へ備えます。
- 仕事ID、版、処理状態と再試行回数を保存します。
- 長時間処理ではロック更新や再取得を考慮します。
- Dead-letter（処理困難なメッセージの隔離）やpoison messageの運用を決めます。

# 6. 注意点

順序保証、重複検出、隔離機能は製品・設定によって違います。Queueがあるだけで「必ず一回だけ実行」にはなりません。滞留が増えると検索索引の更新が遅れるため、最古メッセージの待ち時間も監視します。

# 7. Te社RAG基盤で確認するポイント

利用サービス、送信箇所、Worker入口、完了確定、ロック期限、再配信を確認します。失敗メッセージを誰がどう再処理するか調べます。Queueの権限を送信・受信に分け、質問APIが不要な受信権限を持っていないか確認します。
