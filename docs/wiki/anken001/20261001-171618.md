# 1. 概要

ログは、処理中の出来事や判断を記録した情報です。RAGでは障害の再現だけでなく、どの資料と設定で回答したかを追えることが重要です。すべての本文を保存することとは違います。

# 2. 何のために使うか

問い合わせ調査、性能分析、取り込み失敗、認可拒否、監査に使います。後から処理の流れを説明できる最小限の情報を残します。

# 3. 仕組み

構造化ログは、messageだけでなくrequest_id、stage、duration_ms、statusなどを項目として記録します。Trace IDで処理を結び付けます。索引世代、Prompt版、モデル、出典IDなどを記録すると、同じ質問の回答差を調査しやすくなります。

# 4. 具体例

次のJSONはTe社向けの学習用ログ例です。検索件数と時間を記録し、質問全文、文書本文、トークンは含めません。実装ではloggerへ構造化属性として渡し、JSON化を収集基盤へ任せる構成もあります。

~~~json
{"request_id":"sample-001","stage":"search","duration_ms":320,"hit_count":5,"status":"ok","index_version":"v2"}
~~~

# 5. 実装・設定時のポイント

- 利用者IDは必要性を確認し、仮名化などの方針を決めます。
- DEBUG、INFO、WARNING、ERRORの基準を定義します。
- Retry、Timeout、認可拒否を別のイベントとして残します。
- 保持期間、削除、閲覧権限、サンプリングを設定します。

# 6. 注意点

Access Token、APIキー、SAS付きURLを記録しないようにします。利用者の質問も機密情報になり得ます。例外の文字列へ本文が入る場合があるため、成功ログだけでなくエラーログも点検します。

# 7. Te社RAG基盤で確認するポイント

logger設定、各stageの記録、例外ハンドラー、HTTPデバッグ、Trace連携を確認します。秘密の値をテスト入力にして、ログに残らないか検証します。問い合わせから1要求を追えるか、失敗理由と認可結果が判別できるか調べます。
