## 1. 概要

RAG基盤のログは、

**質問を受けてから回答を返すまでの処理状況を記録し、障害調査・性能分析・検索品質改善に使う情報**

です。

RAGでは処理が多段になっています。

Question  
→ 認証  
→ Search  
→ Reranking  
→ Context作成  
→ LLM  
→ Answer

そのため、

「回答が遅い」

「正しい文書を検索できていない」

「LLM APIが失敗した」

といった問題を切り分けるには、各段階のログが重要です。

---

## 2. ログで確認したいこと

RAG基盤では主に、

- 処理が成功したか
    
- どこで失敗したか
    
- どの処理が遅いか
    
- 何件検索したか
    
- どのChunkが選ばれたか
    
- Retryが発生したか
    
- Tokenをどれだけ使ったか
    

を確認できるようにします。

---

## 3. Request単位で追跡する

1回の質問処理ごとに、

request_id

や、

trace_id

を付けます。

例えば、

```
request_id = req-001
```

です。

このIDを、

- API
    
- Search
    
- Reranking
    
- LLM
    

の各ログへ付けると、

1回のRAG処理を最初から最後まで追跡できます。

---

## 4. API受付ログ

質問APIを受けた時点で、

例えば以下を記録します。

- request_id
    
- endpoint
    
- timestamp
    
- user識別子
    
- HTTP Method
    
- Status Code
    
- 処理時間
    

例えば、

```
request_id=req-001
endpoint=/api/ask
status=200
duration_ms=2400
```

のような情報です。

---

## 5. 認証・認可ログ

認証や認可の結果も重要です。

例えば、

- JWT検証成功 / 失敗
    
- Role
    
- Scope
    
- Group
    
- Permission Denied
    

などです。

ただし、

**Access TokenやJWT全文をログへ残してはいけません。**

---

## 6. Searchログ

検索処理では、

- Query
    
- Search方式
    
- Top-K
    
- Filter
    
- 検索件数
    
- Search Score
    
- 処理時間
    

などを記録します。

例えば、

```
search_type=hybrid
top_k=20
result_count=20
duration_ms=180
```

です。

---

## 7. Keyword SearchとVector Searchを分ける

Hybrid Searchを使う場合、

- Keyword Search時間
    
- Vector Search時間
    
- 統合後件数
    

を分けて記録すると便利です。

例えば、

```
keyword_ms=90
vector_ms=120
hybrid_result_count=30
```

です。

---

## 8. Chunk IDを記録する

検索結果について、

Chunk本文すべて

をログへ出す必要はありません。

代わりに、

- chunk_id
    
- document_id
    
- page_number
    
- score
    

などを記録します。

例えば、

```
chunk_id=DOC001-CH005
document_id=DOC001
page=12
score=0.91
```

です。

---

## 9. Rerankingログ

Rerankingでは、

- Candidate数
    
- Reranking前順位
    
- Reranking後順位
    
- Score
    
- 処理時間
    

を記録すると、検索改善に使えます。

例えば、

```
candidate_count=20
final_count=5
duration_ms=150
```

です。

---

## 10. Contextログ

Contextについては、

全文を保存するより、

- chunk_id
    
- document_id
    
- Context件数
    
- Token数
    

を記録するほうが安全です。

例えば、

```
context_count=5
context_tokens=3200
```

です。

---

## 11. Promptログ

Prompt全文は、

社内文書や機密情報を含む可能性があります。

そのため、

無条件に全文保存するのは避けます。

代わりに、

- prompt_version
    
- prompt_tokens
    
- system_prompt_version
    

などを記録します。

---

## 12. LLMログ

LLM呼び出しでは、

- Model
    
- Deployment
    
- Input Token
    
- Output Token
    
- 処理時間
    
- Status
    
- Retry回数
    

などを記録します。

例えば、

```
model=gpt-deployment
input_tokens=4200
output_tokens=380
duration_ms=1700
retry_count=0
```

です。

---

## 13. Tokenログ

Token数を記録すると、

- コスト分析
    
- Context肥大化
    
- Prompt肥大化
    

を確認できます。

例えば、

Context Tokenが急増

している場合、

Top-KやChunk Sizeを見直す

きっかけになります。

---

## 14. Retryログ

Retryが発生した場合、

- 何回目か
    
- 対象API
    
- Error種別
    
- 待機時間
    

を記録します。

例えば、

```
service=azure_openai
retry=2
wait_seconds=4
error=429
```

です。

---

## 15. Timeoutログ

Timeoutでは、

- 対象処理
    
- Timeout設定値
    
- 実際の待機時間
    

を記録します。

例えば、

```
operation=llm_generation
timeout_seconds=30
result=timeout
```

です。

---

## 16. Circuit Breakerログ

Circuit Breakerを使っている場合、

- Closed
    
- Open
    
- Half-Open
    

の状態変更も記録します。

例えば、

```
service=embedding
circuit_state=open
```

です。

外部サービス障害の把握に役立ちます。

---

## 17. Queueログ

文書取り込みでQueueを使う場合は、

- job_id
    
- queued
    
- processing
    
- completed
    
- failed
    
- retry_count
    

などを記録します。

例えば、

```
job_id=JOB001
document_id=DOC001
status=completed
```

です。

---

## 18. 文書取り込みログ

文書取り込みでは、

- document_id
    
- file_name
    
- page_count
    
- OCR利用有無
    
- Chunk数
    
- Embedding件数
    
- Index登録件数
    
- 成功 / 失敗
    

などを記録します。

これによって、

「どの文書だけ取り込みに失敗したか」

を確認できます。

---

## 19. OCRログ

OCRを使った場合は、

- OCR使用ページ
    
- OCR Engine
    
- Confidence
    
- Error
    
- 処理時間
    

などを記録できます。

特にOCR品質問題の調査に役立ちます。

---

## 20. Embeddingログ

Embeddingでは、

- Chunk数
    
- Model
    
- Token数
    
- Cache Hit / Miss
    
- API呼び出し数
    
- Error
    
- 処理時間
    

などを記録します。

大量文書取り込み時のコスト分析にも使えます。

---

## 21. Cacheログ

Cacheでは、

- Hit
    
- Miss
    
- TTL
    
- Cache Keyの安全な識別子
    

などを記録します。

例えば、

```
cache_type=embedding
result=hit
```

です。

Cache Hit Rateを見ることで効果を確認できます。

---

## 22. エラーログ

Exception発生時は、

- request_id
    
- operation
    
- error_type
    
- error_message
    
- stack trace
    

などを記録します。

ただし、

機密情報がError Messageへ混ざらない

ように注意します。

---

## 23. 何をログに残さないか

特に重要です。

原則として、

- API Key
    
- Password
    
- Client Secret
    
- Access Token
    
- JWT全文
    
- 個人情報
    
- 機密文書全文
    

はそのままログへ残しません。

---

## 24. Question全文も注意する

ユーザー質問にも、

機密情報

が含まれる可能性があります。

そのため、

全文保存するのか  
マスキングするのか  
Hash化するのか

を要件として決めます。

---

## 25. Answer全文も注意する

LLM回答にも、

機密情報が含まれる可能性があります。

そのため、

品質評価目的で保存する場合でも、

- 保存期間
    
- アクセス権
    
- マスキング
    

を考えます。

---

## 26. Structured Logging

ログを単なる文章ではなく、

構造化データ

として記録すると分析しやすくなります。

例えば、

```
{
  "request_id": "req-001",
  "operation": "search",
  "duration_ms": 180,
  "result_count": 20
}
```

のようなJSON形式です。

---

## 27. なぜ構造化ログがよいのか

例えば、

duration_ms > 1000

error_type = timeout

のように、

検索・集計しやすくなります。

Log Analyticsなどで特に扱いやすくなります。

---

## 28. Log Level

ログには重要度があります。

代表的には、

- DEBUG
    
- INFO
    
- WARNING
    
- ERROR
    
- CRITICAL
    

です。

---

## 29. INFO

通常処理の記録です。

例えば、

```
Search completed
LLM generation completed
```

などです。

---

## 30. WARNING

処理は継続できるが、

注意が必要な状態

です。

例えば、

- Retry発生
    
- Cache Miss急増
    
- 検索結果0件
    

などです。

---

## 31. ERROR

処理に失敗した場合です。

例えば、

- LLM API失敗
    
- Search失敗
    
- OCR失敗
    

などです。

---

## 32. DEBUG

開発・調査用の詳細ログです。

本番では、

ログ量や機密情報

に注意して利用します。

---

## 33. RAGで重要なMetric

ログから、

- Request数
    
- Success Rate
    
- Error Rate
    
- P95 Latency
    
- Search Latency
    
- LLM Latency
    
- Token数
    
- Retry数
    
- Timeout数
    
- Queue長
    

などを集計できます。

---

## 34. 品質改善にも使える

RAGログは障害調査だけでなく、

検索品質改善

にも使えます。

例えば、

「正解できなかった質問」

について、

- Search結果
    
- Chunk順位
    
- Reranking順位
    
- Context
    

を確認します。

---

## 35. 原因切り分け

例えば回答が間違った場合、

1. 正解文書は存在したか
    
2. Searchで取得できたか
    
3. Rerankingで落ちていないか
    
4. Contextへ入ったか
    
5. LLMがContextどおり回答したか
    

をログから追います。

---

## 36. Application Insightsとの関係

Application Insightsでは、

- Request
    
- Dependency
    
- Exception
    
- Trace
    
- Latency
    

などを観測できます。

RAGアプリの実行状況を確認するのに向いています。

---

## 37. Log Analyticsとの関係

Log Analyticsでは、

集めたログをKQLで、

- 検索
    
- 集計
    
- 分析
    

できます。

つまり、

Application Insights  
→ ログ・Telemetryを集める

Log Analytics  
→ それを調査する

という関係です。

---

## 38. 一言で理解する

RAG基盤のログとは、

**「質問受付から検索・LLM回答まで、どこで何が起きたかを追えるようにする記録」**

です。

特に、

**request_id / trace_id**

を全処理へ付けて、

API  
→ Search  
→ Reranking  
→ LLM

を1本で追えるようにすることが重要です。

そして、

**本文を大量に残すより、ID・Score・時間・Token・Errorを構造化して残す**

と理解すると分かりやすいです。
