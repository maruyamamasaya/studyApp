# 1. 概要

HTTPはWeb上で要求と応答を送るためのプロトコル（通信の取り決め）です。JSONは、オブジェクト、配列、文字列、数値などでデータを表す形式です。通信の仕組みとデータの書式は別の役割です。

# 2. 何のために使うか

質問、検索条件、生成結果をAPI間で渡すために使います。通信が成功したかと、本文が業務上正しいかを別々に判断する必要があります。

# 3. 仕組み

HTTP要求はメソッド、URL、ヘッダー、本文を持ち、応答にはステータスコードがあります。JSONのキーと文字列は二重引用符で囲みます。PythonのNone、True、FalseはJSONではnull、true、falseになります。[JSON仕様](https://www.rfc-editor.org/rfc/rfc8259.html)

# 4. 具体例

次のJSONはTe社向けの学習用質問データです。Pythonの辞書文字列を手作業で送る代わりに、HTTPクライアントのJSON送信機能でこの形式へ変換します。AuthorizationヘッダーにはAccess Tokenを入れますが、本文やログへトークンを残しません。

~~~json
{"question": "出張申請の承認者は誰ですか", "conversation_id": "sample-001"}
~~~

# 5. 実装・設定時のポイント

- Content-Typeをapplication/jsonにします。
- JSONを解析した後に、型、必須項目、長さを検証します。
- 429は要求過多など、5xxはサーバー側障害などの区分として扱い、詳細と再試行可否も確認します。
- Retry-Afterの指示がある場合は待機時間へ反映します。

# 6. 注意点

200でも本文に失敗情報が含まれる設計があります。HTTP成功だけで業務成功と判定してはいけません。HTTPクライアントによって非成功応答が自動で例外になるか異なります。タイムアウトはHTTP応答ではなく、クライアント側例外として発生する場合があります。

# 7. Te社RAG基盤で確認するポイント

送信ヘッダー、JSON変換、ステータス判定、応答パース、エラー本文の読み方を確認します。JSONの未知項目とnullの扱いを設計書と照合します。大容量本文とストリーミングの仕様は通常の一括JSONと分けて確認します。
