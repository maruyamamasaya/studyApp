# 1. 概要

API Roleは、APIの機能を許可するために定義する役割です。Entra IDのApp Roleとして定義し、利用者やアプリへ割り当てる構成があります。ここではAzureリソースのRoleとは区別します。

# 2. 何のために使うか

質問、文書登録、管理など、API操作の許可を分けるために使います。画面の表示制御に加えて、APIのサーバー側で強制します。

# 3. 仕組み

App RoleをAPIのアプリ登録に定義し、対象の利用者・グループ・Service Principalへ割り当てます。対応するTokenではroles Claimへ値が入ります。利用者向けRoleとアプリ向けRoleは、定義上の割り当て対象を確認します。[App Roleの公式説明](https://learn.microsoft.com/en-us/entra/identity-platform/howto-add-app-roles-in-apps)

# 4. 具体例

Te社向けの学習用RoleとしてRag.ReaderとRag.Ingestorを考えます。前者は質問API、後者は取り込みAPIへ許可する設計です。この名称は仮で、実定義はアプリ登録と認可コードから確認します。

# 5. 実装・設定時のポイント

- Roleの表示名とTokenへ入るvalueを区別します。
- Role判定はJWT検証後に行います。
- Endpointごとの必要Roleを対応表にします。
- 委任アクセスとアプリのみのアクセスを意図して許可します。

# 6. 注意点

rolesがあるだけで必要Roleが含まれているとは限りません。ScopeとRoleを無条件のORで判定すると、想定外の呼び出し方を許す場合があります。API Roleがあっても、全社文書を閲覧できるとは限らず、文書ACLの確認が別に必要です。

# 7. Te社RAG基盤で確認するポイント

App Role定義のvalueとallowed member types、実割り当て、roles判定の文字列を照合します。必要Roleがない時の403と、関係のないRoleだけを持つ場合の拒否を確認します。設計書には操作・主体・必要Role・文書条件を分けて記載します。
