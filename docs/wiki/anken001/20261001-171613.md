## 1. API Roleとは

API Roleは、

**ユーザーやアプリケーションの役割に応じて、APIで実行できる操作を制限する仕組み**

です。

例えば、

- Admin
    
- Manager
    
- User
    

のようなRoleを定義し、

Roleごとに使えるAPIを変えます。

---

## 2. 認証との違い

Roleによる制御は、

Authorization  
＝ 認可

です。

その前に、

Authentication  
＝ 認証

が必要です。

つまり、

認証  
→ 誰なのか確認

Role確認  
→ 何をしてよいか確認

という流れです。

---

## 3. 具体例

例えば、文書管理APIがあるとします。

User Role  
→ 文書閲覧のみ

Manager Role  
→ 文書閲覧 + 登録

Admin Role  
→ 文書閲覧 + 登録 + 削除

というように分けます。

---

## 4. APIごとのRole制御

例えば、

GET /documents  
→ User / Manager / Admin

POST /documents  
→ Manager / Admin

DELETE /documents/{id}  
→ Adminのみ

とします。

API側でRoleを確認して、許可・拒否します。

---

## 5. Roleはどこから取得するか

Roleは、

Access Token

のClaimsに含まれる場合があります。

例えばJWT内に、

```
roles = ["Admin"]
```

が入っている場合です。

API側は、

JWT検証  
→ Role取得  
→ API認可

という流れで処理します。

---

## 6. Entra IDとの関係

Microsoft Entra IDでは、

アプリケーションRole

を定義して、ユーザーやService Principalへ割り当てることができます。

例えば、

RAG.User

RAG.Admin

などです。

Access TokenにRole情報が含まれれば、API側で認可に利用できます。

---

## 7. JWTとの関係

API Roleは、JWTのClaimsから取得することがあります。

例えば、

```
{
  "roles": [
    "RAG.Admin"
  ]
}
```

です。

ただし、

JWTのPayloadを読むだけでは不十分です。

必ず、

- Signature
    
- Issuer
    
- Audience
    
- Expiration
    

を検証してからRoleを利用します。

---

## 8. Roleの確認

例えば、

```
if "RAG.Admin" not in roles:
    raise ForbiddenError()
```

のように、

必要Roleを持っているか

を確認します。

---

## 9. 403 Forbidden

認証は成功しているが、

必要なRoleを持っていない場合、

HTTP 403 Forbidden

を返します。

例えば、

User Roleの人がDELETE APIを呼ぶ

場合です。

---

## 10. 401との違い

401 Unauthorizedは、

認証できていない

場合です。

403 Forbiddenは、

認証できているが権限がない

場合です。

この違いは重要です。

---

## 11. Role-Based Access Control

Roleを使ったアクセス制御を、

RBAC

Role-Based Access Control

と呼びます。

例えば、

Admin  
Manager  
User

というRoleに権限をまとめます。

ユーザーごとに細かく設定するより管理しやすくなります。

---

## 12. Roleを使うメリット

Roleを使うと、

- 権限管理を整理しやすい
    
- ユーザーごとの個別設定を減らせる
    
- APIコードを統一しやすい
    
- 監査しやすい
    

というメリットがあります。

---

## 13. Roleを細かくしすぎない

例えば、

- DocumentReadUser
    
- DocumentReadManager
    
- DocumentReadAdmin
    
- DocumentUploadManager
    
- DocumentUploadAdmin
    

のようにRoleを増やしすぎると、

管理が複雑

になります。

Roleは、

組織上の役割

として大きく分けることが多いです。

---

## 14. Scopeとの違い

RoleとScopeは似ていますが役割が違います。

### Role

誰・何の役割か

例：

Admin  
Manager  
User

### Scope

そのTokenで何の操作が許可されているか

例：

documents.read  
documents.write

と考えると分かりやすいです。

---

## 15. RoleとScopeを組み合わせる

例えば、

Role = Admin

かつ、

Scope = documents.write

を持つ場合だけ、

POST /documents

を許可する

という設計もできます。

---

## 16. RoleはAPIだけで使うのか

Roleは、

- API認可
    
- UI表示
    
- 文書アクセス制御
    
- 管理画面アクセス
    

などにも使えます。

ただし、

UIでボタンを隠すだけ

では不十分です。

必ずAPI側でもRoleを確認します。

---

## 17. UI制御とAPI制御

例えば、

Adminだけ削除ボタン表示

にしていても、

API側にRole確認がなければ、

DELETE APIを直接呼ばれる

可能性があります。

そのため、

UI  
→ 利便性のための制御

API  
→ 本当のセキュリティ制御

と考えます。

---

## 18. RAGでのRole利用

RAGでは例えば、

RAG.User  
→ 質問のみ可能

RAG.Editor  
→ 文書登録可能

RAG.Admin  
→ 文書削除・設定変更可能

のように分けられます。

---

## 19. 文書検索のRole制御

Roleを、

Metadata Filter

へ利用することもあります。

例えば、

access_level = "manager"

の文書は、

Manager Role以上だけ検索可能

とします。

---

## 20. Groupとの違い

Groupは、

所属

を表すことが多いです。

例えば、

HR  
Finance  
IT

です。

Roleは、

役割

を表します。

例えば、

User  
Manager  
Admin

です。

RAGでは、

Group  
→ どの部署文書を見られるか

Role  
→ どの操作ができるか

と分けると理解しやすいです。

---

## 21. Role設計の例

例えば、

### RAG.User

- 質問
    
- 検索
    
- 出典閲覧
    

### RAG.Editor

- User権限
    
- 文書登録
    
- 文書更新
    

### RAG.Admin

- Editor権限
    
- 文書削除
    
- 設定変更
    
- 管理API
    

という設計ができます。

---

## 22. 最小権限

ユーザーには、

必要なRoleだけ

を付与します。

例えば、

質問だけする人

にAdmin Roleを付けない

ことが重要です。

これを、

Principle of Least Privilege

最小権限の原則

と呼びます。

---

## 23. Role変更

ユーザーのRoleが変わった場合、

次回Token取得時などに、

新しいRole情報

を反映します。

古いTokenが有効期限内の場合は、

一定時間古いRoleが残る可能性もあります。

---

## 24. RoleとToken有効期限

RoleをJWT内に含める場合、

Token発行後にRoleを変更しても、

既存TokenのClaimsは変わりません。

そのため、

- Token有効期限
    
- 再認証
    
- Token再発行
    

も考慮します。

---

## 25. API Roleのログ

認可エラーが起きた場合、

- user_id
    
- endpoint
    
- required_role
    
- actual_role
    
- result = denied
    

などをログに残すと調査しやすくなります。

ただしJWT全文はログに出さないようにします。

---

## 26. Pythonでのイメージ

概念的には、

```
def require_role(user_roles, required_role):
    if required_role not in user_roles:
        raise PermissionError(
            "Forbidden"
        )
```

のように確認します。

Frameworkでは認可用MiddlewareやDecoratorを使うこともあります。

---

## 27. FastAPIでの考え方

例えば、

```
@app.delete("/documents/{document_id}")
async def delete_document(
    document_id: str,
    user = Depends(require_admin),
):
    ...
```

のように、

Admin確認をDependencyとして分離

できます。

---

## 28. 自前でRole判定を散らさない

各APIに、

```
if role == "admin":
```

を大量に書くと、

権限制御がバラバラ

になります。

そのため、

- Middleware
    
- Dependency
    
- Authorization Service
    

などへ共通化するのが安全です。

---

## 29. Roleだけでは足りない場合

例えば、

Adminなら全部見られる

という単純なルールだけではなく、

- 部署
    
- 文書所有者
    
- Project
    
- Region
    

なども条件になる場合があります。

その場合は、

Role  
＋ Metadata  
＋ ACL

などを組み合わせます。

---

## 30. RAG全体での位置

例えば、

User  
→ Entra ID Login

→ Access Token

→ JWT検証

→ Role取得

→ API Role確認

→ Metadata Filter

→ Azure AI Search

→ Azure OpenAI

という流れです。

---

## 31. 一言で理解する

API Roleとは、

**「ユーザーやアプリの役割に応じて、APIで何をしてよいかを制御する仕組み」**

です。

覚え方としては、

**Authentication = 誰か**

**Role = どんな役割か**

**Authorization = その役割で何をしてよいか**

とすると分かりやすいです。

RAGでは、

**RoleでAPI操作を制御し、GroupやMetadata Filterで文書閲覧範囲を制御する**

と整理すると理解しやすいです。
