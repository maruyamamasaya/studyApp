## 1. 並列処理とは

並列処理は、

**複数の処理を同時に進めることで、全体の処理時間を短縮する考え方**

です。

RAGでは、

- 複数ChunkのEmbedding
    
- Keyword SearchとVector Search
    
- 複数データソースの検索
    
- 複数文書の解析
    

などを同時に処理できる場合があります。

---

## 2. なぜRAGで並列処理するのか

RAGでは外部サービスとの通信が多くあります。

例えば、

Embedding API  
Search API  
Reranking API  
LLM API

などです。

1つずつ順番に実行すると、待ち時間が積み重なります。

独立した処理を同時に進めることで、レスポンスタイムを短縮できます。

---

## 3. 順番に実行する場合

例えば、

Keyword Search  
3秒

Vector Search  
3秒

だった場合、

順番に実行すると、

Keyword Search  
→ 3秒

Vector Search  
→ 3秒

合計約6秒

となります。

---

## 4. 同時に実行する場合

Keyword SearchとVector Searchは独立しているため、

同時に開始できます。

Keyword Search  
＋  
Vector Search

→ 両方完了

それぞれ3秒なら、理論上は約3秒程度で両方の結果を取得できます。

Hybrid Searchではよく使える考え方です。

---

## 5. すべて同時実行できるわけではない

処理同士に依存関係がある場合は、並列化できません。

例えば、

Question  
→ Embedding  
→ Vector Search

では、

質問のEmbedding結果

がないとVector Searchできません。

そのため、

EmbeddingとVector Search

は基本的に順番に実行します。

---

## 6. RAGで並列化しやすい処理

代表例は以下です。

### Hybrid Search

Keyword Search  
＋  
Vector Search

### 複数検索先

社内Wiki  
＋  
PDF Index  
＋  
FAQ DB

### 文書取り込み

Document A  
Document B  
Document C

### Embedding

Chunk A  
Chunk B  
Chunk C

などです。

## 7. async / awaitとの関係

Pythonでは、

async / await

を使って複数のI/O処理を並行して進めることができます。

例えば、

```
keyword_results, vector_results = await asyncio.gather(
    keyword_search(question),
    vector_search(question),
)
```

です。

Keyword SearchとVector Searchを同時に進められます。

---

## 8. 並行処理と並列処理

厳密には少し違います。

### 並行処理

複数の処理を切り替えながら進める方式です。

async / await

は主にこちらです。

### 並列処理

複数CPUやProcessを使って、本当に同時に計算する方式です。

Pythonでは、

multiprocessing

などがあります。

RAGの外部API通信では、並行処理を使うことが多いです。

---

## 9. I/O Bound

RAGでは、

- HTTP API
    
- DB
    
- Search
    
- LLM
    
- Embedding
    

などの待ち時間が多くあります。

このような処理を、

I/O Bound

と呼びます。

I/O Boundではasync / awaitによる同時実行が有効です。

---

## 10. CPU Bound

CPU計算そのものが重い処理を、

CPU Bound

と呼びます。

例えば、

- OCRのローカル画像処理
    
- 大量画像変換
    
- ローカルAI推論
    
- 重い数値計算
    

などです。

この場合はasync / awaitだけでは高速化しにくく、

- multiprocessing
    
- ProcessPool
    
- GPU
    

などを利用することがあります。

---

## 11. 大量Embedding

例えば1000個のChunkをEmbeddingするとします。

1件ずつ実行すると、

Chunk 1  
→ 完了

Chunk 2  
→ 完了

Chunk 3  
→ 完了

となり、時間がかかります。

複数件を同時に処理すると高速化できます。

---

## 12. 何でも一気に実行しない

例えば、

1000 Chunk

を1000件同時にEmbedding APIへ送るのは危険です。

理由は、

- Rate Limit
    
- 接続数上限
    
- メモリ使用量
    
- API負荷
    
- コスト急増
    

などです。

そのため、

**同時実行数を制限する**

ことが重要です。

---

## 13. Concurrency Limit

同時に処理してよい件数を、

Concurrency Limit

と考えます。

例えば、

最大10件まで

とします。

1000件のJobがあっても、

最初の10件だけ実行  
→ 完了したら次の10件

と進めます。

---

## 14. Semaphore

Pythonでは、

asyncio.Semaphore

を使って同時実行数を制限できます。

例えば、

```
import asyncio

semaphore = asyncio.Semaphore(5)
```

とすると、

最大5件まで

に制限できます。

---

## 15. Semaphoreの例

```
async def embed_with_limit(text):
    async with semaphore:
        return await embed(text)
```

複数Chunkを処理しても、

Embedding APIへ同時に送るRequestを最大5件

にできます。

---

## 16. asyncio.gatherとの組み合わせ

例えば、

```
tasks = [
    embed_with_limit(chunk)
    for chunk in chunks
]

vectors = await asyncio.gather(
    *tasks
)
```

とします。

大量のChunkを処理しながら、

Semaphoreで同時実行数を制御

できます。

---

## 17. Batch処理

1件ずつAPIへ送るのではなく、

複数件をまとめて送る

方法もあります。

これをBatch処理と呼びます。

例えば、

100 Chunk

を、

10 Chunk × 10 Batch

として処理します。

APIがBatchに対応している場合は効率化できます。

---

## 18. Batchと並列処理

Batchと並列処理を組み合わせることもできます。

例えば、

1000 Chunk

→ 50 ChunkずつBatch化

→ 最大4Batchを同時処理

とします。

これによって、

Request数

と、

処理時間

のバランスを取れます。

---

## 19. Rate Limitとの関係

外部APIでは、

1分あたりのRequest数

や、

Token数

に上限がある場合があります。

並列数を増やしすぎると、

HTTP 429 Too Many Requests

が発生します。

そのため、

並列処理ではRate Limitを意識します。

---

## 20. Retryとの関係

並列処理中に一部Requestだけ失敗することがあります。

例えば、

10件同時実行

9件成功  
1件失敗

の場合です。

失敗した1件だけRetryするようにすると効率的です。

---

## 21. Exponential Backoffとの関係

Rate Limitなどで失敗した場合、

失敗した処理を、

1秒  
2秒  
4秒

と待ちながらRetryします。

並列処理では、

Concurrency Limit  
＋  
Retry  
＋  
Exponential Backoff

を組み合わせることが多いです。

---

## 22. Timeoutとの関係

並列実行している1つの処理が、

いつまでも終わらない

可能性もあります。

そのため各処理にTimeoutを設定します。

例えば、

最大10件並行  
各Request Timeout = 30秒

という構成です。

---

## 23. Queueとの関係

Queueと並列処理も組み合わせられます。

例えば、

1000件の文書

→ Queue

→ Worker 5台

→ 各Workerが数件ずつ並行処理

という構成です。

Queueは、

仕事量を管理

し、

並列処理は、

実際の処理速度を上げる

役割があります。

---

## 24. Workerとの関係

複数Workerを起動すると、

複数Jobを同時に処理できます。

例えば、

Worker 1  
→ Document A

Worker 2  
→ Document B

Worker 3  
→ Document C

です。

これもRAG文書取り込みを高速化する方法です。

---

## 25. 処理順序に注意する

並列処理では、

開始した順番

と、

終了する順番

が同じとは限りません。

例えば、

A開始  
B開始  
C開始

でも、

B完了  
C完了  
A完了

になる可能性があります。

順番が重要な処理では注意します。

---

## 26. Race Condition

複数処理が同じデータを同時に変更すると、

結果がおかしくなる

場合があります。

これを、

Race Condition

と呼びます。

例えば、

2つのWorkerが同じDocumentを同時更新

すると問題になる可能性があります。

---

## 27. 二重登録に注意

例えば同じChunkを、

Worker A

と、

Worker B

が同時にVector DBへ登録すると、

重複データ

ができる可能性があります。

そのため、

- chunk_id
    
- document_id
    
- Unique制約
    
- Idempotency
    

などで防止します。

---

## 28. Lock

同じデータを同時に変更させたくない場合、

Lock

を使うことがあります。

例えば、

DOC001をWorker Aが更新中  
→ Worker Bは待つ

という制御です。

ただし、Lockを増やしすぎると並列処理のメリットが減ります。

---

## 29. Error Handling

複数処理を同時実行した場合、

1件失敗したら全部失敗させるのか

それとも、

成功したものはそのまま使うのか

を決めます。

例えば文書取り込みでは、

100件中1件失敗  
→ 99件成功として保存  
→ 1件だけRetry

という設計もできます。

---

## 30. Partial Failure

一部だけ失敗する状態を、

Partial Failure

と呼びます。

並列処理ではよく発生します。

そのため、

全成功 / 全失敗

だけではなく、

どの処理が失敗したか

を管理することが重要です。

---

## 31. RAG質問処理の例

例えばHybrid Searchなら、

Question

→ Keyword Search開始

同時に、

→ Query Embedding

→ Vector Search

を進めます。

その後、

Keyword結果  
＋  
Vector結果

→ Hybrid Ranking

→ Reranking

と続けます。

---

## 32. 文書取り込みの例

例えば、

PDF A  
PDF B  
PDF C

をQueueへ登録します。

複数Workerが、

PDF解析  
→ OCR  
→ Chunk  
→ Embedding

を同時に処理します。

ただし、Embedding APIの同時実行数はSemaphoreなどで制御します。

---

## 33. 並列数を増やせば速くなるとは限らない

例えば、

Concurrency = 5

から、

Concurrency = 100

へ増やしても、

必ず20倍速くなるわけではありません。

むしろ、

- Rate Limit
    
- CPU競合
    
- メモリ不足
    
- DB接続不足
    
- API障害
    

によって遅くなる場合があります。

---

## 34. 適切な並列数

適切な並列数は、

- API制限
    
- CPU
    
- メモリ
    
- DB接続数
    
- Network
    
- Worker数
    

によって変わります。

そのため、

5  
10  
20

などで実際に負荷試験しながら調整します。

---

## 35. Monitoring

並列処理では、

- 同時実行数
    
- 処理件数
    
- Error率
    
- 429発生数
    
- CPU
    
- Memory
    
- Queue長
    
- Response Time
    

などを監視します。

これによって適切な並列数を決められます。

---

## 36. RAGで重要な考え方

並列処理の目的は、

**とにかく大量の処理を同時に実行すること**

ではありません。

目的は、

**サービスやシステムの限界を超えない範囲で、待ち時間を減らして処理量を増やすこと**

です。

---

## 37. 一言で理解する

RAGにおける並列処理とは、

**「独立して実行できる複数の処理を同時に進めて、全体を高速化する仕組み」**

です。

ただし、

無制限に同時実行するのではなく、

**Concurrency Limitを設定する**

ことが重要です。

特にRAGでは、

**async / await + Semaphore + Queue + Retry**

を組み合わせて、大量処理や外部APIへのアクセスを制御する

と理解すると分かりやすいです。
