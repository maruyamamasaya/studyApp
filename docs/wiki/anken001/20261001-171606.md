## 1. Application Insightsとは

Application Insightsは、

**Azure上のアプリケーションが正常に動いているかを監視・分析するためのサービス**

です。

例えば、

- APIが遅い
    
- エラーが多い
    
- LLM呼び出しで失敗している
    
- Search処理に時間がかかっている
    

といった問題を確認できます。

RAGでは、

**システムの動きを可視化するための観測基盤**

として使います。

---

## 2. RAGでなぜ必要なのか

RAGは複数の処理を組み合わせています。

例えば、

Question  
→ API  
→ Embedding  
→ Search  
→ Reranking  
→ LLM  
→ Answer

です。

回答が遅い場合、

どこが遅いのか

を確認する必要があります。

Application Insightsを使うと、

各処理の時間やエラーを追いやすくなります。

---

## 3. 主に確認するもの

代表的には、

- Request
    
- Dependency
    
- Exception
    
- Trace
    
- Performance
    
- Availability
    

などを確認します。

---

## 4. Request

ユーザーや他システムから、

アプリへ入ってきたRequest

を記録します。

例えば、

POST /api/ask

について、

- Status Code
    
- 処理時間
    
- 成功 / 失敗
    

などを確認できます。

---

## 5. Dependency

アプリから外部サービスへ行った通信を、

Dependency

として記録できます。

RAGでは例えば、

- Azure OpenAI
    
- Azure AI Search
    
- Blob Storage
    
- Database
    
- 外部API
    

などです。

これによって、

「RAG API自体は正常だが、Azure OpenAI呼び出しが遅い」

といった切り分けができます。

---

## 6. Exception

アプリ内で発生した例外を記録します。

例えば、

- Timeout
    
- JSON解析エラー
    
- Search API失敗
    
- LLM API失敗
    
- Python Exception
    

などです。

どの処理で失敗したかを調査できます。

---

## 7. Trace

アプリが出力したログを記録します。

例えば、

```
RAG request started
Search completed
Reranking completed
LLM request started
```

などです。

処理の流れを追うために使います。

---

## 8. 処理時間を見る

RAGでは特に、

どの処理に時間がかかっているか

を見ることが重要です。

例えば、

API全体  
2.5秒

Embedding  
0.2秒

Search  
0.4秒

Reranking  
0.3秒

LLM  
1.5秒

と分かれば、

LLMが一番時間を使っている

と判断できます。

---

## 9. End-to-End Latency

ユーザーが質問してから回答が返るまでの時間を、

End-to-End Latency

として見ることがあります。

例えば、

Question受付  
→ Answer返却

まで3秒

などです。

RAGでは重要な性能指標です。

---

## 10. Dependency Latency

外部サービスごとの時間も確認します。

例えば、

Azure AI Search  
300ms

Azure OpenAI Embedding  
200ms

Azure OpenAI Generation  
1800ms

です。

どの外部サービスが遅いか分かります。

---

## 11. Error Rate

一定期間のRequestのうち、

どれくらい失敗したか

を確認します。

例えば、

1000 Request中  
20 Request失敗

なら、

Error Rate = 2%

です。

---

## 12. Availability

APIやWebアプリが、

外部から正常に利用できるか

を定期的に確認できます。

例えば、

5分ごとにAPIへアクセス  
→ 正常Responseか確認

といった監視です。

---

## 13. Application Map

Application Insightsでは、

サービス同士のつながり

を確認できる機能があります。

例えば、

RAG API  
→ Azure AI Search  
→ Azure OpenAI  
→ Database

のような依存関係を可視化できます。

どのサービスで問題が発生しているかを把握しやすくなります。

---

## 14. Distributed Tracing

複数サービスをまたぐ処理を、

1つのRequestとして追跡

する考え方です。

例えば、

User Request

→ RAG API  
→ Search API  
→ LLM API

までを同じTraceとして追います。

---

## 15. Trace ID

1回の処理を識別するために、

Trace ID

を使います。

例えば、

```
trace_id = abc123
```

を、

API  
Search  
LLM

の各ログに付けます。

これによって、1回のRAG処理を最初から最後まで追跡できます。

---

## 16. Request IDとの関係

Request IDも、

1回のAPI Requestを識別するために使います。

Application Insightsや分散トレーシングでは、

Trace ID

Span ID

などを使って処理を関連付けます。

---

## 17. Span

1つのTraceの中の、

個別処理

をSpanと呼びます。

例えば、

Trace  
RAG質問処理

の中に、

Span 1  
Embedding

Span 2  
Search

Span 3  
Reranking

Span 4  
LLM

という形で記録します。

---

## 18. OpenTelemetry

Application Insightsは、

OpenTelemetry

と組み合わせて利用できます。

OpenTelemetryは、

- Trace
    
- Metric
    
- Log
    

を標準的な方法で取得するための仕組みです。

PythonアプリのObservabilityでもよく使われます。

---

## 19. Observability

Observabilityは、

**システム内部で何が起きているかを外部から判断できる状態**

のことです。

主に、

- Logs
    
- Metrics
    
- Traces
    

の3つで考えます。

---

## 20. Logs

何が起きたかを記録します。

例えば、

```
Embedding request started
Embedding request completed
```

です。

---

## 21. Metrics

数値として継続的に確認します。

例えば、

- Request数
    
- Error数
    
- Response Time
    
- Token数
    
- Queue長
    

などです。

---

## 22. Traces

1回の処理が、

どのサービスを通って、

どこに時間がかかったか

を追います。

RAGの性能調査では特に重要です。

---

## 23. RAGで記録したい情報

例えば、

- request_id
    
- trace_id
    
- user_idの匿名化値
    
- endpoint
    
- total_latency
    
- embedding_latency
    
- search_latency
    
- reranking_latency
    
- llm_latency
    
- top_k
    
- result_count
    
- status
    
- error_type
    

などがあります。

---

## 24. Token数の監視

LLMを利用する場合、

- Input Token
    
- Output Token
    

を記録すると、

コストや性能を分析しやすくなります。

例えば、

Input Token増加  
→ Contextが大きすぎる

と判断できる場合があります。

---

## 25. Searchの監視

RAGでは検索側も重要です。

例えば、

- Search時間
    
- Top-K
    
- 取得件数
    
- 0件検索
    
- Reranking時間
    

などを記録します。

「回答できない原因が検索側なのか」

を調査しやすくなります。

---

## 26. Retryの監視

Retryが頻繁に発生している場合、

外部サービスが不安定

な可能性があります。

例えば、

LLM Request  
Retry 0.1%

から、

Retry 20%

へ増えた

場合は異常を疑います。

---

## 27. Timeoutの監視

Timeout数も重要です。

例えば、

Azure OpenAI Timeout  
急増

Azure AI Search Timeout  
正常

なら、

生成AI側の問題

と切り分けやすくなります。

---

## 28. Circuit Breakerとの関係

Circuit BreakerがOpenになった回数も、

監視対象

にできます。

例えば、

LLM Circuit Breaker Open

が発生したら、

Alert

を出すこともできます。

---

## 29. Queueとの関係

文書取り込みでQueueを使っている場合、

- Queue長
    
- Worker処理数
    
- Failed Job
    
- DLQ件数
    

なども監視します。

Queueが増え続けている場合、

Workerの処理能力不足

が考えられます。

---

## 30. Alert

一定条件になったら、

通知を出す

ことができます。

例えば、

Error Rate > 5%

Response Time > 10秒

Timeoutが一定数超過

などです。

---

## 31. Dashboard

重要なMetricをまとめて、

Dashboard

として表示できます。

例えば、

- Request数
    
- Error Rate
    
- P95 Latency
    
- LLM Latency
    
- Search Latency
    

を一覧で確認できます。

---

## 32. Averageだけ見ない

Response Timeを見るとき、

平均値

だけでは問題を見逃すことがあります。

例えば、

ほとんど1秒

一部だけ20秒

でも、

平均はそれほど悪く見えない場合があります。

---

## 33. Percentile

そのため、

P50  
P95  
P99

などを見ることがあります。

例えば、

P95 = 5秒

なら、

95%のRequestは5秒以内

という意味です。

性能監視では重要です。

---

## 34. P95

RAG APIでは、

平均応答時間

だけでなく、

P95 Latency

を見ると実際のユーザー体験を把握しやすくなります。

一部だけ極端に遅い処理も発見しやすくなります。

---

## 35. Application Insightsに入れてはいけない情報

ログには注意が必要です。

例えば、

- API Key
    
- Password
    
- Access Token
    
- 個人情報
    
- 機密文書全文
    
- Prompt全文
    

などを無条件に保存しないようにします。

---

## 36. Promptログ

RAGのデバッグではPromptを確認したくなる場合があります。

ただし、

Promptには検索した社内文書

が含まれる可能性があります。

そのため、

全文保存ではなく、

- document_id
    
- chunk_id
    
- Token数
    

だけ残す

などの設計も検討します。

---

## 37. Sampling

すべてのTelemetryを保存すると、

データ量やコスト

が大きくなる場合があります。

そのため、

一部のTelemetryだけ保存する

Sampling

を使うことがあります。

ただしErrorなど重要な情報は残すようにします。

---

## 38. Pythonからの利用イメージ

Pythonでは、

OpenTelemetry SDK

などを使って、

TraceやMetricをApplication Insightsへ送信する構成があります。

概念的には、

```
with tracer.start_as_current_span(
    "rag-search"
):
    results = search()
```

のように処理単位をTraceできます。

---

## 39. RAGでSpanを分ける例

例えば、

```
rag_request

  ├─ embedding
  ├─ keyword_search
  ├─ vector_search
  ├─ reranking
  └─ llm_generation
```

のようにします。

どの処理に時間がかかったか一目で分かります。

---

## 40. Azure Monitorとの関係

Application Insightsは、

Azure Monitor

のApplication Performance Monitoring機能として利用されます。

つまり、

Application Insights  
＝ アプリケーション観測

Azure Monitor  
＝ Azure全体の監視基盤

というイメージです。

---

## 41. RAG全体での位置

例えば、

User  
→ RAG API  
→ Azure AI Search  
→ Azure OpenAI

という処理に対して、

Application Insights

が横から、

- API時間
    
- Search時間
    
- LLM時間
    
- Error
    
- Trace
    

を監視します。

つまり、

**RAG処理そのものを行うのではなく、その動きを観測する**

サービスです。

---

## 42. Azure RAG構成での役割分担

例えば、

Blob Storage  
→ 文書原本

Azure AI Search  
→ 検索

Azure OpenAI  
→ Embedding / 回答生成

Key Vault  
→ Secret管理

Application Insights  
→ アプリ監視・分析

となります。

---

## 43. Application Insightsで特に見たいもの

RAGでは最低限、

- Request成功率
    
- API Response Time
    
- Azure OpenAI Latency
    
- Azure AI Search Latency
    
- Timeout数
    
- Exception数
    
- Retry数
    
- Token数
    

を見るとよいです。

---

## 44. 一言で理解する

Application Insightsとは、

**「アプリが今どう動いていて、どこで遅くなり、どこで失敗しているかを見るためのAzureの観測サービス」**

です。

RAGでは、

**質問 → Search → LLM → Answer**

の各処理について、

時間  
成功 / 失敗  
エラー

を追跡するために使います。

覚え方としては、

**Application Insights = RAGの健康診断・調査用モニター**

くらいで十分です。
