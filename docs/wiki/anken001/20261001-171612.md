## 1. JWT署名鍵とは

JWTでは、

**Tokenが正しい発行元から発行され、途中で改ざんされていないことを確認するために署名**

を使います。

代表的な構成では、

発行側  
→ 秘密鍵で署名

API側  
→ 公開鍵で検証

します。

つまりAPI側は、

**秘密鍵を持たず、公開鍵だけでJWTを検証できます。**

---

## 2. 秘密鍵と公開鍵

### 秘密鍵

Private Key

Token発行側だけが持つ鍵です。

JWTへの署名に使います。

外部へ公開してはいけません。

### 公開鍵

Public Key

JWTの署名を検証するための鍵です。

API側へ公開して問題ありません。

---

## 3. 基本的な流れ

例えばMicrosoft Entra IDがJWTを発行する場合、

Entra ID  
→ 秘密鍵でJWTへ署名

RAG API  
→ Entra IDの公開鍵を取得

→ JWTの署名を検証

という流れです。

---

## 4. なぜAPI側は秘密鍵を持たなくてよいのか

公開鍵暗号方式では、

秘密鍵で作られた署名を、

対応する公開鍵で検証できます。

そのため、

RAG APIがEntra IDの秘密鍵を知る必要はありません。

むしろ秘密鍵は、Token発行側だけが安全に保持するべきです。

---

## 5. kid

JWTのHeaderには、

kid

Key ID

が含まれることがあります。

例えば、

```
{
  "alg": "RS256",
  "kid": "abc123",
  "typ": "JWT"
}
```

です。

kidは、

**どの署名鍵でこのJWTが署名されたかを識別するID**

です。

---

## 6. なぜkidが必要なのか

Identity Providerは、

署名鍵を1本だけ使い続けるとは限りません。

例えば、

Key A  
Key B  
Key C

という複数の公開鍵がある場合があります。

API側はJWTのkidを確認し、

一致する公開鍵

を選んで署名検証します。

---

## 7. JWKS

公開鍵を配布する仕組みとして、

JWKS

JSON Web Key Set

があります。

JWKS Endpointへアクセスすると、

複数の公開鍵情報

をJSON形式で取得できます。

---

## 8. JWKSのイメージ

概念的には、

```
{
  "keys": [
    {
      "kid": "abc123",
      "kty": "RSA",
      "n": "...",
      "e": "AQAB"
    },
    {
      "kid": "def456",
      "kty": "RSA",
      "n": "...",
      "e": "AQAB"
    }
  ]
}
```

のような情報です。

API側では、

JWTのkid

と、

JWKS内のkid

を照合します。

---

## 9. 公開鍵取得の流れ

基本的には、

JWT受信

→ Headerからkid取得

→ JWKS確認

→ kidと一致する公開鍵取得

→ Signature検証

となります。

---

## 10. OpenID Connect Discovery

JWKS Endpointをコードへ直接固定するのではなく、

OpenID ConnectのDiscovery Document

から確認することがあります。

Discovery Documentには、

- Issuer
    
- Authorization Endpoint
    
- Token Endpoint
    
- JWKS URI
    

などが記載されています。

---

## 11. jwks_uri

Discovery Documentの中には、

jwks_uri

があります。

これは、

**公開鍵一覧を取得するURL**

です。

APIや認証ライブラリは、このURLからJWKSを取得します。

---

## 12. なぜ公開鍵を固定しないのか

Identity Providerは、

セキュリティや運用上の理由から、

署名鍵を変更する

ことがあります。

公開鍵をコードへ固定すると、

鍵が更新された瞬間にJWT検証が失敗する

可能性があります。

そのためJWKSから動的に取得する設計が重要です。

---

## 13. Key Rotation

署名鍵を定期的または必要に応じて変更することを、

Key Rotation

と呼びます。

例えば、

旧秘密鍵  
→ 新秘密鍵

へ切り替えます。

それに伴い、

新しい公開鍵

もJWKSへ追加されます。

---

## 14. 鍵更新時の流れ

例えば、

古い鍵  
kid = A

新しい鍵  
kid = B

になった場合です。

新しいJWT Headerには、

```
kid = B
```

が入ります。

API側は、

JWKSからkid = Bの公開鍵を取得し、

新しい鍵でJWTを検証します。

---

## 15. 古い公開鍵がすぐ消えるとは限らない

Key Rotation中は、

古いJWTがまだ有効期限内

の場合があります。

そのためIdentity Provider側では、

旧公開鍵  
＋  
新公開鍵

を一定期間同時に公開することがあります。

これによって移行中のTokenも検証できます。

---

## 16. API側で鍵更新に追従する

API側では、

「kidに対応する公開鍵が見つからない」

場合に、

JWKSを再取得

する設計があります。

例えば、

JWT受信

→ kid = NEW_KEY

→ Cache内に公開鍵なし

→ JWKS再取得

→ NEW_KEY発見

→ Signature検証

という流れです。

---

## 17. 公開鍵Cache

毎回JWKS Endpointへアクセスすると非効率です。

そのため、

取得した公開鍵をCache

することがあります。

例えば、

JWKS取得  
→ メモリCache

次のJWT  
→ Cacheから公開鍵取得

とします。

---

## 18. Cacheしっぱなしにしない

公開鍵は更新される可能性があります。

そのため、

永久Cache

は避けます。

例えば、

- TTLを設定
    
- kidが見つからなければ再取得
    
- 定期的に更新
    

などの方法があります。

---

## 19. JWT署名検証の流れ

全体としては、

1. JWT取得
    
2. Header Decode
    
3. kid取得
    
4. 公開鍵取得
    
5. Signature検証
    
6. Issuer確認
    
7. Audience確認
    
8. Expiration確認
    
9. Role / Scope確認
    

となります。

公開鍵検証だけで終わりではありません。

---

## 20. 公開鍵が正しくてもTokenを許可できるとは限らない

Signatureが正しくても、

- Audienceが違う
    
- Issuerが違う
    
- 有効期限切れ
    
- Scope不足
    
- Role不足
    

なら拒否します。

つまり、

**署名検証 = Tokenの正当性確認**

**認可 = そのTokenで何をしてよいか確認**

です。

---

## 21. RS256の場合

RS256では、

RSA秘密鍵  
→ 署名

RSA公開鍵  
→ 検証

という構成になります。

Entra IDなどのIdentity Providerでよく使われる方式です。

---

## 22. HS256との違い

HS256では、

同じSecret Key

を署名と検証の両方に使います。

一方RS256では、

秘密鍵  
＋  
公開鍵

を分けます。

複数のAPIがTokenを検証する構成では、

公開鍵だけ配布できるRS256のような方式が扱いやすいです。

---

## 23. 秘密鍵をAPIへ配布しない

例えば、

RAG API  
Search API  
Document API

の3つがJWTを検証するとします。

公開鍵方式なら、

3つのAPIへ公開鍵だけ渡せばよい

ため、

秘密鍵を各APIへ配布する必要がありません。

---

## 24. JWTのkidを信用しすぎない

JWT Headerのkidをそのまま、

ファイルパス

URL

SQL

などへ利用してはいけません。

kidは、

信頼済みJWKS内の公開鍵を選択するためだけ

に利用します。

---

## 25. 外部URLから自由に鍵を取得しない

JWTの内容に書かれた任意のURLから、

公開鍵を取得する

ような実装は危険です。

公開鍵の取得元は、

**信頼しているIdentity ProviderのDiscovery / JWKS Endpoint**

に限定します。

---

## 26. 鍵取得失敗時

JWKS Endpointへアクセスできない場合もあります。

そのため、

- Timeout
    
- Retry
    
- Cache
    
- Circuit Breaker
    

などを考慮できます。

Cache済みの有効な公開鍵があれば、

一時的なJWKS障害でもJWT検証を継続できる場合があります。

---

## 27. Pythonでのイメージ

実際には認証ライブラリを使うことが一般的です。

概念的には、

```
kid = get_kid(token)

public_key = jwks_client.get_key(
    kid
)

claims = verify_jwt(
    token,
    public_key,
)
```

という流れです。

---

## 28. 自前実装しすぎない

JWTの署名検証には、

- アルゴリズム確認
    
- kid
    
- JWKS
    
- Cache
    
- Key Rotation
    
- Issuer
    
- Audience
    
- Expiration
    

など多くの注意点があります。

そのため、

信頼できるJWT / OAuth / OIDCライブラリ

を利用することが重要です。

---

## 29. Entra IDでのイメージ

例えば、

User  
→ Entra ID Login

→ Access Token取得

→ RAG API

RAG API  
→ JWT Headerのkid確認

→ Entra IDのJWKSから公開鍵取得

→ Signature検証

→ Claims確認

→ Metadata Filter

→ Azure AI Search

という流れです。

---

## 30. Key Vaultとの違い

少し混同しやすいです。

### JWT署名鍵

Identity ProviderがJWT署名・検証に使う鍵。

### Key Vault

アプリケーションのSecretや暗号鍵などを管理するサービス。

Entra IDが使うJWT署名秘密鍵を、

RAG APIがKey Vaultから取得して検証する

という考え方ではありません。

RAG APIは通常、

公開されたJWKSから公開鍵を取得

して検証します。

---

## 31. JWT署名鍵で重要な考え方

特に覚えておきたいのは、

- JWTは秘密鍵で署名される
    
- APIは公開鍵で検証する
    
- kidで使用された鍵を識別する
    
- JWKSから公開鍵を取得する
    
- 公開鍵はCacheする
    
- Key Rotationに追従する
    
- 署名だけでなくIssuerやAudienceも確認する
    

です。

---

## 32. 一言で理解する

JWT署名鍵とは、

**「JWTが正しい発行元から発行され、改ざんされていないことを確認するための鍵」**

です。

基本構成は、

**発行側 = 秘密鍵で署名**

**API側 = 公開鍵で検証**

です。

そして実運用では、

**JWTのkid → JWKSから公開鍵取得 → 署名検証**

という流れになります。

鍵が更新された場合も、

JWKSを再取得することで、

新しい公開鍵へ追従します。

覚え方としては、

**kid = どの鍵か**

**JWKS = 公開鍵一覧**

**Key Rotation = 鍵の更新**

で十分です。
