## 1. Cacheとは

Cache（キャッシュ）は、

**一度計算・取得した結果を保存しておき、同じ処理が必要になったときに再利用する仕組み**

です。

例えば、

同じ質問  
→ 毎回Embedding APIを呼ぶ

のではなく、

一度作ったEmbedding結果を保存  
→ 次回は保存済み結果を利用

できます。

これによって、

- 処理速度向上
    
- API呼び出し削減
    
- コスト削減
    
- 外部サービス負荷軽減
    

につながります。

---

## 2. RAGでCacheを使う場所

RAGでは、例えば以下をCacheできます。

- Embedding結果
    
- 検索結果
    
- Reranking結果
    
- LLM回答
    
- 文書解析結果
    
- OCR結果
    
- Promptの固定部分
    

ただし、すべてを同じようにCacheしてよいわけではありません。

---

## 3. Embedding Cache

同じ文章を何度もEmbeddingする必要はありません。

例えば、

Chunk:

「バックアップは30日保存します。」

を一度Embeddingしたら、

```
文章
→ Hash作成
→ Cache確認
→ あればVector再利用
→ なければEmbedding API
```

という流れにできます。

---

## 4. Hashを使う

文章そのものをCache Keyにすると長くなるため、

Hash

を使うことがあります。

例えば、

```
chunk_text
→ SHA-256
→ abc123...
```

という形です。

同じ文章なら同じHashになります。

そのHashを使ってCacheを検索します。

---

## 5. EmbeddingモデルもKeyに含める

文章が同じでも、

Embeddingモデルが違えばVectorも違います。

そのためCache Keyには、

- text_hash
    
- embedding_model
    
- model_version
    

などを含めると安全です。

例えば、

```
embedding:model-v2:abc123
```

のようにします。

---

## 6. OCR Cache

同じPDFを何度もOCRすると、

- 時間
    
- API料金
    

が無駄になります。

そのため、

PDF Hash  
＋  
ページ番号

などをKeyにしてOCR結果をCacheできます。

---

## 7. 検索結果Cache

同じ質問が頻繁に来る場合、

検索結果をCacheすることもできます。

例えば、

「パスワード変更期限は？」

という質問の検索結果を保存します。

次回同じ質問が来たときに、

Search処理を省略できます。

---

## 8. 検索Cacheの注意点

検索結果は、

文書更新

によって古くなる可能性があります。

例えば、

旧規程  
「90日」

新規程  
「60日」

に変わったのに、

古い検索結果Cache

を使うと問題です。

そのため、

TTL

や、

Index Version

を使ってCacheを無効化します。

---

## 9. TTL

TTLは、

Time To Live

の略です。

Cacheを何秒・何分・何時間使ってよいか

を決めます。

例えば、

TTL = 300秒

なら、

5分経過後にCacheを無効化します。

---

## 10. Cache Invalidation

Cacheを削除・更新する処理を、

Cache Invalidation

と呼びます。

例えば、

文書更新  
→ Search Index更新  
→ 関連Cache削除

という流れです。

Cacheでは、

**いつ無効化するか**

が非常に重要です。

---

## 11. LLM回答Cache

同じ質問に対する回答をCacheすることもできます。

例えば、

Question  
→ 検索  
→ LLM  
→ Answer

という処理を一度行い、

結果を保存します。

次回は、

Cache  
→ Answer

と返せます。

---

## 12. LLM回答Cacheの注意点

LLM回答Cacheは特に注意が必要です。

なぜなら、

- 文書が更新される
    
- ユーザー権限が違う
    
- 会話履歴が違う
    
- Prompt Versionが違う
    

可能性があるためです。

単純に、

「質問文が同じ」

だけで再利用するのは危険です。

---

## 13. 権限とCache

社内RAGでは重要です。

例えば、

User A  
→ 人事文書を閲覧可能

User B  
→ 人事文書を閲覧不可

なのに、

User Aの検索結果や回答Cache

をUser Bへ返してはいけません。

そのためCache Keyに、

- user_id
    
- role
    
- group
    
- permission_scope
    

などを含める場合があります。

---

## 14. 権限Cacheで重要な考え方

Cacheによって、

本来見えない情報が別ユーザーへ漏れる

ことは避けなければなりません。

そのため、

**Cacheは性能機能であると同時に、セキュリティ設計でもある**

と考えます。

---

## 15. Prompt Cache

System Promptなど、

毎回ほぼ同じ内容

を使う場合があります。

LLMサービスによっては、

共通Prompt部分をCache

できる機能があります。

これによって、

Tokenコスト

や、

処理時間

を減らせる場合があります。

---

## 16. Cache Hit

必要なデータがCacheに存在することを、

Cache Hit

と呼びます。

例えば、

Embedding取得  
→ Cacheに存在  
→ API呼び出し不要

です。

---

## 17. Cache Miss

Cacheにデータが存在しない場合を、

Cache Miss

と呼びます。

その場合、

通常処理を実行  
→ 結果をCache保存

します。

---

## 18. Cacheの基本フロー

基本的には、

```
Request
→ Cache確認

Cache Hit
→ 保存済み結果を返す

Cache Miss
→ 通常処理
→ Cache保存
→ 結果を返す
```

となります。

---

## 19. Cache Hit Rate

どれくらいCacheが使われたかを、

Cache Hit Rate

として確認することがあります。

例えば、

100 Request中  
70 RequestがCache Hit

なら、

Hit Rate = 70%

です。

Cacheの効果を見る指標になります。

---

## 20. Cacheを使わないほうがよいもの

例えば、

- 常に最新情報が必要
    
- ユーザーごとに内容が大きく違う
    
- 重要な権限制御が複雑
    
- 非常に更新頻度が高い
    

場合は、Cacheを慎重に使います。

---

## 21. Stale Cache

古くなったCacheを、

Stale Cache

と呼ぶことがあります。

例えば、

文書更新後も古い回答Cacheが残っている

状態です。

RAGでは非常に危険です。

---

## 22. VersionをCache Keyに入れる

古いCacheを使わない方法として、

Version

をKeyへ含めることがあります。

例えば、

```
search:index-v3:question-hash
```

とします。

Indexがv4になれば、

v3のCacheは自然に使われなくなります。

---

## 23. Cacheの保存先

Cacheには、

- メモリ
    
- Redis
    
- データベース
    
- ローカルファイル
    

などを使えます。

用途によって選びます。

---

## 24. Memory Cache

アプリケーションのメモリに保存する方法です。

高速ですが、

アプリ再起動で消える

という特徴があります。

小規模な一時Cacheに向いています。

---

## 25. Redis

Cache用途でよく使われる仕組みの1つです。

- 高速
    
- TTL対応
    
- 複数Serverから利用可能
    

という特徴があります。

Web APIやRAGでも利用されることがあります。

---

## 26. Cache Stampede

同じCacheが失効した瞬間に、

大量のRequestが同時に通常処理へ流れる

ことがあります。

これを、

Cache Stampede

と呼びます。

例えば、

人気QueryのCacheが失効  
→ 100 Request同時  
→ 100回LLM API呼び出し

となる場合です。

---

## 27. Cache Stampede対策

例えば、

- Lock
    
- TTLを少しずらす
    
- Stale While Revalidate
    

などがあります。

同じ処理を大量に重複実行しないようにします。

---

## 28. Stale While Revalidate

少し古いCacheを一時的に返しつつ、

裏で新しいCacheを作り直す

考え方があります。

これを、

Stale While Revalidate

と呼びます。

ただし、正確性が重要なRAGでは、使う場面を慎重に選びます。

---

## 29. RAGでCacheしやすいもの

比較的Cacheしやすいのは、

- Embedding
    
- OCR結果
    
- 文書解析結果
    

です。

入力が同じなら結果も大きく変わらないためです。

---

## 30. RAGで慎重にCacheするもの

特に注意が必要なのは、

- Search結果
    
- Reranking結果
    
- LLM回答
    

です。

なぜなら、

- 文書更新
    
- 権限
    
- Prompt変更
    
- 会話履歴
    

などで結果が変わるためです。

---

## 31. RAGでの構成例

例えばEmbeddingでは、

Chunk  
→ Text Hash作成  
→ Cache確認

Hit  
→ Vector再利用

Miss  
→ Embedding API  
→ Cache保存

という流れにできます。

---

## 32. Pythonの簡単なイメージ

概念的には、

```
def get_embedding(text):
    key = create_hash(text)

    cached = cache.get(key)

    if cached is not None:
        return cached

    vector = embed(text)

    cache.set(
        key,
        vector,
    )

    return vector
```

となります。

---

## 33. CacheとRetry

外部APIが不安定な場合、

Cache HitならAPIを呼ばなくてよいため、

Retry自体を減らせる

可能性があります。

つまりCacheは性能だけでなく、

外部API依存度を下げる

効果もあります。

---

## 34. CacheとRate Limit

Embedding APIやLLM APIへの呼び出し回数を減らせるため、

Rate Limit対策

にもなります。

同じ処理を何度もAPIへ送らないことが重要です。

---

## 35. Cacheとコスト

LLMやEmbedding APIは、

Token量やRequest数

で料金が発生する場合があります。

Cacheによって、

同じ処理を再実行しない

ようにするとコスト削減につながります。

---

## 36. Cacheとログ

確認したい情報として、

- Cache Hit / Miss
    
- Key
    
- TTL
    
- Hit Rate
    
- Cache Error
    

などがあります。

ただし、Cache KeyやValueに機密情報をそのまま残さないよう注意します。

---

## 37. 一言で理解する

Cacheとは、

**「一度作った結果を保存して、同じ処理をもう一度やらずに再利用する仕組み」**

です。

RAGでは特に、

**EmbeddingやOCR結果の再利用**

と相性が良いです。

ただし、

**古い情報や別ユーザーの権限情報を再利用しない**

ことが非常に重要です。

覚え方としては、

**Cache = 高速化 + コスト削減 + ただし鮮度と権限に注意**

で十分です。
