> Te社向けの例は学習用の想定です。実際の採用サービス・設定・権限は、既存コードと正式資料で確認してください。

# 1. 概要

RAGの問題は、「回答が間違う」という一つの症状でも、原本、抽出、検索、Context、生成、権限、運用の別々の段階から発生します。症状から原因を決めつけず、処理段階ごとに切り分けます。

# 2. 何のために使うか

既存基盤の課題を、再現条件と根拠付きで整理するために使います。Prompt調整だけで直そうとすると、取り込み漏れや権限不備が残ることがあります。

# 3. 仕組み

まず正しい原本があるか確認し、抽出本文、索引、検索結果、Context、回答を順に比較します。API失敗は認証、認可、通信、容量、アプリ例外へ分類します。ログの要求IDを使って同じ実行を追います。

# 4. 具体例

| 症状 | 主な確認箇所 | 次の検証 |
| --- | --- | --- |
| 正しい資料が出ない | 抽出、版、検索条件 | 正解Chunkが索引にあるか |
| 旧規程で答える | 世代管理、Cache | 更新後の検索と再利用 |
| 番号検索に弱い | Analyzer、Hybrid | 識別子を含む評価質問 |
| 403になる | Role、Scope、Azure RBAC | 呼び出し主体と不足権限 |
| 429が増える | 並列数、容量、Retry | 要求量とToken量 |
| 機密が見える | Filter、引用、Cache | 別部署での拒否テスト |

Te社ではこれを初期仮説として使い、コード・ログ・設定で確定します。

# 5. 実装・設定時のポイント

- 評価質問、利用者、文書版、設定版、日時を固定します。
- 一度に多くの設定を変えず、改善効果を比較します。
- 原因、影響、暫定対応、恒久対応を分けて記録します。
- 解決した問題は再発を検出できるテストへ反映します。

# 6. 注意点

障害を空回答に変換すると、成功しているように見えます。失敗した検索経路だけ無視する場合も、部分成功を明示します。機密情報を含む問題の再現は、許可された環境とデータで行います。

# 7. Te社RAG基盤で確認するポイント

代表質問ごとに期待根拠と実際の候補を保存し、段階別に比較します。認証失敗と根拠不足を別に記録しているか調べます。PoC時の制限や暫定コードが現行で残っているか、履歴と提供HTML資料から確認します。
