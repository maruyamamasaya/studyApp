# 1. 概要

Circuit Breaker（サーキットブレーカー）は、障害が続く依存先への呼び出しを一時的に止める仕組みです。電気のブレーカーのように、失敗の連鎖や資源の浪費を防ぎます。[公式パターン](https://learn.microsoft.com/en-us/azure/architecture/patterns/circuit-breaker)

# 2. 何のために使うか

Azure OpenAIや検索サービスが長く不調なとき、無駄な要求と再試行を抑え、API全体の応答能力を守るために使います。

# 3. 仕組み

Closedでは通常通り呼び出します。一定の失敗条件でOpenへ移り、呼び出しを即座に拒否します。待機後にHalf-Openで少数の試験呼び出しを許し、成功ならClosed、失敗ならOpenへ戻します。Retryは一時失敗の回復、Circuit Breakerは継続障害の封じ込めを担当します。

# 4. 具体例

Te社の想定例で生成サービスの障害が続く場合、質問ごとに長いRetryを重ねず「現在回答生成を利用できません」と返します。検索だけの代替表示を許すなら、通常の生成回答と区別し、許可された根拠だけを表示します。

# 5. 実装・設定時のポイント

- 失敗率の観測期間、最低件数、Open時間を決めます。
- 入力不正や利用者の403を依存先の障害として数えないようにします。
- 接続先やデプロイ単位で状態を分けます。
- 状態遷移をログとメトリクスへ出します。

# 6. 注意点

アプリが複数台あると、各台のブレーカー状態が違う場合があります。共有するか独立するかを設計します。Half-Openで大量の試験呼び出しを許すと、復旧しかけたサービスを再び過負荷にします。

# 7. Te社RAG基盤で確認するポイント

採用ライブラリや独自実装、状態管理の粒度、例外分類、Retryとの呼び出し順を確認します。正常化後に自動復帰する条件と代替応答を調べます。実装がない場合は「未実装」と記録し、存在する前提で詳細設計書を書かないようにします。
