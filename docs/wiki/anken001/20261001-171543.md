## 1. Hybrid Searchとは

Hybrid Search（ハイブリッド検索）は、

**複数の検索方式を組み合わせて、より精度の高い検索結果を取得する方法**

です。

RAGでは特に、

- Keyword Search
    
- Vector Search
    

を組み合わせる方式がよく使われます。


Keyword Searchは、

「文字や単語の一致」

に強く、

Vector Searchは、

「文章の意味の近さ」

に強いという特徴があります。

Hybrid Searchでは、この2つの長所を組み合わせます。

---

## 2. なぜHybrid Searchが必要なのか

Keyword Searchだけでも、Vector Searchだけでも、苦手な検索があります。

例えば、

「ERR-50001が出てログインできません」

という質問を考えます。

この質問には、

ERR-50001

という正確な文字列と、

ログインできない

という意味的な情報の両方が含まれています。

Keyword Searchでは、

ERR-50001

を正確に検索できます。

一方Vector Searchでは、

ログインできない  
認証に失敗する  
サインインできない

のような意味が近い文章を検索できます。

両方を組み合わせることで、より適切な検索結果を取得できます。

---

## 3. Keyword SearchとVector Searchの違い

### Keyword Search

文字列や単語を中心に検索します。

得意なもの：

- 製品名
    
- エラーコード
    
- 型番
    
- 人名
    
- バージョン
    
- 正式名称
    
- 固有名詞
    

### Vector Search

Embeddingによって文章をVector化し、意味の近さで検索します。

得意なもの：

- 自然な質問
    
- 言い換え
    
- 類似表現
    
- 曖昧な表現
    
- 長い質問
    

Hybrid Searchは、

**文字検索と意味検索を同時に利用する**

考え方です。

---

## 4. 基本的な処理フロー

Hybrid Searchの基本的な流れは以下です。

ユーザー質問  
→ Query前処理  
→ Keyword Search  
→ Vector Search  
→ それぞれの検索結果取得  
→ Score統合  
→ Ranking  
→ 必要に応じてReranking  
→ 上位Chunk取得  
→ LLMへ渡す

重要なのは、

Keyword SearchとVector Searchで検索した結果を、そのまま別々に使うのではなく、

**最終的に1つのRankingへ統合する**

ことです。

---

## 5. 具体例

ユーザーが、

「Windows Server 2025への移行でIISが動かない場合の原因は？」

と質問したとします。

### Keyword Search

以下の単語に強く反応します。

- Windows Server 2025
    
- IIS
    
- 移行
    

### Vector Search

以下のような文章も取得できます。

- OS更新後にWebアプリケーションが起動しない
    
- サーバー移行後のWebサービス障害
    
- IIS互換性の確認方法
    

Keyword Searchでは固有名詞を正確に拾い、

Vector Searchでは関連する意味を拾います。

---

## 6. Parallel Search

Hybrid Searchでは、

Keyword Search

と

Vector Search

を並行して実行することがあります。

例えば、

Question

から、

Keyword Search  
→ Top 20

Vector Search  
→ Top 20

を取得します。

その後、

40件の候補

を統合します。

実際には同じChunkが両方に含まれる場合があるため、重複を除去します。

---

## 7. 検索結果の統合

Keyword SearchとVector Searchでは、Scoreの意味が異なります。

例えば、

Keyword Search Score  
= 12.4

Vector Similarity  
= 0.87

だったとしても、

12.4と0.87をそのまま比較することはできません。

そのため、

- Scoreを正規化する
    
- 順位を使う
    
- 重み付けする
    

などの方法で統合します。

---

## 8. Score Normalization

異なる検索方式のScoreを、同じような範囲へ変換する方法です。

例えば、

Keyword Score  
12.4  
→ 0.92

Vector Score  
0.87  
→ 0.87

のように変換します。

その後、

Keyword Score  
＋  
Vector Score

を計算できます。

ただし、Scoreの分布は検索方式によって異なるため、単純な正規化が常に最適とは限りません。

---

## 9. Weighted Score

Keyword SearchとVector Searchに重みを付ける方法があります。

例えば、

Hybrid Score  
= Keyword Score × 0.4

- Vector Score × 0.6
    

のように計算します。

意味検索を重視する場合は、

Vector Searchの重みを大きくする

ことができます。

---

## 10. 重みの決め方

例えば、

業務マニュアルを自然言語で検索する

場合は、

Vector Search重視

にすることがあります。

一方、

エラーコードや型番検索が多い

場合は、

Keyword Search重視

が有効なことがあります。

つまり、固定的に、

Keyword 50%  
Vector 50%

が正しいわけではありません。

実際の検索Queryを使って調整します。

---

## 11. Reciprocal Rank Fusion

Hybrid Searchでよく使われる検索結果統合方法の1つが、

Reciprocal Rank Fusion

です。

略して、

RRF

と呼びます。

RRFでは、検索Scoreそのものではなく、

**検索結果の順位**

を利用します。

---

## 12. RRFの考え方

例えば、

Keyword Search

1位：Document A  
2位：Document B  
3位：Document C

Vector Search

1位：Document B  
2位：Document D  
3位：Document A

だったとします。

Document AとDocument Bは、

両方の検索方式で上位

に出ています。

そのためRRFでは、

Document A  
Document B

を総合的に高く評価できます。

---

## 13. RRFを使うメリット

Keyword SearchとVector SearchではScoreの尺度が違います。

RRFではScoreそのものではなく、

Ranking

を使用するため、

異なる検索Scoreを無理に揃える必要がありません。

そのためHybrid Searchで扱いやすい方法です。

---

## 14. RRFの基本イメージ

RRFでは概念的に、

1 / (k + 順位)

のような形でScoreを計算します。

例えば、

Keyword Searchで1位  
Vector Searchで2位

なら、

両方からScoreを受け取ります。

複数の検索方式で上位になった文書ほど、最終Rankingも上がります。

---

## 15. 重複結果

Keyword SearchとVector Searchの両方から同じChunkが取得されることがあります。

例えば、

Keyword Search：

Chunk A  
Chunk B  
Chunk C

Vector Search：

Chunk A  
Chunk D  
Chunk E

の場合、

Chunk A

が重複します。

通常はChunk IDやDocument IDを使って重複を統合します。

---

## 16. Candidate Retrieval

Hybrid Searchでは、

最終回答に使うChunkを直接決めるのではなく、

最初に候補を多めに集める

ことがあります。

例えば、

Keyword Search  
Top 30

Vector Search  
Top 30

統合  
→ 50候補

Reranking  
→ Top 5

という流れです。

この最初の候補取得を、

Candidate Retrieval

と考えると分かりやすいです。

---

## 17. Hybrid SearchとReranking

Hybrid SearchとRerankingは非常に相性が良いです。

Hybrid Searchで、

幅広く候補を集める

Rerankingで、

質問との関連性を細かく評価する

という役割分担ができます。

流れとしては、

Question  
→ Keyword Search  
＋ Vector Search  
→ Hybrid Ranking  
→ Top 20  
→ Reranking  
→ Top 5  
→ LLM

となります。

---

## 18. Hybrid Searchだけで十分なのか

Hybrid Searchを使っても、

検索順位が完璧になるわけではありません。

例えば、

単語は一致しているが文脈が違う文書

が上位になる場合があります。

そのため、

Reranker

を追加して、質問とChunkの関連性をより詳しく評価する構成があります。

---

## 19. Semantic Rankingとの違い

検索サービスによっては、

Semantic Ranking

という機能があります。

Hybrid Searchで候補を集めた後、

意味的な関連度で再評価

します。

考え方としては、

Hybrid Search  
→ Semantic Ranking  
→ 上位結果

です。

サービスによって名称や実装は異なります。

---

## 20. Metadata Filterとの組み合わせ

Hybrid SearchにもMetadata Filterを組み合わせられます。

例えば、

department = "人事部"

というFilterを設定してから、

Keyword Search  
＋ Vector Search

を実行します。

これによって、

人事部の資料だけ

をHybrid Searchできます。

---

## 21. 権限制御

社内RAGでは重要です。

ユーザーがアクセスできない文書を、

Keyword SearchやVector Searchで取得してはいけません。

そのため、

認証  
→ 権限情報取得  
→ Metadata Filter  
→ Hybrid Search

という流れにします。

検索後に隠すのではなく、

**検索対象そのものから除外する**

ことが重要です。

---

## 22. Query Parsing

Hybrid Searchでは、質問を分析して、

どの部分をKeyword Searchへ使うか

を決めることがあります。

例えば、

「ERR-50001でログインできない」

なら、

Exact Keyword  
ERR-50001

Semantic Query  
ログインできない

のように分けることができます。

---

## 23. Entity Extraction

Queryから、

- 製品名
    
- バージョン
    
- エラーコード
    
- 人名
    
- 日付
    

などを抽出する処理を、

Entity Extraction

と呼ぶことがあります。

例えば、

「Windows Server 2025でERR-50001が発生した」

から、

Product  
= Windows Server

Version  
= 2025

Error Code  
= ERR-50001

を抽出します。

これらをKeyword SearchやFilterへ利用できます。

---

## 24. Query Rewriteとの組み合わせ

ユーザーの質問が検索しにくい場合は、

Query Rewrite

を行います。

例えば、

「それの期限は？」

という質問を、

会話履歴から、

「PC購入申請の提出期限」

へ書き換えます。

そのQueryを使って、

Keyword Search  
＋ Vector Search

を実行します。

---

## 25. Multi Query

1つの質問から複数の検索Queryを生成することもあります。

例えば、

「VPN接続できない原因と対処方法」

を、

Query 1  
VPN接続できない原因

Query 2  
VPN接続の対処方法

に分けます。

それぞれHybrid Searchし、結果を統合します。

複雑な質問で検索漏れを減らせる場合があります。

---

## 26. Hybrid SearchとSynonym

Keyword Search側にSynonym設定を追加できます。

例えば、

PC  
= パソコン

サーバ  
= サーバー

とします。

これにより、

Keyword Search自体も言い換えにある程度対応できます。

そのうえでVector Searchも使うことで、より柔軟な検索になります。

---

## 27. Fuzzy Searchとの組み合わせ

Keyword Search側で、

Fuzzy Search

を使うこともできます。

例えば、

Windwos Server

というスペルミスでも、

Windows Server

を検索できるようにします。

Hybrid Searchでは、

Exact Match  
Fuzzy Search  
Vector Search

など複数の検索方式を組み合わせることもできます。

---

## 28. Phrase Searchとの組み合わせ

正式名称などではPhrase Searchも有効です。

例えば、

"Windows Server 2025"

というフレーズを強く評価します。

そのうえで、

Vector Search

による意味検索も行います。

これによって、

正式名称を含む文書

を優先しながら、関連情報も取得できます。

---

## 29. Field Boost

Keyword Search側では、

タイトルや見出しを強く評価

することがあります。

例えば、

title × 3  
heading × 2  
body × 1

とします。

Hybrid Searchでは、

Keyword RankingにField Boostを適用  
＋  
Vector Search

という構成も可能です。

---

## 30. Vector Search側のTop K

例えば、

Vector Search Top K = 30

とします。

Keyword Search側も、

Top 30

取得します。

その後に統合します。

ただし、Top Kを大きくしすぎると、

- 候補数が増える
    
- Rerankingコストが増える
    
- 検索時間が増える
    

ため調整が必要です。

---

## 31. 検索候補数と最終件数

Hybrid Searchでは、

「候補を何件取るか」

と、

「最終的にLLMへ何件渡すか」

は分けて考えます。

例えば、

Keyword  
Top 30

Vector  
Top 30

統合候補  
50件

Reranking  
Top 5

LLM Context  
5件

という構成です。

---

## 32. SearchとGenerationを分ける

Hybrid Searchは、

回答を生成する技術

ではありません。

あくまで、

**LLMへ渡す根拠を探す技術**

です。

つまり、

Hybrid Search  
→ Retrieval

LLM  
→ Generation

という役割分担です。

---

## 33. Hybrid Searchが向いている質問

例えば、

「Windows Server 2025の移行時に.NET Frameworkで注意することは？」

という質問です。

Keyword Searchでは、

Windows Server 2025  
.NET Framework

を正確に検索できます。

Vector Searchでは、

OSアップグレード時のアプリ互換性

のような関連情報を取得できます。

---

## 34. エラー検索での例

質問：

「ERR-A102でAPI接続に失敗します」

Keyword Search：

ERR-A102

を正確に検索します。

Vector Search：

API接続失敗  
通信エラー  
接続できない

などの意味を検索します。

このようなQueryはHybrid Searchが有効です。

---

## 35. 社内規程検索での例

質問：

「パソコンを買うとき誰の許可が必要？」

文書：

「PC購入申請には所属長の承認を必要とする。」

Keyword Searchでは、

パソコン  
買う

と、

PC  
購入

が一致しない可能性があります。

Vector Searchなら意味的に検索できます。

一方、文書番号や規程名が指定された場合はKeyword Searchも有効です。

---

## 36. Hybrid Searchが万能ではない理由

Hybrid Searchを使えば必ず正解になるわけではありません。

例えば、

- 元文書に正解がない
    
- Chunkが壊れている
    
- OCRが間違っている
    
- Query Rewriteが間違っている
    
- Metadata Filterが間違っている
    

場合は、Hybrid Searchでも正しい情報を取得できません。

検索方式だけでなく、RAG全体を評価する必要があります。

---

## 37. Chunkとの関係

Hybrid Searchも基本的にはChunkを検索します。

Document  
→ Chunk  
→ Keyword Index

と、

Chunk  
→ Embedding  
→ Vector Index

を用意します。

質問時に、

Keyword Index  
＋  
Vector Index

から同じChunk群を検索します。

---

## 38. 同じChunkを両検索に使う

一般的には、

同じChunk本文

を、

Keyword Search用Index

と、

Vector Search用Index

の両方で検索可能にします。

例えば1つのChunkに、

- text
    
- vector
    
- metadata
    

を持たせます。

検索サービスによっては、1つのIndexの中で両方を管理できます。

---

## 39. Hybrid Search用データのイメージ

vector  
[0.12, -0.45, ...]

textはKeyword Search、

## 40. Hybrid Searchと検索速度

Keyword SearchとVector Searchの両方を実行するため、

単独検索より処理量が増える場合があります。

ただし、

- 並列実行
    
- Vector Index
    
- Keyword Index
    
- キャッシュ
    

などを利用して高速化できます。

---

## 41. 並列実行

Keyword SearchとVector Searchは独立しているため、

同時に実行

できる場合があります。

Keyword Search開始  
＋  
Vector Search開始

両方完了  
→ 統合

という方式です。

これによってレスポンスタイムを抑えられます。

## 43. なぜこのChunkが選ばれたか

Hybrid Searchでは検索方式が複数あるため、

「なぜこのChunkが上位になったのか」

が分かりにくくなる場合があります。

そこで、

Keyword Rank = 2  
Vector Rank = 1  
Hybrid Rank = 1

のように記録すると、デバッグしやすくなります。

---

## 44. Hybrid Searchの評価

実際の質問と正解Chunkを用意して評価します。

例えば、

質問：

「Windows Server 2025でIISが起動しない」

正解Chunk：

「Windows Serverアップグレード時のIIS互換性」

について、

Keywordのみ  
Vectorのみ  
Hybrid

を比較します。

---

## 45. 比較評価

Hybrid Searchを導入するときは、

Keyword Searchだけの場合

Vector Searchだけの場合

Hybrid Searchの場合

を比較すると効果が分かりやすいです。

例えば、

Top 5に正解が入った割合

を比較します。

---

## 46. Recall

Recallは、

**本来取るべき正解Chunkを検索できた割合**

です。

Hybrid Searchは候補を広く取得できるため、Recall改善を狙いやすい方法です。

---

## 47. Precision

Precisionは、

**取得したChunkのうち、どれだけ関連情報だったか**

です。

候補を増やしすぎるとPrecisionが落ちる場合があります。

そこでRerankingを利用します。

---

## 48. MRR

MRRは、

Mean Reciprocal Rank

の略です。

正解が、

1位  
2位  
5位

のどこに出ているか

を評価する指標です。

単にTop 10に入っただけでなく、

上位に出ているか

を評価できます。

---

## 49. NDCG

NDCGは、

ランキング全体の品質

を評価するために使われることがあります。

複数の関連文書について、

どれだけ関連性が高いものを上位に配置できたか

を確認できます。

検索システムを本格的に評価するときに使われます。

のような関係検索です。

Keyword  
Vector  
Graph

Hybrid Searchは広い意味では、

**複数の検索技術を組み合わせる考え方**

として使われることもあります。

---

## 57. 検索結果がない場合

Hybrid Searchでも十分な結果がない場合があります。

例えば、

Keyword Search  
0件

Vector Search  
Similarityが非常に低い

場合です。

この場合、

「関連資料がありません」

と判断する設計があります。

無関係なChunkをLLMへ渡さないことが重要です。

---

## 58. 検索結果が多すぎる場合

逆に候補が大量にある場合は、

- Metadata Filter
    
- Reranking
    
- Duplicate除去
    
- Document単位の件数制限
    

などを使って絞り込みます。

---

## 59. Document Diversity

検索上位がすべて同じ文書の似たChunkになることがあります。

例えば、

1位 DOC001 Chunk 1  
2位 DOC001 Chunk 2  
3位 DOC001 Chunk 3  
4位 DOC001 Chunk 4

となる場合です。

必要に応じて、

複数Documentから結果を取る

ように調整することがあります。

---

## 60. Duplicate除去

Chunk Overlapなどによって、

ほぼ同じ文章

が複数検索される場合があります。

そのため、

- chunk_id
    
- text hash
    
- 類似度
    

などを利用して重複を除去する場合があります。

---

## 61. Hybrid SearchとLLM Context

検索結果は最終的にLLMのContextになります。

そのため、

Hybrid Searchで大量に取得できても、

すべてLLMへ渡す

わけではありません。

例えば、

候補50件  
→ Reranking  
→ 5件  
→ LLM

とします。

---

## 62. 検索精度とTokenコスト

検索結果を増やすと、

正解を含みやすくなる

一方、

LLMへ渡すTokenも増えます。

そのため、

Retrieval Recall

と、

LLM Context Size

のバランスを考えます。

---

## 63. Hybrid Searchで重要な考え方

Hybrid Searchの目的は、

**KeywordとVectorのScoreを混ぜることそのもの**

ではありません。

目的は、

**質問に答えるための正しい根拠を、できるだけ漏らさず、不要な情報を減らして取得すること**

です。

そのため、

- Chunk
    
- Query
    
- Metadata
    
- Ranking
    
- Reranking
    

まで含めて考えることが重要です。

---

## 64. RAG全体での位置

RAG全体では、

Document  
→ Parse  
→ Chunk  
→ Embedding  
→ Search Index

までを事前に準備します。

質問時は、

Question  
→ Query Rewrite  
→ Metadata Filter  
→ Keyword Search  
＋  
Vector Search  
→ Hybrid Ranking  
→ Reranking  
→ Context  
→ Prompt  
→ LLM

という流れになります。

Hybrid Searchは、

**Retrieval部分の中心となる検索方式の1つ**

です。

---

## 65. よくある構成

実際のRAGでは、例えば以下のような構成があります。

Question

→ Query Rewrite

→ Permission Filter

→ Keyword Search Top 30  
＋  
Vector Search Top 30

→ RRFで統合

→ Duplicate除去

→ Reranking

→ Top 5

→ Prompt作成

→ LLM

→ Answer

この形を理解しておくと、RAGの検索処理をかなり追いやすくなります。

---

## 66. 一言で理解する

Hybrid Searchとは、

**「文字が一致する検索」と「意味が近い検索」を組み合わせ、それぞれの弱点を補う検索方法」**

です。

Keyword Searchは、

**何という文字が書かれているか**

に強く、

Vector Searchは、

**何について書かれているか**

に強いです。

RAGでは、

**Keyword Search + Vector Search → Ranking → Reranking**

という構成にすることで、より正確な根拠をLLMへ渡せるようになります。

特に覚えておきたい流れは、

**Question → Keyword Search + Vector Search → RRF / Score統合 → Reranking → LLM**

です。
