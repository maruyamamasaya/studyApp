> Te社向けの例は学習用の想定です。実際の採用サービス・設定・権限は、既存コードと正式資料で確認してください。

# 1. 概要

処理フローは、入力がどの順番で加工され、どこで分岐し、何を返すかを表したものです。RAGでは文書取り込みと質問回答を分けて追うと理解しやすくなります。

# 2. 何のために使うか

詳細設計書の処理手順と、ソースコードの呼び出し順序を照合するために使います。正常系だけでなく、根拠がない、権限がない、外部APIが遅い場合も対象です。

# 3. 仕組み

取り込みは、原本取得、本文抽出、文書分割、Embedding生成、索引登録、処理状態更新の順で整理できます。質問回答は、入力検証、トークン検証、権限決定、質問のEmbedding、検索、必要な再順位付け、Context構築、LLM呼び出し、回答整形の順です。

実装によってはキーワード検索だけで質問Embeddingを使わない場合もあります。会話履歴による質問書き換えがある場合は、その位置と権限の扱いを追加します。

# 4. 具体例

Te社の想定例では、質問APIが認可を終えた後に部署条件を付けて検索します。候補を絞って根拠を構築し、回答と出典IDを返します。権限不足なら生成処理を開始せず、該当資料がないなら根拠不足の応答へ分岐します。

# 5. 実装・設定時のポイント

- 各処理の入力型、出力型、例外、所要時間を記録します。
- request_idという追跡用IDを各段階に引き継ぎます。
- エラー時に状態を更新する場所と、再実行可能な単位を決めます。
- ストリーミングでは、応答開始前と開始後で失敗通知方法を分けます。

# 6. 注意点

一部の検索が失敗したのに、全検索が成功したように扱うと利用者が誤解します。部分成功を許す場合は、回答の制約とログへ明示します。認証失敗を検索結果なしへ変換する実装も原因を見えにくくします。

# 7. Te社RAG基盤で確認するポイント

APIルーター、サービス関数、検索アダプター、LLMアダプターの順に呼び出しを追います。分岐条件と例外ハンドラーを含めて図を起こし、各段階をログで再現できるか確認します。非同期処理の開始だけで完了と判定していないかも調べます。
