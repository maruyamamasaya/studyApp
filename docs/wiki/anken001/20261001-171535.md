## 1. 概要

RAGの処理フローは、大きく以下の2つに分かれます。

1. 文書を登録する処理
    
2. ユーザーの質問に回答する処理
    

文書登録側では、資料を検索できる状態にします。

質問回答側では、ユーザーの質問に関連する資料を検索し、その内容をLLMへ渡して回答を生成します。

---

## 2. 全体フロー

RAG全体の流れは以下です。

### 文書登録

文書取得  
→ テキスト抽出  
→ 前処理  
→ Chunk分割  
→ Embedding  
→ Metadata付与  
→ 検索インデックスへ登録

### 質問回答

ユーザーから質問  
→ 認証・権限確認  
→ 質問の前処理  
→ 文書検索  
→ 検索結果取得  
→ Reranking  
→ Prompt生成  
→ LLMへ送信  
→ 回答生成  
→ 出典付与  
→ ユーザーへ返却

---

# 3. 文書登録フロー

## 3.1 文書取得

最初にRAGで利用する資料を取得します。

対象例：

- PDF
    
- Word
    
- Excel
    
- PowerPoint
    
- HTML
    
- Markdown
    
- Webページ
    
- 社内Wiki
    
- データベース
    

元データをRAG基盤に取り込みます。

---

## 3.2 テキスト抽出

取得したファイルからテキストを取り出します。

例えばPDFの場合、

- テキストPDF
    
- スキャンPDF
    
- 画像PDF
    

などによって処理方法が異なります。

画像しか含まれていない場合はOCRを使用して文字を取得することがあります。

---

## 3.3 前処理

抽出したテキストを検索しやすい形に整えます。

例えば、

- 不要な改行削除
    
- 空白整理
    
- HTMLタグ削除
    
- ヘッダー・フッター除去
    
- 文字化け修正
    
- OCR誤認識の補正
    
- 重複文章削除
    

などを行います。

---

## 3.4 Chunk分割

長い文章を小さな単位へ分割します。

この単位をChunkと呼びます。

例えば、

100ページのPDF

を、

見出し単位や数百文字単位

に分割します。

Chunkが大きすぎると不要な情報まで含まれます。

逆に小さすぎると前後の意味が失われる可能性があります。

---

## 3.5 Metadata付与

Chunkには本文以外の情報も持たせます。

例えば、

- 文書ID
    
- ファイル名
    
- ページ番号
    
- 見出し
    
- 作成日
    
- 更新日
    
- カテゴリ
    
- 部署
    
- 権限情報
    

などです。

Metadataは検索の絞り込みや出典表示に利用します。

---

## 3.6 Embedding

各ChunkをEmbeddingモデルへ渡してVectorへ変換します。

例えば、

「PCを購入する」

と

「パソコンを買う」

は文章は違いますが意味が近いため、Vector上でも近い位置になります。

このVectorを使って意味検索を行います。

---

## 3.7 検索インデックス登録

最後に、

- Chunk本文
    
- Vector
    
- Metadata
    

を検索サービスやデータベースへ保存します。

これで文書登録側の処理は完了です。

---

# 4. 質問回答フロー

## 4.1 ユーザーから質問

ユーザーがRAGシステムへ質問します。

例：

「PCを購入するときの申請方法を教えて」

質問はWeb画面やAPIなどからバックエンドへ送られます。

---

## 4.2 認証

まず、

「誰が質問しているか」

を確認します。

例えば、

- User ID
    
- 所属部署
    
- Role
    
- Group
    

などを取得します。

社内RAGでは、ユーザーごとに閲覧できる文書が異なる場合があります。

---

## 4.3 質問の前処理

ユーザーの質問を、そのまま検索に使うとは限りません。

必要に応じて、

- 不要文字削除
    
- キーワード抽出
    
- Query Rewrite
    
- 会話履歴の追加
    
- 質問の補完
    

などを行います。

例えば、

「それの申請期限は？」

という質問だけでは意味が分からない場合、

過去の会話から、

「PC購入申請の期限は？」

のように検索用の質問へ変換することがあります。

---

## 4.4 質問をEmbedding

Vector Searchを利用する場合、ユーザーの質問もEmbeddingします。

質問：

「PC購入の手続きを知りたい」

をVectorへ変換します。

そのVectorと、登録済みChunkのVectorを比較します。

---

## 4.5 文書検索

検索インデックスから関連するChunkを取得します。

検索方式として、

- Keyword Search
    
- Vector Search
    
- Hybrid Search
    

などがあります。

例えば、

Top 20

の候補を取得します。

---

## 4.6 Metadata Filter

検索時にMetadataを使用して対象を絞り込みます。

例えば、

- 所属部署
    
- 文書カテゴリ
    
- 公開範囲
    
- 更新日
    
- 権限
    

などです。

ユーザーが閲覧できない資料は、この段階で検索対象から除外します。

---

## 4.7 検索結果取得

検索結果として関連するChunkが返ってきます。

例えば、

1. PC購入申請手順
    
2. IT機器購入規程
    
3. 経費申請ルール
    

などです。

この時点ではまだ候補が多い場合があります。

---

## 4.8 Reranking

検索結果をさらに評価し、質問との関連性が高いものを上位へ並べ替えます。

例えば、

検索結果20件  
→ Reranking  
→ 上位5件

のように絞ります。

この処理によって、LLMへ渡す情報の質を高めます。

---

## 4.9 Context作成

LLMへ渡す資料をまとめます。

この検索結果を、

Context

と呼ぶことがあります。

例えば、

Context 1  
PC購入申請は社内システムから実施する。

Context 2  
申請には所属長の承認が必要。

Context 3  
10万円以上の場合は追加承認が必要。

などです。

---

## 4.10 Prompt生成

ユーザーの質問とContextを組み合わせてPromptを作成します。

Promptには例えば、

- システム指示
    
- 回答ルール
    
- ユーザーの質問
    
- 検索結果
    
- 出力形式
    

を含めます。

イメージとしては、

「以下の資料のみを根拠として回答してください」

という指示と一緒に検索結果を渡します。

---

## 4.11 LLMへ送信

生成したPromptをLLMへ送ります。

LLMは、

- ユーザーの質問
    
- Context
    
- 回答ルール
    

をもとに回答を生成します。

ここで重要なのは、

LLM自身が文書を検索しているわけではない

ということです。

検索はRAG基盤側で行い、LLMは渡された資料を使って文章を生成します。

---

## 4.12 回答生成

LLMから回答を受け取ります。

例：

「PC購入は社内申請システムから申請します。所属長の承認が必要です。」

などです。

---

## 4.13 出典付与

回答に使用した元文書の情報を付けます。

例えば、

- 文書名
    
- ページ番号
    
- URL
    
- セクション名
    

などです。

これにより利用者が元資料を確認できます。

---

## 4.14 ユーザーへ返却

最後に、

- 回答本文
    
- 出典
    
- 関連情報
    

をユーザー画面へ返します。

これで質問1回分のRAG処理が完了します。

---

# 5. 質問1回の流れ

質問回答側だけを見ると、以下の流れです。

ユーザー質問  
→ 認証  
→ Query Rewrite  
→ 質問Embedding  
→ Search  
→ Metadata Filter  
→ Top K取得  
→ Reranking  
→ Context作成  
→ Prompt作成  
→ LLM  
→ 回答  
→ 出典  
→ ユーザー

---

# 6. 検索結果がない場合

RAGでは、検索結果がない場合の処理も重要です。

例えば、

検索結果なし  
→ LLMへ通常回答させない  
→ 「該当する情報を確認できませんでした」と返す

という設計があります。

検索結果がないにもかかわらずLLMへ自由に回答させると、Hallucinationが発生しやすくなります。

---

# 7. 文書更新時の処理

RAGでは、一度文書を登録したら終わりではありません。

文書が変更された場合は、

文書更新  
→ 古いChunk削除  
→ 新しいテキスト取得  
→ Chunk再作成  
→ Embedding再作成  
→ 検索インデックス更新

などを行います。

削除された文書も検索結果から削除する必要があります。

---

# 8. エラー発生時の処理

RAGでは複数の外部サービスを利用することがあるため、エラー処理も重要です。

例えば、

- 文書取得失敗
    
- OCR失敗
    
- Embedding API失敗
    
- 検索サービス失敗
    
- LLM API失敗
    
- Timeout
    
- Rate Limit
    

などがあります。

そのため、

- Retry
    
- Timeout
    
- Logging
    
- Exception Handling
    

などを組み込みます。

---

# 9. RAGの処理で重要なポイント

RAGでは、最終回答だけを見るのではなく、途中処理を分けて確認することが重要です。

例えば回答が間違っていた場合、

- 文書自体が間違っていた
    
- Chunk分割が悪かった
    
- Embeddingが適切でなかった
    
- 検索で正しい文書を取れなかった
    
- Rerankingで落とした
    
- Promptが悪かった
    
- LLMが根拠を無視した
    

など、原因は複数考えられます。

そのため、

**検索と生成を分けて確認する**

ことが重要です。

---

# 10. 一言で理解する

RAGの処理フローは、

**資料を事前に検索できる状態へ加工しておき、質問されたら関連資料を探して、その資料と質問をLLMへ渡して回答させる流れ**

です。

特に質問時は、

**Question → Search → Context → Prompt → LLM → Answer**

という流れを理解しておくと、RAGのコードや設計書も追いやすくなります。
