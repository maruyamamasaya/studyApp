> Te社向けの例は学習用の想定です。実際の採用サービス・設定・権限は、既存コードと正式資料で確認してください。

# 1. 概要

Azure OpenAIは、Azure上で提供されるOpenAIモデルの機能をAPIから利用するサービスです。RAGでは文章生成とEmbeddingに利用する構成が考えられます。Microsoft Foundry関連の名称や提供形態もあるため、既存資材では採用したリソースとAPIを確認します。

# 2. 何のために使うか

検索した資料を使った回答生成や、文書と質問のベクトル化を行います。検索索引や原本の保存は、それぞれ別の責務です。

# 3. 仕組み

アプリは接続先のエンドポイントとモデルのデプロイを指定して要求します。デプロイ名は環境で付ける名前で、モデルそのものの名前と同じとは限りません。APIキーまたは対応するEntra ID認証などでアクセスします。[Entra ID認証の公式説明](https://learn.microsoft.com/en-us/azure/foundry-classic/openai/how-to/managed-identity)

# 4. 具体例

Te社の想定例では、取り込みWorkerがEmbedding用デプロイを呼び、質問APIが生成用デプロイを呼びます。同じリソースでも、モデル、権限、容量を区別して確認します。

# 5. 実装・設定時のポイント

- リソース、エンドポイント、デプロイ名、モデル版を一覧化します。
- 利用APIとSDK版に対応する引数を確認します。
- 要求数・Token量の容量、429時の対応、Timeoutを設定します。
- Managed Identityへ必要なデータ操作権限を付与します。

# 6. 注意点

モデル名だけでは、リージョン、提供方式、容量、データ処理条件は確定しません。料金、入力上限、対応パラメーターは採用モデルの現行仕様で確認します。Content Filterによる停止と通常の通信失敗を分けて扱います。

# 7. Te社RAG基盤で確認するポイント

SDKクライアント生成、credential、接続先、model引数、API版、usageの取得を確認します。アプリ上の設定がAzureの実デプロイと一致するか調べます。プロンプト、回答、元資料の送信先と保存方針も確認します。
