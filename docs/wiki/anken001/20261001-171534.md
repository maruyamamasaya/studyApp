> Te社向けの例は学習用の想定です。実際の採用サービス・設定・権限は、既存コードと正式資料で確認してください。

# 1. 概要

RAG基盤は、文書を検索可能にする取り込み系と、利用者の質問に答える問い合わせ系から構成されます。その周囲に、認証、秘密情報管理、ログ、監視があります。構成図ではサービス名に加えて、保存するデータと通信方向を読むことが重要です。

# 2. 何のために使うか

役割を分けることで、文書更新を回答処理から独立させ、障害や負荷の影響範囲を小さくできます。どのサービスが個人情報や社内文書を扱うのかも整理できます。

# 3. 仕組み

以下は学習用の構成例であり、Te社の実構成を示すものではありません。

| 区分 | 構成例 | 主な責務 |
| --- | --- | --- |
| 原本保存 | Blob Storage | 文書と版の保存 |
| 取り込み | Python Worker、必要に応じてOCR | 抽出、分割、登録 |
| 検索 | Azure AI Search | 本文、ベクトル、権限属性の検索 |
| 生成 | Azure OpenAI | 根拠を使った回答生成 |
| API | Python Webアプリ | 入力検証、認可、処理の調整 |
| 共通 | Entra ID、Key Vault、Azure Monitor | 認証、秘密管理、観測 |

構成図の線ごとに、プロトコル、認証方式、タイムアウト、ネットワーク制限を説明できるようにします。

# 4. 具体例

Te社の規程PDFを保存し、取り込みWorkerが検索索引を更新します。利用者の質問APIはEntra IDのトークンを検証して検索します。Workerと質問APIは、別のManaged Identityにすると権限の分離がしやすくなります。

# 5. 実装・設定時のポイント

- リソース名、環境、リージョン、所有者を一覧化します。
- 制御プレーン（設定変更）とデータプレーン（文書や検索の操作）の権限を分けます。
- APIを動かすサービスはApp Service、Functions、Container Appsなどから実環境で特定します。
- ネットワーク図と論理的な処理図は必要に応じて別に作ります。

# 6. 注意点

サービスが存在するだけでは連携は証明できません。未使用リソースやPoCの残骸を現行構成へ混ぜないように、接続設定と実行ログを照合します。Azureに配置しただけで通信が自動的に非公開になるわけではありません。

# 7. Te社RAG基盤で確認するポイント

デプロイ定義、環境変数名、SDKクライアント生成箇所、リソース設定を対応付けます。構成図の各箱にコードの入口を付け、各線に認証と送受信データを付けます。実在が未確認のサービスは、想定として区別します。
