## 1. 概要

RAGは、大きく分けると以下の2つの仕組みで構成されます。

1. 文書を検索できる状態にする仕組み
    
2. ユーザーの質問に対して検索・回答する仕組み
    

RAGでは、単にLLMへ質問を送るのではなく、事前に登録した文書から関連情報を検索し、その情報をLLMへ渡して回答を生成します。

---

## 2. RAG全体の構成イメージ

RAG全体は、次のような構成で考えると理解しやすいです。

文書  
→ テキスト抽出  
→ Chunk分割  
→ Embedding  
→ 検索インデックス / Vector DB

ユーザー  
→ 質問  
→ 検索  
→ 関連Chunk取得  
→ Prompt生成  
→ LLM  
→ 回答

つまり、

**文書登録側**

と

**質問・回答側**

の2つがあります。

---

## 3. 文書登録側

文書登録側では、PDFやWordなどの資料を検索できる状態に加工します。

主な処理は以下です。

1. 文書取得
    
2. テキスト抽出
    
3. 文書整形
    
4. Chunk分割
    
5. Embedding
    
6. Metadata付与
    
7. 検索インデックスへ登録
    

---

## 4. 文書取得

最初に、RAGで利用する文書を取得します。

対象になるデータは、例えば以下です。

- PDF
    
- Word
    
- Excel
    
- PowerPoint
    
- HTML
    
- Markdown
    
- テキスト
    
- Webページ
    
- 社内Wiki
    
- データベース
    

RAGでは、元データの種類によって取り込み方法が変わります。

---

## 5. テキスト抽出

取得した文書から、LLMや検索で利用できるテキストを抽出します。

PDFの場合でも、内部にテキストを持っているPDFと、画像として保存されているPDFでは処理が異なります。

画像PDFの場合はOCRを利用して文字を取得することがあります。

この段階で、

- 文字化け
    
- 不要な改行
    
- ヘッダー
    
- フッター
    
- ページ番号
    
- OCR誤認識
    

などを整理することも重要です。

---

## 6. 文書整形

抽出したテキストをそのまま使用するのではなく、検索しやすい状態へ整形します。

例えば、

- 不要な空白を削除
    
- 不要な改行を削除
    
- HTMLタグを削除
    
- 見出し構造を保持
    
- 表データを整形
    
- 重複文章を削除
    

などを行います。

RAGでは元データの品質が検索精度に大きく影響します。

---

## 7. Chunk分割

長い文章を検索しやすいサイズへ分割します。

分割された単位をChunkと呼びます。

例えば、

1つの100ページPDF

を、

数百文字から数千文字程度のChunk

に分割します。

Chunkには、

- 文書ID
    
- ファイル名
    
- ページ番号
    
- 見出し
    
- 作成日時
    

などのMetadataを付けることがあります。

---

## 8. Embedding

ChunkごとにEmbeddingを作成します。

Embeddingとは、文章の意味を数値ベクトルへ変換する処理です。

例えば、

「パソコンを購入する」

と

「PCを買う」

は単語が違いますが意味は近いため、Embeddingでも近い位置になります。

この仕組みを利用して意味検索を行います。

---

## 9. 検索インデックス

作成したChunkやEmbeddingを検索できる状態で保存します。

保存するものとしては、

- Chunk本文
    
- Embedding
    
- Metadata
    

などがあります。

代表的には、

- Vector DB
    
- 検索エンジン
    
- Vector検索対応DB
    

などが使用されます。

---

## 10. 質問・回答側

ユーザーから質問が来た場合は、登録済みの文書を検索して回答を生成します。

主な処理は以下です。

1. ユーザー認証
    
2. 質問受付
    
3. 質問前処理
    
4. 検索
    
5. 検索結果取得
    
6. Reranking
    
7. Prompt作成
    
8. LLM呼び出し
    
9. 回答生成
    
10. 出典付与
    
11. ユーザーへ返却
    

---

## 11. ユーザー認証

社内RAGなどでは、最初にユーザーを認証します。

確認する情報として、

- User ID
    
- Role
    
- Group
    
- Department
    

などがあります。

この情報を利用して、

「このユーザーがどの文書を検索できるか」

を制御します。

---

## 12. 質問受付

ユーザーから自然言語で質問を受け取ります。

例えば、

「PCを購入するときの申請方法を教えて」

といった質問です。

質問はAPIやWeb画面などからRAG基盤へ送られます。

---

## 13. 質問の前処理

検索しやすくするため、質問を加工する場合があります。

例えば、

- 不要な文字を除去
    
- 質問文を短くする
    
- 検索用キーワードを生成
    
- 質問を書き換える
    
- 会話履歴を考慮する
    

などです。

この処理をQuery Rewriteなどと呼ぶことがあります。

---

## 14. 検索

加工した質問を使用して文書を検索します。

検索方式としては主に、

- Keyword Search
    
- Vector Search
    
- Hybrid Search
    

があります。

実際のRAGでは、Hybrid Searchが使われることも多いです。

---

## 15. Metadata Filter

検索時には、Metadataを利用して対象を絞り込むことがあります。

例えば、

- 所属部署
    
- 文書種別
    
- 作成日
    
- 更新日
    
- 権限
    
- カテゴリ
    

などです。

特に社内RAGでは、

**検索時点で権限制御する**

ことが重要です。

---

## 16. 検索結果取得

検索結果として、質問に関連するChunkを複数取得します。

例えば、

Top 5

や

Top 10

などです。

検索結果が多すぎるとLLMへ不要な情報を渡してしまう可能性があります。

少なすぎると必要な情報が不足する可能性があります。

---

## 17. Reranking

検索結果をさらに評価して、関連性が高い順に並び替える処理です。

例えば、

検索結果20件  
→ Reranking  
→ 上位5件

という処理を行います。

最初の検索は高速に候補を探し、Rerankingでより正確に絞り込むイメージです。

---

## 18. Prompt生成

検索結果とユーザーの質問をまとめてLLMへ渡します。

Promptには例えば、

- システム指示
    
- ユーザーの質問
    
- 検索した資料
    
- 回答ルール
    

などを含めます。

回答ルールとして、

「資料に書かれていない内容は推測しない」

などを指定することもあります。

---

## 19. LLM呼び出し

完成したPromptをLLMへ送信します。

LLMは、

- ユーザーの質問
    
- 検索された資料
    
- 回答ルール
    

をもとに回答を生成します。

RAGでは、LLM自体が文書を検索しているわけではありません。

検索処理はRAG基盤側で行い、その検索結果をLLMへ渡しています。

---

## 20. 回答生成

LLMから生成された文章を受け取ります。

このとき、

- 回答内容
    
- 出典
    
- 文書名
    
- ページ番号
    
- URL
    

などをユーザーへ返すことがあります。

出典を表示することで、利用者が元資料を確認できます。

---

## 21. RAG全体の処理フロー

全体をまとめると、以下のようになります。

### 文書登録

文書取得  
→ テキスト抽出  
→ 文書整形  
→ Chunk分割  
→ Embedding  
→ Metadata付与  
→ 検索インデックス登録

### 質問・回答

ユーザー  
→ 認証  
→ 質問  
→ 質問前処理  
→ 検索  
→ Metadata Filter  
→ 検索結果  
→ Reranking  
→ Prompt生成  
→ LLM  
→ 回答生成  
→ 出典付与  
→ ユーザー

---

## 22. 主な構成要素

|構成要素|役割|
|---|---|
|Document Source|元となる文書を保存|
|Parser|文書からテキストを取得|
|Chunker|文書を小さく分割|
|Embedding Model|文章をVector化|
|Search Engine|文書を検索|
|Vector DB|Vectorを保存・検索|
|Metadata|文書情報や権限情報を保持|
|Retriever|関連する文書を取得|
|Reranker|検索結果を再評価|
|Prompt Builder|LLMへ送るPromptを作成|
|LLM|最終的な回答を生成|
|API|ユーザーとRAG基盤を接続|
|Authentication|ユーザー認証|
|Authorization|文書アクセス権を制御|

---

## 23. RAGで重要な3つの部分

RAG全体を見ると、特に重要なのは以下の3つです。

### 23.1 Ingestion

文書を取り込み、検索できる状態にする部分です。

主に、

文書取得  
→ Chunk  
→ Embedding  
→ Index登録

を担当します。

---

### 23.2 Retrieval

ユーザーの質問に関連する情報を検索する部分です。

主に、

質問  
→ 検索  
→ Filter  
→ Reranking

を担当します。

RAGでは非常に重要な部分です。

---

### 23.3 Generation

検索した情報をLLMへ渡して回答を作る部分です。

主に、

検索結果  
→ Prompt  
→ LLM  
→ 回答

を担当します。

---

## 24. RAG全体で見るべきポイント

RAGを設計・確認するときは、次の流れで見ると理解しやすいです。

### データ側

- どこから文書を取得するか
    
- どうテキスト化するか
    
- どうChunkに分割するか
    
- どのEmbeddingモデルを使うか
    
- どこへ保存するか
    
- 文書更新をどう反映するか
    

### 検索側

- Keyword Searchか
    
- Vector Searchか
    
- Hybrid Searchか
    
- Metadata Filterはあるか
    
- Rerankingするか
    
- Top Kはいくつか
    

### LLM側

- どのLLMを利用するか
    
- Promptをどう作るか
    
- 検索結果を何件渡すか
    
- 根拠がない場合どうするか
    
- 出典をどう表示するか
    

### セキュリティ側

- 認証方法
    
- 権限制御
    
- 文書アクセス制御
    
- APIアクセス制御
    
- 秘密情報管理
    

---

## 25. 一言で理解する

RAG全体構成は、

**「資料を検索できる形に準備する部分」と「質問されたときに資料を検索してLLMへ渡す部分」**

の2つで構成されています。

さらに細かく見る場合は、

**Ingestion → Retrieval → Generation**

の3段階で考えると理解しやすいです。

RAGを勉強するときは、まずこの3つの役割を把握してから、

- Chunk
    
- Embedding
    
- Vector Search
    
- Hybrid Search
    
- Reranking
    
- Prompt
    

を個別に理解していくと、全体像を掴みやすくなります。
