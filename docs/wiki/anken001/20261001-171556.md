# 1. 概要

Exponential Backoff（指数バックオフ）は、再試行を重ねるごとに待機時間を増やす方法です。Jitter（ジッター）は待機時間にばらつきを加え、複数クライアントの再試行が一斉に発生するのを避ける工夫です。

# 2. 何のために使うか

過負荷の検索・生成サービスへ連続して要求を送り、状況を悪化させることを防ぎます。Retryが「もう一度呼ぶか」を決めるのに対し、Backoffは「いつ呼ぶか」を決めます。

# 3. 仕組み

上限待機時間をmin（最大値、初期待機 × 2の試行段階乗）で増やし、その範囲内でランダムに待つ方法があります。Retry-Afterがある場合はその指示を優先し、全体期限が足りなければ再試行を打ち切ります。

# 4. 具体例

次のPythonコードは、待機時間を決める部分だけの例です。初回失敗後をattempt=0として、上限0.5秒、1秒、2秒などの範囲から選びます。呼び出し側で再試行対象、最大回数、総期限を別に管理する必要があります。

~~~python
import random

def backoff_seconds(attempt, base=0.5, cap=8.0):
    ceiling = min(cap, base * (2 ** attempt))
    return random.uniform(0, ceiling)
~~~

Te社の一括Embedding処理で同時に429が出ても、各Workerの待機をずらす意図があります。

# 5. 実装・設定時のポイント

- 非同期処理ではasyncio.sleepで待ちます。
- 最大値と総期限の両方を設けます。
- Retry-Afterが秒数か日時かをHTTP仕様に従って扱います。
- テストでは乱数を制御して待機計算を確認します。

# 6. 注意点

待機を増やすだけでは恒常的な容量不足は解決しません。並列数や要求量も見直します。サービスの指示する待機時間が利用者の期限を超える場合は、短く偽装せず、停止や非同期受付へ切り替える設計を考えます。

# 7. Te社RAG基盤で確認するポイント

Backoffの式、上限、Jitter、Retry-After、SDK内部の再試行を確認します。試行番号がどこから始まるかを調べます。429が継続する時間と並列数をログで照合し、再試行が障害を増幅していないか確認します。
