# 1. 概要

Hallucination（ハルシネーション）は、LLMが事実や根拠と一致しない内容を、もっともらしく生成する現象です。流暢な文章であることと、内容が正しいことは別です。

# 2. 何のために使うか

RAGの設計では、誤った断定を減らし、根拠不足を適切に伝えるためにこの現象を理解します。利用者が出典を確認できる仕組みと、品質評価が必要です。

# 3. 仕組み

原因を、資料自体の誤り、検索漏れ、Contextの欠落、生成時の推測に分けます。LLMは与えられた資料を必ず厳密に再現するわけではありません。検索と生成のどちらで失敗したかを切り分けると、改善箇所を絞れます。

# 4. 具体例

Te社の想定例で、規程に承認期限がないのに「3営業日」と回答した場合は、根拠のない補完です。検索結果に正しい条文があったか、Contextへ入ったか、出力が条文を支持しているかを順に確認します。

# 5. 実装・設定時のポイント

- 正解のある質問と、資料に答えがない質問を両方評価します。
- 根拠がない場合の応答と確認先の案内を定義します。
- 引用IDだけでなく、主張を引用本文が支持するか確認します。
- Prompt、検索設定、モデルの変更ごとに代表質問を比較します。

# 6. 注意点

temperatureという生成のばらつきに関わる設定を下げても、事実誤りはなくなりません。また、モデルによって対応する設定が違います。「根拠に忠実だが原本が間違っている」ケースと、根拠を逸脱したケースを分けて報告します。

# 7. Te社RAG基盤で確認するポイント

評価データ、根拠不足の判定、出典検証、利用者の訂正受付を確認します。正解文書と実検索結果を対応付け、問題が取り込み・検索・生成のどこで起きたか記録します。業務上重要な回答の確認手順があるか調べます。
