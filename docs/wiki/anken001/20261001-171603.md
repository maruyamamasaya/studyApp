## 1. Azure AI Searchとは

Azure AI Searchは、

**Azure上で文書やデータを検索するための検索サービス**

です。

RAGでは主に、

- Keyword Search
    
- Vector Search
    
- Hybrid Search
    
- Metadata Filter
    
- Semantic Ranking
    

などを担当します。

つまりAzure AI Searchは、

**LLMに渡す根拠情報を探すための検索基盤**

です。

---

## 2. RAG全体での位置

Azureを使ったRAGでは、例えば以下のような構成になります。

文書  
→ テキスト抽出  
→ Chunk  
→ Embedding  
→ Azure AI Searchへ登録

質問時：

Question  
→ Embedding  
→ Azure AI Search  
→ 関連Chunk取得  
→ Reranking  
→ Context  
→ Prompt  
→ Azure OpenAI  
→ Answer

Azure AI Searchは、この中の、

**Search / Retrieval**

を担当します。

Microsoftの現行ドキュメントでも、Azure AI SearchはRAGでLLMへ渡すGrounding Dataを検索する役割として説明されています。

---

## 3. Azure OpenAIとの違い

混同しやすいので重要です。

### Azure OpenAI

主に、

- Embedding生成
    
- LLMによる回答生成
    

を担当します。

### Azure AI Search

主に、

- 文書検索
    
- Vector Search
    
- Keyword Search
    
- Hybrid Search
    
- Filter
    
- Ranking
    

を担当します。

つまり、

**Azure OpenAI = AIモデル**

**Azure AI Search = 検索エンジン**

と考えると分かりやすいです。

---

## 4. Search Index

Azure AI Searchでは、

検索対象となるデータを、

Search Index

へ登録します。

Indexは、

**検索しやすい形に整理されたデータ置き場**

と考えると分かりやすいです。

例えば1つのChunkを、

```
chunk_id
document_id
content
title
page
department
vector
```

のようなFieldとして登録します。

---

## 5. Field

Indexは複数のFieldで構成されます。

例えば、

```
chunk_id
content
title
page
department
access_level
content_vector
```

などです。

それぞれに、

- 検索対象にするか
    
- Filterできるか
    
- Sortできるか
    
- Vector Fieldか
    

などを設定します。

---

## 6. Text Field

例えば、

content

に、

「バックアップは30日保存します。」

というChunk本文を入れます。

このFieldは、

Keyword Search

などに利用できます。

---

## 7. Vector Field

Embeddingによって生成したVectorを保存するFieldです。

例えば、

```
content_vector
```

というFieldを作り、

```
[0.12, -0.44, 0.81, ...]
```

のようなVectorを保存します。

このVectorを使って、

Vector Search

を行います。

Azure AI Searchでは、Vector Fieldを持つIndexに対して類似度検索を実行できます。

---

## 8. Keyword Search

Azure AI Searchでは、

全文検索

を利用できます。

例えば、

「ERR-50001」

「Windows Server 2025」

などを検索します。

文字列そのものが重要な、

- 型番
    
- エラーコード
    
- 製品名
    
- 人名
    
- 固有名詞
    

などに強い検索方式です。

全文検索のランキングにはBM25系のスコアリングが利用されます。

---

## 9. Vector Search

Vector Searchでは、

質問をEmbeddingしてVector化し、

Index内のVectorと比較します。

例えば、

Question:

「パソコンを買う場合の申請方法は？」

をVector化し、

意味が近いChunk

を探します。

Azure AI SearchではHNSWやeKNNを利用したVector検索がサポートされています。

---

## 10. HNSW

HNSWは、

Hierarchical Navigable Small World

の略です。

大量のVectorから、

近いVectorを高速に探す

ための方式です。

Azure AI SearchのVector Searchで利用できます。

---

## 11. eKNN

eKNNは、

Exhaustive K Nearest Neighbors

の考え方です。

候補を近似的に探すHNSWに対して、

より網羅的にVector比較を行う方式です。

データ量や精度要件によって使い分けます。

---

## 12. Hybrid Search

Azure AI Searchでは、

Keyword Search

と、

Vector Search

を1つのQueryで同時に実行できます。

これを、

Hybrid Search

と呼びます。

例えば、

「ERR-50001でログインできません」

という質問なら、

ERR-50001  
→ Keyword Search

ログインできない  
→ Vector Search

という両方の特徴を利用できます。

Microsoftの現行仕様では、Hybrid Searchは全文検索とVector Searchを並列に実行し、その結果をRRFで統合します。

---

## 13. RRF

Hybrid Searchでは、

Keyword Searchの順位

と、

Vector Searchの順位

を統合する必要があります。

Azure AI Searchでは、

Reciprocal Rank Fusion

略して、

RRF

が使われます。

RRFは、

複数の検索ランキングを1つにまとめる仕組み

です。

---

## 14. Semantic Ranker

Azure AI Searchには、

Semantic Ranker

という機能があります。

検索結果を、

Microsoftの言語理解モデル

で再評価して、

意味的により関連性が高いものを上位へ並べ替えます。

つまり、

Search  
→ 初期Ranking  
→ Semantic Ranker  
→ 再Ranking

という流れです。

---

## 15. Semantic RankerとReranking

Semantic Rankerは、

Rerankingの一種

として理解できます。

例えば、

Hybrid Search  
→ RRF  
→ Top候補  
→ Semantic Ranker  
→ 最終Ranking

という構成です。

Azure AI Searchでは、BM25やRRFで得られた初期結果をSemantic Rankerが再評価できます。

---

## 16. Metadata Filter

Azure AI Searchでは、

MetadataによるFilter

も利用できます。

例えば、

```
department = "人事部"
```

や、

```
access_level = "manager"
```

などです。

これによって、

検索対象を限定

できます。

---

## 17. 権限制御

社内RAGでは、

ユーザーごとに閲覧可能な文書が違う

場合があります。

そのため、

認証  
→ User Role / Group取得  
→ Filter作成  
→ Azure AI Search

という流れにします。

例えば、

```
allowed_groups contains "HR"
```

のようなFilterです。

重要なのは、

**LLMへ渡す前ではなく、検索段階で権限制御する**

ことです。

---

## 18. Filterable Field

Metadata Filterに使うFieldは、

Filter可能なField

としてIndexに定義する必要があります。

例えば、

department  
access_level  
document_type

などです。

Index設計時に、

後から何で絞り込みたいか

を考えることが重要です。

---

## 19. Searchable Field

Keyword Searchの対象にしたいFieldは、

Searchable

として設定します。

例えば、

content  
title  
heading

などです。

これらの文字列を全文検索できます。

---

## 20. Retrievable Field

検索結果として返したいFieldを、

Retrievable

にします。

例えば、

content  
title  
page  
document_id

などです。

LLMへContextとして渡す情報になります。

---

## 21. Sortable / Facetable

用途によって、

Sortable

Facetable

などの属性も設定できます。

例えば、

updated_atでSort

categoryでFacet

などです。

RAGでは必須ではありませんが、検索UIを作る場合に役立ちます。

---

## 22. Indexへ登録するデータ

RAGでは通常、

1文書 = 1件

ではなく、

**1 Chunk = 1検索Document**

として登録することがあります。

例えば、

100ページPDF  
→ 200 Chunk  
→ 200件をIndex登録

という形です。

これによって、

必要な部分だけ検索できます。

---

## 23. ChunkとIndex

例えば、

```
chunk_id
DOC001-005

document_id
DOC001

page
12

content
バックアップは30日保存します。

content_vector
[...]
```

という1件をIndexへ登録します。

この1件が、

検索単位

になります。

---

## 24. Embeddingはどこで作るのか

Embeddingは、

- アプリケーション側
    
- Azure AI SearchのVectorization機能
    

などで作る構成があります。

Microsoftの現行RAGガイドでは、Indexing時にChunkingとVectorizationを組み合わせる構成も案内されています。

---

## 25. Integrated Vectorization

Azure AI Searchでは、

Embedding生成を検索Index作成の流れに組み込む

構成があります。

例えば、

Blob Storage  
→ Indexer  
→ Chunk  
→ Azure OpenAI Embedding  
→ Azure AI Search Index

という流れです。

アプリ側でVector生成処理を全部書かなくてもよい場合があります。

---

## 26. Indexer

Azure AI Searchには、

データソースから情報を取得してIndexへ登録する、

Indexer

という仕組みがあります。

例えば、

Azure Blob Storage

などから文書を読み込み、

Indexへ取り込めます。

---

## 27. Data Source

Indexerが取得する元データを、

Data Source

として設定します。

例えば、

- Azure Blob Storage
    
- Azure SQL系データ
    
- Cosmos DB系
    

などがあります。

利用可能な接続先はサービス仕様に依存します。

---

## 28. Skillset

Indexer処理の途中で、

文書へ追加処理を行う仕組みとして、

Skillset

があります。

例えば、

- テキスト分割
    
- OCR
    
- AI処理
    
- Embedding
    

などを組み合わせる構成があります。

---

## 29. Integrated Vectorizationのイメージ

例えば、

PDF  
→ Blob Storage

Azure AI Search Indexer  
→ テキスト取得  
→ Chunk  
→ Azure OpenAI Embedding  
→ Vector作成  
→ Index登録

という流れです。

文書取り込みPipelineをAzure側で組みやすくなります。

---

## 30. Query時のVectorization

質問時にも、

ユーザーQueryをEmbedding

する必要があります。

構成によっては、

Query Text  
→ Embedding  
→ Vector Search

までAzure AI Search側のVectorizer構成と連携できます。

---

## 31. Top-K

Vector Searchでは、

上位何件取得するか

を指定します。

例えば、

k = 20

なら、

Vector的に近い上位20件

を取得します。

この候補を、

Semantic Ranker

などでさらに絞ります。

---

## 32. Search Score

検索結果には、

Score

が付きます。

例えば、

Keyword Search Score  
Vector Search Score  
RRF Score  
Semantic Reranker Score

などがあります。

Azure AI Searchでは検索方式によってスコアの意味が異なるため、単純に異なるScoreを直接比較しないことが重要です。

---

## 33. @search.score

検索結果では、

@search.score

のようなScore情報が返ります。

Vector Searchの場合も、

検索結果のRanking用Score

として利用されます。

Cosine類似度そのものではなく、ランキング用に変換された値になる場合があります。

---

## 34. @search.rerankerScore

Semantic Rankerを使った場合、

@search.rerankerScore

が返されます。

Microsoftの現行仕様では、Semantic RankerのScoreは初期Rankingとは別のScoreとして返されます。

---

## 35. Similarity Threshold

関連度が低い検索結果を、

LLMへ渡さない

ためにThresholdを設定する考え方があります。

ただし、Vector Scoreは検索方式によって意味が異なるため、

実際のデータで評価

してThresholdを決めます。

---

## 36. Azure AI SearchとReranking

Azure AI Searchでは、

Hybrid Search  
＋  
Semantic Ranker

という構成が使えます。

例えば、

Keyword Search  
＋  
Vector Search  
→ RRF  
→ Semantic Ranker  
→ Top結果

です。

この流れによって、

広く候補取得  
→ 意味的に再評価

できます。

---

## 37. Classic RAG

Azure AI Searchの現行ドキュメントでは、

Classic RAG

という構成も説明されています。

代表的には、

Hybrid Search  
＋  
Semantic Ranking

を使って根拠を検索します。

---

## 38. Agentic Retrieval

Azure AI Searchでは、

Agentic Retrieval

という新しい検索方式も提供されています。

LLMが質問を分析して、

複数のSub Query

へ分解し、複数検索を実行する考え方です。

複雑な質問や会話型検索で利用できます。

---

## 39. Classic RAGとの違い

簡単にいうと、

### Classic RAG

アプリ側で、

Query  
→ Hybrid Search  
→ Semantic Ranker

などを制御します。

### Agentic Retrieval

LLMがQueryを分析し、

複数検索へ分解して検索

します。

まずRAGを学ぶ段階では、

**Classic RAGを理解すれば十分**

です。

## 52. 一言で理解する

Azure AI Searchとは、

**「RAGで、質問に関連するChunkを探すためのAzureの検索基盤」**

です。

RAGでは主に、

**Keyword Search + Vector Search + Metadata Filter + Ranking**

を担当します。

特にAzure OpenAIとの関係は、

**Azure OpenAI = Embeddingと回答生成**

**Azure AI Search = 根拠検索**

と覚えると分かりやすいです。

さらに、

**Keyword Search + Vector Search → RRF → Semantic Ranker**

という流れを理解すると、Azure AI Searchを使ったRAG検索の全体像がかなり見えてきます。
