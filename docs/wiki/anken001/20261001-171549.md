> Te社向けの例は学習用の想定です。実際の採用サービス・設定・権限は、既存コードと正式資料で確認してください。

# 1. 概要

Token（トークン）は、LLMが文章を処理する際の分割単位です。文字や単語と一対一ではなく、日本語、英数字、記号によって分割のされ方が違います。ここでのTokenは、認証に使うAccess Tokenとは別の概念です。

# 2. 何のために使うか

入力上限、生成量、料金を管理するために使います。Chunkの大きさやContext件数も、最終的にはToken予算と関係します。

# 3. 仕組み

Tokenizer（文章をTokenへ分割する処理）が入力を数値列へ変換します。モデルには入力と出力に関する上限があり、APIごとに指定項目も異なります。総入力を見積もる時は、根拠本文だけでなく指示、質問、履歴、メッセージの付加情報も含めます。

# 4. 具体例

学習用に総枠12,000 Token、出力予約2,000、指示と履歴3,000を仮定すると、根拠へ使える枠は最大7,000程度です。これは説明用の数値で、Te社のモデル上限ではありません。採用モデルとAPIの仕様で確認します。

# 5. 実装・設定時のポイント

- 使用モデルに対応するTokenizerで測ります。
- API応答の入力・出力使用量を記録します。
- 長い会話では履歴を選択または要約し、上限を管理します。
- 出力が上限で切れた場合の終了理由を確認します。

# 6. 注意点

文字数を一定の係数で割る見積もりは概算にとどまります。短い日本語でもTokenが多くなる場合があります。出力予約、推論用Token、キャッシュされた入力などの扱いはモデルによって異なるため、固定の料金計算を使い回さないようにします。

# 7. Te社RAG基盤で確認するポイント

入力長チェック、Context切り詰め、出力上限の引数、usage集計を確認します。SDK更新で引数名が変わっていないか、利用版の仕様と照合します。認証トークンと混同しないよう、設計書ではLLM TokenとAccess Tokenを区別します。
