# 1. 概要

OAuth 2.0は、アプリが別のサービスを利用する権限を得るための枠組みです。利用者のパスワードをAPIへ直接渡す代わりに、Access Tokenを使います。利用者のサインイン情報を伝える仕組みはOpenID Connectと区別します。

# 2. 何のために使うか

画面からRAG APIを呼ぶ委任アクセスや、Workerが利用者なしで動くアプリのみのアクセスに使います。どの主体へ、どのAPIの、どの権限を与えるかを整理します。

# 3. 仕組み

画面からのアクセスにはAuthorization Code FlowとPKCEを使う構成があります。PKCEは認可コードを横取りされた場合の悪用を防ぐ仕組みです。利用者なしのバックエンドではClient Credentialsなどを使います。[Entra IDのCode Flow](https://learn.microsoft.com/en-us/entra/identity-platform/v2-oauth2-auth-code-flow)

# 4. 具体例

Te社の想定例で画面がRAG APIの委任Scopeを要求し、取得したAccess TokenをBearerヘッダーへ送ります。取り込みWorkerは利用者のScopeを偽装せず、アプリ向け権限やManaged Identityで接続します。

# 5. 実装・設定時のポイント

- Tokenの宛先、フロー、Scope、同意主体を確認します。
- ブラウザーへClient Secretを配置しないようにします。
- stateで認可応答を要求と結び付け、PKCEを適用します。
- Tokenの保存と更新は適切な認証ライブラリで管理します。

# 6. 注意点

Graph用のAccess TokenをRAG APIへ流用してはいけません。ID TokenもAPI用Access Tokenの代わりにはなりません。Bearer Tokenは所持者が使えるため、URLやログへ漏らさないようにします。

# 7. Te社RAG基盤で確認するポイント

MSALなどの認証ライブラリ、authority、requested scopes、Code Flow、Client Credentialsを確認します。フロントエンドとバックエンドのIDを対応付けます。Token更新失敗時の再サインインとAPIの401応答も調べます。
