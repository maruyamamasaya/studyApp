# 1. 概要

Managed Identity（マネージドID）は、Azureが資格情報を管理するIdentityです。アプリへ長期のClient Secretを埋め込まず、対応サービスへEntra IDのTokenで接続できます。[公式概要](https://learn.microsoft.com/en-us/entra/identity/managed-identities-azure-resources/overview)

# 2. 何のために使うか

質問APIやWorkerから、Search、Blob、Key Vault、Azure OpenAIなどへ接続するために使います。利用者のログインと、アプリ自身のサービス接続を分けられます。

# 3. 仕組み

System-assignedはAzureリソースに結び付き、そのライフサイクルと連動します。User-assignedは独立したリソースとして複数のサービスへ割り当てられます。Identityを有効化するだけでなく、接続先のデータ操作Roleを割り当てる必要があります。

# 4. 具体例

Te社の想定例で質問APIにはSearchの読取と生成の利用権限、取り込みWorkerにはBlob読取とSearch登録、Embeddingの利用権限を付けます。両者が同じ広い権限を共有する必要があるか見直します。

# 5. 実装・設定時のポイント

- IdentityのClient IDとPrincipal IDを区別します。
- User-assignedが複数ある場合は使用対象を明示します。
- DefaultAzureCredentialが開発と本番でどの認証を選ぶか確認します。
- Roleを必要なリソースや操作へ絞ります。

# 6. 注意点

Managed Identityがあってもネットワークが到達できるとは限りません。Roleの反映には時間がかかる場合があります。開発者の強い権限で動いていても、本番Identityでは失敗する可能性があるため、実行主体をそろえて評価します。

# 7. Te社RAG基盤で確認するポイント

実行リソースのIdentity設定、SDK credential、User-assigned選択、各接続先のRole割り当てを確認します。APIキーへ暗黙に切り替える経路がないか調べます。不要Role、環境をまたぐ共有、データプレーンと管理権限の混同を確認します。
