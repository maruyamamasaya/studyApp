> Te社向けの例は学習用の想定です。実際の採用サービス・設定・権限は、既存コードと正式資料で確認してください。

# 1. 概要

RAGの認証・認可は、利用者やアプリを検証し、API操作と文書閲覧を制御する仕組みです。ログイン、API利用、文書の閲覧、Azureへの接続は、それぞれ別の判断として整理します。

# 2. 何のために使うか

権限のない質問操作、文書登録、機密資料の取得を防ぎます。RAGでは本文が検索結果、Context、回答、出典、キャッシュへ移るため、各経路に認可が必要です。

# 3. 仕組み

API入口でAccess Tokenを検証し、必要なRoleまたはScopeを確認します。検証済み利用者とグループ情報から文書条件を作り、検索時に適用します。API自身はManaged IdentityなどでAzureへ接続します。[文書のSecurity Filter](https://learn.microsoft.com/en-us/azure/search/search-security-trimming-for-azure-search)

# 4. 具体例

Te社の想定例で質問Roleがある利用者でも、人事限定文書は取得しません。引用リンクから原本を取得する際にも再認可します。文書登録APIは別のRoleで制限し、アップロード側が任意に権限を拡張できないようにします。

# 5. 実装・設定時のポイント

- Endpoint × 呼び出し主体 × 必要Role／Scopeを表にします。
- 文書ACLの取得元、更新、例外条件を定義します。
- グループ情報不足時の補完方法と失敗時の拒否を設計します。
- 権限を剥奪した後の会話履歴やキャッシュも確認します。

# 6. 注意点

検索後に機密本文をLLMへ渡し、画面でだけ隠す方式では不十分です。認可できない資料の存在や件数自体が機密になる場合もあります。失敗時に部署条件を外して再検索する処理は避けます。

# 7. Te社RAG基盤で確認するポイント

JWT middleware、Role／Scope判定、Filter生成、原本ダウンロード、会話保存、キャッシュを一続きに確認します。許可と拒否の両方を、別利用者・別部署・アプリのみのTokenで検証します。実Role名やTenantは実資材で確定します。
