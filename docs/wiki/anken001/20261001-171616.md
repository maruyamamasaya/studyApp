## 1. 概要

RAG基盤の認証・認可では、

**「誰がRAGを利用しているか」を確認し、そのユーザーが許可されたAPIと文書だけを利用できるようにする**

ことが重要です。

特に社内RAGでは、

ログインできる  
= すべての文書を検索できる

ではありません。

認証後に、

- APIを利用してよいか
    
- どの操作をしてよいか
    
- どの文書を検索してよいか
    

まで確認します。

---

# 2. 認証と認可の違い

## 2.1 Authentication

Authenticationは、

**誰なのかを確認すること**

です。

日本語では、

認証

と呼びます。

例えば、

ユーザー  
→ Microsoft Entra IDへサインイン  
→ 本人確認

という処理です。

---

## 2.2 Authorization

Authorizationは、

**認証されたユーザーが何をしてよいかを確認すること**

です。

日本語では、

認可

と呼びます。

例えば、

一般ユーザー  
→ RAGへの質問のみ可能

管理者  
→ 文書登録・削除も可能

人事部ユーザー  
→ 人事部文書を検索可能

という制御です。

---

# 3. RAGの認証・認可 全体フロー

社内RAGでは、例えば以下の流れになります。

User  
→ RAG Webアプリへアクセス  
→ Microsoft Entra IDでサインイン  
→ OpenID Connectでユーザー認証  
→ OAuth 2.0でAccess Token取得  
→ Access Tokenを付けてRAG APIを呼ぶ  
→ APIでJWTを検証  
→ Role / Scopeを確認  
→ User / Group情報を取得  
→ 文書権限をMetadata Filterへ変換  
→ Azure AI Searchで検索  
→ 許可されたChunkのみ取得  
→ Context作成  
→ Azure OpenAIへ送信  
→ Answer

重要なのは、

**権限外の情報をLLMへ渡す前に除外する**

ことです。

---

# 4. Microsoft Entra ID

Microsoft Entra IDは、

**ユーザーやアプリケーションのIdentityを管理する認証基盤**

です。

RAGでは主に、

- ユーザーログイン
    
- Group管理
    
- Role管理
    
- Token発行
    
- アプリケーション認証
    

などに利用します。

以前の名称は、

Azure Active Directory  
Azure AD

です。

---

# 5. OpenID Connect

OpenID Connectは、

**ログインしたユーザーが誰なのかをアプリへ伝える仕組み**

です。

Entra IDでログインすると、

ID Token

を利用して、

「このユーザーが誰なのか」

を確認できます。

簡単に整理すると、

OpenID Connect  
= ログイン・ユーザー認証

です。

---

# 6. OAuth 2.0

OAuth 2.0は、

**アプリケーションがAPIを利用するための権限を取得する仕組み**

です。

認証後、

Access Token

を取得します。

そのAccess Tokenを、

```
Authorization: Bearer <token>
```

としてRAG APIへ送ります。

OAuth 2.0は、

主にAPIアクセスの認可

を担当します。

---

# 7. ID TokenとAccess Token

似ていますが役割が違います。

## ID Token

**誰がログインしたか**

をClient Applicationへ伝えます。

## Access Token

**APIへアクセスするための権限**

を表します。

RAG APIを呼ぶときは、

通常Access Token

を利用します。

---

# 8. JWT

Access TokenやID Tokenには、

JWT

JSON Web Token

形式が使われることがあります。

JWTは、

Header  
Payload  
Signature

から構成されます。

Payloadには、

Claims

として、

- User ID
    
- Tenant
    
- Role
    
- Scope
    
- 有効期限
    

などが含まれる場合があります。

---

# 9. JWTの検証

APIでは、

JWTを受信しただけで信用してはいけません。

主に、

1. Signature
    
2. Issuer
    
3. Audience
    
4. Expiration
    

を確認します。

その後、

RoleやScope

を使って認可します。

---

# 10. JWT署名鍵

JWTは、

Identity Provider側の秘密鍵

で署名されます。

API側は、

公開鍵

を使って署名を検証します。

流れとしては、

JWT Headerのkid確認  
→ JWKSから対応する公開鍵取得  
→ Signature検証

となります。

---

# 11. JWKS

JWKSは、

JSON Web Key Set

の略です。

Identity Providerが公開している、

**JWT検証用の公開鍵一覧**

です。

署名鍵は更新される可能性があるため、

API側で公開鍵を永久固定するのではなく、

JWKSから取得してKey Rotationへ追従します。

---

# 12. Role

Roleは、

**ユーザーやアプリの役割**

を表します。

例えば、

- User
    
- Editor
    
- Admin
    

です。

RAGでは例えば、

User  
→ 質問

Editor  
→ 質問 + 文書登録

Admin  
→ 文書削除・管理

というAPI認可に使えます。

---

# 13. Scope

Scopeは、

**Access Tokenに許可されたAPI操作の範囲**

です。

例えば、

- rag.ask
    
- documents.read
    
- documents.write
    
- documents.delete
    

などです。

APIごとに、

必要なScopeを持っているか

を確認します。

---

# 14. RoleとScopeの違い

簡単に整理すると、

Role  
= どんな役割か

Scope  
= どんな操作が許可されているか

です。

例えば、

Role  
Editor

Scope  
documents.read  
documents.write

という状態が考えられます。

---

# 15. Group

Groupは、

**ユーザーがどの組織・グループに所属しているか**

を表します。

例えば、

- HR
    
- Finance
    
- IT
    

などです。

RAGでは、

Groupを文書閲覧権限

へ利用できます。

---

# 16. Role・Scope・Groupの使い分け

RAGでは、

### Role

アプリ内でどんな役割か。

### Scope

どのAPI操作が許可されているか。

### Group

どの文書を閲覧できるか。

と整理すると分かりやすいです。

例えば、

Role = Editor

Scope = documents.read / documents.write

Group = HR

なら、

文書登録APIを利用でき、

人事部文書を検索できる

という形です。

---

# 17. 文書単位の認可

RAGでは、

APIを使えるか

だけでは不十分です。

**どの文書を検索できるか**

まで制御します。

例えば、

Document A  
allowed_groups = All

Document B  
allowed_groups = HR

Document C  
allowed_groups = Admin

のようなMetadataを持たせます。

---

# 18. Metadata Filter

検索時に、

ユーザーのGroupやRole

を使って検索対象を絞ります。

例えば、

User Group = HR

なら、

allowed_groups contains HR

という条件で検索します。

これによって、

権限のあるChunkだけ

を取得します。

---

# 19. なぜ検索時に権限制御するのか

悪い例は、

全文書を検索  
→ 機密文書もContextへ入れる  
→ LLMへ送信  
→ 最後に画面で隠す

という方式です。

これでは、

LLMがすでに権限外情報を受け取っています。

そのため、

認証  
→ 認可  
→ Metadata Filter  
→ Search  
→ Context  
→ LLM

という順番にします。

---

# 20. ACL

文書単位で、

誰が閲覧できるか

を管理する情報を、

ACL

Access Control List

として持つことがあります。

例えば、

allowed_users  
allowed_groups

などです。

Metadata Filterと組み合わせて検索時に適用します。

---

# 21. App Registration

ユーザーだけでなく、

アプリケーション自身にもIdentity

を持たせることがあります。

Entra IDへアプリを登録する仕組みが、

App Registration

です。

ここで、

- Client ID
    
- Redirect URI
    
- Scope
    
- App Role
    

などを設定します。

---

# 22. Service Principal

Service Principalは、

**Entra ID Tenant内で実際に権限を持つアプリケーションIdentity**

です。

App Registrationされたアプリが、

Azure ResourceへアクセスするときのIdentityとして使われます。

---

# 23. Managed Identity

Azure上のアプリの場合、

Client Secretの代わりに、

Managed Identity

を利用できます。

例えば、

RAG API  
→ Managed Identity  
→ Azure AI Search

RAG API  
→ Managed Identity  
→ Azure OpenAI

Worker  
→ Managed Identity  
→ Blob Storage

という構成です。

---

# 24. Managed Identityのメリット

最大のメリットは、

**Client SecretやAPI Keyをアプリ側で保持しなくてよい**

ことです。

AzureがCredentialを管理します。

そのため、

Secret漏えい

や、

Rotation管理

を減らせます。

---

# 25. RBAC

Azure Resourceへの権限は、

RBAC

Role-Based Access Control

で制御できます。

例えば、

RAG APIのManaged Identity

に、

Azure AI Searchの検索権限だけ

を付与します。

必要以上の権限を与えない、

Least Privilege

が重要です。

---

# 26. ユーザー認証とアプリ認証

RAGでは2種類を分けて考えると分かりやすいです。

## ユーザー

User  
→ Entra ID  
→ OpenID Connect / OAuth 2.0  
→ RAG API

## アプリケーション

RAG API  
→ Managed Identity  
→ Azure AI Search / Azure OpenAI / Blob Storage

つまり、

**人にもIdentityがあり、アプリにもIdentityがある**

ということです。

---

# 27. Key Vaultとの関係

Client SecretやAPI Keyが必要な場合は、

Key Vault

で管理します。

ただし、

Managed Identityで直接認証できるなら、

そもそもSecretを持たない

ほうが安全です。

---

# 28. API側の基本処理

RAG APIでは例えば、

1. Authorization Header取得
    
2. Access Token取得
    
3. JWT署名検証
    
4. Issuer確認
    
5. Audience確認
    
6. Expiration確認
    
7. Scope確認
    
8. Role確認
    
9. User / Group取得
    
10. 文書Filter作成
    
11. Search実行
    

という流れになります。

---

# 29. 401と403

認証・認可ではよく使います。

### 401 Unauthorized

認証できない。

例えば、

- Tokenなし
    
- Token無効
    
- Token期限切れ
    

### 403 Forbidden

認証できているが権限がない。

例えば、

documents.write Scopeがない

Admin Roleがない

などです。

---

# 30. 権限変更への対応

ユーザーのGroupやRole、

文書のACL

は変更される可能性があります。

例えば、

昨日  
→ HR所属

今日  
→ HRから異動

となった場合です。

古い権限情報が、

- Token
    
- Cache
    
- Search Index
    

に残らないようにする必要があります。

---

# 31. Cacheと認可

RAGの回答や検索結果をCacheする場合、

権限情報を考慮する必要があります。

例えば、

HRユーザー向け検索結果

を、

一般ユーザーへ返してはいけません。

必要に応じて、

User / Group / Permission Scope

をCache Keyへ含めます。

---

# 32. ログ

認証・認可では、

- request_id
    
- user識別子
    
- endpoint
    
- Role
    
- Scope
    
- 認証成功 / 失敗
    
- 403発生
    
- Permission Filter
    

などを記録すると調査しやすくなります。

ただし、

- Access Token
    
- JWT全文
    
- Client Secret
    

はログへ残しません。

---

# 33. 認証・認可で重要なセキュリティ

最低限、

- HTTPSを利用
    
- JWT署名検証
    
- Issuer / Audience確認
    
- Token有効期限確認
    
- API側でRole / Scope確認
    
- 検索時に文書権限を適用
    
- Secretをコードへ書かない
    
- Managed Identityを優先
    
- 最小権限
    
- Tokenをログへ出さない
    

ことが重要です。

---

# 34. RAGで特に重要なポイント

一般的なWeb APIと比べて、RAGで特に重要なのは、

**文書検索時の認可**

です。

ログインできるユーザーでも、

検索できない文書

があります。

そのため、

User認証  
→ API認可  
→ 文書認可  
→ Search

という3段階で考えると分かりやすくなります。

---

# 35. Azure構成で見ると

例えば、

### Microsoft Entra ID

ユーザー / アプリのIdentity管理とToken発行。

### OpenID Connect

ユーザーログイン。

### OAuth 2.0

APIアクセス権の取得。

### JWT

Tokenの形式と検証。

### Role / Scope

API操作の認可。

### Group / ACL

文書閲覧範囲の決定。

### Azure AI Search

Metadata Filterによる検索時の文書認可。

### Managed Identity

Azureサービス間のアプリ認証。

### RBAC

Azure Resourceへの権限。

### Key Vault

必要なSecretの管理。

という役割分担になります。

---

# 36. 全体を一行で理解する

RAGの認証・認可は、

**Entra IDで誰かを確認し、Access TokenをAPIで検証し、Role / ScopeでAPI操作を制御し、Group / ACLで検索可能な文書を絞り込む**

仕組みです。

最終的な流れは、

**Login → Token → JWT検証 → Role / Scope → Group / ACL → Metadata Filter → Search → Context → LLM**

と覚えると分かりやすいです。
