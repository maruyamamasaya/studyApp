# 1. 概要

監視は、ログやメトリクス（件数や時間などの数値指標）から状態を把握し、必要な場合に通知や復旧を行う仕組みです。アプリの稼働だけでなく、RAGの検索・回答品質と文書更新の遅れも対象です。

# 2. 何のために使うか

利用者から連絡が来る前に障害や劣化を見つけます。サービスが200を返していても、根拠が取れない状態を検出する必要があります。

# 3. 仕組み

SLO（Service Level Objective：サービス目標）を応答成功率や応答時間に置き、測定と閾値を決めます。検索空振り率、429、Token使用量、Queue滞留、取り込み失敗、索引更新時刻を組み合わせます。[Azure Monitorの概要](https://learn.microsoft.com/en-us/azure/azure-monitor/fundamentals/overview)

# 4. 具体例

Te社の想定例でAPIの成功率は正常でも、取り込みWorkerが停止して索引が1日更新されていなければ通知します。質問の代表サンプルを定期的に検証し、最新版の根拠が見つかるか確認します。

# 5. 実装・設定時のポイント

- p95などの高い分位の遅延も測ります。
- 通知先、担当者、初動、復旧確認をRunbook（対応手順書）にします。
- トラフィックがない状態と、ログ収集停止を区別します。
- 一時的な揺れで通知を乱発しない継続条件を設けます。

# 6. 注意点

平均時間だけでは一部の極端な遅延を見落とします。ヘルスチェックが依存先を毎秒大量に呼ぶと費用と負荷が増えます。アラートを作るだけでなく、通知が届き担当者が判断できるかを検証します。

# 7. Te社RAG基盤で確認するポイント

Azure Alert、Action Group、Dashboard、計測項目、収集停止検知を確認します。検索・生成・取り込みの目標が別にあるか調べます。通知テストと障害シミュレーションの証跡、担当者の対応手順を設計書へ対応付けます。
