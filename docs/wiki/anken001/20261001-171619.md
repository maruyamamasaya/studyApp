## 1. 概要

RAG基盤の監視は、

**システムが正常に動いているかを継続的に確認し、異常が起きたときに早く検知するための仕組み**

です。

RAGでは、

Question  
→ API  
→ Search  
→ Reranking  
→ LLM  
→ Answer

と複数の処理を通るため、

「動いているか」

だけでなく、

- 遅くなっていないか
    
- エラーが増えていないか
    
- 検索結果が取れているか
    
- LLM APIが不安定でないか
    
- 文書取り込みが詰まっていないか
    

まで確認します。

---

## 2. ログとの違い

ログと監視は似ていますが、役割が少し違います。

### ログ

何が起きたかを記録する。

### 監視

現在の状態や傾向を継続的に確認し、異常を検知する。

例えば、

ログ  
→ 15:32にLLM Timeoutが発生した

監視  
→ 過去5分間でLLM Timeoutが急増している

という違いです。

---

## 3. RAG監視の主な対象

大きく分けると、

1. API
    
2. Search
    
3. LLM
    
4. 文書取り込み
    
5. Queue
    
6. インフラ
    
7. RAG品質
    

を監視します。

---

# 4. API監視

まず、

RAG API自体が正常に動いているか

を確認します。

例えば、

- Request数
    
- Success Rate
    
- Error Rate
    
- Response Time
    
- 4xx / 5xx件数
    
- Timeout数
    

などです。

---

## 5. Response Time

ユーザーが質問してから、

回答が返るまでの時間

を確認します。

例えば、

平均Response Time  
= 2.1秒

P95  
= 4.8秒

のように監視します。

---

## 6. P95 / P99

平均値だけではなく、

P95  
P99

も確認します。

例えば、

P95 = 5秒

なら、

95%のRequestが5秒以内

という意味です。

一部だけ極端に遅い処理を発見しやすくなります。

---

## 7. Error Rate

例えば、

1000 Request中  
50件失敗

なら、

Error Rate = 5%

です。

通常よりError Rateが急増した場合は、

異常としてAlertを出します。

---

# 8. Search監視

RAGでは、

検索が正常に動いているか

も重要です。

例えば、

- Search Latency
    
- 検索結果件数
    
- 0件検索率
    
- Top-K
    
- Filter適用状況
    
- Search Error
    

などを監視します。

---

## 9. 検索結果0件率

例えば、

通常は検索結果が出るのに、

0件になる質問

が急増した場合です。

原因として、

- Index更新失敗
    
- Metadata Filter不具合
    
- Embedding異常
    
- Search障害
    

などが考えられます。

---

## 10. Search Latency

Azure AI Searchなどの検索時間も監視します。

例えば、

通常  
200ms

障害時  
3秒

になっていれば、

Search側に問題がある可能性があります。

---

# 11. Embedding監視

Embeddingでは、

- Request数
    
- Latency
    
- Error Rate
    
- Retry数
    
- Token数
    
- Rate Limit
    

などを確認します。

特に大量文書取り込み時には、

429 Too Many Requests

が増えていないか注意します。

---

# 12. LLM監視

LLM部分では、

- Generation Latency
    
- Error Rate
    
- Timeout
    
- Retry
    
- Input Token
    
- Output Token
    
- Rate Limit
    

などを監視します。

RAG全体の中でも、LLMが最も時間やコストを使うことが多いため重要です。

---

## 13. Token監視

Token数が急増すると、

- コスト増加
    
- Response Time増加
    
- Context肥大化
    

につながる可能性があります。

例えば、

平均Input Token  
4000 → 12000

へ増えた場合、

Top-KやContext設計を確認します。

---

# 14. Retry監視

Retryが増えている場合、

外部サービスが不安定

な可能性があります。

例えば、

通常Retry率  
0.5%

障害時  
20%

になったら異常を疑います。

---

## 15. Timeout監視

Timeout数も重要です。

例えば、

LLM Timeout  
Search Timeout  
DB Timeout

を分けて監視します。

どの外部サービスが遅いか切り分けやすくなります。

---

## 16. Circuit Breaker監視

Circuit Breakerを利用している場合、

- Open回数
    
- Open時間
    
- Half-Open失敗
    

などを監視します。

Circuit Breaker Openは、

外部サービスが継続障害状態

である可能性を示します。

---

# 17. 文書取り込み監視

RAGでは質問処理だけでなく、

文書取り込み処理

も監視します。

例えば、

- 文書取り込み件数
    
- 成功件数
    
- 失敗件数
    
- OCR失敗
    
- Chunk生成失敗
    
- Embedding失敗
    
- Index登録失敗
    

などです。

---

## 18. 文書更新遅延

元文書が更新されたのに、

Search Indexへ反映されていない

状態にも注意します。

例えば、

Blob更新  
→ Index反映まで30分以上

になっている場合です。

この遅延を、

Index Freshness

として監視することもできます。

---

# 19. Queue監視

文書取り込みにQueueを使っている場合、

特に、

- Queue Length
    
- Processing Rate
    
- Failed Job
    
- Retry Job
    
- DLQ件数
    

を確認します。

---

## 20. Queue Length

QueueにたまっているJob数です。

例えば、

通常  
10件以下

異常時  
5000件

となっていれば、

Workerが処理に追いついていない

可能性があります。

---

## 21. Processing Rate

例えば、

1分あたり100件追加

されているのに、

Workerが1分50件しか処理できない

場合、

Queueは増え続けます。

そのため、

入力速度と処理速度

を比較します。

---

## 22. DLQ監視

Dead Letter QueueにJobが入った場合、

通常処理では回復できなかった

ことを意味します。

DLQ > 0

になったらAlertする設計もあります。

---

# 23. インフラ監視

RAG APIやWorkerが動く基盤も監視します。

例えば、

- CPU
    
- Memory
    
- Disk
    
- Network
    
- Connection数
    
- Instance数
    

などです。

---

## 24. CPU / Memory

CPUやMemoryが高騰すると、

- API遅延
    
- Worker遅延
    
- Timeout増加
    

につながります。

特にOCRやローカル処理がある場合は重要です。

---

## 25. Connection監視

DBや外部APIへのConnection数が上限に近づくと、

処理できなくなる

場合があります。

並列数を増やしたときには特に注意します。

---

# 26. Availability監視

RAG APIが、

外部から正常に利用できるか

を定期的に確認します。

例えば、

5分ごとに、

GET /health

を実行して、

200 OK

が返るか確認します。

---

## 27. Health Check

Health Check用Endpointを作ることがあります。

例えば、

```
GET /health
```

です。

ただし、

APIが起動しているだけ

では不十分な場合があります。

---

## 28. Dependency Health

より詳しく見る場合は、

- Azure AI Searchへ接続できるか
    
- Azure OpenAIへ接続できるか
    
- DBへ接続できるか
    

も確認します。

ただしHealth Checkで外部APIを毎回呼びすぎないよう注意します。

---

# 29. RAG品質の監視

RAGでは、

システムが動いている

だけでは十分ではありません。

回答品質も監視対象です。

例えば、

- 検索結果0件率
    
- 正解Chunk取得率
    
- Citation有無
    
- Hallucination率
    
- ユーザー評価
    

などです。

---

## 30. Retrieval品質

例えば定期的に評価用Queryを実行し、

正解Chunkが、

Top 1  
Top 3  
Top 5

に入るかを確認します。

検索設定変更によって品質が低下していないか検知できます。

---

## 31. Citation監視

回答に出典が必要な場合、

Citationなし回答

が増えていないか確認します。

例えば、

回答100件中  
Citationなし20件

なら、

検索やPromptに問題がある可能性があります。

---

## 32. Hallucination監視

完全自動で正確にHallucinationを検出するのは難しいですが、

- Contextに根拠があるか
    
- Citationと回答が一致するか
    
- 回答不能時に推測していないか
    

などを評価できます。

---

# 33. Alert

一定条件を超えた場合、

自動で通知します。

例えば、

Error Rate > 5%

P95 Latency > 10秒

Queue Length > 1000

Timeout > 20件 / 5分

などです。

---

## 34. Alertを増やしすぎない

Alert条件を厳しくしすぎると、

通知が大量発生

します。

これを、

Alert Fatigue

と呼びます。

本当に対応が必要なものに絞ることが重要です。

---

# 35. Dashboard

運用時に確認したい情報を、

Dashboard

へまとめます。

例えば、

- Request数
    
- Success Rate
    
- P95 Latency
    
- Search Latency
    
- LLM Latency
    
- Token数
    
- Queue Length
    
- Error数
    

です。

---

## 36. RAG監視Dashboardの例

例えば、

### API

Request / Error / Latency

### Search

Search Time / 0件率

### LLM

Latency / Token / Retry / Timeout

### Ingestion

処理件数 / Failed Job / Queue Length

### Infrastructure

CPU / Memory

という形でまとめます。

---

# 37. Application Insights

Azure環境では、

Application Insights

で、

- Request
    
- Dependency
    
- Exception
    
- Trace
    
- Latency
    

などを観測できます。

RAG APIの実行状況確認に使えます。

---

## 38. Log Analytics

Application Insightsなどから集めたログを、

Log Analytics

で検索・分析できます。

例えば、

過去1時間のTimeout

をKQLで調べます。

---

## 39. Azure Monitor

大きく見ると、

Azure Monitor

が監視全体の基盤です。

その中で、

Application Insights  
→ アプリ観測

Log Analytics  
→ ログ分析

Alerts  
→ 異常通知

Workbooks  
→ 可視化

という役割があります。

---

# 40. セキュリティ監視

RAGではセキュリティ面も監視します。

例えば、

- 401急増
    
- 403急増
    
- 不審な大量Request
    
- Rate Limit超過
    
- 認可失敗
    
- 異常な文書アクセス
    

などです。

---

## 41. 403急増

403 Forbiddenが急増した場合、

- 攻撃
    
- Role設定ミス
    
- Scope設定ミス
    
- Metadata Filter不具合
    

などが考えられます。

単なるAPI障害とは別に調査します。

---

# 42. 監視で重要な考え方

RAG監視では、

単に、

ServerがUpかDownか

だけを見るのではありません。

以下を分けて考えます。

### Availability

使えるか

### Performance

速いか

### Reliability

安定しているか

### Quality

正しい検索・回答ができているか

### Security

不正利用されていないか

---

## 43. 最低限監視したいもの

最初は以下だけでも十分です。

- API Success Rate
    
- P95 Response Time
    
- Error Rate
    
- Search Latency
    
- LLM Latency
    
- Timeout
    
- Retry
    
- Token数
    
- Queue Length
    
- 文書取り込み失敗件数
    

ここから必要に応じて増やします。

---

## 44. 一言で理解する

RAG基盤の監視とは、

**「RAGが使える・速い・安定している・正しく動いている状態を継続的に確認すること」**

です。

ログが、

**何が起きたかを記録するもの**

なら、

監視は、

**そのログやMetricを見続けて、異常を早く見つける仕組み**

です。

RAGでは特に、

**API → Search → LLM → 文書取り込み**

を分けて監視すると、問題箇所を特定しやすくなります。
