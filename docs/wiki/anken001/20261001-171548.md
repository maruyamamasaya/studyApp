> Te社向けの例は学習用の想定です。実際の採用サービス・設定・権限は、既存コードと正式資料で確認してください。

# 1. 概要

Context（コンテキスト）は、LLMが回答を作る際に参照する入力情報です。RAGでは検索した根拠本文を指すことが多いですが、広い意味では質問、指示、会話履歴も含みます。

# 2. 何のために使うか

LLMに必要な事実を与えるために使います。検索で取得した候補をそのまま全部渡すのではなく、根拠として使える情報へ整理する役割があります。

# 3. 仕組み

検索結果から重複を除き、出典を付け、Token予算の範囲で並べます。必要なら隣接Chunkを補います。資料の位置や順序によって回答が変わる場合があるため、順位だけでなく章のつながりや矛盾も考慮します。

# 4. 具体例

Te社の申請規程を想定し、「通常の締切」と「休日の例外」を併せて渡します。各本文にdocument_id、版、ページ、source_idを付け、回答の引用から元資料へ戻れるようにします。これは例であり、実フィールド名はコードで確認します。

# 5. 実装・設定時のポイント

- 指示・質問・履歴・出力用の余裕を先に確保し、残りを根拠へ割り当てます。
- 削る時は文章や表の意味を壊さない単位を使います。
- 認可済みの本文だけを入力します。
- 検索候補数と最終Context件数をログで区別します。

# 6. 注意点

関連度の低い資料が増えると、回答が混乱します。矛盾する旧版を混ぜると、LLMが都合よく統合するおそれがあります。要約を挟む場合は、元資料にない内容や重要条件の脱落を別途検査します。

# 7. Te社RAG基盤で確認するポイント

Context builderの重複除去、並べ方、切り詰め、出典付与を確認します。会話履歴の長さと、他利用者の会話が混ざらない分離も調べます。索引更新後に古いContextを再利用するキャッシュ経路がないか確認します。
