## 1. Log Analyticsとは

Log Analyticsは、

**Azure上のログや監視データを検索・分析するための仕組み**

です。

例えば、

- APIエラー
    
- Timeout
    
- Azure OpenAI呼び出し
    
- Azure AI Searchの処理
    
- Application InsightsのTelemetry
    
- Azure Resourceのログ
    

などを集めて、

「いつ、どこで、何が起きたか」

を調べるために使います。

---

## 2. Application Insightsとの違い

Application Insightsは、

**アプリケーションの動作を観測する仕組み**

です。

例えば、

- Request
    
- Dependency
    
- Exception
    
- Trace
    
- Latency
    

などを記録します。

Log Analyticsは、

**それらのログや監視データを検索・分析する場所**

と考えると分かりやすいです。

つまり、

Application Insights  
→ アプリのTelemetryを集める

Log Analytics  
→ 集めたデータを検索・分析する

という関係です。

---

## 3. Log Analytics Workspace

ログを保存・分析する単位を、

Log Analytics Workspace

と呼びます。

複数のAzure Resourceから、

同じWorkspaceへログを集約できます。

例えば、

```
RAG API
Azure OpenAI
Azure AI Search
Blob Storage
Application Insights
```

のログを、

1つのLog Analytics Workspace

へ集める構成があります。

---

## 4. なぜ集約するのか

ログが各サービスにバラバラにあると、

障害調査が大変です。

例えば、

RAG API  
→ Azure AI Search  
→ Azure OpenAI

という処理で問題が起きた場合、

同じWorkspaceにログがあれば、

1つの場所から横断的に確認できます。

---

## 5. KQL

Log Analyticsでは、

KQL

Kusto Query Language

を使ってログを検索します。

SQLに少し似ていますが、

ログ分析向けのQuery言語

です。

---

## 6. KQLの基本イメージ

例えば、

直近1時間のエラー

を調べる場合、

```
exceptions
| where timestamp > ago(1h)
```

のようなQueryを書きます。

つまり、

ログデータ  
→ 条件で絞る  
→ 集計する  
→ 並べる

といった分析ができます。

---

## 7. where

whereは、

条件でログを絞り込む

ときに使います。

例えば、

```
requests
| where success == false
```

なら、

失敗したRequestだけ

を表示します。

---

## 8. project

表示したいColumnだけを選ぶときに使います。

例えば、

```
requests
| project timestamp, name, duration, resultCode
```

です。

必要な情報だけ見やすくできます。

---

## 9. order by

ログを並び替えます。

例えば、

```
requests
| order by timestamp desc
```

なら、

新しいログから順に表示します。

---

## 10. summarize

ログを集計するときに使います。

例えば、

```
requests
| summarize count() by resultCode
```

なら、

Status Codeごとの件数

を確認できます。

---

## 11. RAGで見るログ

RAGでは例えば、

- API Request
    
- Search処理
    
- Embedding処理
    
- Reranking処理
    
- LLM生成
    
- Timeout
    
- Retry
    
- Exception
    
- Token数
    

などを分析できます。

---

## 12. APIエラーを調べる

例えば、

500 Errorが増えた

場合です。

KQLで、

```
requests
| where resultCode == "500"
```

のように絞ります。

その時間帯のExceptionやDependencyも確認します。

---

## 13. 遅いRequestを調べる

例えば、

5秒以上かかったAPI

を探す場合、

```
requests
| where duration > 5s
```

のように検索できます。

RAG APIの遅延原因調査に使えます。

---

## 14. Azure OpenAIの遅延を見る

DependencyとしてAzure OpenAI呼び出しが記録されていれば、

Azure OpenAI関連のDependencyだけ絞り、

処理時間を確認できます。

例えば、

```
dependencies
| where name contains "OpenAI"
| order by duration desc
```

です。

---

## 15. Azure AI Searchの遅延を見る

同じように、

Search関連Dependency

を確認できます。

これによって、

RAG全体が遅いのか

Searchだけ遅いのか

を切り分けられます。

---

## 16. Trace IDで追跡する

1回のRAG処理を、

Trace ID

で追うことができます。

例えば、

Question  
→ Search  
→ LLM  
→ Answer

のログに同じTrace IDを持たせます。

Log AnalyticsでそのIDを検索すれば、

1回の処理全体

を追跡できます。

---

## 17. Request IDで追跡する

API側で、

request_id

を発行している場合も同様です。

例えば、

```
request_id = req-12345
```

で検索します。

障害問い合わせ時に便利です。

---

## 18. Token数の分析

RAGでは、

Input Token  
Output Token

をログに持たせることがあります。

例えば、

質問ごとのToken数

を集計して、

Contextが大きすぎないか

を確認できます。

---

## 19. Top-Kの分析

検索ログに、

top_k

を持たせておけば、

Top-K変更前後で、

- Latency
    
- Token数
    
- 回答品質
    

の変化を比較できます。

---

## 20. Retry回数を見る

例えば、

LLM APIのRetryが急増

している場合です。

ログにretry_countを記録しておけば、

```
traces
| where retry_count > 0
```

のように確認できます。

---

## 21. Timeout数を見る

Timeoutが増えている場合、

- Azure OpenAI
    
- Azure AI Search
    
- DB
    

のどこで発生しているかを調べます。

ログを集約しておくと比較しやすくなります。

---

## 22. Queueの分析

文書取り込みでQueueを使っている場合、

- queued
    
- processing
    
- completed
    
- failed
    
- retry_count
    

などをログへ出せます。

これをLog Analyticsで集計すれば、

処理詰まり

を確認できます。

---

## 23. DLQの監視

Dead Letter Queueへ送られたJob数も、

ログやMetricとして確認できます。

例えば、

DLQ > 0

になったらAlert

という運用ができます。

---

## 24. Alertとの関係

Log AnalyticsのQuery結果を使って、

Alert

を作れます。

例えば、

過去5分で500 Errorが10件以上

なら通知する、

という設定です。

---

## 25. Dashboardとの関係

Log AnalyticsのQuery結果を、

DashboardやWorkbook

へ表示できます。

例えば、

- Request数
    
- Error Rate
    
- P95 Latency
    
- Token数
    
- Timeout数
    

を1画面で確認できます。

---

## 26. Workbook

Azure Monitor Workbookを使うと、

複数のKQL Queryを組み合わせて、

運用ダッシュボード

を作れます。

RAG専用の監視画面を作ることもできます。

---

## 27. ログ保存期間

Log Analytics Workspaceでは、

ログの保持期間

を設定します。

長く保持すると、

調査には便利

ですが、

ストレージコスト

も増えます。

そのため要件に合わせて決めます。

---

## 28. ログ量とコスト

大量のログをすべて送ると、

Log Analyticsの取り込み量が増えます。

例えば、

Prompt全文  
Context全文  
LLM回答全文

を毎回保存すると、

データ量が大きくなります。

そのため、

必要なTelemetryだけ

を記録することが重要です。

---

## 29. 機密情報に注意

RAGでは、

検索した社内文書

がContextに含まれます。

そのため、

- Prompt全文
    
- Context全文
    
- ユーザー質問
    
- LLM回答
    

を無条件にログへ保存すると、

機密情報がLog Analyticsへ蓄積

される可能性があります。

---

## 30. ログに残しやすい情報

例えば、

- request_id
    
- trace_id
    
- document_id
    
- chunk_id
    
- top_k
    
- latency
    
- token_count
    
- status
    
- error_type
    

などです。

全文ではなくID中心にすると安全性を高めやすくなります。

---

## 31. Application InsightsとLog Analyticsの流れ

イメージとしては、

```
RAG Application
→ Application Insights
→ Log Analytics Workspace
→ KQLで検索・分析
```

となります。

Application Insightsで取得したTelemetryを、

Log Analytics上でQuery

する構成が一般的です。

---

## 32. Azure Monitorとの関係

大きく見ると、

Azure Monitor

の中に、

- Application Insights
    
- Log Analytics
    
- Alerts
    
- Metrics
    
- Workbooks
    

などがあります。

つまり、

Azure Monitor  
→ 監視全体

Application Insights  
→ アプリ観測

Log Analytics  
→ ログ検索・分析

という関係です。

---

## 33. RAGでの典型的な調査

例えば、

「回答が遅い」

という問い合わせが来た場合、

1. Request Latencyを確認
    
2. Search Dependencyを確認
    
3. LLM Dependencyを確認
    
4. Retry / Timeoutを確認
    
5. Token数を確認
    

という流れで調査できます。

---

## 34. RAGでの典型的な障害調査

例えば、

「回答できない」

場合は、

1. API Error確認
    
2. Search結果件数確認
    
3. Azure AI Search Error確認
    
4. Azure OpenAI Error確認
    
5. Timeout / Retry確認
    
6. Trace IDで全処理追跡
    

という流れです。

---

## 35. 一言で理解する

Log Analyticsとは、

**「Azureに集めたログを、KQLを使って検索・集計・分析するための場所」**

です。

Application Insightsが、

**アプリの動作を記録する**

役割なら、

Log Analyticsは、

**その記録を調べる**

役割です。

覚え方としては、

**Application Insights = 観測**

**Log Analytics = 調査**

で理解すると分かりやすいです。
