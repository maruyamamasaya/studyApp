# 1. 概要

Log Analyticsは、Azure Monitorへ集めたログをKQL（Kusto Query Language：ログ検索・集計用の言語）で分析するための機能です。Workspaceはログの保存・管理単位です。[公式概要](https://learn.microsoft.com/en-us/azure/azure-monitor/logs/log-analytics-overview)

# 2. 何のために使うか

RAG APIの失敗傾向、応答時間、外部依存の429、取り込み失敗を集計し、運用上の問題を発見します。個別要求の調査だけでなく、期間内の傾向を見る役割があります。

# 3. 仕組み

テーブルを選び、期間を絞り、条件で抽出し、summarizeで集計します。テーブルや列名は収集方式によって違います。WorkspaceではAppRequestsなど、別の参照画面ではrequestsなどが使われる場合があります。

# 4. 具体例

次のKQLはWorkspaceのAppRequestsテーブルがある構成の学習用例です。過去1時間の要求数、失敗数、応答時間の95パーセンタイルを5分単位で集計します。95パーセンタイルは、95%の要求がその時間以下になる指標です。

~~~kusto
AppRequests
| where TimeGenerated > ago(1h)
| summarize requests=sum(ItemCount),
    failures=sumif(ItemCount, Success == false),
    p95_ms=percentile(DurationMs, 95) by bin(TimeGenerated, 5m)
~~~

Te社の実Workspaceでは、最初にテーブルと列の存在を確認して読み替えます。サンプリングがある場合、分位値は収集されたデータの指標として扱います。

# 5. 実装・設定時のポイント

- TimeGeneratedの時刻表示と調査期間を確認します。
- Trace ID、処理ID、サービス名を条件に使います。
- ログ量、保持、アクセス制御を設計します。
- よく使う調査クエリと障害対応手順を保存します。

# 6. 注意点

収集設定がなければ、必要なデータは自動的に集まりません。表の空欄と正常動作を混同しないようにします。長期間の全件検索は費用や応答時間が増えるため、期間と列を絞ります。

# 7. Te社RAG基盤で確認するポイント

診断設定の送信先、テーブル、保持、収集遅延、利用権限を確認します。質問APIとAzureリソースのログを同じ要求へ結び付けられるか調べます。アラートクエリが現行Schemaに合っているかも確認します。
