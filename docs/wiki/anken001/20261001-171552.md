# 1. 概要

API（Application Programming Interface）は、ソフトウェア間で処理やデータをやり取りする取り決めです。Web APIでは、URL、HTTPメソッド、ヘッダー、本文、応答形式を決めます。

# 2. 何のために使うか

RAGの画面から質問を受け付けたり、文書取り込みを依頼したり、外部の検索・生成サービスを呼んだりするために使います。呼び出す側と提供する側で同じ契約を共有します。

# 3. 仕組み

APIの入口で入力形式と認証を検証し、権限を判定して業務処理を呼びます。処理結果をHTTPステータスと本文へ変換します。OpenAPIは、この入出力契約を記述する代表的な形式です。

# 4. 具体例

Te社の学習用例として、POST /questionsに質問を送り、回答と出典一覧を返すAPIを考えます。文書取り込みはPOST /ingestionsで受け付け、202と処理IDを返し、別のGETで完了状態を確認する設計もあります。実際のパスは既存コードから確認します。

# 5. 実装・設定時のポイント

- 質問長、必須項目、未知の項目、ファイル容量を検証します。
- 401は認証が不足・無効な場合、403は権限不足などを表します。
- エラー本文には利用者向けの理由と追跡IDを付けます。
- APIの版変更、互換性、ストリーム形式を定義します。

# 6. 注意点

画面で非表示にするだけではAPIの認可になりません。GETのパラメーターへ機密の質問やトークンを入れるとログへ残りやすくなります。詳細な内部例外や接続先情報をそのままエラー本文へ返さないようにします。

# 7. Te社RAG基盤で確認するポイント

ルート定義、入力モデル、認証依存、認可関数、エラー変換を確認します。OpenAPIと実際の返却値を照合し、詳細設計書のAPI項目へ対応付けます。成功・入力不正・認証失敗・権限不足・外部障害を代表ケースとして確認します。
