## 1. JWTとは

JWTは、

JSON Web Token

の略です。

一般には、

**ユーザーやアプリケーションに関する情報を、署名付きのTokenとして安全に受け渡すための形式**

として使われます。

OAuth 2.0やOpenID Connectでは、Access TokenやID TokenがJWT形式になることがあります。

---

## 2. JWTの読み方

JWTは、

「ジョット」

または、

「ジェイ・ダブリュー・ティー」

と読まれます。

実務では「JWT」とそのまま呼ぶことも多いです。

---

## 3. JWTの基本構造

JWTは通常、

3つの部分

で構成されています。

```
Header.Payload.Signature
```

それぞれ、

- Header
    
- Payload
    
- Signature
    

です。

3つの部分は、

`.`

で区切られています。

---

## 4. Header

Headerには、

Tokenの種類や署名方式

などが入ります。

例えば、

```
{
  "alg": "RS256",
  "typ": "JWT"
}
```

です。

ここでは、

alg  
= 署名アルゴリズム

typ  
= Tokenの種類

を表します。

---

## 5. Payload

Payloadには、

Claims

と呼ばれる情報が入ります。

例えば、

```
{
  "sub": "user123",
  "role": "admin",
  "exp": 1790000000
}
```

です。

ここには、

- User ID
    
- Role
    
- Tenant
    
- Scope
    
- 有効期限
    

などが入る場合があります。

---

## 6. Signature

Signatureは、

**JWTが途中で改ざんされていないことを確認するための署名**

です。

HeaderとPayloadをもとに、

秘密鍵などを使って署名を作ります。

受け取った側は、

公開鍵などを使ってSignatureを検証します。

---

## 7. JWTは暗号化されているわけではない

重要です。

JWTのPayloadは、

通常は暗号化されていません。

Base64URL形式でエンコードされているだけなので、

中身は読むことができます。

つまり、

**JWTにPasswordやAPI Keyなどの秘密情報を入れてはいけません。**

---

## 8. Base64URL

HeaderとPayloadは、

Base64URL

という形式でエンコードされます。

例えば、

JSON  
→ Base64URL

に変換されます。

ただし、

Base64URLは暗号化ではありません。

誰でもDecodeできます。

---

## 9. JWTの目的

JWTの目的は、

中身を隠すこと

ではなく、

**中身が改ざんされていないことを検証できるようにすること**

です。

ここでSignatureが重要になります。

---

## 10. Claims

JWTのPayloadに入る情報を、

Claims

と呼びます。

代表的なClaimsとして、

- sub
    
- iss
    
- aud
    
- exp
    
- nbf
    
- iat
    
- roles
    
- scp
    

などがあります。

---

## 11. sub

subは、

Subject

の略です。

Tokenの対象となるユーザーやIdentityを表します。

例えば、

user123

などです。

---

## 12. iss

issは、

Issuer

です。

JWTを、

誰が発行したか

を表します。

例えば、

Microsoft Entra ID

などです。

API側では、

信頼しているIssuerか

を確認します。

---

## 13. aud

audは、

Audience

です。

このTokenが、

どのAPIやApplication向けに発行されたか

を表します。

例えば、

RAG API向けAccess Token

なら、

RAG API側でAudienceを確認します。

---

## 14. exp

expは、

Expiration Time

です。

Tokenの有効期限を表します。

API側では、

期限切れToken

を拒否します。

---

## 15. nbf

nbfは、

Not Before

です。

指定された時刻より前は、

そのTokenを使用できません。

---

## 16. iat

iatは、

Issued At

です。

Tokenが発行された時刻を表します。

---

## 17. roles

アプリケーションRoleなどが入ることがあります。

例えば、

```
Admin
User
Manager
```

などです。

API側の認可処理に利用できます。

---

## 18. scp

Microsoft系のAccess Tokenでは、

scp

にScope情報が入る場合があります。

例えば、

```
documents.read
rag.ask
```

などです。

API側で、

必要なScopeを持っているか

を確認します。

---

## 19. JWT署名

JWTのSignatureは、

Header  
＋  
Payload

から作られます。

例えば概念的には、

```
sign(
    encoded_header + "." + encoded_payload,
    private_key
)
```

という形です。

実際の処理は使用する署名アルゴリズムによって異なります。

---

## 20. RS256

JWTでよく使われる署名方式の1つが、

RS256

です。

RSA秘密鍵で署名し、

RSA公開鍵で検証します。

つまり、

発行側  
→ Private Key

検証側  
→ Public Key

という構成です。

---

## 21. Private Key

Private Keyは、

秘密鍵

です。

Tokenを署名する側だけが保持します。

外部へ公開してはいけません。

---

## 22. Public Key

Public Keyは、

公開鍵

です。

JWTの署名検証に利用します。

公開されても問題ありません。

API側は公開鍵を取得して、

Tokenが正しいIssuerによって署名されたか

を確認します。

---

## 23. なぜ公開鍵で検証できるのか

公開鍵暗号では、

秘密鍵で作った署名を、

対応する公開鍵で検証できます。

そのため、

API側が秘密鍵を持つ必要はありません。

これは非常に重要です。

---

## 24. JWTの検証

JWTを受け取ったAPIは、

単にPayloadを読むだけでは不十分です。

主に以下を確認します。

1. Signature
    
2. Issuer
    
3. Audience
    
4. Expiration
    
5. 必要なRole / Scope
    

---

## 25. Signature検証

まず、

JWTが改ざんされていないか

を確認します。

例えばPayloadの、

```
role = user
```

を、

```
role = admin
```

へ勝手に変更すると、

Signatureが一致しなくなります。

そのため改ざんを検出できます。

---

## 26. Payloadだけ信用してはいけない

JWTは簡単にDecodeできます。

そのため、

```
payload = decode_without_verification(token)
```

のように、

署名検証なしで中身だけ見て認可判断

するのは危険です。

必ずSignatureを検証します。

---

## 27. JWKS

JWTの公開鍵を配布する仕組みとして、

JWKS

JSON Web Key Set

があります。

Identity Providerは、

公開鍵情報

をJWKS Endpointで公開します。

API側はそこから公開鍵を取得します。

---

## 28. kid

JWT Headerには、

kid

Key ID

が入る場合があります。

例えば、

```
{
  "alg": "RS256",
  "kid": "abc123"
}
```

です。

API側はkidを使って、

どの公開鍵でSignatureを検証するか

を判断します。

---

## 29. Key Rotation

Identity Providerは、

署名用Keyを変更する場合があります。

これを、

Key Rotation

と呼びます。

そのためAPI側では、

公開鍵をコードへ固定

するのではなく、

JWKSなどから取得

する方式が使われます。

---

## 30. Entra IDとの関係

Microsoft Entra IDは、

Access TokenやID Token

を発行します。

アプリやAPIは、

Entra IDが公開している公開鍵情報

を使って署名を検証します。

---

## 31. OpenID Connectとの関係

OpenID Connectでは、

ID Token

がJWT形式で発行されることがあります。

アプリ側は、

ID Tokenを検証して、

ログインしたユーザー情報

を確認します。

---

## 32. OAuth 2.0との関係

OAuth 2.0では、

Access Token

を使ってAPIへアクセスします。

Access TokenがJWT形式の場合、

API側でJWTを検証します。

つまり、

OAuth 2.0  
= Tokenを取得・利用する仕組み

JWT  
= Tokenの形式の1つ

です。

---

## 33. ID TokenとAccess Token

どちらもJWT形式になることがありますが、

目的が違います。

### ID Token

ログインしたユーザー情報をClientへ伝える。

### Access Token

APIアクセス権をAPIへ伝える。

用途を混同しないことが重要です。

---

## 34. Python APIでのイメージ

概念的には、

```
token = get_bearer_token(request)

claims = verify_jwt(
    token=token,
    issuer=EXPECTED_ISSUER,
    audience=EXPECTED_AUDIENCE,
)
```

のように、

検証済みClaims

を取得します。

実際には認証ライブラリを利用することが一般的です。

---

## 35. JWTを自前で検証しすぎない

署名アルゴリズムやKey Rotationなど、

認証処理には注意点が多くあります。

そのため、

認証ライブラリ

や、

Frameworkの認証Middleware

を利用するほうが安全です。

---

## 36. API認証の流れ

例えば、

User  
→ Entra ID Login

→ Access Token取得

→ RAG API

→ JWT署名検証

→ Issuer確認

→ Audience確認

→ Expiration確認

→ Scope / Role確認

→ API処理

となります。

---

## 37. RAGとの関係

例えば社内RAGでは、

JWT検証

によってユーザーを確認し、

Claimsから、

- User ID
    
- Group
    
- Role
    
- Scope
    

などを取得します。

その後、

Metadata Filter

へつなげます。

---

## 38. JWTから文書権限へつなげる例

例えば、

JWT Claims:

```
user_id = U001
role = employee
group = HR
```

なら、

Azure AI Searchで、

```
allowed_groups contains "HR"
```

のようなFilterを作ります。

つまり、

JWT検証  
→ User情報  
→ Permission Filter  
→ Search

という流れです。

---

## 39. JWTだけで認可を完結しない場合

JWTにすべての文書権限を入れるとは限りません。

例えば、

JWTからUser ID取得

→ DBやDirectoryからGroup取得

→ 文書権限判定

とすることもあります。

Tokenを巨大化させないためです。

---

## 40. Tokenの有効期限が必要な理由

Access Tokenが盗まれた場合でも、

有効期限が短ければ、

悪用できる時間を限定できます。

そのためJWTには、

exp

が重要です。

---

## 41. JWTをログへ出さない

JWTには、

- User情報
    
- Role
    
- Scope
    

などが含まれます。

さらにAccess Token自体が認証情報です。

そのため、

JWT全文をログへ出力しない

ことが重要です。

---

## 42. HTTPSも必要

JWTに署名があっても、

通信中にTokenを盗まれる可能性

は別問題です。

そのため、

JWTはHTTPS通信

と組み合わせて利用します。

---

## 43. JWTでよくある誤解

### JWTは暗号化されている

通常は違います。

### JWTは中身を読めない

Base64URL Decodeすれば読めます。

### JWTがあれば信用してよい

SignatureやIssuerなどの検証が必要です。

### JWT = OAuth 2.0

JWTはToken形式、OAuth 2.0は認可の仕組みです。

---

## 44. JWT検証で重要なポイント

最低限、

- Signature
    
- iss
    
- aud
    
- exp
    

を確認します。

そのうえで、

- Role
    
- Scope
    
- Tenant
    

などを認可処理で利用します。

---

## 45. 署名検証と認可は別

JWTのSignatureが正しい

ということは、

「正しい発行元から発行されたToken」

という意味です。

しかし、

そのユーザーが管理者操作をしてよい

とは限りません。

その後、

Role / Scope

を確認する必要があります。

---

## 46. RAG全体での位置

例えば、

User  
→ Entra ID

→ Access Token

→ RAG API

→ **JWT検証**

→ User / Role / Scope取得

→ Metadata Filter

→ Azure AI Search

→ Azure OpenAI

という流れになります。

---

## 47. 一言で理解する

JWTとは、

**「ユーザーや権限情報を含み、改ざんを検出できる署名付きToken形式」**

です。

重要なのは、

**JWTは暗号化ではなく署名**

という点です。

覚え方としては、

**Header = Tokenの情報**

**Payload = Claims**

**Signature = 改ざん確認**

そして、

**署名 → Issuer → Audience → Expiration → Role / Scope**

の順で確認する、

と理解すると分かりやすいです。
