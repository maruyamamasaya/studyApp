# 1. 概要

JWT（JSON Web Token）は、情報をJSONで表すトークン形式です。一般的な署名付き形式は、Header、Payload、Signatureの3部分をピリオドで連結します。Claim（クレーム）はPayloadに入る属性です。

# 2. 何のために使うか

Entra IDが発行したAccess Tokenの利用者、宛先、有効期限、権限などをAPIが検証する場面で使います。JWT形式であるだけでは、その内容を信用できません。

# 3. 仕組み

Headerにalg（署名方式）やkid（鍵の識別子）、Payloadにiss、aud、expなどが入ります。APIは信頼する発行者の鍵で署名を検証し、発行者、宛先、有効期限、必要な主体・権限を確認します。文字列をデコードするだけでは検証になりません。[JWTのセキュリティ指針](https://www.rfc-editor.org/rfc/rfc8725.html)

# 4. 具体例

Te社の学習用例で、issが許可Tenant、audがRAG API、expが有効期間内であることを確認してからrolesやscpを読みます。権限の判断は署名などの検証後に行います。Claimの存在と形式はToken版・フローによって確認します。

# 5. 実装・設定時のポイント

- 許可アルゴリズムをサーバー側で固定します。
- 必須Claimと許可Issuer・Audienceを設定します。
- expやnbf（有効開始）に小さな時計ずれ許容を設けます。
- JWTライブラリの検証を無効化しないようにします。

# 6. 注意点

署名付きJWTのPayloadは通常暗号化されておらず、読めます。機密情報を入れてよいとは限りません。トークンが期限内でも、利用者の権限変更が即時反映されない場合があります。ログへToken全文を残さないようにします。

# 7. Te社RAG基盤で確認するポイント

decode関数の検証オプション、鍵取得、Issuer、Audience、Tenant制限、期限、Role／Scope判定を確認します。署名不正、別Audience、期限切れ、未知kid、ID Tokenの誤使用を拒否するテストを確認します。
