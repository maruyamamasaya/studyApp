# 1. 概要

Scope（スコープ）は、OAuthで要求・付与するアクセス権の範囲です。Entra IDの委任アクセスでは、利用者の代わりにアプリがAPIを使う権限を表すScopeがAccess Tokenのscp Claimへ入る構成があります。

# 2. 何のために使うか

利用者が操作する画面からRAG APIを呼ぶ権限を分けるために使います。文書の部署権限やAzure RBACのScopeという用語とは、文脈を区別します。

# 3. 仕組み

APIが委任Scopeを公開し、クライアントがその権限を要求して同意を得ます。APIはToken検証後、scpを空白区切りの値として扱い、必要なScopeの完全一致を確認します。Client Credentialsでは通常scpではなくアプリ権限を使います。[公式説明](https://learn.microsoft.com/en-us/entra/identity-platform/scopes-oidc)

# 4. 具体例

Te社の学習用例でRag.Queryという委任Scopeを質問APIへ要求します。実際に要求する識別子にはAPIの識別URIなどが付きます。名前は仮なので、公開Scopeとクライアント設定を確認します。

# 5. 実装・設定時のポイント

- 要求したScopeと付与されたScopeを分けて考えます。
- scpへ部分文字列が含まれるだけの判定を避けます。
- .defaultは対象APIに設定済みの権限を要求する形式で、無制限の権限ではありません。
- openidやprofileは、RAG APIの質問操作を許可するScopeではありません。

# 6. 注意点

アプリがScopeを持っていても、利用者がすべての文書を閲覧できるわけではありません。Roleを持つアプリのみのTokenでscpがないことは、必ずしもToken不正を意味しません。許可するフローをEndpoint単位で明示します。

# 7. Te社RAG基盤で確認するポイント

Expose an APIのScope定義、MSALの要求Scope、同意、scp検証を照合します。Client Credentialsに委任Scopeを要求していないか確認します。Scope不足、別API向けToken、部分一致する偽のScopeを拒否するかテストします。
