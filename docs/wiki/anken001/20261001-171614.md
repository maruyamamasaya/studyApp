## 1. Scopeとは

Scope（スコープ）は、

**Access Tokenに与えられたAPI操作の権限範囲**

です。

OAuth 2.0でよく使われます。

例えば、

- rag.read
    
- documents.read
    
- documents.write
    

のように、

「このTokenで何をしてよいか」

を表します。

---

## 2. 基本イメージ

例えばユーザーがRAGアプリへログインし、

Access Tokenを取得したとします。

そのTokenに、

```
rag.read
documents.read
```

というScopeが付いていれば、

- RAGへ質問する
    
- 文書を読む
    

ことは許可できます。

一方、

documents.write

がなければ、

文書登録APIは拒否できます。

---

## 3. Scopeはどこで使うのか

基本的には、

API側

で確認します。

流れは、

User  
→ Access Token取得  
→ APIへToken送信  
→ JWT検証  
→ Scope確認  
→ API処理

です。

---

## 4. 具体例

例えば以下のAPIがあるとします。

```
POST /ask
GET /documents
POST /documents
DELETE /documents/{id}
```

必要Scopeを、

```
POST /ask
→ rag.read

GET /documents
→ documents.read

POST /documents
→ documents.write

DELETE /documents/{id}
→ documents.delete
```

のように決められます。

---

## 5. Access Tokenとの関係

Scopeは、

Access Token

に含まれます。

例えばTokenのClaimsに、

```
scp = "rag.read documents.read"
```

のように入る場合があります。

API側はこの値を見て、

必要なScopeがあるか

を確認します。

---

## 6. JWTとの関係

Access TokenがJWT形式の場合、

Payload内のClaimsからScopeを取得します。

例えば、

```
{
  "scp": "rag.read documents.read"
}
```

です。

ただし、

JWTの中身を読むだけでは不十分です。

先に、

- Signature
    
- Issuer
    
- Audience
    
- Expiration
    

を検証してからScopeを利用します。

---

## 7. Roleとの違い

ScopeとRoleは似ていますが、考え方が違います。

### Scope

**何の操作が許可されているか**

例：

- documents.read
    
- documents.write
    

### Role

**どんな役割なのか**

例：

- User
    
- Editor
    
- Admin
    

です。

---

## 8. RoleとScopeの例

例えば、

Role:

```
Editor
```

Scope:

```
documents.read
documents.write
```

という状態が考えられます。

Roleはユーザーの役割、

ScopeはTokenが持つ具体的なAPI権限

と考えると分かりやすいです。

---

## 9. Scopeは委任アクセスでよく使う

Scopeは特に、

**ユーザーの代わりにアプリがAPIへアクセスする**

Delegated Permission

でよく使われます。

例えば、

User  
→ RAG Webアプリ

→ Access Token取得

→ RAG WebアプリがUserの代わりにAPI呼び出し

という構成です。

---

## 10. Delegated Permission

Delegated Permissionは、

**ログインユーザーの権限を使ってアプリがAPIへアクセスする方式**

です。

つまり、

User  
＋  
Application

の組み合わせでAPIアクセスします。

Scopeはこの権限範囲を表します。

---

## 11. Application Permissionとの違い

ユーザーなしで、

アプリケーション自身がAPIへアクセスする

場合があります。

例えば、

Batch Worker  
→ API

です。

この場合は、

Application Permission

やApp Role

を使う構成があります。

つまり、

Scope  
→ ユーザー委任アクセスでよく使う

App Role  
→ アプリ単体アクセスでも使う

と整理すると分かりやすいです。

---

## 12. Entra IDとの関係

Microsoft Entra IDでは、

API側でScopeを定義できます。

例えば、

```
rag.read
documents.read
documents.write
```

です。

Client Applicationは必要なScopeを要求し、

Entra IDからAccess Tokenを取得します。

---

## 13. Consent

ClientがScopeを要求すると、

その権限を許可してよいか

をユーザーや管理者が承認する場合があります。

これを、

Consent

と呼びます。

例えば、

```
このアプリに documents.read を許可しますか？
```

というイメージです。

---

## 14. Admin Consent

強いScopeや組織全体へ影響する権限では、

管理者承認

が必要になることがあります。

これを、

Admin Consent

と呼びます。

---

## 15. Scopeは必要最小限にする

例えば、

文書を読むだけのアプリ

に、

documents.write

documents.delete

まで与える必要はありません。

必要なScopeだけを要求します。

これを、

Least Privilege

最小権限

と考えます。

---

## 16. Scope確認のイメージ

API側では概念的に、

```
required_scope = "documents.write"

if required_scope not in user_scopes:
    raise PermissionError("Forbidden")
```

のように確認します。

Frameworkの認証機能へ組み込むこともあります。

---

## 17. Scope不足時

認証は成功していても、

必要なScopeを持っていない場合は、

403 Forbidden

を返すことが一般的です。

例えば、

documents.read

しかないTokenで、

POST /documents

を呼ぶ場合です。

---

## 18. 401との違い

401 Unauthorized

→ Tokenがない、無効、期限切れなど

403 Forbidden

→ Tokenは有効だが必要なScopeがない

という違いです。

---

## 19. ScopeとUI

Web画面側で、

documents.writeがなければ、

「文書登録」ボタンを非表示

にすることもできます。

ただし、

**本当の権限制御はAPI側で行う**

必要があります。

UIだけ隠しても、APIを直接呼ばれる可能性があります。

---

## 20. ScopeとMetadata Filterは役割が違う

Scopeは、

API操作を制御

します。

Metadata Filterは、

どの文書を検索できるか

を制御します。

例えば、

documents.read  
→ 文書検索APIを使ってよい

HR Group  
→ 人事文書を検索してよい

という違いです。

---

## 21. RAGでの例

例えば、

Access Token:

```
scp = rag.read documents.read
```

User Group:

```
HR
```

の場合、

rag.read  
→ RAG質問APIを利用可能

documents.read  
→ 文書閲覧APIを利用可能

HR  
→ HR文書を検索可能

という形で使い分けます。

---

## 22. Scopeだけで文書権限を管理しない

例えば、

documents.read

というScopeを持っているからといって、

全社のすべての文書を読める

とは限りません。

Scopeは、

「文書閲覧機能を使ってよい」

という操作権限です。

実際の文書範囲は、

- Group
    
- Role
    
- ACL
    
- Metadata Filter
    

などで別に制御します。

---

## 23. Scopeの粒度

Scopeは細かくしすぎると管理が大変です。

例えば、

```
document1.read
document2.read
document3.read
```

のように文書単位で作るより、

```
documents.read
documents.write
```

程度にAPI操作単位で作り、

文書単位の権限はMetadataやACLで管理する

ほうが整理しやすい場合があります。

---

## 24. Scope設計例

RAGなら例えば、

```
rag.ask
documents.read
documents.write
documents.delete
admin.settings
```

のように、

機能単位

で定義できます。

---

## 25. ScopeとTokenの有効期限

ScopeはAccess Token発行時に入ります。

そのため、

権限変更後も、

古いAccess Tokenが有効期限内

なら古いScopeが残る場合があります。

そのため、

Token Lifetime

も権限制御設計に関係します。

---

## 26. Scopeのログ

認可エラー調査のために、

- endpoint
    
- required_scope
    
- granted_scopes
    
- result
    

などを記録すると便利です。

ただし、

Access Token全文

はログへ残さないようにします。

---

## 27. RAG認証・認可フローでの位置

全体としては、

User  
→ Entra ID Login

→ OAuth 2.0

→ Access Token取得

→ RAG API

→ JWT検証

→ **Scope確認**

→ Role / Group確認

→ Metadata Filter

→ Azure AI Search

→ Azure OpenAI

という流れです。

---

## 28. Role・Scope・Groupの整理

覚えるなら、以下で十分です。

### Role

**どんな役割か**

例：

Admin  
Editor  
User

### Scope

**どのAPI操作が許可されているか**

例：

documents.read  
documents.write

### Group

**どこに所属しているか**

例：

HR  
Finance  
IT

RAGでは、

Role / Scope  
→ API操作制御

Group / ACL / Metadata  
→ 文書アクセス制御

と整理すると分かりやすいです。

---

## 29. 一言で理解する

Scopeとは、

**「Access Tokenで許可されているAPI操作の範囲」**

です。

特にOAuth 2.0のDelegated Accessでよく使われます。

覚え方としては、

**Role = 役割**

**Scope = できる操作**

**Group = 所属**

です。

RAGでは、

**ScopeでAPIを使えるか確認し、その後GroupやMetadata Filterで読める文書を絞る**

という流れで理解すると分かりやすいです。
