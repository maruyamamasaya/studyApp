# 1. 概要

Key Vaultは、秘密情報、暗号鍵、証明書を管理するAzureのサービスです。Secret（秘密情報）とKey（暗号操作に使う鍵）は役割が異なります。APIキーをソースコードへ直接書かないための保管先として利用できます。[公式概要](https://learn.microsoft.com/en-us/azure/key-vault/general/overview)

# 2. 何のために使うか

やむを得ず必要なAPIキーや接続秘密を保護します。対応サービスへManaged Identityで接続できる場合は、アプリが秘密情報を持たない構成も検討します。

# 3. 仕組み

アプリは自身のIdentityでKey Vaultへ認証し、許可されたSecretなどを取得します。取得した秘密はメモリーで利用し、ログへ出しません。保管だけでなく、権限、期限、ローテーション、監査を含めて管理します。

# 4. 具体例

Te社の想定例で外部サービスのキーだけをVaultへ保存し、生成・検索はManaged Identityにします。起動時に必要なSecretを読み、更新時に再取得する仕組みを設けます。

# 5. 実装・設定時のポイント

- Secret取得とSecret変更の権限を分けます。
- 環境ごとに保管先とIdentityを分離します。
- Secret名、版、取得頻度、更新反映時間を定義します。
- Soft Delete、Purge Protection、期限、アクセスログを確認します。

# 6. 注意点

Vaultへ保存しても、取得したキーをログや例外へ出せば漏えいします。全要求でVaultを呼ぶと遅延と依存が増えるため、更新対応を含めた安全な再利用を考えます。Vault障害時に秘密を平文設定へ戻すような回避は避けます。

# 7. Te社RAG基盤で確認するポイント

SecretClient、Vault URI、credential、Secret名、取得例外、キャッシュを確認します。実際のRole割り当てとネットワーク制限を調べます。キー更新時の作業者、アプリへの反映方法、復旧手順を詳細設計書へ対応付けます。
