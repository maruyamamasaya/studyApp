# 1. 概要

PythonでのRAG実装は、入力検証、検索、根拠構築、生成、回答整形を関数やクラスに分けてつなぐ作業です。ライブラリ名を覚えるだけでなく、入力と出力の型、例外、外部通信の位置を読むことが大切です。

# 2. 何のために使うか

既存コードを読み、詳細設計書の各処理へ対応付けるために使います。Azure SDKやLLM SDKへの依存を分けると、処理ごとの検証と変更がしやすくなります。

# 3. 仕組み

典型的にはAPI層、RAGサービス層、検索クライアント、生成クライアント、設定層へ分けます。認証情報から決めた権限を検索関数へ渡し、検索結果を型の揃ったデータへ変換してContextを作ります。

# 4. 具体例

次のコードは処理順を読むための学習用抜粋です。search_allowed、build_context、generate_groundedは実装が必要な関数で、そのままAzureへ接続するコードではありません。生成前に認可済み検索を行い、根拠が空なら生成を止める意図を示します。

~~~python
async def answer(question, verified_principal):
    # verified_principalはAPI入口で検証済みの利用者情報
    hits = await search_allowed(question, verified_principal)
    context, sources = build_context(hits)
    if not context:
        return {"answer": "資料から確認できません", "sources": []}
    text = await generate_grounded(question, context)
    return {"answer": text, "sources": sources}
~~~

Te社のコードでは、この各呼び出しに相当する関数を探し、Timeoutやログがどこに入るか追います。

# 5. 実装・設定時のポイント

- requirements、pyproject、ロックファイルから採用版を確認します。
- 同期SDKをasync関数内で直接呼んで待機処理を止めていないか確認します。
- 設定と秘密情報をソースへ直書きしないようにします。
- 外部APIの戻り値を、自前の型へ変換する場所を明確にします。

# 6. 注意点

例外を一律に空の回答へ変換すると、検索障害を根拠不足と誤認します。例示コードでは省略した出典検証、認証、期限、クライアント終了処理を、本番実装で別途確認する必要があります。

# 7. Te社RAG基盤で確認するポイント

エントリーポイントから関数定義へ移動し、引数、戻り値、await、try/except、設定参照を順に読みます。設計書の処理名と関数名が違う場合は対応表を作ります。テストが外部APIの失敗と権限不足を検証しているか調べます。
