## 1. Rerankingとは

Reranking（リランキング）は、

**検索で取得した候補を、質問との関連性でもう一度評価して並び替える処理**

です。

RAGでは、Keyword SearchやVector Search、Hybrid Searchで取得した検索結果を、そのままLLMへ渡すとは限りません。

まず多めに候補を取得し、その中から本当に関連性が高いChunkを選びます。

基本イメージは以下です。

検索  
→ 候補を多めに取得  
→ Reranking  
→ 上位だけ選択  
→ LLMへ渡す

---

## 2. なぜRerankingが必要なのか

検索エンジンは高速に候補を見つけることが得意です。

ただし、

- Keywordが一致しただけ
    
- 意味が少し近いだけ
    
- 同じ単語はあるが文脈が違う
    

といったChunkも上位に入ることがあります。

そこでRerankingを使って、

**質問と検索結果をより詳しく比較**

します。

---

## 3. 基本的な処理フロー

例えば、

Hybrid Search  
→ Top 30取得

Reranker  
→ 30件を再評価

最終結果  
→ Top 5

LLM  
→ Top 5をContextとして使用

という流れです。

つまり、

最初の検索  
＝ 候補探し

Reranking  
＝ 候補の精査

という役割分担です。

---

## 4. RetrievalとRerankingの違い

Retrievalは、

大量のデータから関連しそうな候補を高速に取得する処理

です。

Rerankingは、

取得済みの少数候補をより丁寧に評価する処理

です。

例えば、

100万Chunk  
→ Retrievalで30件

30件  
→ Rerankingで5件

という流れにします。

---

## 5. 検索だけでは不十分な例

ユーザー質問：

「Windows Server 2025へ移行するときのIIS互換性について知りたい」

検索結果：

1. Windows Server 2025のライセンス
    
2. IISの基本設定
    
3. Windows Server更新時のIIS互換性
    
4. Windows Server 2025のバックアップ
    
5. IISログの保存方法
    

Keyword Searchでは、

Windows Server 2025  
IIS

という単語を含む結果が上位に来る可能性があります。

しかし本当に必要なのは、

3. Windows Server更新時のIIS互換性
    

です。

Rerankingでは質問全体の意味を見て、3を上位にできます。

---

## 6. Rerankerとは

検索結果を再評価するモデルや仕組みを、

Reranker

と呼びます。

Rerankerには、

質問  
＋  
候補Chunk

を渡します。

そして、

「このChunkは質問への回答にどれくらい関連しているか」

をScoreとして返します。

---

## 7. Rerankingの入力

例えば、

Question:

「バックアップの保存期間は？」

Candidate 1:

「バックアップは30日間保存します。」

Candidate 2:

「バックアップは毎日午前2時に実行します。」

Candidate 3:

「監査ログは90日間保存します。」

という候補があります。

Rerankerは、それぞれを質問と比較します。

---

## 8. Rerankingの出力

例えば、

Candidate 1  
Score = 0.96

Candidate 2  
Score = 0.62

Candidate 3  
Score = 0.31

のように評価します。

そしてScoreの高い順に並べ替えます。

---

## 9. Vector Searchとの違い

Vector Searchも意味の近さを見ています。

では、

「Vector SearchがあるならRerankingはいらないのでは？」

と思うかもしれません。

違いは、

**比較の細かさ**

です。

Vector Searchでは、質問とChunkをそれぞれEmbeddingし、

Vector同士を比較します。

一方Rerankerでは、

質問とChunkをセットで読ませて評価

する方式があります。

---

## 10. Bi-EncoderとCross-Encoder

Embedding検索では、

Bi-Encoder

という考え方が使われます。

質問  
→ Vector

Chunk  
→ Vector

として別々に変換し、そのVectorを比較します。

高速ですが、質問とChunkを直接一緒に読んでいるわけではありません。

---

## 11. Cross-Encoder

Rerankingでは、

Cross-Encoder

というモデルが使われることがあります。

Question  
＋  
Chunk

を同時にモデルへ入力します。

例えば、

「バックアップの保存期間は？」

と、

「バックアップは30日間保存します。」

を一緒に読み、

どれくらい関連しているか

を直接評価します。

---

## 12. Cross-Encoderが高精度になりやすい理由

Embeddingでは、

質問Vector

と

文書Vector

を別々に作ります。

Cross-Encoderでは、

質問と文書の関係そのもの

を見ます。

そのため、

- 条件
    
- 否定
    
- 時間
    
- 対象
    
- 主語
    

などを細かく評価しやすくなります。

---

## 13. Cross-Encoderの弱点

精度が高い代わりに、

処理が重い

という特徴があります。

例えば100万ChunkすべてをCross-Encoderで評価すると非常に重くなります。

そのため、

最初に検索で候補を絞り、

その候補だけReranking

します。

---

## 14. Two-Stage Retrieval

この構成を、

Two-Stage Retrieval

と考えることができます。

### Stage 1

高速検索

- Keyword Search
    
- Vector Search
    
- Hybrid Search
    

### Stage 2

精密評価

- Reranking
    

という2段階です。

---

## 15. 典型的な構成

例えば、

100万Chunk

から、

Hybrid Search  
→ Top 50

Reranker  
→ Top 5

LLM  
→ Top 5

という構成です。

この方法なら、

検索速度

と

検索精度

の両立を狙えます。

---

## 16. RerankingとKeyword Search

Keyword Searchで取得した結果もRerankingできます。

例えば、

Question  
「ログインできない原因は？」

Keyword Search結果：

- Login画面のデザイン
    
- Loginエラー対処方法
    
- Loginログ保存方法
    

Rerankingによって、

Loginエラー対処方法

を上位にできます。

---

## 17. RerankingとVector Search

Vector Searchでは意味的に似た文章を取得しますが、

似ているだけで回答には使えないChunk

も含まれることがあります。

例えば、

質問：

「バックアップの保持期間は？」

Vector Search結果：

- バックアップ実行方法
    
- バックアップ保存場所
    
- バックアップ保持期間
    

などです。

Rerankingによって、

保持期間

を直接説明しているChunkを上位にできます。

---

## 18. RerankingとHybrid Search

よくある構成は、

Keyword Search  
＋  
Vector Search

→ Hybrid Search

→ Reranking

です。

Hybrid Searchで幅広く候補を集め、

Rerankingで関連性を精査します。

---

## 19. Candidate Size

Rerankingへ渡す候補数も重要です。

例えば、

Top 10  
Top 20  
Top 50  
Top 100

などがあります。

候補数を増やすと正解を含みやすくなりますが、

Reranking処理が重くなります。

---

## 20. 候補数が少なすぎる場合

例えば検索段階でTop 5しか取得しない場合、

正解Chunkが6位だったら、

Rerankerまで届きません。

Rerankerは、

検索されていないChunkを新しく見つける

ことはできません。

そのため、最初のRetrievalである程度Recallを確保する必要があります。

---

## 21. 候補数が多すぎる場合

逆にTop 500をRerankingすると、

- 処理時間増加
    
- API料金増加
    
- CPU / GPU負荷増加
    

などが発生します。

そのため、

候補取得数

と

Rerankingコスト

のバランスを考えます。

---

## 22. Final Top K

Reranking後に、

最終的に何件LLMへ渡すか

も設定します。

例えば、

Retrieval  
Top 50

Reranking  
Top 5

とします。

最終Top Kを増やしすぎると、

不要なContextまでLLMへ渡されます。

---

## 23. Reranking Score

Rerankerは、各候補に関連度Scoreを付けます。

例えば、

0.98  
0.87  
0.43  
0.12

などです。

ただし、

Score = 0.8なら必ず正しい

という絶対基準ではありません。

使用するRerankerごとにScoreの意味が異なります。

---

## 24. Score Threshold

Reranking後、

一定Score以下の候補を除外する

こともできます。

例えば、

Score >= 0.6

だけ採用します。

これにより、

関係の薄いChunkをLLMへ渡さない

ようにできます。

---

## 25. Thresholdの注意点

Thresholdを高くしすぎると、

必要な情報まで除外

する可能性があります。

逆に低すぎると、

不要な情報

が残ります。

実際の質問データを使って調整する必要があります。

---

## 26. Rerankingと文章の長さ

Candidate Chunkが長すぎると、

Rerankerの入力制限

に引っかかる場合があります。

そのため、

Chunk Size

もRerankingへ影響します。

長いChunkでは、

重要な部分が埋もれる

可能性もあります。

---

## 27. QueryとChunkのペア

Rerankingでは、基本的に、

Query  
＋  
Chunk

を1ペアとして評価します。

候補が50件なら、

50ペア

を評価します。

そのため、候補数に応じて処理量が増えます。

---

## 28. Batch処理

複数候補をまとめてRerankerへ送ることがあります。

これをBatch処理と考えます。

例えば、

50候補  
→ 10件ずつ5Batch

として処理します。

サービスやモデルによって対応方法は異なります。

---

## 29. LLMをRerankerとして使う方法

専用Rerankerではなく、

LLM

を使って検索結果を評価する方法もあります。

例えば、

「以下の10件を質問との関連度順に並べてください」

とLLMへ依頼します。

---

## 30. LLM Rerankingのメリット

LLMは、

- 複雑な質問
    
- 条件付き質問
    
- 文脈
    

を理解できます。

そのため高度な評価が可能な場合があります。

---

## 31. LLM Rerankingのデメリット

一方、

- 処理時間
    
- Tokenコスト
    
- 出力の安定性
    

などの問題があります。

大量の候補を毎回LLMで評価するとコストが高くなります。

---

## 32. 専用RerankerとLLM Reranker

### 専用Reranker

メリット：

- 高速
    
- 比較的安定
    
- 大量候補に向く
    

デメリット：

- 対応言語やモデル性能に依存
    

### LLM Reranker

メリット：

- 複雑な意味理解
    
- 柔軟
    

デメリット：

- 遅い
    
- コストが高い
    
- 出力制御が必要
    

用途によって使い分けます。

---

## 33. Semantic Ranker

検索サービスによっては、

Semantic Ranker

という機能が提供されます。

これは検索結果を意味的に再評価する機能です。

考え方としては、

検索  
→ Semantic Ranking  
→ 上位結果

です。

Rerankingの一種として理解できます。

---

## 34. RerankingとExact Match

例えば質問に、

ERR-50001

というエラーコードが含まれている場合、

完全一致したChunkを非常に高く評価したい場合があります。

その場合、

Rerankerだけでなく、

Keyword Score

や、

Exact Match Bonus

を組み合わせることもあります。

---

## 35. Score Fusion

Reranker Scoreだけで最終順位を決めるとは限りません。

例えば、

Final Score =

Keyword Score  
＋ Vector Score  
＋ Reranker Score

のように組み合わせる場合があります。

実装方法は検索システムによって異なります。

---

## 36. Document Diversity

Reranking結果の上位が、

同じDocumentの似たChunk

ばかりになる場合があります。

例えば、

1位 DOC001 Chunk 1  
2位 DOC001 Chunk 2  
3位 DOC001 Chunk 3

です。

必要に応じて、

別Documentも含める

ように調整します。

---

## 37. Duplicate除去

Chunk Overlapによって、

ほぼ同じ文章

が複数検索される場合があります。

Reranking前後で、

- Chunk ID
    
- Text Hash
    
- 類似度
    

などを使って重複を除去します。

---

## 38. Neighbor Chunk

検索されたChunkの前後を一緒に取得する場合があります。

例えば、

正解Chunk  
= Chunk 5

なら、

Chunk 4  
Chunk 5  
Chunk 6

をまとめてContextへ入れます。

Reranking後に周辺文脈を追加する構成もあります。

---

## 39. Parent-Child Chunkとの組み合わせ

検索は小さいChild Chunkで行い、

Reranking後にParent Chunkを取得

することもできます。

例えば、

検索対象  
200 Token

Reranking対象  
200 Token

LLM Context  
1000 TokenのParent

という構成です。

---

## 40. RerankingとMetadata

Rerankingは本文だけでなく、

- title
    
- heading
    
- section
    

などの情報も含めて評価できる場合があります。

例えば、

Heading  
「バックアップ保持期間」

本文  
「30日間保存する。」

を一緒に渡すと、意味を判断しやすくなります。

---

## 41. 権限制御との順序

権限制御は、

Reranking後

ではなく、

検索対象の段階

で適用することが重要です。

流れとしては、

認証  
→ Permission Filter  
→ Retrieval  
→ Reranking

です。

閲覧できない文書をRerankerへ渡さないようにします。

---

## 42. Rerankingのレスポンスタイム

Rerankingを追加すると、

検索だけの場合より処理時間が増えます。

そのため、

- 候補数削減
    
- 軽量モデル
    
- Batch
    
- 並列化
    
- キャッシュ
    

などを検討します。

---

## 43. キャッシュ

同じ質問が繰り返される場合、

検索結果やReranking結果をキャッシュできる場合があります。

ただし、

- 文書更新
    
- 権限
    
- ユーザー
    

などに注意が必要です。

---

## 44. Rerankingの評価

Rerankingの効果は、

導入前と導入後

で比較します。

例えば、

Retrievalだけ：

正解Chunkが5位

Reranking後：

正解Chunkが1位

なら改善しています。

---

## 45. MRR

Reranking評価では、

MRR

が利用されることがあります。

Mean Reciprocal Rankの略です。

正解Chunkがどれだけ上位に出るかを評価します。

Rerankingでは特に相性のよい指標です。

---

## 46. NDCG

複数の関連Chunkが存在する場合、

NDCG

を利用することがあります。

関連性が高いChunkを上位に並べられているか

を評価します。

---

## 47. Recallとの関係

Rerankingでは、

Recallを大幅に改善する

というより、

検索済み候補の順位改善

が主な役割です。

つまり、

正解Chunkが候補に入っていない

場合は、Rerankingでは救えません。

---

## 48. Precisionとの関係

Rerankingは、

上位検索結果のPrecision

を改善するために使われます。

例えば、

Top 5に関係ないChunkが3件

あった状態を、

Top 5すべて関連Chunk

に近づけます。

---

## 49. RetrievalとRerankingの役割

重要なのは、

Retrieval  
→ 正解を候補に入れる

Reranking  
→ 正解を上位に持ってくる

という違いです。

この2つを分けて評価すると、検索問題の原因を特定しやすくなります。

---

## 50. 検索トラブルの切り分け

例えば正解が回答に使われなかった場合、

### 正解Chunkが検索候補にない

Retrieval側の問題。

確認：

- Chunk
    
- Embedding
    
- Keyword Search
    
- Top K
    
- Query
    

### 正解Chunkは候補にあるが順位が低い

Reranking側の改善余地があります。

確認：

- Reranker
    
- Score
    
- Candidate数
    
- Input内容
    

---

## 51. Rerankingのログ

デバッグのために、

- Query

- Retrieval Score
    
- Reranker Score
    
- Reranking後Rank
    
- chunk_id
    
- document_id
    

などを記録すると便利です。

## 52. 具体的なログイメージ

例えば、

Chunk A

Retrieval Rank  
12

Vector Score  
0.78

Reranker Score  
0.96

Final Rank  
1

という情報があれば、

Vector Searchでは12位だったが、

Rerankingによって最重要と判断された

ことが分かります。

---

## 53. Rerankingでよくある問題

### 正解Chunkが上がらない

Rerankerが対象ドメインに合っているか確認します。

### 処理が遅い

Candidate数やモデルサイズを確認します。

### コストが高い

候補数やReranker方式を見直します。

### 同じChunkばかり残る

Duplicate除去やDocument Diversityを確認します。

### 日本語精度が低い

モデルの多言語・日本語性能を確認します。

---

## 54. Rerankingを使わない構成

小規模なRAGでは、

Hybrid Search  
→ Top 5  
→ LLM

だけで十分な場合もあります。

すべてのRAGにRerankingが必須ではありません。

検索精度、レスポンスタイム、コストを見て判断します。

---

## 55. Rerankingが有効になりやすいケース

特に、

- 文書数が多い
    
- 似た文書が多い
    
- Chunk数が多い
    
- 検索結果の順位が安定しない
    
- 高い回答精度が必要
    

といったケースでは有効です。

---

## 56. Rerankingの位置

RAG全体では、

Document  
→ Chunk  
→ Embedding  
→ Index

質問時は、

Question  
→ Query Rewrite  
→ Permission Filter  
→ Hybrid Search  
→ **Reranking**  
→ Context  
→ Prompt  
→ LLM

という位置になります。

---

## 57. 典型的なRAG検索構成

例えば、

Question

→ Query Rewrite

→ Permission Filter

→ Keyword Search Top 30  
＋  
Vector Search Top 30

→ RRFで統合

→ Duplicate除去

→ Top 30

→ Reranker

→ Top 5

→ Context作成

→ LLM

→ Answer

という流れです。

この構成は、

検索で広く拾う  
→ Rerankingで絞る

という考え方です。

---

## 58. 一言で理解する

Rerankingとは、

**「検索で見つけた候補を、質問との関連性でもう一度詳しく評価して並び替える処理」**

です。

検索は、

**正解候補を見つける**

ことが得意で、

Rerankingは、

**その中から本当に重要な候補を上位にする**

ことが得意です。

RAGでは、

**Hybrid Search → Reranking → Top K → LLM**

という流れで利用されることが多いです。

特に覚えておきたいのは、

**Retrievalは候補を集める処理、Rerankingは候補を精査する処理**

という違いです。
