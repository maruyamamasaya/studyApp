# 1. 概要

Retry（再試行）は、一時的な失敗に対して同じ処理をもう一度行う方法です。ネットワーク切断や短時間のサービス過負荷から回復するために使います。[Retryパターン](https://learn.microsoft.com/en-us/azure/architecture/patterns/retry)

# 2. 何のために使うか

外部検索・生成・取り込みの一時障害を利用者へ直接見せる頻度を減らします。ただし、再試行による追加時間、費用、副作用を制御する必要があります。

# 3. 仕組み

例外やステータスを分類し、再試行可能なものだけを対象にします。最大試行回数、待機時間、総期限を設け、必要に応じてRetry-Afterを尊重します。401や入力不正は、同じ要求をただ繰り返しても通常は直りません。

# 4. 具体例

Te社の想定例でEmbedding要求が429になった場合、SDKの再試行設定とサービスの待機指示を確認します。索引登録が途中成功した場合は、失敗した項目だけを安定したキーで再登録する設計にします。

# 5. 実装・設定時のポイント

- 「再試行3回」と「合計3回の試行」を区別します。
- SDK、アプリ、プロキシの多重Retryを確認します。
- POSTなどの副作用には冪等性キーや状態照会を検討します。
- 再試行理由、試行番号、待機時間を構造化ログへ残します。

# 6. 注意点

タイムアウト時も、サーバー側では処理が完了している可能性があります。LLM呼び出しをやり直すと追加課金や異なる回答が発生し得ます。ストリームの一部を利用者へ返した後に先頭から再試行すると、回答が重複します。

# 7. Te社RAG基盤で確認するポイント

SDKのmax_retries、独自ループ、対象例外、HTTP判定、全体Timeoutを確認します。取り込みと回答APIで方針が同じか、意図的に違うかを調べます。詳細設計書には回数だけでなく対象、待機、打ち切り、最後のエラーを記載します。
