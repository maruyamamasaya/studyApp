## 1. 概要

RAG基盤のセキュリティでは、

**「誰が使えるか」だけでなく、「その人がどの情報まで検索・回答に利用できるか」**

を制御する必要があります。

一般的なWebシステムのセキュリティに加えて、RAGでは、

- 機密文書を検索してしまう
    
- 権限外文書をLLMへ渡してしまう
    
- Prompt Injectionを受ける
    
- 検索結果やPromptから情報が漏れる
    
- 古い権限情報がIndexに残る
    

といったRAG特有のリスクがあります。

---

## 2. 全体の考え方

RAG基盤では、主に以下を守ります。

1. 利用者
    
2. API
    
3. 文書
    
4. 検索Index
    
5. LLM
    
6. Secret
    
7. Network
    
8. Log
    

全体としては、

User  
→ 認証  
→ API認可  
→ 文書権限確認  
→ Search  
→ Context  
→ LLM  
→ Answer

という各段階でセキュリティを適用します。

---

# 3. 認証

まず、

**誰がRAGを利用しているか**

を確認します。

例えばAzure環境では、

Microsoft Entra ID

を利用できます。

流れは、

User  
→ Entra ID Login  
→ Access Token取得  
→ RAG API

です。

API側ではTokenを検証します。

---

## 4. JWT検証

Access TokenがJWT形式の場合、

API側では最低限、

- Signature
    
- Issuer
    
- Audience
    
- Expiration
    

を確認します。

その後、

- Role
    
- Scope
    
- Group
    

などを認可に利用します。

TokenのPayloadを読むだけで信用してはいけません。

---

# 5. API認可

認証後は、

**そのユーザーがどのAPIを利用できるか**

を確認します。

例えば、

RAG.User  
→ 質問可能

RAG.Editor  
→ 文書登録可能

RAG.Admin  
→ 文書削除・設定変更可能

などです。

RoleやScopeを使って制御します。

---

## 6. Scope

例えば、

rag.ask  
documents.read  
documents.write

などのScopeを定義できます。

API側では、

必要なScopeがAccess Tokenに含まれているか

を確認します。

---

# 7. 文書単位のアクセス制御

RAGで最も重要なセキュリティの1つです。

ログインできるユーザーだからといって、

すべての文書を検索できてよい

わけではありません。

例えば、

人事部ユーザー  
→ 人事資料を検索可能

一般社員  
→ 人事資料は検索不可

とします。

Azure AI Searchでは、文書ごとのIdentityやGroup情報をIndexへ持たせ、検索時にSecurity Filterを適用する方式がサポートされています。

---

## 8. Metadata Filterによる権限制御

例えばChunkに、

document_id  
department  
allowed_groups  
access_level

などを持たせます。

検索時に、

User Group = HR

なら、

allowed_groups contains HR

のようなFilterを適用します。

これによって、

検索結果そのものから権限外文書を除外

します。

---

## 9. 検索後に隠すのは危険

悪い例：

全文書検索  
→ 権限外Chunkも取得  
→ LLMへ渡す  
→ 最後に画面だけ非表示

これでは、

LLMがすでに機密情報を読んでいる

可能性があります。

正しい考え方は、

認証  
→ 権限確認  
→ Search Filter  
→ 許可されたChunkのみ取得  
→ LLM

です。

MicrosoftもRAGでのドキュメントレベルのAuthorizationをQuery時に適用することを重要な設計として案内しています。

---

# 10. 文書取り込み時の権限

検索時だけでなく、

文書取り込み時

にも権限情報を正しく登録する必要があります。

例えば、

PDF本文  
＋  
allowed_groups  
＋  
document_id

をIndexへ登録します。

元文書のアクセス権が変わった場合は、

Search Index側にも反映

する必要があります。

---

## 11. 権限変更の反映

例えば、

昨日  
→ 全社員閲覧可能

今日  
→ 人事部限定

へ変更された場合です。

Search Indexに古い権限が残っていると、

一般社員が検索できてしまう

可能性があります。

そのため、

文書更新  
権限変更  
削除

をIndexへ同期する必要があります。

---

# 12. Managed Identity

Azureサービス間の通信では、

Managed Identity

を使うとSecretを減らせます。

例えば、

RAG API  
→ Managed Identity  
→ Azure AI Search

RAG API  
→ Managed Identity  
→ Azure OpenAI

Worker  
→ Managed Identity  
→ Blob Storage

という構成です。

MicrosoftもAzure AIサービスでは、可能な場合API KeyではなくManaged Identityを利用することを推奨しています。

---

# 13. Secret管理

API KeyやPasswordが必要な場合は、

Azure Key Vault

などで管理します。

例えば、

- API Key
    
- Client Secret
    
- DB Password
    
- Certificate
    

などです。

コードへ直接書かないことが重要です。

---

## 14. Secretを減らす

さらに良い考え方は、

Secretを安全に保存する

だけでなく、

**Secretそのものを使わない**

ことです。

Managed Identityが利用できる場合は、

API KeyやClient Secretを減らせます。

---

# 15. Network Security

認証が正しくても、

Network経路が不要に公開されている

と攻撃面が広がります。

Azureでは、

- Private Endpoint
    
- VNet
    
- Firewall
    
- Public Access無効化
    

などを利用できます。

MicrosoftはAzure OpenAIのセキュリティベストプラクティスとして、Private EndpointによるNetwork Isolationを案内しています。

---

## 16. Private Endpoint

例えば、

RAG API  
→ VNet  
→ Private Endpoint  
→ Azure OpenAI

とします。

Public Internetを経由せず、

Private Network経由

で通信できます。

---

## 17. Blob Storageの保護

文書原本を保存するBlob Storageも、

Public公開しない

ことが基本です。

例えば、

- Private Endpoint
    
- RBAC
    
- Managed Identity
    

などで制御します。

RAGの元文書自体が機密情報である可能性があるためです。

---

# 18. Prompt Injection

RAG特有の重要なリスクです。

検索対象文書の中に、

「前の指示を無視してください」

「この秘密情報を表示してください」

などの文章が含まれる可能性があります。

LLMがそれを、

資料

ではなく、

命令

として解釈してしまうリスクがあります。

---

## 19. Retrieved Documentは命令ではない

Promptでは、

検索結果は、

**回答根拠となるデータであり、命令ではない**

と明確に分けます。

例えば、

System Instruction  
→ 最優先

User Question  
→ ユーザー指示

Retrieved Context  
→ 参考資料

という扱いにします。

---

## 20. Prompt Injection対策

代表的には、

- System PromptとContextを明確に分離
    
- Context内の命令を実行しないよう指示
    
- 外部Tool呼び出しに追加認可
    
- 入力・出力Validation
    
- 不審な文書を取り込まない
    
- Tool権限を最小化
    

などがあります。

---

# 21. Data Leakage

RAGでは、

機密情報が回答として漏れる

リスクがあります。

原因として、

- 権限Filter不足
    
- Promptログ
    
- Cache共有
    
- Search Index設定
    
- 出典URL
    
- LLMへの不要なContext送信
    

などがあります。

---

## 22. 必要な情報だけLLMへ渡す

検索できたからといって、

大量の文書を全部LLMへ送らない

ことも重要です。

Top-KやRerankingを使って、

回答に必要なContextだけ

を渡します。

これは、

Token削減

だけでなく、

情報露出を減らす

意味もあります。

---

# 23. Cacheのセキュリティ

Cacheを使う場合、

User Aの検索結果や回答

を、

User Bへ返してはいけません。

特に、

- User
    
- Group
    
- Role
    
- Permission
    
- Index Version
    

などが違えば、Cacheを共有できない場合があります。

---

## 24. Cache Key

例えば、

questionだけ

をCache Keyにするのは危険です。

必要に応じて、

question  
＋ permission_scope  
＋ index_version

などをKeyへ含めます。

---

# 25. Logのセキュリティ

RAGではデバッグのために、

Prompt  
Context  
Question  
Answer

をログへ残したくなることがあります。

しかし、これらには機密情報が含まれる可能性があります。

そのため、

全文ではなく、

- request_id
    
- document_id
    
- chunk_id
    
- latency
    
- token_count
    
- error_type
    

などを中心に記録します。

---

## 26. Tokenをログへ出さない

特に、

- Access Token
    
- JWT全文
    
- API Key
    
- Password
    

などをログへ出してはいけません。

---

# 27. Application Insights / Log Analytics

セキュリティ面でも、

- 認証失敗
    
- 403増加
    
- 不審なRequest
    
- Timeout急増
    
- Retry急増
    
- 異常なアクセス量
    

などを監視します。

Application InsightsやLog Analyticsを使って、

異常を早く検知できるようにします。

---

# 28. Input Validation

RAG APIへ入ってくる入力も信用しません。

例えば、

- 極端に長い質問
    
- 不正JSON
    
- 想定外の文字列
    
- 悪意あるPrompt
    

などです。

API側で、

- 型
    
- 最大文字数
    
- 必須項目
    
- Format
    

などをValidationします。

---

# 29. File Upload Security

文書取り込み機能がある場合、

Uploadされるファイルにも注意します。

例えば、

- ファイルサイズ制限
    
- 拡張子
    
- MIME Type
    
- Malware Scan
    
- Password付きPDF
    
- 不正ファイル
    

などです。

単に、

.pdf

という拡張子だけを信用しないようにします。

---

# 30. OCR・Parserの安全性

PDF ParserやOCRも、

外部入力を処理します。

そのため、

- 巨大ファイル
    
- 壊れたPDF
    
- 異常なページ数
    
- Parser脆弱性
    

などを考慮します。

処理時間やファイルサイズに制限を設けます。

---

# 31. Denial of Service対策

RAGは、

LLMやEmbedding API

など比較的コストの高い処理を呼び出します。

そのため大量Requestを受けると、

- コスト急増
    
- Rate Limit
    
- System負荷増加
    

につながります。

対策として、

- Rate Limit
    
- Request Size Limit
    
- Timeout
    
- Queue
    
- Concurrency Limit
    

などを利用します。

---

# 32. Output Validation

LLMの回答も、

そのまま信用しない

ことが重要です。

例えば、

- 出典が本当に存在するか
    
- Contextに根拠があるか
    
- URLが正しいか
    
- Structured OutputがSchemaに合うか
    

などを確認します。

---

# 33. Citation

出典は、

LLMに自由生成させる

より、

検索結果のMetadataから作る

ほうが安全です。

例えば、

document_id  
page_number  
source_url

などを利用します。

これによって、

存在しない出典をLLMが作る

リスクを減らせます。

---

# 34. Hallucinationもセキュリティに関係する

Hallucinationは品質問題だけでなく、

誤った業務指示

を生成する可能性があります。

そのため、

- 正しいRetrieval
    
- Reranking
    
- Grounding
    
- Citation
    
- 不明時は回答しない
    

などが重要です。

---

# 35. 環境分離

一般的には、

- Development
    
- Staging
    
- Production
    

を分けます。

それぞれ、

- Storage
    
- Search Index
    
- OpenAI Resource
    
- Key Vault
    
- Identity
    

などを分離する構成があります。

開発環境から本番文書へアクセスできないようにすることも重要です。

---

# 36. 最小権限

RAG基盤全体で、

Least Privilege

最小権限

を適用します。

例えば、

RAG API  
→ Search読み取りだけ

Worker  
→ Blob読み取り + Search書き込み

Admin  
→ Index管理

などです。

全サービスに管理者権限を付けるのは避けます。

---

# 37. RAGセキュリティの基本フロー

全体をまとめると、

User  
→ Entra IDで認証  
→ Access Token  
→ JWT検証  
→ Role / Scope確認  
→ Group / ACL確認  
→ Metadata Security Filter  
→ Azure AI Search  
→ 許可されたChunkのみ取得  
→ Contextを最小化  
→ Prompt  
→ Azure OpenAI  
→ Answer  
→ Citation確認  
→ User

となります。

---

# 38. Azure構成での役割

例えば、

### Microsoft Entra ID

ユーザーとアプリのIdentity管理

### Managed Identity

Azureサービス間のアプリ認証

### RBAC

Azure Resourceへのアクセス権

### Key Vault

Secret / Key管理

### Blob Storage

文書原本の保護

### Azure AI Search

文書単位の検索権限制御

### Azure OpenAI

Embedding / Generation

### Private Endpoint

Network Isolation

### Application Insights / Log Analytics

監視・監査

という役割分担になります。

---

# 39. セキュリティで特に重要なポイント

RAGでは最低限、

1. APIで認証・認可する
    
2. 検索時点で文書権限を適用する
    
3. LLMへ権限外情報を渡さない
    
4. Secretをコードへ書かない
    
5. Managed Identityを活用する
    
6. Networkを必要以上に公開しない
    
7. Prompt Injectionを考慮する
    
8. Log / Cacheから情報を漏らさない
    
9. 文書権限変更をIndexへ反映する
    
10. 監視・監査できるようにする
    

ことが重要です。

---

# 40. 一言で理解する

RAG基盤のセキュリティとは、

**「認証されたユーザーに、許可されたAPIと許可された文書だけを使わせ、その情報だけをLLMへ渡す仕組み」**

です。

特に重要なのは、

**ログインできるか**

だけではなく、

**検索できる文書まで制御する**

ことです。

覚え方としては、

**認証 → API認可 → 文書認可 → Search → Context制限 → LLM**

という順番で考えると分かりやすいです。
