# 1. 概要

Microsoft Entra IDは、利用者やアプリのIdentity（識別情報）を管理し、サインインやトークン発行を行うサービスです。旧称Azure ADが資料に残っている場合もあります。認証は「誰か」の確認、認可は「何を許すか」の判断です。

# 2. 何のために使うか

社内利用者のサインイン、APIのAccess Token、アプリからAzureリソースへ接続するIdentityの管理に使います。ただし、文書単位の閲覧権限はRAG側の処理との連携が必要です。

# 3. 仕組み

TenantはIdentityの管理境界です。App Registrationはアプリの識別子や公開する権限などを定義し、Service Principalはテナント内のアプリ実体です。Client IDはアプリの識別子で、認証秘密そのものではありません。

# 4. 具体例

Te社の想定例で、画面用アプリと質問API用アプリを登録し、画面が質問API向けAccess Tokenを取得します。APIは許可されたTenantとAudience（宛先）を検証します。API自身のAzure接続には別のManaged Identityを利用できます。

# 5. 実装・設定時のポイント

- Tenant ID、Client ID、APIのAudienceを区別します。
- Redirect URI、公開Scope、App Role、同意を確認します。
- ユーザーの無効化やグループ変更の反映時間を考えます。
- 単一テナントか複数テナントかを仕様にします。

# 6. 注意点

サインイン成功だけで質問APIの利用や全資料閲覧を許可しないようにします。テナント内の管理Role、Azure RBAC、API App Roleは別の体系です。既存案件メモの「専用AIなら安全」という認識も、正式な利用規程や設定で確認が必要です。

# 7. Te社RAG基盤で確認するポイント

アプリ登録、Enterprise Application、Token取得設定、APIの検証設定を確認します。開発・本番の分離と許可Tenantを調べます。認証ライブラリがどのTokenを取得し、APIがどのAudienceを要求しているか照合します。
