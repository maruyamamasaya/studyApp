> Te社向けの例は学習用の想定です。実際の採用サービス・設定・権限は、既存コードと正式資料で確認してください。

# 1. 概要

Chunk（チャンク）は、検索やLLM入力のために文書を分割した単位です。文章の途中で切るだけではなく、見出しや表を含めて意味が通じる単位にすることが重要です。

# 2. 何のために使うか

関連する箇所だけを検索し、限られた入力容量へ入れるために使います。文書全体を1件にすると不要な情報が増え、細かくしすぎると規則と例外の関係を失います。

# 3. 仕組み

文字数、Token数、段落、見出しなどを基準に分割します。Overlap（重なり）は境界付近の情報を隣のChunkにも含める方法です。章名や文書名を各Chunkへ追加すると、単独で検索された場合にも意味を理解しやすくなります。

# 4. 具体例

Te社の規程で「通常の締切」と「休日の場合の例外」を別々に切ると、片方だけ検索されるおそれがあります。同じChunkに保持するか、隣接Chunkを取得する設計を評価します。仮に400 Tokenと50 Tokenの重なりを試す場合も、固定の推奨値とはせず比較の出発点とします。

# 5. 実装・設定時のポイント

- chunk_id、document_id、version、page、heading、権限を持たせます。
- 表は行・列の対応が壊れない単位で扱います。
- 重複する検索結果をまとめて入力の浪費を減らします。
- 分割方式を変えたら再取り込みと評価を行います。

# 6. 注意点

Token数と文字数は同じではありません。Overlapを増やしすぎると登録件数、Embedding費用、Contextの重複が増えます。関連情報をまとめすぎると検索粒度が粗くなるため、評価質問に対する根拠の回収率で判断します。

# 7. Te社RAG基盤で確認するポイント

splitterの種類、単位、サイズ、重なり、見出し付与、Chunk IDの生成式を確認します。ページがまたがるChunkの出典表示と、元文書の権限が全Chunkに引き継がれることを調べます。設計の設定値と実行時の上書き値を照合します。
