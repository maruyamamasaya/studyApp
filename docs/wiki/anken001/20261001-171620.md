> Te社向けの例は学習用の想定です。実際の採用サービス・設定・権限は、既存コードと正式資料で確認してください。

# 1. 概要

RAGのコスト管理は、生成、Embedding、OCR、検索容量、保存、ログなどの費用を把握し、品質と必要容量を保ちながら調整する活動です。利用者の質問回数だけでは総費用を説明できません。

# 2. 何のために使うか

大量取り込みや長い会話、再試行による予想外の費用増を見つけ、環境や機能ごとの予算を管理します。

# 3. 仕組み

学習用の概算では「入力Token × 入力単価 + 出力Token × 出力単価」に、Embedding、OCRページ、Search容量、Storage、ログなどを加えます。単価と課金単位はモデル・提供方式・地域で変わるため、実契約と料金表を確認します。

# 4. 具体例

Te社の想定例で、一括再取り込みによってEmbedding費用が増えた場合、本文が変わらない文書まで再処理していないか調べます。質問APIでは、重複Chunkや長すぎる履歴が入力Tokenを増やしていないか確認します。

# 5. 実装・設定時のポイント

- 環境、サービス、処理種別で使用量を分けます。
- 入力・出力Token、ページ数、Retry回数を記録します。
- Budgetと通知を作り、異常増加の対応を決めます。
- CacheやChunk変更は、品質評価と一緒に判断します。

# 6. 注意点

AzureのBudgetは、作っただけで自動的に全リソースを停止するものではありません。[Budgetの公式説明](https://learn.microsoft.com/en-us/azure/cost-management-billing/costs/tutorial-acm-create-budgets)

費用を減らすために権限条件を外したり、必要な監査を失ったりしないようにします。Token集計と請求には対象期間や遅延の差があるため、合計が即時一致するとは限りません。

# 7. Te社RAG基盤で確認するポイント

利用モデル、デプロイ方式、Search SKU、OCR処理量、ログ保持、Budgetを確認します。生成と取り込みのusage集計が分離されているか調べます。SDKのRetryが追加費用へ与える影響と、環境別の実請求を対応付けます。
