## 1. Blob Storageとは

Azure Blob Storageは、

**Azure上でファイルや大容量データを保存するためのストレージサービス**

です。

RAGでは主に、

- PDF
    
- Word
    
- Excel
    
- 画像
    
- スキャン文書
    
- Markdown
    
- テキストファイル
    

などの元文書を保存する場所として使われます。

つまり、

**検索用データではなく、文書原本を置く場所**

として理解すると分かりやすいです。

---

## 2. RAG全体での位置

Azureを使ったRAGでは、例えば以下のような流れになります。

文書アップロード  
→ Azure Blob Storage  
→ 文書解析  
→ Chunk  
→ Embedding  
→ Azure AI Search

質問時：

Question  
→ Azure AI Search  
→ Context  
→ Azure OpenAI  
→ Answer

Blob Storageは、

**RAGの入口側で文書原本を保持する役割**

を担当します。

---

## 3. なぜ原本を保存するのか

RAGでは最終的に、

- Chunk
    
- Embedding
    
- Metadata
    

へ加工します。

しかし、加工後のデータだけでは、

元のPDFや画像を確認できません。

そのため原本をBlob Storageに残しておきます。

これによって、

- 再解析
    
- OCRやり直し
    
- Chunk再作成
    
- 出典確認
    
- 文書更新
    
- 監査
    

などができます。

---

## 4. Blobとは

Blobは、

Binary Large Object

の略です。

簡単にいうと、

**ファイルとして扱うデータ**

です。

例えば、

manual.pdf  
rule.docx  
scan001.png

などをBlobとして保存します。

---

## 5. Storage Account

Blob Storageを使うには、

Storage Account

を作成します。

イメージとしては、

Azure Subscription  
→ Resource Group  
→ Storage Account  
→ Container  
→ Blob

という構造です。

---

## 6. Container

Containerは、

Blobをまとめる箱

です。

例えば、

documents

manuals

contracts

などです。

Containerの中に複数のファイルを保存します。

---

## 7. Blobの構造

例えば、

```
Storage Account
└── Container: documents
    ├── manual.pdf
    ├── rule.docx
    └── scan001.png
```

のような構成です。

---

## 8. 仮想フォルダ

Blob Storageでは、

フォルダのように見えるパス

を作ることができます。

例えば、

```
documents/hr/rule.pdf
documents/it/manual.pdf
```

です。

実際にはBlob名の一部として扱われる構成ですが、フォルダのように整理できます。

---

## 9. RAGで保存するもの

RAGでは例えば、

- 原本PDF
    
- OCR前画像
    
- Word原本
    
- Excel原本
    
- 変換前ファイル
    

などをBlob Storageへ置きます。

必要に応じて、

解析結果JSON

を保存することもあります。

---

## 10. 文書アップロード

ユーザーやバッチ処理から、

Blob Storageへ文書をアップロードします。

例えば、

Web画面  
→ API  
→ Blob Storage

という流れです。

アップロード後に、

文書取り込み処理

を開始します。

---

## 11. 文書取り込みとの関係

典型的には、

Blob Storage  
→ ファイル取得  
→ PDF解析  
→ OCR  
→ Chunk  
→ Embedding  
→ Azure AI Search

となります。

つまり、

Blob Storageは元文書、

Azure AI Searchは検索用データ

という役割分担です。

---

## 12. Azure AI Search Indexerとの連携

Azure AI Searchでは、

Blob StorageをData Sourceとして利用する

構成があります。

例えば、

Blob Storage  
→ Indexer  
→ Skillset  
→ Azure AI Search Index

という流れです。

これによって、

Blobに保存された文書を検索用Indexへ取り込めます。

---

## 13. 文書更新

例えば、

rule.pdf

が更新された場合、

Blob Storage上のファイルを更新します。

その後、

- 再解析
    
- 再Chunk
    
- 再Embedding
    
- Index更新
    

を行います。

原本を一元管理しておくと、この流れを作りやすくなります。

---

## 14. 文書削除

元文書を削除した場合は、

検索Index側のChunkも削除する必要があります。

Blobだけ削除して、

Azure AI Searchに古いChunkが残る

状態は避けます。

---

## 15. Version管理

Blob Storageでは、

Versioning

を有効にする構成があります。

例えば、

rule.pdf v1  
rule.pdf v2  
rule.pdf v3

のように過去Versionを保持できます。

誤更新時の復旧や監査に役立ちます。

---

## 16. Soft Delete

誤ってBlobを削除した場合に備えて、

Soft Delete

を利用することがあります。

完全削除する前に一定期間保持する仕組みです。

---

## 17. Metadata

Blob自体にもMetadataを持たせることができます。

例えば、

- document_id
    
- department
    
- category
    
- uploaded_at
    

などです。

ただし、RAG検索用MetadataはAzure AI Search側でも管理することが多いです。

---

## 18. Blob Tags

BlobにはTagsを付けて管理する方法もあります。

例えば、

department=hr

document_type=manual

などです。

運用上の検索や管理に使えます。

---

## 19. 認証

Blob Storageへアクセスするには認証が必要です。

代表的には、

- Microsoft Entra ID
    
- Managed Identity
    
- SAS
    
- Access Key
    

などがあります。

Azure環境では、

Managed Identity + RBAC

を利用する構成がよくあります。

---

## 20. Access Key

Storage AccountにはAccess Keyがあります。

強い権限を持つため、

- コードへ直書きしない
    
- Gitへ保存しない
    

ことが重要です。

可能ならManaged Identityなどを利用します。

---

## 21. SAS

SASは、

Shared Access Signature

の略です。

一定期間だけ、

特定Blobへのアクセスを許可

するときに使えます。

例えば、

このPDFだけ  
10分間だけ  
読み取り可能

といったURLを発行できます。

---

## 22. Managed Identity

Azure上のアプリケーションにIdentityを付与し、

Blob Storageへのアクセス権を与える方法です。

例えば、

App Service  
→ Managed Identity  
→ Blob Storage

とできます。

秘密鍵をアプリへ保存しなくてよいのがメリットです。

---

## 23. RBAC

Blob Storageでも、

Role-Based Access Control

を利用できます。

例えば、

- 読み取りのみ
    
- 書き込み可能
    
- 管理者
    

などをRoleで制御します。

---

## 24. Public Access

RAGの社内文書を保存する場合、

BlobをPublic公開しない

設計が基本です。

誰でもURLから取得できる状態は避けます。

---

## 25. 暗号化

Blob Storageでは、

保存データはAzure側で暗号化されます。

必要に応じて、

Microsoft管理鍵

または

Customer Managed Key

を使う構成があります。

---

## 26. Private Endpoint

セキュリティ要件が高い場合、

Blob StorageへPublic Internet経由でアクセスさせず、

Private Endpoint

を利用する構成があります。

例えば、

VNet  
→ Private Endpoint  
→ Blob Storage

という形です。

---

## 27. Network制御

Blob Storageでは、

- Firewall
    
- VNet
    
- Private Endpoint
    

などを使って、

どこからアクセスできるか

を制御できます。

---

## 28. Lifecycle Management

古いファイルを自動で、

- Cool Tier
    
- Archive Tier
    
- 削除
    

へ移動する仕組みがあります。

これをLifecycle Managementと呼びます。

大量文書を長期保管する場合に使えます。

---

## 29. Access Tier

Blobには、

- Hot
    
- Cool
    
- Cold
    
- Archive
    

などの保存Tierがあります。

頻繁に読む文書はHot、

長期間ほぼ使わない原本は低頻度Tier

などにできます。

---

## 30. RAGではHotだけとは限らない

RAGで常に検索されるのは、

Azure AI Search上のChunk

です。

そのため原本PDFは、

毎回Blobから読むとは限りません。

検索Index作成後は、

原本の利用頻度が低い

場合があります。

そのためStorage Cost最適化を検討できます。

---

## 31. Eventとの連携

Blobが追加されたことをTriggerにして、

文書取り込み処理を開始

する構成があります。

例えば、

Blob Upload  
→ Event  
→ Function  
→ Queue  
→ Worker

という流れです。

---

## 32. Queueとの組み合わせ

大きなPDFをアップロードした場合、

Upload APIの中で全部解析する

のではなく、

Blobへ保存  
→ QueueへJob登録

とできます。

その後Workerが、

PDF解析  
→ OCR  
→ Chunk  
→ Embedding

を行います。

---

## 33. 文書IDとの関係

Blob名だけで管理するより、

document_id

を別に持つと管理しやすくなります。

例えば、

```
document_id = DOC001
blob_path = documents/hr/rule.pdf
```

とします。

Azure AI Search側のChunkにも、

document_id = DOC001

を持たせます。

---

## 34. 出典表示との関係

RAG回答から、

元PDFを開けるようにする場合があります。

例えば、

回答  
→ 出典  
→ document_id  
→ Blobの原本

という流れです。

必要に応じてSAS URLを生成して、

一定時間だけ閲覧可能

にする方法もあります。

---

## 35. 原本と検索データを分ける

重要なのは、

Blob Storage  
＝ 原本

Azure AI Search  
＝ 検索用データ

と分けることです。

例えば、

PDF原本  
→ Blob

Chunk本文  
Vector  
Metadata  
→ Azure AI Search

という役割分担です。

---

## 36. Blob Storageが担当しないもの

Blob Storage自身は、

- Vector Search
    
- Keyword Search
    
- Embedding
    
- LLM回答
    

を担当しません。

あくまで、

**ファイル保存**

が主な役割です。

---

## 37. Pythonからの利用イメージ

概念的には、

```
blob_client.upload_blob(
    data=file_data,
    overwrite=True,
)
```

でアップロードします。

取得する場合は、

```
data = blob_client.download_blob().readall()
```

のような形です。

実際のSDK仕様は利用Versionに合わせて確認します。

特に、

---

## 40. 一言で理解する

Azure Blob Storageとは、

**「RAGで使うPDFやWordなどの元文書を保存しておくAzureのファイル置き場」**

です。

RAGでは、

**Blob Storage = 文書原本**

**Azure AI Search = 検索用Chunk**

**Azure OpenAI = Embeddingと回答生成**

と覚えると分かりやすいです。

全体としては、

**Blob → 解析 → Chunk → Embedding → Azure AI Search → Azure OpenAI**

という流れになります。
